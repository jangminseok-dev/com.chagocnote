# 차곡노트 — ⑥-1b 알림톡 백엔드 보완 설계 (I6 가족 묶음 · I7 문안 판 올림)

2026-11-10. ⑥-1 최종 검토가 남긴 판정 대기 둘을 사용자가 "⑥-2 앱 전에 둘 다 고친다"로 정했다.
바탕 문서: `docs/superpowers/specs/2026-10-14-notification-design.md`(이하 "설계"), `_docs/decisions/009-notification.md`(이하 "009").

## 1. 왜

- **I6.** 가족 묶음(같은 보호자·같은 시작 시각의 방문들)은 알림톡 한 통이고 그 줄은 방문 하나에 달린다. 지금은 묶음에서 한 마리만 취소·노쇼·시각 변경하면 (가) 줄이 달린 방문이 빠질 때 남은 아이의 리마인드가 함께 사라지고 (나) 다른 아이가 빠질 때 리마인드가 빠진 아이 이름까지 싣고 나간다. 보호자에게 틀린 이름이 가거나 리마인드가 안 간다.
- **I6 의 반대 방향(이번에 찾음).** 이미 대기 줄이 있는 시각에 같은 보호자의 다른 아이를 **나중에 따로** 예약하거나 그 시각으로 옮기면 `has_pending_for_group` 이 참이라 줄을 만들지 않고, 기존 줄의 `pet_ids` 에도 더하지 않는다 — 리마인드가 먼저 예약한 아이 이름만으로 간다.
- **I7.** 문안을 고쳐 `TEXT_VERSION` 을 올리고 재등록하면 `upsert` 가 승인된 줄을 `pending`·새 업체 ID 로 덮는다. 심사(영업일 1~3일) 동안 구독자는 그 종류의 줄을 만들지 않고 대기 줄은 10분씩 미뤄진다. 설계 6.3 "그사이에는 옛 판으로 계속 보낸다" 위반이다. 지금은 판이 1 이라 일어나지 않지만, 실계정 심사에서 반려가 나오면 곧 문안을 고치게 된다.

## 2. 목표·하지 않는 것

목표

1. 아직 안 나간 묶음 줄은 **지금 그 시각에 오는 아이들**을 싣는다 — 빠지면 빼고, 들어오면 더한다.
2. 승인된 종류를 새 판으로 재등록해도 심사가 끝날 때까지 옛 판으로 끊김 없이 나간다.
3. ⑥-2 앱이 기댈 API 계약(009)은 바뀌지 않는다. 응답 스키마·경로·오류 코드 그대로.

하지 않는 것

- 반려동물만 바꾼 수정(`UpdateVisitInteractor`, 009 의 M4)은 여전히 대기 줄을 고치지 않는다.
- 변수 이름 집합이 바뀌는 문안 개정(3.2 의 제약).
- 009 의 나머지 Minor(M1~M3, M5~M8).
- 이미 `sending`·`accepted`·끝난 줄을 고치는 것. 나간 알림톡은 회수할 수 없다(설계 9.8).

실패로 보는 것(기술적으로 돌아가도): 묶음을 통째로 예약·변경·취소하는 보통 경로의 결과(줄 수·문안·시각)가 지금과 달라지는 것. 방문 저장 트랜잭션 안에서 업체를 부르게 되는 것(N13·N14).

## 3. 동작

### 3.1 I6 — 묶음 줄의 아이 빼기·더하기·옮기기

"묶음 줄"은 같은 매장·같은 보호자·같은 종류·같은 `variables.starts_at` 의 줄이다. 아래 규칙은 **`scheduled` 인 줄에만** 쓴다(`sending` 은 지금 나가는 줄이라 두고, 지금처럼 방문 ID 로 거두는 대상에만 든다).

**빼기** — 방문 X(아이 P)가 취소·노쇼·시각 변경될 때, 옛 시각의 묶음 줄 가운데 `pet_ids` 에 P 가 있는 줄에서:

- P 를 빼고 남는 아이가 있으면 줄을 살려 둔다. 그 줄이 X 에 달려 있었으면 **남은 아이의 방문으로 옮긴다**(`visit_id`·`pet_id` 를 그 방문 것으로). 취소된 방문의 상세에 "리마인드 예정"이 보이지 않게 하려는 것이다.
- 남는 아이가 없으면 지금처럼 취소한다(이유는 지금과 같은 `visit_canceled`·`no_show`·`rescheduled`).
- 종류: 취소·노쇼는 전 종류, 시각 변경은 지금처럼 `reminder`·`change`, **완료 되돌리기(`revived`)는 `next_visit`**(이유 `reverted`) — 함께 완료한 묶음의 제안 줄은 몇 주 동안 대기라 같은 문제가 더 오래 열려 있다.
- **한 명령이 함께 다룬 아이들은 한 번에 뺀다.** 이벤트의 `family_pet_ids`(비면 자기 `pet_id`)를 통째로 빼므로, 묶음을 통째로 취소·변경하면 첫 이벤트에서 줄이 비어 제자리(지금과 같은 방문)에서 취소된다 — 옮겼다가 취소하지 않는다. 한 마리만 다루는 명령은 그 아이만 빠진다.
- 옮길 방문에 같은 종류의 대기 줄이 이미 있으면(재발송 줄 — 방문·종류당 대기 줄 하나 색인) 옮기지 않고 제자리에 둔다.
- 묶음이 아닌 줄(아이가 P 하나거나 보호자만의 방문)은 지금 동작 그대로다.

**더하기** — 줄을 만들려는데 같은 묶음의 `scheduled` 줄이 이미 있으면, 건너뛰기 전에 이벤트의 아이들(`family_pet_ids`, 비면 자기 `pet_id`) 가운데 빠진 아이를 그 줄의 `pet_ids` 에 더한다(오름차순, 중복 없음). 대기 줄이 `sending` 이면 지금처럼 건너뛰기만 한다.

- 종류는 `_create_for_group` 이 다루는 다섯 전부다. 다만 `change` 는 대기 줄의 `previous_starts_at` 이 이벤트의 옛 시각과 같을 때만 더하고, 다르면(다른 시각에서 옮겨 온 아이) 그 아이의 변경 안내를 따로 한 통 만든다 — 틀린 "변경 전" 시각이 나가면 안 된다.
- 아이가 이미 줄에 있어도 방문 짝(아래 `visit_ids`)은 채운다.
- **보호자만의 방문(줄의 `pet_id` 가 없음)에 달린 줄에는 더하지 않는다** — 지금처럼 건너뛰기만 한다. 더하면 그 아이를 취소할 때 "남는 아이 없음"으로 보호자 방문의 리마인드까지 사라진다. 그래서 보호자만의 방문과 아이 방문이 같은 시각에 섞인 묶음은 지금 동작 그대로 남는다(먼저 온 방문의 이름으로 한 통, 그 방문을 취소하면 함께 거둠 — 009 "알려진 동작"에 적는다).

**옮길 방문을 아는 방법(만드는 사람 몫, 권고).** notification 은 visit 을 조회하지 않는다. 묶음 줄을 만들거나 아이를 더할 때 아이별 방문 ID 를 줄에 함께 적어 두면(`variables` 에 `pet_ids` 와 나란한 `visit_ids`) 조회 없이 옮길 수 있다. 이벤트는 자기 `visit_id`·`pet_id` 를 이미 싣고 있으므로 방문마다 오는 이벤트가 자기 짝을 채운다. 이 칸이 없는 옛 줄, 짝을 모르는 아이만 남은 줄은 옮기지 않고 제자리에 둔다(이름만 뺀다). 다른 방법을 쓰더라도 지킬 것: 스포크끼리 import 하지 않는다, 잠금 순서(고객 행 → 방문 행 → 알림 행)를 지킨다, `visit_ids` 는 `variables` 안이라 응답에 나가지 않는다(N12).

**결과가 바뀌는 경우와 안 바뀌는 경우**(콩이·두부, 14:00, 리마인드 줄은 콩이 방문에 달림)

| 명령 | 지금 | 고친 뒤 |
|---|---|---|
| 둘 다 취소(한 명령) | 리마인드 취소, 취소 안내 한 통 "콩이·두부" | 같다 |
| 둘 다 16:00 로(한 명령) | 옛 리마인드 취소, 새 리마인드·변경 안내 한 통씩 | 같다 |
| 콩이만 취소 | 리마인드 사라짐 | 리마인드 "두부", 두부 방문으로 옮김 |
| 두부만 취소 | 리마인드 "콩이·두부" | 리마인드 "콩이" |
| 두부만 16:00 로 | 14:00 리마인드 "콩이·두부" + 16:00 리마인드 "두부" | 14:00 "콩이" + 16:00 "두부" |
| 콩이 예약 뒤 두부를 14:00 에 따로 예약 | 리마인드 "콩이" | 리마인드 "콩이·두부" |
| 두부(16:00)를 콩이의 14:00 로 옮김 | 14:00 리마인드 "콩이" | 14:00 리마인드 "콩이·두부" |
| 함께 완료한 뒤 콩이만 되돌림 | 다음 예약 제안 사라짐 | 제안 "두부", 두부 방문으로 옮김 |
| 함께 완료한 뒤 두부만 되돌림 | 제안 "콩이·두부" | 제안 "콩이" |

되돌린 방문(`VisitReserved(revived=True)`)은 더하기 규칙으로 그 시각의 리마인드 줄에 다시 들어간다.

한 마리만 취소했을 때의 취소 안내, 한 마리만 옮겼을 때의 변경 안내는 지금처럼 그 아이 이름으로 한 통 간다.

**동시성.** 방문을 쓰는 유스케이스는 고객 행부터 잠그므로 같은 보호자의 이벤트는 차례로 온다. 디스패처와는 겹칠 수 있다 — 줄을 고치는 UPDATE 는 `status = 'scheduled'` 조건을 달아, 그사이 집힌 줄은 건드리지 않는다(009 의 M3 과 같은 방향).

### 3.2 I7 — 승인 전 판을 따로 둔다

`notification_templates` 에 칸 둘을 더한다(마이그레이션 0013, 추가만): `pending_text_version`(smallint, null), `pending_provider_template_id`(varchar(100), null). 둘은 함께 null 이거나 함께 값이 있다(CHECK).

- **재등록, 기존 줄이 `approved`** → `status`·`text_version`·`provider_template_id`·`decided_at` 은 그대로 두고 대기 칸 둘에 새 판을 적는다. 발송과 구독자는 `status` 와 `provider_template_id` 만 보므로 옛 판으로 계속 간다.
- **재등록, 기존 줄이 없거나 `pending`·`rejected`** → 지금처럼 덮는다(계속 보낼 승인 판이 없다). 대기 칸은 비운다.
- **디스패처 주기(10분)** 는 `status = pending` 인 줄에 더해 대기 칸이 찬 줄도 업체에 묻는다(대기 칸의 업체 ID 로).
  - 승인 → 대기 판을 본 칸으로 올리고(`text_version`·`provider_template_id`), 대기 칸을 비우고, `decided_at` 을 적는다. `status` 는 `approved` 그대로.
  - 반려 → 대기 칸을 비우고 옛 판으로 계속 보낸다. `status` 는 `approved` 그대로, `rejected_reason` 에 사유를 적고 WARNING 로그(매장·종류·판만). 운영자가 문안을 고쳐 다음 판으로 재등록한다.
  - 조회 실패 → 지금처럼 다음 주기.
  - 스크립트의 `--refresh`(심사 상태 조회)도 같은 규칙을 쓴다.
- 대기 판이 걸려 있는 줄을 다시 재등록하면 대기 칸을 새 것으로 덮는다.
- `scripts/reregister_templates.py` 의 고르는 기준은 "본 칸과 대기 칸 어느 쪽도 코드의 판이 아니거나 `rejected`"가 된다 — 심사 중인 새 판을 또 등록하지 않는다. 승인 뒤 새 판이 반려된 종류(본 칸은 옛 판, 대기 칸 빔)는 다시 고른다(운영자가 문안을 고친 뒤 돌리는 스크립트다).
- 연동 해제는 지금처럼 줄을 지운다. 연동·`next_visit` 켜기·빠진 종류 채우기는 첫 등록이라 그대로다.
- overview 응답은 그대로다. 재심사 중인 종류는 `approved` 로 보이고 대기 칸은 내보내지 않는다. 승인 판이 있는 채 새 판이 반려되면 `status: approved` 에 `rejected_reason` 이 찬 채로 나간다 — 앱은 `status` 로만 문구를 고른다(⑥-2 계획에 적는다).

**제약 — 판을 올릴 때 변수 이름은 바꾸지 않는다.** 심사 중에는 옛 문안(업체에 있는 것)에 지금 코드가 만드는 변수 값을 채워 보낸다. 변수 이름 집합이 달라지면 옛 판 발송이 깨질 수 있으므로 `TEMPLATES` 의 변수 이름 집합을 테스트로 못 박고(바꾸면 실패하며 이 절을 가리킨다) `templates.py` 머리말에 적는다. 문자용 문안은 심사가 없어 코드의 새 문안이 바로 나간다 — 받아들인다.

## 4. 바뀌는 곳 (예상)

- `notification`: `handle_visit_event_interactor`(빼기·더하기·옮기기), `MessageRepository` 와 pg 구현(묶음의 `scheduled` 줄을 찾아 고치는 메서드), `TemplateRepository.upsert`·`set_status` 와 pg 구현, ORM·매퍼·엔티티(대기 칸), 디스패처 `refresh_templates` 와 `list_pending_templates`, `templates.py` 머리말.
- `scripts/reregister_templates.py`, 마이그레이션 0013, `test_schema_drift`·CHECK 대조 테스트.
- 허브·visit: 권고안대로면 바꾸지 않는다(이벤트가 이미 `visit_id`·`pet_id` 를 싣는다).
- 문서: 설계 6.3 은 그대로 맞게 되고, 009 의 "알려진 동작"(가족 묶음 항)·"남는 것"(I7 항)을 고친 내용으로 바꾸고 ⑥-2 계약의 가족 묶음 문단에 "한 마리가 빠지면 줄이 남은 아이의 방문으로 옮겨진다"를 더한다.

## 5. 검증

- 단위(스텁 포트): 3.1 표의 아홉 줄을 한 줄씩(통째 취소·변경은 줄이 **같은 방문에서** 취소되는 것까지). 더해서 — `change` 는 옛 시각이 다르면 따로 한 통, 보호자만의 방문에 달린 줄에는 더하지 않는다, 옮길 방문에 대기 줄이 있으면 제자리, 되돌린 방문이 리마인드에 다시 들어간다, `sending` 줄은 고치지 않는다, `visit_ids` 없는 옛 줄은 이름만 빼고 제자리, 보호자만의 방문·한 마리 방문은 지금과 같다, 세 마리에서 한 마리씩 차례로 빠져 마지막에 취소.
- 단위: 3.2 의 재등록 네 갈래(없음·pending·rejected·approved), 주기 조회의 승인·반려·실패, 대기 중 재등록, 스크립트의 고르는 기준, 변수 이름 집합 고정.
- 통합(실제 DB): 묶음 예약 → 한 마리 취소 → `run_once` → 가짜 게이트웨이가 받은 `#{대상}` 이 남은 아이뿐이고 줄이 남은 아이 방문의 내역에 있다. 승인된 종류 재등록 → 심사 중 예약 등록 → 줄이 생기고 옛 업체 ID 로 나간다 → 승인 뒤 새 업체 ID. 0013 의 CHECK.
- 기존 것 전부: 단위 1873·통합 487 이 그대로 통과(묶음 통째 경로가 안 바뀌었다는 증거), import-linter 6 kept, 라우트 표 80줄 그대로, `check_notification_flow.sh` 53줄.
- 새 규칙마다 변이 한 번(조건을 뒤집어 테스트가 떨어지는지).

## 6. 만드는 사람에게 맡기는 것

- 묶음 줄을 찾아 고치는 저장소 메서드의 모양과 이름, `visit_ids` 를 적는 정확한 형식(3.1 의 권고를 따르거나 같은 조건을 지키는 다른 방법).
- 승인 뒤 새 판이 반려됐을 때 스크립트 출력에 사유를 어떻게 보일지.
- 0013 의 `downgrade`(칸 둘과 CHECK 를 지운다).

# ⑪ 전자 동의서 + 첫 방문 문진표 — 설계

2026-11-16. ③-B 설계(`2026-11-14-visit-checks-design.md`)가 "하지 않는 것"으로 미뤄 둔 전자 동의서와, 경쟁 조사(`.superpowers/research/reports/펫미용 앱 경쟁 기능 비교.md` 1순위)가 권한 첫 방문 문진표를 한 묶음으로 만든다. 둘 다 **보호자가 로그인 없이 웹에서 적어 보내는 서류**다.

사용자는 "순위에 써 있는 11개 설계를 시작"하라고 했다. **아래의 문안·항목·기준값·화면 자리는 모두 내가 정한 것이고**, 사용자만 답할 수 있는 것은 9절에 따로 모았다.

## 1. 왜

- 지금 미용 동의는 "받았다"는 표시뿐이다(`pets.grooming_consent_on`). 종이나 말로 받은 것을 사장이 적는다. 무엇을 읽고 동의했는지, 누가 했는지가 남지 않는다.
- 새 손님의 정보는 카카오톡으로 주고받은 것을 사장이 다시 친다. 사장님은 적는 것을 귀찮아한다. 첫 매장은 이 일을 별도 신청서 웹으로 하고 있다.
- 경쟁사: 그루머노트는 카카오톡 서명 동의서를 월 12,900원 구간에, 포들리는 동의서를 팀 플랜에 두고, 티피는 매장이 템플릿을 직접 만들게 한다(리뷰: "너무 불편하고 복잡해요 … 교육 들어야 된다고"). 동의서 자체에 대한 불만은 찾지 못했다 — 드러난 것은 "유료 구간"과 "설정이 많다"는 주변 문제다. **근거가 약하다**: 리뷰 표본이 앱스토어 수십 건이고, 본인 인증·서명본 보관 방식은 어느 제품에서도 확인하지 못했다.

## 2. 목표와 하지 않는 것

**목표**

- 확인할 것의 `consent` 가 뜬 아이에게 **그 아이에게 필요한 문안만** 담긴 동의서 링크를 보내고, 보호자가 서명하면 `consent` 가 저절로 사라진다.
- 서명한 것이 남는다 — 읽은 문안의 판, 그때 보인 사실(아이 이름·지병 이름), 적은 이름, 손가락 서명, 시각.
- 새 손님이 문진표를 적어 보내면 사장은 **확인만** 하고 등록한다. 다시 치지 않는다.
- 0원이다. 링크는 공유 시트로 보낸다.
- 설정 화면을 늘리지 않는다. 매장이 만들거나 고를 것이 없다.

**하지 않는 것**

| 항목 | 까닭·때 |
|---|---|
| 본인 인증(휴대폰·카카오 인증) | 유료 외부 서비스다. 서명한 사람이 누구인지 증명하지 않는다. |
| "법적 효력"이라는 말 | 화면·문서·알림 어디에도 쓰지 않는다. 문안은 법률 검토를 받지 않았다(9절). |
| 매장이 문안을 고치거나 새로 만들기 | 설정이 는다(티피의 불만). 문안이 달라지면 판 관리가 매장마다 필요하다. 요청이 나오면. |
| 알림톡으로 보내기, 예약과 동시에 자동으로 보내기 | 알림톡 종류를 더해야 하고 템플릿 심사가 있다. 실발송을 붙일 때. |
| 문진표 안에서 동의 서명까지 받기 | 문진표를 낼 때는 아이의 행이 없다. 등록한 뒤 동의서를 따로 보낸다(9절 질문 3). |
| 문진표의 답을 자동으로 등록 | 사람이 확인한다. 전화번호가 이미 있는 고객이면 어디에 붙일지 사람이 고른다. |
| 예방접종 증명, 사진 첨부(원하는 스타일 사진) | 로그인 없는 경로에 파일 올리기를 열지 않는다. 글로만 받는다. |
| 호텔·유치원용 동의서, 마취·의료 행위 동의 | 범위 밖이다. |
| 서명한 접속 주소(IP)·기기 정보 저장 | 개인정보를 더 쌓지 않는다. 횟수 제한에만 쓰고 버린다. |
| 히스하우스 신청서 옮기기 | 별도 프로젝트다. 건드리지 않는다 — 나중에 이 문진표로 옮길 수 있다. |
| 받은 문진표 알림(푸시) | 푸시가 없다. 고객 탭을 열 때 보인다. |

**이렇게 되면 실패다**: 링크를 주운 사람이 매장의 다른 고객 정보를 본다 · 내부 메모·지병 메모·주의 사유가 서류 화면에 실린다 · 익명화한 고객의 서명 그림·이름·문진표가 남는다 · 서명했는데 `consent` 가 그대로다 · 지병이 더해진 뒤 옛 문안의 서명이 새 지병까지 덮는다 · 문진표가 사람 확인 없이 고객을 만든다 · 토큰이 로그에 남는다.

## 3. 무엇을 만드나

### 3.1 서류 링크 — 둘이 함께 쓰는 틀

- 서류 요청 하나가 링크 하나다. 알림장 링크와 같은 모양이다 — DB 에는 `public_id`(16바이트)만 있고 토큰은 `base64url(public_id ‖ HMAC)[43글자]` 로 그때마다 계산한다. 주소는 `{REPORT_WEB_BASE_URL}/f/{토큰}`.
- 키는 `REPORT_LINK_KEY` 를 그대로 쓰되 **서명 대상 앞에 `form:` 을 붙인다**. 알림장 토큰을 서류 경로에 넣어도, 그 반대도 서명이 맞지 않는다. 새 비밀값이 없다.
- 웹 서버가 백엔드를 부를 때 토큰은 헤더 **`X-Form-Token`** 에 싣는다(알림장의 `X-Report-Token` 과 같은 규칙 — 경로·질의에 두지 않고, 로그·문서·커밋에 남기지 않는다).
- **기간 14일**(고정, 내가 정한 것). 알림장의 30일보다 짧다 — 서류는 곧 할 일이고, 문진표는 전화번호를 받는 창구라 오래 열어 두지 않는다.
- **한 번 내면 닫힌다.** 낸 뒤 같은 링크를 열면 "제출했어요"와 낸 날만 보인다(낸 내용은 다시 보이지 않는다). 매장이 끊을 수 있다. 닫힌 이유(끊음·기간·매장 정지)는 가르지 않는다.
- 같은 대상에 살아 있는 요청이 있으면 [보내기]는 **같은 링크**를 돌려준다(다시 공유). 기간이 지난 줄은 발급이 먼저 닫는다 — `visit_reports` 와 같다.
- 횟수 제한은 알림장의 것(접속 주소당 조회 수, 서명이 틀린 토큰의 실패 수 차단)을 같은 규칙·**다른 이름 공간**으로 쓴다. 제출은 접속 주소당 10분에 10번을 넘으면 429.

### 3.2 동의서

**문안은 세 토막이다**(내가 정한 것). 아이의 지금 사실로 필요한 토막만 이어 붙인다.

| 토막 | 붙는 조건 | 담는 것(요지 — 글자는 계획에서 굳힌다) |
|---|---|---|
| `basic` 미용 안내 | 늘 | 미용 중 생길 수 있는 일(피부 자극·작은 상처, 엉킨 털은 짧게 밀 수 있음, 낯선 환경의 스트레스) · 아이가 힘들어하면 미용을 멈추거나 줄일 수 있음 · 건강 상태를 사실대로 알렸음 · 응급 때 보호자에게 연락하고 가까운 동물병원으로 옮길 수 있음 |
| `senior` 노령 | 10살 이상(③-B 의 노령 판정과 같은 함수) | 나이가 많은 아이는 미용의 부담이 크고 숨은 질환이 드러날 수 있음 · 서 있기 힘들어하면 마무리가 고르지 않을 수 있음 |
| `condition` 지병 | `pet_conditions` 가 하나라도 있음 | **적힌 지병의 이름을 그대로 나열**(`심장 · 피부`) · 그 지병 때문에 미용 중·뒤에 상태가 나빠질 수 있음 · 수의사와 상의했는지는 보호자의 책임으로 확인 |

- 문안에는 **판(version, 정수)** 이 있다. 코드에 든 상수다(`customer/domain/services/consent_text.py`). 글자를 고치면 판을 올린다. 옛 판의 글자는 지우지 않는다 — 옛 서명을 그 글자로 다시 보여야 한다.
- **문안은 열 때 조립한다**(발급 때가 아니다). 보낸 뒤 지병이 더해졌으면 보호자는 더해진 문안을 읽는다.
- **서명**: 적은 이름(1~50자, 필수) + 손가락 서명(PNG, 64KB 이하, 필수) + "위 내용을 읽었고 동의합니다" 체크. 웹이 서명과 함께 **자기가 보여 준 판과 토막**을 실어 보낸다.
- **낼 때 다시 견준다.** 서버가 고객 행을 잠근 뒤 아이의 사실로 토막을 다시 계산해, 보호자가 본 것과 다르면(그 사이 지병이 더해졌다) 409 — 웹은 "내용이 바뀌었어요. 다시 읽어 주세요"와 새 문안을 그린다. 서명은 저장하지 않는다.
- **서명이 남기는 것**: 판, 붙은 토막, 그때 보인 사실(아이 이름·지병 이름들 — 글자 그대로의 사본), 적은 이름, 서명 PNG, 서명 시각, 보낸 멤버.
- **서명하면 `pets.grooming_consent_on` 이 그날(매장 시간대)로, `grooming_consent_by_member_id` 가 보낸 멤버로 찍힌다.** ③-B 의 판정·기한(365일)·"지병 종류가 늘면 받은 날을 지운다"는 그대로다. 받은 날을 지워도 서명 기록은 남는다(이력).
- 노령도 지병도 아닌 아이에게도 보낼 수 있다(`basic` 만). 막지 않는다 — ③-B 와 같다.
- 무지개다리를 건넌 아이·익명화한 고객에게는 보낼 수 없고, 살아 있던 링크는 닫힌 것으로 읽힌다.
- 보호자만의 방문에는 동의서가 없다(아이가 없다).

### 3.3 문진표

- **보내는 곳 둘**: (가) 고객 탭 — 아직 등록하지 않은 새 손님. (나) 반려동물 상세 — 이미 있는 아이의 정보를 보호자에게 다시 물을 때.
- **보호자가 적는 것**(내가 정한 것 — 등록 화면의 칸과 같게 맞췄다):

| 묶음 | 칸 | 필수 |
|---|---|---|
| 보호자 | 이름, 전화번호 | (가)에서 필수. (나)에서는 묻지 않는다 |
| 아이 | 이름, 종(강아지·고양이), 품종, 성별, 중성화, 생일 또는 태어난 해(모르면 "몰라요"), 몸무게(모르면 비움) | 이름·종만 필수 |
| 건강 | 지병 칩(`pet_condition_types` 의 그 목록 + 기타 한 줄) 또는 "없어요", 지병에 대해 알려 줄 것(500자) | "없어요"나 하나 이상 |
| 성격 | 싫어하는 것·조심할 것(500자) — 예: 발 만지기, 드라이기 소리 | 아니오 |
| 스타일 | 원하는 스타일(500자) | 아니오 |
| 안내 | 개인정보 수집·이용 안내(항목·목적·보관 기간)와 동의 체크 | 필수 |

- 한 링크에 아이 한 마리다. 둘째는 등록 뒤 앱에서 더한다(사장이 [반려동물 추가]) — 문진표를 여러 마리로 늘리지 않는다.
- **낸 것은 "받은 문진표"다.** 고객·반려동물 표를 건드리지 않는다. 사장이 열어 보고 셋 중 하나를 한다.
  - **[등록하기]**((가)) — 기존 등록 흐름(번호 → 보호자 → 반려동물)이 답으로 **미리 채워져** 열린다. 번호가 이미 있는 고객이면 기존의 번호 조회(`lookup_customer`)가 그대로 알려 주고 그 가족에 아이를 더하는 길로 간다. 저장은 기존 유스케이스(`register_customer`·`add_pet`)다.
  - **[이 아이에 반영]**((나)) — 반려동물 수정 화면이 답으로 미리 채워져 열린다. 지병이 늘면 ③-B 대로 동의가 비워진다.
  - **[지우기]**.
- "성격"과 "스타일"은 반려동물 메모(`pets.memo`) 초안에 `조심할 것: … / 원하는 스타일: …` 로 들어가고 사장이 고칠 수 있다. "지병에 대해 알려 줄 것"은 고른 지병의 메모(`pet_conditions.note`) 초안으로 들어간다. **글은 기존 쓰기를 거쳐 들어가므로 `SearchSourceChanged` 가 그대로 나가고 기록 검색에 걸린다** — 문진표 표 자체는 검색 원본이 아니다.
- 등록·반영이 끝나거나 지우면 **받은 문진표의 답은 지운다**(요청 줄만 남는다 — 언제 보내고 언제 받았는지). 답은 이미 고객·반려동물에 들어갔다.
- **확인하지 않은 채 30일이 지난 답은 읽을 때 없는 것으로 치고**, 운영자 스크립트가 지운다(미디어 정리와 같은 방식). 전화번호가 든 글을 무한정 두지 않는다.

### 3.4 화면

톤은 지금 그대로다(무채색, 잉크색 글자, 가는 선). "AI"·"법적 효력"이라는 말이 없다.

**앱** (`features/customer`, 쓰기는 `CustomerCommands`)

1. **방문 상세·예약 등록의 `consent` 항목** — 지금의 [받았어요] 옆에 **[동의서 보내기]**. 누르면 링크를 만들고 공유 시트가 열린다(글: `{매장 이름} 미용 동의서예요. 읽고 서명해 주세요.` + 주소). 보낸 뒤에는 항목 아래 `동의서를 보냈어요 · 서명 전`(누르면 다시 공유). 서명되면 항목이 사라진다. 예약 등록 화면에서는 아이가 이미 있을 때만 버튼이 있다.
2. **반려동물 상세 정보 탭의 미용 동의 줄** — 서명으로 받은 것이면 `미용 동의 · 2026년 11월 16일에 서명 받음` 과 [서명 보기]. 줄 끝에 [동의서 보내기]. [서명 보기]는 문안(그 판의 글자)·보인 사실·적은 이름·서명 그림·시각 한 장이다. 지난 서명이 여럿이면 날짜 목록.
3. **고객 탭** — 받은 문진표가 있을 때만 목록 위에 `받은 문진표 2` 한 줄. 누르면 목록(아이 이름·보호자 이름·받은 날) → 한 장(답 전부, [등록하기] 또는 [이 아이에 반영], [지우기]). 고객 등록의 첫 화면에 `문진표 링크 보내기`(공유 시트, 글: `{매장 이름}이에요. 오시기 전에 아이에 대해 알려 주세요.`). 반려동물 상세 [보호자] 탭에 `문진표 다시 받기`.
4. 서명 그림은 앱이 받은 바이트를 그대로 그린다(네이티브 이미지). 웹뷰가 없다.

**웹** (`web/`, 경로 `app/f/[token]/page.tsx` · 제출 `app/f/[token]/submit/route.ts`)

5. **동의서** — 매장 이름, 아이 이름, 문안 토막들, 이름 칸, 서명 칸(손가락·마우스, [다시 쓰기]), 체크, [동의하고 보내기]. 서명 칸은 브라우저 동작이라 `'use client'` 다. 자바스크립트를 끈 브라우저에는 "서명하려면 자바스크립트를 켜 주세요" 한 줄.
6. **문진표** — 3.3 의 칸. 한 화면 세로 스크롤(단계로 나누지 않는다). 폭 320 에서 가로로 넘치지 않는다.
7. **낸 뒤·닫힘·없음·잠시 후** — 알림장의 화면 넷과 같은 규칙(200·404 뿐, 닫힌 이유를 가르지 않는다). 낸 뒤는 `보냈어요. {매장 이름}에서 확인할게요.`
8. 제출은 폼 POST → 경로 핸들러 → 303 으로 같은 주소다. `Sec-Fetch-Site` 가 있고 `same-origin` 이 아니면 403. 응답 헤더 셋(`noindex`·`no-store`·`no-referrer`)이 그대로 붙는다. 미리보기(og)는 `{매장 이름}` 과 "미용 동의서"/"문진표"뿐이다 — 아이 이름·지병을 싣지 않는다.

### 3.5 권한

새 권한을 만들지 않는다. 보내기·끊기·등록·반영·지우기는 `require_permission("customer:write")`(사장·직원). 서명 보기·받은 문진표 읽기는 매장 멤버(`get_shop_context`). 보낸 사람은 `ShopContext.member_id`.

## 4. 어떻게 — 정해 둔 것

### 4.1 어디에 사는가

- **전부 `customer` 스포크다.** 동의의 사실(`pets.grooming_consent_on`)과 등록이 여기 있다. `visit` 은 지금처럼 허브 포트로 사실을 읽기만 한다.
- **스포크 사이에 나눠 써야 하는 것 셋을 올린다**(스포크끼리 import 하지 않는다 — 알림장의 것은 `visit` 안에 있다). 이름과 동작은 그대로다.
  - 토큰 만들기·읽기 `visit/domain/services/report_token.py` → `core/`(순수 함수). 서명 대상에 붙일 앞말(`b""` / `b"form:"`)을 인자로 받는다.
  - 접속 주소 `visit/dependencies/public_client.py` 와 횟수 제한(`PublicReportLimiterPort`·Redis 어댑터) → `core/`. 이름 공간을 인자로 받는다.
  - `visit/app/services/public_context.py` → `hub/app/dtos/shop_context.py` 의 `public_context`(이미 `system_context` 가 있는 파일). **코드에서 확인해 바꾼 것이다** — 루트 `CLAUDE.md` 는 "가드 없이 `ShopContext` 를 만드는 곳은 둘뿐"이라 하고 그 하나가 `visit` 안에 있어, `customer` 의 공개 경로가 쓸 수 없다. 옮기면 둘이 한 파일에 모이고 규칙의 글자("둘뿐")는 그대로다. `CLAUDE.md` 의 경로를 고친다.

### 4.2 자료 모양 (Alembic 다음 번호 — 다른 묶음과 겹치니 계획 때 정한다)

- `customer_forms` — 서류 요청. `id`, `shop_id`, `kind`(`consent`·`intake`), `public_id bytea(16) unique`, `customer_id null`, `pet_id null`, `expires_at not null`, `revoked_at`, `submitted_at`, `created_by_member_id`, `created_at`.
  - CHECK: `consent` 는 `pet_id`·`customer_id` 가 있다. `intake` 는 둘 다 없거나((가)) 둘 다 있다((나)).
  - 부분 유일 색인: 동의서는 `(pet_id) WHERE kind='consent' AND revoked_at IS NULL AND submitted_at IS NULL`, (나)의 문진표도 같은 모양. (가)는 대상이 없어 유일 조건이 없다 — 누를 때마다 새 링크다.
- `consent_signatures` — 서명. `id`, `shop_id`, `form_id unique`, `customer_id`, `pet_id`, `text_version smallint`, `with_senior bool`, `with_condition bool`, `shown_pet_name varchar`, `signer_name varchar(50)`, `signature_png bytea`(CHECK `octet_length <= 65536`), `signed_at`.
  - `consent_signature_conditions(signature_id, position, label)` — 그때 보인 지병 이름(사본, 3NF).
- `intake_answers` — 받은 문진표. `id`, `shop_id`, `form_id unique`, 3.3 의 칸들(등록 화면의 형과 같게), `submitted_at`.
  - `intake_answer_conditions(answer_id, type_code, custom_label)`.
  - 등록·반영·지우기에서 행을 지운다(`customer_forms` 줄은 남는다).
- 서명 그림은 DB 에 둔다. 미디어 스포크(S3)를 거치지 않는다 — 로그인 없는 경로에 업로드 발급을 열지 않고, 64KB 이하의 그림 한 장이다.

### 4.3 API (모양은 계획에서 굳힌다)

**매장** (`/v1/shops/{id}/…`)

- `POST …/pets/{pet_id}/consent-form` → `{url, expires_on, sent_at}`(있으면 같은 것) · `DELETE` 같은 경로(끊기).
- `GET …/pets/{pet_id}/consent-signatures` → 목록 · `GET …/consent-signatures/{id}` → 한 장(문안 글자 포함) · `GET …/consent-signatures/{id}/image` → `image/png`.
- `POST …/intake-forms` 본문 `{pet_id: int|null}` → `{url, expires_on}`.
- `GET …/intake-answers`(목록·개수) · `GET …/intake-answers/{id}` · `DELETE …/intake-answers/{id}`. 등록·반영이 끝났다는 신호는 기존 등록·수정 요청 본문의 선택 칸 `intake_answer_id` — 같은 트랜잭션에서 답을 지운다.
- 반려동물 상세 응답에 `consent_form: {sent_at, expires_on}|null` 과 마지막 서명의 유무. 고객 목록 응답에 받은 문진표 수.
- **`visit` 이 읽는 것**: `CustomerDirectoryPort` 의 확인할 것용 읽기(③-B 가 더한 것)의 아이 항목에 `consent_form_sent_at` 칸 하나. `checks` 의 `consent` 항목이 이것을 실어 앱이 "보냈어요 · 서명 전"을 그린다.

**공개** (`/v1/public/…`, 로그인 없음 — `route_inspection._PUBLIC_ROUTES` 와 프로세스별 목록 테스트에 더한다)

- `GET /v1/public/form` — 헤더 `X-Form-Token`. `{kind, state(open·submitted), shop: {name}, …}`. 동의서면 `pet_name`, `text_version`, 토막들(글자 포함), 지병 이름들. 문진표면 지병 종류 목록과 (나)일 때 아이 이름.
- `POST /v1/public/form/consent` — `{text_version, with_senior, with_condition, signer_name, signature_png(base64)}` → 204 / 409(문안 바뀜) / 410 / 404 / 429.
- `POST /v1/public/form/intake` — 3.3 의 칸 → 204 / 422 / 410 / 404 / 429.
- **공개 스키마는 매장용과 따로 쓰고 칸을 하나하나 적는다.** 싣지 않는 것: 지병 메모, 반려동물 메모, 내부 메모, 주의 표시, 노쇼, 전화번호, 고객·반려동물·매장의 ID, 다른 아이.

### 4.4 잠금·트랜잭션

- 동의서 발급·끊기·서명: **고객 행(`pets.lock_owner`) → 서류 요청 행**. 서명은 그 안에서 사실을 다시 읽어 견주고, 서명 행을 쓰고, 받은 날을 찍고, 요청을 닫는다 — 한 트랜잭션.
- (가)의 문진표는 고객이 없으니 요청 행만 잠근다. (나)는 고객 행 → 요청 행.
- 익명화(`delete_customer`): 고객 행을 잠근 그 트랜잭션에서 그 고객의 서명 행(그림·이름)과 받은 문진표를 지우고 살아 있는 요청을 끊는다. 순서는 **고객 행 → 서류 요청 행 → (기존) 보호자 연결 행**. 루트 `CLAUDE.md` 의 잠금 순서에 "서류 쪽은 고객 행 → 서류 요청 행"을 더한다.
- 반려동물 삭제·무지개다리: 살아 있는 요청을 끊는다. 서명 기록은 남는다(무지개다리) / 지운다(삭제).
- 잠금을 쥔 채 외부 HTTP 를 부르지 않는다(부를 것이 없다).

### 4.5 로그

- 토큰·서명 그림·적은 이름·문진표의 글·전화번호를 로그·오류 메시지·예외 문자열에 남기지 않는다. 로그는 `shop_id`·`form_id`·종류·결과뿐이다.
- 웹은 요청 본문·토큰을 `console.*` 에 넣지 않는다(지금 규칙 그대로).

### 4.6 나누기

- **⑪-1 백엔드** — 올리기 셋(4.1), 표·마이그레이션, 문안 상수와 조립, 매장·공개 경로, 익명화·삭제 잇기, 허브 포트 칸, 흐름 스크립트 `check_forms_flow.sh`.
- **⑪-2 웹** — `/f/[token]` 동의서·문진표·낸 뒤·닫힘, 서명 칸, 제출 핸들러, `check:server`·e2e.
- **⑪-3 앱** — 보내기 버튼 셋, 서명 보기, 받은 문진표 목록·한 장, 미리 채운 등록·수정, 시뮬레이터 흐름.

## 5. 위험과 막는 법

| | 위험 | 막는 법 |
|---|---|---|
| F1 | 링크를 주운 사람이 아이의 지병을 본다 | 추측 불가 토큰 + 14일 + 한 번 내면 닫힘. 싣는 것은 아이 이름과 지병 **이름**뿐(메모 없음). 미리보기에 싣지 않는다. 받아들인 한계: 링크를 받은 사람은 본다. |
| F2 | 남이 대신 서명한다 | 본인 인증이 없다 — **받아들인 한계**다. 그래서 "법적 효력"을 말하지 않고, 서명 보기에 "링크를 받은 사람이 적은 서명이에요"를 적는다. |
| F3 | 옛 문안의 서명이 새 지병을 덮는다 | 열 때 조립 + 낼 때 다시 견줘 409. 서명 뒤 지병이 늘면 ③-B 가 받은 날을 지운다. |
| F4 | 문진표로 쓰레기·대량 제출 | 링크 하나에 제출 한 번, 접속 주소당 제한, 칸마다 길이 제한, 본문 크기 제한(웹·백엔드 둘 다). |
| F5 | 서명 그림에 이상한 파일 | PNG 머리 바이트와 크기만 보고 서버는 풀지 않는다. `image/png` 로만 내주고 `nosniff`. 앱의 이미지 풀기는 프레임워크가 한다. |
| F6 | 익명화 뒤 서명·문진표가 남는다 | 같은 트랜잭션에서 지운다. 테스트가 행 수를 본다. 확인 안 한 문진표는 30일. |
| F7 | 알림장 토큰과 서류 토큰이 섞인다 | 서명 앞말이 다르다. 테스트: 서로의 경로에서 404. |
| F8 | 공개 응답에 매장용 칸이 샌다 | 공개 스키마를 따로 쓰고 테스트가 칸 목록을 고정한다. |
| F9 | 문진표가 기존 고객을 덮어쓴다 | 자동 반영이 없다. 번호가 있으면 기존 조회가 알려 주고 사람이 고른다. |
| F10 | 올리기(4.1)가 알림장을 깨뜨린다 | 동작을 바꾸지 않는 옮기기다. 알림장의 단위·통합·흐름·e2e 가 그대로 통과해야 한다. |

## 6. 테스트와 검증

- **백엔드 단위**: 토막 조립(나이 9/10살, 지병 0/1개, 무지개다리), 판, 요청의 상태(살아 있음·기간·끊음·냄), 문진표 칸 검증. **통합**: 발급이 같은 링크를 돌려준다 · 동시 발급 하나 · 서명이 받은 날을 찍고 `consent` 가 사라진다 · 문안 바뀜 409 · 두 번 내기 410 · 다른 매장의 요청 404 · 익명화가 지운다 · 공개 응답의 칸 목록 · 허용 목록 테스트 · 등록·반영이 답을 지운다 · 로그에 토큰·이름이 없다.
- **웹**: 컴포넌트(토막의 유무, 서명 칸, 낸 뒤·닫힘), `check:server`(상태 코드·헤더 셋·미리보기에 아이 이름이 없음·다른 출처 POST 403·기록에 토큰 없음), e2e(동의서 서명, 문진표 제출, 문안 바뀜, 닫힌 링크, 폭 320).
- **앱**: 보내기·다시 공유·서명 뒤 사라짐, 서명 보기, 받은 문진표에서 미리 채운 등록, 골든. 시뮬레이터 흐름(iOS·안드로이드): 보내기 → (준비 스크립트가 웹 서버로 서명) → 항목이 사라짐 → 서명 보기 → 받은 문진표 → 등록.
- 흐름 스크립트: 발급 → 공개 읽기 → 서명 → 받은 날 → 지병 더하기 → 다시 발급·옛 토큰 닫힘 → 문진표 → 등록 → 익명화 뒤 없음.

## 9. 사용자에게 물을 것

1. **문안을 누가 책임지나.** 동의서 세 토막과 개인정보 수집 안내는 내가 쓴 초안이고 법률 검토를 받지 않았다. 그대로 내보낼지, 히스하우스가 지금 쓰는 종이 동의서의 글을 받아 맞출지, 검토를 받은 뒤 켤지.
2. **매장이 문안을 고칠 수 있어야 하나.** 지금 설계는 고정 문안이다(설정이 없다). 매장마다 문안이 달라야 한다면 문안·판을 매장별로 저장하는 표와 편집 화면이 더해진다.
3. **첫 방문의 노령·지병 아이.** 지금 설계는 문진표와 동의서가 따로라 링크를 두 번 보낸다(문진표 → 등록 → 동의서). 문진표 끝에서 서명까지 한 번에 받게 하려면 서명을 아이의 행 없이 맡아 두었다가 등록 때 옮기는 길이 더해진다.

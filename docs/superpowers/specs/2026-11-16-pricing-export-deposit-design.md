# 차곡노트 — ⑮ 가격 계산기 · 매출 CSV와 기록 가져가기 · 예약금 안내 설계

2026-11-16. 경쟁 서비스 조사(`.superpowers/research/reports/펫미용 앱 경쟁 기능 비교.md`)의 5·7·8순위를 한 묶음으로 설계한다. 세 기능은 서로 기대지 않는다 — 문서는 세 부(部)로 나누고 계획도 셋으로 나눈다.

- 범위: 백엔드(`visit` 의 메뉴·설정·방문·매출 읽기, `customer` 의 내보내기 읽기, `tenancy` 의 내보낸 기록), 앱(`visit`·`sales`·`shop` 기능 폴더, 공유 시트의 파일 넘기기). 웹(`web/`)은 바꾸지 않는다.
- 바탕: 예약 설계(③ `2026-09-23-visit-reservation-design.md`), 기록 설계(④ — 총액·항목·결제 수단, `sales:write`), 매출 설계(⑧ `2026-11-14-sales-design.md` — 6절이 CSV 와 선결제·환불을 미뤘다), 확인할 것 설계(③-B `2026-11-14-visit-checks-design.md` — "예약금·노쇼 위약금: 결제가 없다"로 미뤘다).
- 사용자는 "순위에 써 있는 11개 설계를 시작"하라고 했다. **아래의 항목·기준값·문안·자리는 모두 내가 정한 것이다.** 사용자만 답할 수 있는 것은 맨 끝 "사용자에게 물을 것"에 있다.
- 다른 묶음에 넘기는 것: 예약금 받음 표시를 달력 칸에 싣는 것(⑬), 정기권 내역의 내보내기(⑭ 뒤), 보호자 쪽 사진 한꺼번에 받기(⑫).

## 0. 공통으로 지키는 것

- 과금되는 것·외부 서비스 연결이 없다. 결제 대행·은행 조회·알림톡 실발송을 붙이지 않는다.
- 새 설정 화면을 만들지 않는다. 지금 있는 화면(메뉴 설정, 예약 설정, 매출 탭)에 구역을 더한다.
- 사장님은 적는 것을 귀찮아한다 — 세 기능 모두 **아무것도 넣지 않아도 지금처럼 돌아간다.**
- 보호자에게 가는 것(공개 알림장·보호자 웹·알림톡)의 스키마는 건드리지 않는다. 허용 목록 테스트(`backend/tests/route_inspection.py`)가 그대로 통과해야 한다.
- 전화번호·계좌번호·메모의 글·금액을 로그·오류 메시지에 남기지 않는다. 새 로그는 shop_id·종류·건수·결과뿐이다.

# 1부. 가격 계산기

## 1.1 왜

지금은 메뉴마다 정가 하나(`service_menus.price`)가 있고, 기록 화면이 예약한 메뉴의 정가로 항목 금액을 미리 채운다(`record_rules.dart` 의 `recordFormStart`). 미용 요금은 대개 몸무게에 따라 다르고 엉킴·특수 미용이 붙는다 — 그래서 미리 채운 값이 자주 틀리고 사장이 매번 고친다.

그루머노트는 견종·무게 기준 계산기를 무료 구간에 두고 가격표를 대신 넣어 준다. 계산기 자체에 대한 불만은 찾지 못했고, 가격 설정이 뜻대로 안 된다는 리뷰(티피)와 개편 뒤 0원으로 뜬다는 리뷰(반짝)가 한 건씩 있다. **근거는 앱스토어 리뷰 몇 건이라 약하다** — "처음 넣는 수고가 걸림돌"이라는 것은 그루머노트가 대리 입력을 내세우는 데서 읽은 추론이다.

## 1.2 정한 것

| 항목 | 결정 |
|---|---|
| 무엇으로 값을 고르나 | **몸무게 구간**만. 구간의 경계는 **매장에 하나**(최대 4개 → 구간 최대 5개)이고 모든 메뉴가 같은 경계를 쓴다. 메뉴마다 경계를 따로 두면 넣을 것이 곱절이 된다. |
| 견종별 가격 | **하지 않는다.** `pets.breed` 는 자유 글이라 표의 열쇠로 쓸 수 없고(품종 사전을 새로 만들어야 한다), 견종 차이는 아래의 추가 항목(`특수견 추가`)으로 적을 수 있다. 첫 매장의 가격표가 견종 기준이면 다시 본다(물을 것 1). |
| 덧붙는 값(엉킴·특수 미용) | **새 개념을 만들지 않는다 — 메뉴다.** 기록의 항목은 `(visit_id, menu_id, amount)` 이고 매출의 메뉴별 집계가 그것을 읽는다. 추가 항목을 따로 두면 매출 화면에서 "조정" 한 줄에 묻힌다. 메뉴에 `추가 항목` 표시 하나(`is_extra`)를 더해 칩 줄만 나눈다. (처음 방향은 "덧붙는 값을 따로 둔다"였다 — 코드를 보고 바꿨다.) |
| 계산은 어디서 | **앱에서.** 서버는 경계와 구간 값을 내려 주기만 한다. 기록 화면에서 몸무게를 고치는 즉시 값이 따라와야 하고, 결과는 제안일 뿐 저장되는 것은 사람이 확정한 금액이다. |
| 채운 값의 지위 | **제안.** 지금처럼 항목 금액·총액 모두 손으로 고칠 수 있다. 손댄 줄은 몸무게를 바꿔도 다시 채우지 않는다. |
| 우선순위 | 이미 적은 기록 → 구간 값 → 정가 → 빈 칸. '지난번처럼'(`GET …/visits/defaults`)은 메뉴와 소요만 채우고 금액을 싣지 않으므로(코드 확인) 충돌이 없다. 지난번에 받은 금액으로 채우지 않는다 — 몸무게가 달라졌을 수 있다. |
| 예약 등록 화면 | 방문에는 금액 칸이 없다(금액은 기록의 것). **저장하지 않는 "예상 금액" 한 줄**만 보인다. (처음 방향은 "예약 등록의 총액을 채운다"였다 — 그런 칸이 없어 바꿨다.) |
| 넣는 수고 | 경계를 한 번 정하면 메뉴마다 구간 값 칸이 한 줄로 나온다. 첫 칸과 "구간마다 더할 값"을 적으면 나머지를 채워 준다. 비워 둔 구간은 정가로 떨어진다. 경계를 정하지 않으면 계산기가 없는 것이고 지금과 똑같다. |
| 가격표 붙여넣기 | 이번에 하지 않는다(1.6). |
| 누가 | 가격표를 고치는 것은 사장(`shop:update` — 지금 메뉴 가격과 같다). 채워진 값을 보는 것은 돈 칸을 보는 사람(`sales:write` — 사장·직원). |
| 보호자 | 가격표를 공개하지 않는다. 알림장의 금액 표시는 지금 설정(`report_show_amount`) 그대로다. |

## 1.3 규칙

- 경계 `[3, 5, 8]` 이면 구간은 `3kg 까지 / 5kg 까지 / 8kg 까지 / 8kg 넘음` 넷이다. **경계의 몸무게는 아래 구간**이다(3.0kg 은 첫 구간).
- 값 고르기: 그 구간의 값이 있으면 그것, 없으면 정가, 정가도 없으면 빈 칸. 몸무게를 모르면(보호자만의 방문, 몸무게 칸을 비움) 정가.
- 추가 항목 메뉴에는 구간 값을 두지 않는다(정가 하나).
- **기록 화면**: 처음 열 때 반려동물의 지금 몸무게(`pets.weight_kg`)로 채운다. 몸무게 칸을 고치면 손대지 않은 줄만 다시 채운다. 총액은 지금처럼 항목 합을 따라간다.
- **구간이 바뀌면 한 줄로 알린다** — 몸무게 칸 아래 `지난번 4.8kg 보다 한 구간 올랐어요`(내렸어요). 지난 몸무게는 반려동물의 지금 값이다(기록을 저장하면 그 값이 바뀐다 — 기존 규칙).
- **예약 등록**: 메뉴 칩 아래 `예상 금액 약 55,000원`. 여러 마리면 아이마다 계산해 더한다. 값이 하나도 없으면 줄이 없다. `sales:write` 가 없으면 줄이 없다.
- 지난 기록의 금액은 바뀌지 않는다(금액은 기록에 옮겨 적은 사실이다). 매출 탭의 "남은 예약 · 정가로 약 N원"은 **그대로 정가**로 센다(서버가 아이의 몸무게를 읽으려면 허브 포트가 늘어난다 — 어림이라 두고, 문구가 이미 "정가로"다).

## 1.4 자료와 API

- `visit_shop_settings.weight_bounds numeric(4,1)[] null` — 오름차순, 0 보다 크고 서로 다르고 최대 4개(CHECK 와 도메인 검증). NULL·빈 배열이면 계산기 없음.
- 새 표 `service_menu_tier_prices(menu_id → service_menus.id ON DELETE CASCADE, tier smallint 0~4, price int 0~1억)` · PK `(menu_id, tier)`.
- `service_menus.is_extra boolean not null default false`.
- 경계의 개수를 줄이면 넘치는 구간의 값을 같은 트랜잭션에서 지운다. 경계의 숫자만 고치면 값은 그대로다(앱이 저장 전에 "구간의 무게가 바뀌어요. 값은 그대로 둬요"를 한 번 묻는다).
- `GET /v1/shops/{id}/menus`(매장 멤버) 응답 항목에 `is_extra`, `tier_prices: [int|null, …]`(구간 수만큼). `GET …/visit-settings` 응답에 `weight_bounds`.
- `POST …/menus` · `PUT …/menus/{menu_id}` 본문에 `is_extra`, `tier_prices`(통째 교체). `PUT …/visit-settings` 본문에 `weight_bounds`. 모두 `shop:update`.
- 기록 저장(`PUT …/visits/{id}/record`)은 바뀌지 않는다. 추가 항목도 `items` 의 한 줄이다.

## 1.5 화면

1. **메뉴 설정**(`menu_settings_screen.dart`) 맨 위에 `몸무게 구간` 한 줄 — 누르면 경계를 적는 시트(칸 넷, 비우면 그 경계 없음). 정하지 않았으면 `몸무게에 따라 값이 다르면 구간을 정해 주세요` 한 줄.
2. 메뉴 편집 시트 — 정가 아래에 구간 값 칸들(구간 이름이 딱지: `3kg 까지`). [구간마다 더하기] 칸 하나. `추가 항목으로 쓰기` 토글.
3. **기록 화면** — 메뉴 칩이 두 줄로 나뉜다: 메뉴 / 추가. 구간이 바뀌었다는 한 줄.
4. **예약 등록** — 예상 금액 한 줄. 예약 화면의 메뉴 칩에도 추가 항목 줄을 둔다(예약 때 이미 엉킴을 아는 경우 — 고르지 않아도 된다).

색 딱지·경고 삼각형을 쓰지 않는다. 계산식(`기본 + 추가`)을 화면에 풀어 쓰지 않는다 — 줄마다 금액이 보이면 된다.

## 1.6 하지 않는 것

| 항목 | 까닭·때 |
|---|---|
| 견종별·털 길이별 가격표 | 1.2. 추가 항목으로 적는다. |
| 가격표 글을 붙여넣어 표로 바꾸기 | 매장마다 가격표의 모양이 달라 규칙으로 읽으면 틀린 값이 조용히 들어간다. 구간 값 칸이 5개 이하라 손으로 넣는 편이 안전하다. 입점 매장이 늘면 운영자가 대신 넣는 스크립트부터. |
| 서버에서 계산해 저장 | 금액은 사람이 확정한다. |
| 할인·쿠폰·회원가 | ⑭(정기권) 뒤. |
| 가격표 바뀐 이력 | 지난 기록의 금액이 이미 그때의 사실이다. |

# 2부. 매출 CSV 와 내 기록 가져가기

## 2.1 왜

⑧ 은 CSV 를 "파일 공유 채널이 없다"는 까닭으로 미뤘다 — 공유 시트가 글자만 넘긴다(`lib/core/proxy/share_sheet.dart` 의 `shareText`). 세무사에게 넘기거나 엑셀로 보려면 파일이 필요하다.

경쟁 쪽: 티피는 엑셀을 주지만 "결제를 끊으면 지난 기록을 볼 수 없다"는 리뷰가 있고, 반짝은 매출 조회가 최대 90일이다(둘 다 앱스토어 리뷰·릴리스 노트 한두 건 — 약한 근거). 무료였던 경쟁자가 유료로 돌아서는 시장이라 **"내 기록은 언제든 가져간다"** 를 약속으로 둔다.

## 2.2 정한 것

| 항목 | 결정 |
|---|---|
| 두 가지 | **매출 내보내기**(기간을 골라 방문 한 줄씩) · **내 기록 가져가기**(고객·반려동물·방문 기록 전부). |
| 파일은 어디서 만드나 | **기기에서.** 서버는 쪽으로 나눈 JSON 을 주고 앱이 CSV 로 적는다. 서버에 파일을 두지 않는다(저장소·수명·내려받기 주소를 만들지 않는다 — `media` 를 건드리지 않는다). |
| 형식 | CSV. UTF-8 **BOM**, 줄 끝 CRLF, RFC 4180 따옴표 — 엑셀에서 한글이 깨지지 않는다. `=`·`+`·`-`·`@` 로 시작하는 칸은 앞에 `'` 를 붙인다(수식 주입). 전화번호는 글자로(앞의 0 이 사라지지 않게 `="…"` 가 아니라 하이픈 든 모양 그대로). xlsx 는 만들지 않는다. |
| 넘기기 | 공유 시트에 **파일을 넘기는 메서드를 더한다**(`shareFiles`). 외부 패키지 없이 네이티브 — iOS `UIActivityViewController` 에 파일 주소, 안드로이드 `FileProvider` + `ACTION_SEND(_MULTIPLE)`. 압축하지 않는다(파일 셋을 그대로 넘긴다 — 압축 패키지를 들이지 않는다). |
| 기간 | 매출: 시작·끝 날짜(기본 이번 달, 빠른 고르기 `이번 달·지난달·올해·작년`), **길이 제한 없음.** ⑧ 의 S5("임의 기간을 받지 않는다")는 한 번에 집계하는 요약의 이야기다 — 내보내기는 쪽으로 나눠 읽으므로 한 요청이 무겁지 않다. 기록 가져가기는 기간이 없다(전부). |
| 누가 | **사장만.** 새 권한 `data:export` 를 사장 역할에 심는다. `sales:read` 를 돌려쓰지 않는다 — 전화번호가 든 파일이라 "통계를 본다"와 다른 일이고, 나중에 역할을 나눌 때 따로 줄 수 있어야 한다. 매출 내보내기는 `sales:read` 와 `data:export` 둘 다 필요하다. |
| 구독과의 관계 | **내보내기는 요금제·정지와 무관하게 열려 있다.** 지금은 요금제가 없으니 규칙으로만 적는다: 나중에 과금·기능 제한을 만들 때 `data:export` 경로는 제한 목록에 넣지 않는다. 매장이 정지(`suspended_at`)된 경우의 읽기는 지금 가드의 동작을 따르고, 정지 중에도 내보내기를 열지는 과금 설계 때 정한다. |
| 사진·영상 | **넣지 않는다.** 한 해치 원본은 수 GB 라 기기에서 한 파일로 묶을 수 없고, 서버에서 묶으면 저장·전송 비용이 생긴다. 방문 기록 파일에 사진·영상 **수**만 싣는다. 사진은 지금처럼 방문 상세에서 원본을 받는다(물을 것 3). |
| 내보낸 사실 | 누가·언제·무엇을(종류, 기간, 줄 수) 남긴다. 내용은 남기지 않는다. 화면 아래에 최근 것 몇 줄을 보인다. |
| 익명화한 고객 | 고객·반려동물 파일에서 뺀다. 매출 줄에는 금액이 남고 이름 칸이 빈다(⑧ 의 S3 과 같다). |

## 2.3 파일의 칸

**매출**(`차곡노트_매출_2026-01-01_2026-11-16.csv`) — 완료한 방문 한 줄. 방문한 날 기준(⑧ 3.1).

`날짜 · 시각 · 고객 번호 · 보호자 · 아이 · 메뉴(이름을 " / " 로) · 항목 합 · 총액 · 결제 수단 · 받은 예약금`

- 메뉴마다 열을 만들지 않는다(매장마다 메뉴가 달라 열이 흔들린다). 메뉴별 합은 매출 탭에 있다.
- 총액을 적지 않은 완료 방문은 총액 칸이 빈 채로 나온다(0 이 아니다).
- 3부를 만든 뒤에는 **돌려주지 않은 예약금**이 든 취소·노쇼 방문도 줄로 나온다(총액 빈 칸, 예약금 칸에 금액, 상태 칸을 하나 더한다). 3부보다 먼저 만들면 예약금 칸이 없다.

**내 기록**(파일 셋)

- `차곡노트_고객.csv`: `고객 번호 · 이름 · 전화번호 · 메모 · 등록일 · 마지막 방문일 · 노쇼 수 · 주의 사유 · 주의 끝나는 날`
- `차곡노트_반려동물.csv`: `반려동물 번호 · 고객 번호 · 이름 · 종 · 품종 · 성별 · 생일(또는 출생 연도) · 몸무게 · 지병(이름을 " / " 로) · 지병 메모 · 메모 · 미용 동의 받은 날 · 무지개다리`
- `차곡노트_방문기록.csv`: `방문 번호 · 날짜 · 시각 · 고객 번호 · 반려동물 번호 · 상태 · 취소 사유 · 예약 메모 · 메뉴 · 몸무게 · 케어 메모 · 내부 메모 · 총액 · 결제 수단 · 사진 수 · 영상 수`

번호는 차곡노트 안의 ID 다 — 세 파일을 잇는 열쇠로만 쓴다. 칸의 정확한 이름·순서는 계획에서 굳힌다(지금 엔티티에 없는 칸은 뺀다).

## 2.4 구조

- **읽기는 글의 주인이 준다.**
  - `visit`: `GET /v1/shops/{id}/sales/export?from=&to=&cursor=`(`sales:read` + `data:export`) · `GET /v1/shops/{id}/visits/export?cursor=`(`data:export`). 고객·아이의 이름은 지금처럼 `CustomerDirectoryPort.briefs` 로 받는다.
  - `customer`: `GET /v1/shops/{id}/customers/export?cursor=` · `GET /v1/shops/{id}/pets/export?cursor=`(`data:export`).
  - 한 쪽 500줄, ID 오름차순 커서(매출은 `(starts_at, id)`). 응답 스키마는 칸을 하나하나 적는다. 한 쪽의 질의 수는 줄 수와 무관하다(테스트가 고정).
- **내보낸 기록은 `tenancy` 가 갖는다**(매장과 멤버의 것). 새 표 `shop_export_logs(id, shop_id, member_id, kind 'sales'|'records', date_from null, date_to null, row_count null, created_at)`.
  - 시작: `POST /v1/shops/{id}/exports` `{kind, from?, to?}` → `{export_id}`. 끝: `PATCH …/exports/{export_id}` `{row_count}`. 목록: `GET …/exports`(최근 20). 모두 `data:export`.
  - 자료 경로는 `export_id` 를 받지 않는다 — 스포크끼리 묶지 않는다. 기록은 사장 자신을 위한 흔적이지 통제가 아니다(자료를 읽을 수 있는 사람은 사장뿐이다). 서버 로그에도 `shop_id·kind·쪽 번호·줄 수` 를 남긴다.
- **앱**: `features/sales` 에 매출 내보내기(매출 탭 맨 아래, 요약 공유 옆 `파일로 내보내기`), `features/shop` 에 내 기록 가져가기(매장 설정 화면 아래 `내 기록 가져가기` 한 줄 → 확인 시트). 새 화면을 만들지 않고 시트로 한다.
  - CSV 적기는 순수 함수(`core/` 에 하나 — 두 기능이 함께 쓴다). 쪽을 받을 때마다 임시 폴더(`path_provider` 의 임시 디렉터리)의 파일에 이어 적는다 — 전부를 메모리에 올리지 않는다.
  - 진행을 `1,200줄 받았어요` 로 보이고 취소할 수 있다. 중간에 실패하면 반쪽 파일을 지우고 넘기지 않는다.
  - 공유 시트를 띄운 뒤, 그리고 앱을 다시 열 때 임시 파일을 지운다. 문서 폴더·사진첩에 두지 않는다.
  - 확인 시트 문구: `보호자 전화번호가 든 파일이에요. 믿을 수 있는 곳에만 보내 주세요.`

# 3부. 예약금 안내 (계좌 방식)

## 3.1 왜

노쇼를 줄이는 업계의 수단이 예약금이다. 그루머노트는 결제 연동 없이 계좌·예약금·환불 규칙을 안내하고, 티피는 카카오톡 결제 요청과 기한 내 미결제 자동 취소까지 간다(둘 다 업체 소개 페이지). 차곡노트는 결제가 없으므로 그루머노트 쪽이다. 지금 사장은 카카오톡에 계좌를 손으로 적어 보내고, 입금을 받았는지는 머리로 기억한다.

③-B 가 노쇼 이력을 이미 예약 앞에 띄운다(`no_show`) — 그 자리에서 예약금 안내로 이어 준다.

## 3.2 정한 것

| 항목 | 결정 |
|---|---|
| 결제 | 없다. 계좌로 받고 사람이 `받았어요` 를 누른다. 은행 조회·자동 확인 없음. |
| 매장 설정 | 칸 셋 — **계좌 한 줄**(자유 글 60자, `국민 123-456-78-901234 홍길동`), **기본 금액**(원), **안내 한 줄**(선택 100자, 환불 규칙 등). 지금의 예약 설정 화면에 `예약금` 구역으로 더한다. 계좌가 비어 있으면 기능이 꺼진 것이다. |
| 보내기 | 방문 상세에서 [예약금 안내 보내기] → 금액을 확인하는 시트(기본 금액이 채워져 있고 고칠 수 있다) → 안내 글을 **공유 시트**로(카카오톡으로 보낸다). 알림톡으로 보내지 않는다(템플릿 심사·실발송이 필요하다). |
| 기한 | 안내 글에 `{안내한 다음 날}까지`(예약이 그보다 이르면 `예약 시간 전까지`). **지나도 자동으로 취소하지 않는다** — 받았는지는 사람이 알고, 취소는 사람이 한다. 기한이 지났다고 경고를 띄우지도 않는다. 하루 목록에서 `예약금 기다리는 중` 을 보면 된다. |
| 제안 | 그 방문의 확인할 것에 `no_show` 또는 `caution` 이 있고 계좌가 설정돼 있으면, 방문 상세의 예약금 줄이 `노쇼 이력이 있어요 · 예약금 안내 보내기` 로 바뀐다. **강제하지 않고, 확인할 것의 새 코드를 만들지 않는다**(`확인 N` 의 수가 바뀌지 않는다 — 판정 연쇄를 건드리지 않고 앱이 기존 코드로 문구만 바꾼다). 노쇼 이력이 없어도 줄은 있다(작게). |
| 누가 | 보내기·받음·돌려줌 표시는 `reservation:write`(사장·직원). 설정은 `shop:update`(사장). |
| 가족 묶음 | 예약금은 **방문 하나에** 단다(누른 그 방문). 묶음을 보이는 화면은 묶음 안의 예약금을 한 줄로 합쳐 보인다. 금액에 마릿수를 곱하지 않는다 — 사장이 시트에서 고친다. |
| 보호자에게 | 공유한 글 말고는 아무것도 가지 않는다. 공개 알림장·보호자 웹에 예약금 칸이 없다. |

## 3.3 상태와 돈

방문 하나의 예약금은 넷 가운데 하나다.

| 상태 | 뜻 | 바뀌는 때 |
|---|---|---|
| 없음 | 안내한 적 없다 | — |
| 기다리는 중 | 안내를 보냈다(금액이 정해졌다) | [예약금 안내 보내기]에서 공유 시트를 띄웠을 때. 다시 보내면 금액·시각을 덮어쓴다. [안내 취소]로 없음. |
| 받음 | 입금을 확인했다 | [받았어요]. 안내 없이 바로 받음으로 적을 수도 있다(현장·말로 받은 것). [되돌리기]로 기다리는 중. |
| 돌려줌 / 돌려주지 않음 | 취소·노쇼 뒤의 처리 | 받음인 방문을 취소·노쇼로 바꾸면 상세에 `예약금 20,000원 — [돌려줬어요] [돌려주지 않아요]`. 고르지 않아도 취소는 된다(막지 않는다). |

**매출과 겹쳐 세지 않는다.**

- 매출은 지금 그대로 **완료한 방문의 기록 총액**이다. 예약금은 그 자체로 매출이 아니다.
- **총액은 예약금을 포함한 전체 요금이다.** 기록 화면의 총액 아래에 `예약금 20,000원을 받았어요 · 오늘 받을 돈 35,000원` 한 줄을 보인다(총액 − 예약금, 계산해 보일 뿐 저장하지 않는다). 예약금이 총액보다 크면 줄을 `예약금 20,000원을 받았어요` 로만 둔다.
- **결제 수단별 집계는 예약금을 `이체`로 가른다.** 받음 상태의 예약금이 있는 완료 방문은 `min(예약금, 총액)` 을 이체에, 나머지를 기록의 결제 수단에 넣는다. 합은 여전히 매출과 같다. 가르지 않으면 카드 매출이 카드사 정산과 예약금만큼 어긋난다.
- **돌려주지 않은 예약금은 매출에 넣지 않고 따로 보인다** — 매출 탭의 예약 구역에 `돌려주지 않은 예약금 2건 · 40,000원`. 위약금을 매출로 볼지는 세무 판단이라 숫자에 섞지 않는다(물을 것 2).
- 취소·노쇼인데 받음인 채 고르지 않은 예약금은 매출 탭의 같은 구역에 `처리하지 않은 예약금 N건 ›` 으로 뜬다(누르면 그 방문 목록).

## 3.4 자료와 API

- `visit_shop_settings`: `deposit_account varchar(60) null`, `deposit_default_amount integer null`(0~1억), `deposit_note varchar(100) null`.
- `visits`: `deposit_amount integer null`, `deposit_requested_at timestamptz null`, `deposit_received_at timestamptz null`, `deposit_received_by_member_id bigint null`, `deposit_settled varchar(10) null`(`refunded`·`kept`), `deposit_settled_at timestamptz null`.
  - CHECK: 금액이 없으면 나머지도 없다 · 받음이면 금액이 있다 · `deposit_settled` 는 받음이고 상태가 취소·노쇼일 때만.
  - 새 표를 만들지 않는다 — 방문 하나에 "지금의 것 하나"이고, 방문을 옮기면(`reschedule`) 따라간다.
- `PUT /v1/shops/{id}/visits/{visit_id}/deposit` `{amount, state: 'requested'|'received'}` · `DELETE` 같은 경로(없음으로) · `PUT …/deposit/settlement` `{result: 'refunded'|'kept'|null}`. 모두 `reservation:write`.
- 방문 상세·하루 목록의 방문 항목에 `deposit: {amount, state, requested_at, received_at, settled}|null`. `GET/PUT …/visit-settings` 에 설정 칸 셋.
- 매출 요약(`GET …/sales/summary`)의 결제 수단별에 3.3 의 가르기, 예약 구역에 돌려주지 않은·처리하지 않은 예약금. `GET …/sales/visits` 의 `filter` 에 `deposit_open`.
- **잠금**: 예약금 쓰기는 방문 쓰기다 — `CustomerDirectoryPort.lock_family` 로 고객 행을 먼저 잠그고 방문 행을 잠근다(지금 순서 그대로).
- **이벤트**: 내지 않는다. 검색되는 글이 아니고(`SearchSourceChanged` 없음) 알림톡도 가지 않는다(`VisitEvent` 없음).
- 완료한 방문에는 새로 안내·받음을 달 수 없다(409) — 이미 달려 있던 것은 남는다. 상태를 예약으로 되돌리면 `deposit_settled` 를 비운다.

## 3.5 화면

1. **예약 설정**(`schedule_settings_screen.dart`)에 `예약금` 구역 — 계좌, 기본 금액, 안내 한 줄. 사장만 고친다.
2. **방문 상세** — 확인할 것 묶음 아래 예약금 한 줄.
   - 없음: `예약금 안내 보내기`(노쇼·주의가 있으면 3.2 의 문구). 계좌가 없으면 사장에게는 `예약금을 쓰려면 계좌를 적어 주세요 ›`, 직원에게는 줄이 없다.
   - 기다리는 중: `예약금 20,000원 · 기다리는 중` + [받았어요] · 더 보기에 [다시 보내기] [안내 취소].
   - 받음: `예약금 20,000원 · 11월 16일에 받음` · 더 보기에 [되돌리기].
   - 취소·노쇼 + 받음: 3.3 의 두 버튼.
3. **하루 목록의 방문 줄** — `예약금 기다리는 중` / `예약금 받음` 작은 글자 하나(`확인 N` 옆). 달력 칸의 표식은 ⑬.
4. **기록 화면** — 총액 아래 3.3 의 한 줄.
5. **안내 글**(앱이 만든다, `features/visit/state/` 의 순수 함수)

```
[Hiss Haus] 예약금 안내
11월 20일(금) 오후 2시 콩이 예약을 잡아 두었어요.
11월 17일까지 예약금 20,000원을 보내 주시면 예약이 확정돼요.
국민 123-456-78-901234 홍길동
예약금은 미용 요금에서 빼 드려요.
(매장이 적은 안내 한 줄)
```

보호자만의 방문이면 아이 이름이 빠진다. 가족 묶음이면 아이 이름을 `콩이·보리` 로.

## 3.6 위험과 막는 법

| # | 위험 | 막는 법 |
|---|---|---|
| D1 | 예약금이 매출에 두 번 들어간다 | 매출은 총액뿐. 결제 수단 가르기의 합이 매출과 같음을 테스트가 고정(예약금 > 총액, 총액 없음, 결제 수단 없음 포함). |
| D2 | 계좌번호가 로그·오류에 남는다 | 설정 본문을 로그에 남기지 않는 지금 규칙. 검증 오류 메시지에 값을 싣지 않는다. |
| D3 | 직원이 받지 않은 예약금을 받음으로 적는다 | 받은 사람(`deposit_received_by_member_id`)을 남긴다. 상세에 이름이 보인다. |
| D4 | 안내만 보내고 예약이 확정된 것처럼 보인다 | 예약 상태는 바뀌지 않는다. `기다리는 중` 이 하루 목록에 보인다. |
| D5 | 자동 취소가 없어 자리가 묶인다 | 받아들인다 — 사람이 취소한다. 자동 취소는 "입금했는데 취소됐다"는 사고가 더 무겁다. |
| D6 | 방문을 옮기거나 되돌릴 때 예약금이 사라진다 | 칸이 방문 행에 있다. 옮기기·상태 되돌리기 테스트에 예약금이 든 방문. |
| D7 | 다른 매장의 방문에 단다 | `ShopContext` 로 거른다(404). |
| D8 | 보호자 쪽 응답에 예약금이 샌다 | 공개·보호자 스키마에 칸이 없다(칸 고정 테스트). |

## 3.7 하지 않는 것

| 항목 | 까닭·때 |
|---|---|
| 결제 링크·카드 결제·자동 입금 확인 | 결제 대행·은행 연동은 과금이고 외부 서비스다. |
| 기한 뒤 자동 취소, 기한 지남 알림 | 3.2·D5. |
| 알림톡으로 안내 | 템플릿 심사와 실발송을 붙일 때. |
| 모든 예약에 예약금을 기본으로 걸기 | 설정이 는다. 사장이 줄을 누르면 된다. |
| 예약금의 일부만 돌려주기, 돌려준 금액 적기 | 둘 가운데 하나만 적는다. |
| 노쇼 위약금을 매출·세금으로 처리 | 세무 판단. |

# 4. 테스트와 검증

- **백엔드 단위**: 구간 경계 검증(오름차순·중복·개수), 경계 줄이면 값 지우기 / CSV 와 무관(서버는 JSON) / 예약금 상태 전이(없음↔기다림↔받음, 완료 방문 409, 되돌리면 정산 비움), 결제 수단 가르기.
- **백엔드 통합**: 테넌트 격리(세 부 모두 첫 줄), 권한(직원이 가격표·내보내기·설정에 403, 직원이 예약금 표시는 됨), 내보내기 쪽 나누기와 질의 수 고정, 익명화한 고객 빠짐, 옮기기·상태 되돌리기와 예약금, 공개·보호자 스키마의 칸 고정, 허용 목록.
- **import-linter**: `visit`·`customer`·`tenancy` 가 서로를 import 하지 않는다(내보낸 기록은 앱이 `tenancy` 경로를 따로 부른다 — 허브 포트가 늘지 않는다).
- **앱 단위**: 값 고르기(경계의 몸무게, 빈 구간, 몸무게 없음), 손댄 줄은 다시 채우지 않음, 구간 바뀜 문구 / CSV 적기(BOM·CRLF·따옴표·줄바꿈 든 메모·수식 주입·전화번호) / 안내 글(기한 두 갈래, 보호자만, 묶음), 오늘 받을 돈.
- **앱 위젯·골든**: 메뉴 편집 시트, 기록 화면의 두 칩 줄, 방문 상세의 예약금 줄 네 상태, 매출 탭의 예약 구역.
- **시뮬레이터 흐름**(iOS·안드로이드): ① 경계 정하기 → 구간 값 → 기록 화면에서 몸무게를 바꾸면 값이 따라옴 ② 매출 내보내기 → 공유 시트가 뜸(파일을 받는 쪽은 자동으로 못 본다 — 임시 파일의 머리 줄을 읽어 확인) ③ 계좌 적기 → 노쇼 이력 고객의 예약 → 안내 → 받음 → 완료 → 매출 탭의 이체.
- **흐름 스크립트**(`backend/scripts/`): `check_sales_flow.sh` 에 예약금이 든 방문을 더해 결제 수단 합을 손계산과 견준다.
- **눈으로 볼 것**(자동으로 못 본다): 만든 CSV 를 맥의 엑셀·숫자에서 열어 한글과 전화번호, 안드로이드의 `FileProvider` 공유, 아이패드의 공유 말풍선 자리.

# 5. 계획을 어떻게 나눌지

세 부가 독립이라 순서를 바꿔도 된다. 권하는 순서는 **1부 → 3부 → 2부** — 매출 파일의 예약금 칸이 3부 뒤에 굳는다.

| 계획 | 백엔드 | 앱 |
|---|---|---|
| ⑮-1 가격 계산기 | 마이그레이션(경계·구간 값 표·`is_extra`), 메뉴·설정 API | 값 고르기 규칙, 메뉴 설정·편집 시트, 기록 화면, 예약 등록의 예상 금액 |
| ⑮-2 예약금 안내 | 마이그레이션(설정 칸 셋·방문 칸 여섯), 예약금 쓰기 셋, 상세·하루 목록·매출 요약 | 설정 구역, 방문 상세 줄, 안내 글, 하루 목록 글자, 기록 화면 한 줄, 매출 탭 |
| ⑮-3 내보내기 | 권한 `data:export` 시드, 읽기 넷, `shop_export_logs` | 공유 시트 `shareFiles`(iOS·안드로이드 네이티브), CSV 적기, 매출 탭·매장 설정의 시트 |

각 계획은 백엔드와 앱을 한 계획에 담을 만큼 작다(⑮-2 가 가장 크다 — 넘치면 백엔드·앱으로 가른다). 마이그레이션 번호와 결정 기록 번호는 계획을 쓸 때 그때의 다음 번호로 잡는다(다른 묶음이 함께 진행 중이다).

# 6. 만드는 사람에게 맡기는 것

- 문구의 마지막 다듬기, 시트의 모양(기존 시트를 따른다), 구간 이름 딱지의 표기.
- 구간 값 칸의 이름(`tier_prices`), 내보내기 응답의 칸 이름·순서, 커서의 모양.
- `shop_export_logs` 를 다루는 `tenancy` 슬라이스의 이름, 공유 시트 네이티브 코드의 파일 이름.
- 결제 수단 가르기를 SQL 에서 할지 읽은 뒤 파이썬에서 할지(합이 매출과 같다는 테스트만 지키면 된다).

# 7. 사용자에게 물을 것

1. **가격표가 몸무게 기준인가요, 견종 기준인가요?** 히스하우스의 지금 가격표가 견종별(푸들·비숑…)로 값이 갈리면 몸무게 구간만으로는 모자랍니다. 그렇다면 견종 사전을 만드는 일이 1부에 더해집니다(크기가 두 배쯤).
2. **돌려주지 않은 예약금을 매출 숫자에 넣을까요?** 지금 안은 매출과 따로 한 줄로만 보입니다. 넣으면 "방문한 날의 완료 방문" 이라는 매출의 뜻이 하나 늘어납니다.
3. **내 기록 가져가기에 사진·영상 원본도 필요한가요?** 넣으려면 서버에서 묶음 파일을 만들어야 하고 저장·전송 비용이 생깁니다(유료 전환 지점). 지금 안은 글과 숫자만입니다.

## 0. 공통으로 지키는 것

- 과금되는 것·외부 서비스 연결이 없다. 결제 대행·은행 조회·알림톡 실발송을 붙이지 않는다.
- **아무것도 넣지 않아도 첫날부터 돈다.** 그리고 넣고 싶은 것은 전부 넣고 고칠 수 있다.
- 새 설정 화면을 만들지 않는다. 지금 있는 화면(메뉴 설정, 예약 설정, 매장 설정, 매출 탭)에 구역을 더한다. 줄 이름은 일어나는 일로 쓰고, 보호자에게 나가는 글은 설정 줄 아래에 그대로 보인다(공통 3절).
- 보호자에게 가는 응답의 **스키마**는 건드리지 않는다. 허용 목록 테스트(`backend/tests/route_inspection.py`)가 그대로 통과해야 한다.
- 전화번호·계좌번호·메모의 글·금액·견종을 로그·오류 메시지에 남기지 않는다. 새 로그는 shop_id·종류·건수·결과뿐이다.

# 1부. 가격 채우기

## 1.1 왜

지금은 메뉴마다 정가 하나(`service_menus.price`)가 있고, 기록 화면이 예약한 메뉴의 정가로 항목 금액을 미리 채운다(`record_rules.dart` 의 `recordFormStart`). 미용 요금은 대개 견종·몸무게에 따라 다르고 엉킴·특수 미용이 붙는다 — 그래서 미리 채운 값이 자주 틀리고 사장이 매번 고친다.

그루머노트는 견종·무게 기준 계산기를 두지만 **가격표를 먼저 채워야 돈다**(대신 넣어 주는 것을 내세운다). 티피에는 가격 설정이 뜻대로 안 된다는 리뷰, 반짝에는 개편 뒤 0원으로 뜬다는 리뷰가 한 건씩 있다. **근거는 업체 소개 글과 앱스토어 리뷰 몇 건이라 약하다.** 차곡노트가 다르게 할 수 있는 것은 값을 **매장이 이미 적은 기록에서** 가져오는 것이다 — 사장은 가격표를 넣지 않는다.

## 1.2 정한 것

| 항목 | 결정 |
|---|---|
| 값을 어디서 가져오나 | **기록에서.** 왔던 아이는 지난번에 받은 값, 처음 온 아이는 같은 견종·비슷한 몸무게의 아이들이 보통 낸 값. 가격표를 넣지 않아도 된다. |
| 가격표 | **선택이다.** 넣고 싶은 매장은 메뉴마다 견종·몸무게 구간별 값을 넣을 수 있고, **넣은 값이 기록에서 가져온 값보다 앞선다.** 넣지 않은 칸은 기록으로 떨어진다. |
| 채우는 순서 | ① 이미 적은 기록 → ② 가격표(있으면) → ③ 그 아이의 지난번 값 → ④ 비슷한 아이들의 값 → ⑤ 정가 → ⑥ 그 자리에서 묻는다. |
| 근거를 보인다 | 채운 줄마다 금액 아래에 작은 글자로 **어디서 온 값인지** 적는다 — `가격표` / `지난번 값` / `말티즈 3~4kg · 지난 8번 기준` / `정가`. 어림을 사실처럼 보이지 않는다. 손으로 고치면 근거 글이 사라진다. |
| 채운 값의 지위 | **제안.** 항목 금액·총액 모두 지금처럼 고칠 수 있다. 손댄 줄은 몸무게를 바꿔도 다시 채우지 않는다. |
| 견종 | 견종 사전을 만들지 않는다. `pets.breed` 는 50자 글이지만 등록 화면(`pet_form.dart`)이 종별 견종 칩을 주므로 대부분 같은 글자로 들어온다. **공백을 없애고 소문자로 맞춘 글자가 같으면 같은 견종**으로 친다. 손으로 적은 `말티`와 `말티즈`는 다른 견종으로 세어진다 — 받아들인 한계다(물을 것 2). |
| 덧붙는 값(엉킴·특수 미용) | **새 개념을 만들지 않는다 — 메뉴다.** 기록의 항목은 `(visit_id, menu_id, amount)` 이고 매출의 메뉴별 집계가 그것을 읽는다. 메뉴에 `추가 항목` 표시 하나(`is_extra`)를 더해 칩 줄만 나눈다. 추가 항목은 그날의 상태에 달린 값이라 ③·④로 채우지 않는다(가격표 또는 정가뿐). |
| 계산은 어디서 | **서버에서.** 다른 아이들의 기록과 견종을 읽어야 한다(견종은 `customer` 의 것이라 허브 포트 `CustomerDirectoryPort.briefs` 로 받는다 — 새 포트 메서드 없음). 처음 안은 "앱에서"였다 — 값의 출처가 기록이 되면서 바꿨다. 저장되는 것은 여전히 사람이 확정한 금액이다. |
| 누가 | 채워진 값과 근거를 보는 것은 돈 칸을 적는 사람(`sales:write` — 사장·직원. 직원은 지금도 기록의 금액을 적고 본다). 응답에 다른 아이·보호자의 이름과 낱낱의 금액은 없다 — 값 하나와 건수뿐이다. 가격표를 고치는 것은 사장(`shop:update` — 지금 메뉴 가격과 같다). |
| 예약 등록 화면 | 방문에는 금액 칸이 없다(금액은 기록의 것). **저장하지 않는 `예상 금액` 한 줄**만 보인다(자리는 공통 8절: 반복 줄 아래). |
| 보호자 | 가격표·어림을 공개하지 않는다. 알림장의 금액 표시는 지금 설정(`report_show_amount`) 그대로다. |

## 1.3 기록에서 가져오는 규칙

읽는 범위는 **이 매장의 최근 365일, 완료한 방문의 기록 항목**이다(금액이 0 인 줄은 뺀다, 새 것부터 2,000줄까지).

- **지난번 값**(③): 이 아이가 이 메뉴로 완료한 가장 최근 방문의 항목 금액. 그때의 몸무게와 지금 몸무게가 10% 넘게 다르면 근거 글에 `지난번 4.8kg → 지금 5.6kg` 를 덧붙인다(값은 그대로 채운다 — 올릴지는 사람이 정한다).
- **비슷한 아이들의 값**(④): 같은 메뉴 · 같은 종(`species`) · 같은 견종(1.2) · 몸무게가 이 아이의 `±max(1.0kg, 20%)` 안인 항목들의 **중앙값**(천 원 단위로 반올림). 표본의 몸무게는 그 기록에 적힌 몸무게이고, 없으면 그 아이의 지금 몸무게다.
  - **표본이 3건 이상이고 서로 다른 아이가 2마리 이상일 때만** 낸다(한 아이의 값이 "보통"이 되지 않게).
  - 견종 표본이 모자라면 견종을 빼고 같은 종·비슷한 몸무게로 한 번 더 본다 — 이때는 5건 이상·3마리 이상이고, 근거 글이 `비슷한 몸무게 3~4kg · 지난 12번 기준` 으로 바뀐다(견종을 맞춘 것처럼 보이지 않는다).
  - 근거 글의 몸무게 범위는 실제로 쓴 표본의 최소~최대다(0.5kg 단위로 넓혀 적는다).
- **몸무게를 모르면**(보호자만의 방문) ③만 쓰고 ④는 건너뛴다.
- **아무 값도 없으면**(정가도 없음) 금액 칸에 `얼마를 받았나요?` 가 뜬다. 적고 저장하면 사장에게 `다음에도 {메뉴} 을(를) {금액}원으로 채울까요?` 를 한 번 묻고, [네]면 그 메뉴의 정가로 기억한다(직원에게는 묻지 않는다 — `shop:update` 가 없다). 기록은 지금처럼 금액 없이도 저장된다(막지 않는다 — "나중에 적고 완료"는 지금 규칙이다).
- 지난 기록의 금액은 바뀌지 않는다. 매출 탭의 "남은 예약 · 정가로 약 N원"은 **그대로 정가**로 센다(문구가 이미 "정가로"다).

## 1.4 가격표(선택)

- **몸무게 구간의 경계는 매장에 하나**(최대 4개 → 구간 최대 5개)이고 모든 메뉴가 같은 경계를 쓴다. 경계 `[3, 5, 8]` 이면 `3kg 까지 / 5kg 까지 / 8kg 까지 / 8kg 넘음`. 경계의 몸무게는 아래 구간이다(3.0kg 은 첫 구간).
- 메뉴의 가격표는 **줄의 모음**이다 — 줄 하나는 `(견종 또는 모든 견종, 구간 또는 모든 몸무게, 값)`. 몸무게만으로 값을 가르는 매장은 견종을 비우고, 견종만으로 가르는 매장은 구간을 비우고, 둘 다 쓰는 매장은 둘 다 적는다.
- **찾는 순서**(가장 좁은 것부터): 견종+구간 → 견종만 → 구간만. 하나도 없으면 1.3 으로 떨어진다. 몸무게를 모르면 구간이 든 줄은 건너뛴다.
- 견종은 등록 화면의 견종 칩과 **이 매장의 아이들에게 실제로 적힌 견종**에서 고른다(손으로 적을 수도 있다). 비교는 1.2 의 맞춘 글자다.
- 넣는 수고를 줄인다: 구간 줄은 첫 값과 `구간마다 더할 값`을 적으면 나머지를 채워 준다. 견종 줄은 [다른 견종에서 가져오기]로 복사한다.
- 구간이 바뀌면 한 줄로 알린다 — 몸무게 칸 아래 `지난번 4.8kg 보다 한 구간 올랐어요`(가격표의 구간 줄을 쓰는 매장에서만).
- 가격표의 지난 이력은 두지 않는다(지난 기록의 금액이 그때의 사실이다).

## 1.5 자료와 API

- `service_menus.is_extra boolean not null default false`, `service_menus.report_visible boolean not null default true`(1.6).
- `visit_shop_settings.weight_bounds numeric(4,1)[] null` — 오름차순, 0 보다 크고 서로 다르고 최대 4개(CHECK 와 도메인 검증). NULL·빈 배열이면 구간 줄을 쓸 수 없다(견종 줄은 쓸 수 있다).
- 새 표 `service_menu_prices(id, menu_id → service_menus.id ON DELETE CASCADE, breed varchar(50) null, breed_key varchar(50) null, tier smallint null 0~4, price int 0~1억)` · 유일 `(menu_id, coalesce(breed_key,''), coalesce(tier,-1))` · `breed`·`tier` 가 둘 다 NULL 인 줄은 없다(그것은 정가다).
- 경계의 개수를 줄이면 넘치는 구간의 줄을 같은 트랜잭션에서 지운다. 경계의 숫자만 고치면 값은 그대로다(앱이 저장 전에 `구간의 무게가 바뀌어요. 값은 그대로 둬요` 를 한 번 묻는다).
- **값 받기**: `GET /v1/shops/{id}/price-hints?pet_id=&weight_kg=&menu_ids=`(`sales:write`). `pet_id` 가 없으면(보호자만) ③만.
  - 응답 `items: [{menu_id, amount|null, basis: 'table'|'last'|'similar'|'similar_weight'|'list'|null, sample_count|null, breed|null, weight_from|null, weight_to|null, last_amount|null, last_weight_kg|null, tier_moved: 'up'|'down'|null}]`. `last_amount` 는 채운 값이 가격표·어림일 때도 싣는다 — 앱이 `지난번에는 50,000원을 받았어요` 를 한 줄로 보이고 누르면 그 값으로 바꾼다.
  - 질의 수는 메뉴 수·표본 수와 무관하다(이 아이의 지난 항목 1, 매장의 최근 항목 1, 가격표 1, `briefs` 포트 1 — 테스트가 고정). 걸러 내기는 파이썬에서 한다.
  - 익명화한 고객의 아이도 표본에 든다(이름 없이 금액·견종·몸무게만 쓰인다).
- `GET /v1/shops/{id}/menus`(매장 멤버) 응답 항목에 `is_extra`, `report_visible`. 가격표는 `GET /v1/shops/{id}/menus/{menu_id}/prices`(`shop:update`)로 따로 받는다 — 멤버 모두가 받는 목록에 가격표를 싣지 않는다.
- `POST …/menus` · `PUT …/menus/{menu_id}` 본문에 `is_extra`, `report_visible`. `PUT …/menus/{menu_id}/prices`(통째 교체, `shop:update`). `GET/PUT …/visit-settings` 에 `weight_bounds`(지금 응답은 `opens_at`·`closes_at`·`default_duration_minutes`·`closed_weekdays` 넷이다 — 코드 확인).
- 기록 저장(`PUT …/visits/{id}/record`)은 바뀌지 않는다. 추가 항목도 `items` 의 한 줄이다.
- 검색되는 글을 쓰지 않는다(`SearchSourceChanged` 없음). 잠금을 잡지 않는다(읽기).

## 1.6 추가 항목과 알림장

알림장은 메뉴 이름을 싣고 기본이 켜짐이다(`report_show_menus` 기본 true). 추가 항목(`엉킴 추가`·`특수견 추가`)의 이름이 보호자에게 그대로 나가면 곤란할 수 있다.

- **추가 항목은 알림장에 기본으로 보이지 않는다.** 메뉴를 추가 항목으로 만들 때 `report_visible` 의 기본이 꺼짐이고, 메뉴 편집 시트의 `알림장에 보이기` 로 켤 수 있다. 보통 메뉴는 기본이 켜짐이고 끌 수 있다.
- 공개·보호자 알림장의 조립이 `report_visible` 이 꺼진 메뉴를 뺀다. **스키마는 그대로이고 실리는 메뉴만 달라진다.** 금액 표시(`report_show_amount`)는 총액이라 영향이 없다 — 추가 항목의 값도 총액에 들어 있다.
- 편집 시트의 토글 아래에 보호자가 받는 모습을 한 줄로 보인다: `알림장: 전체 미용 · 엉킴 추가` / `알림장: 전체 미용`.

## 1.7 화면

1. **기록 화면** — 메뉴 칩이 두 줄로 나뉜다: 메뉴 / 추가. 항목 줄의 금액 아래에 근거 글(1.2). `지난번에는 …을 받았어요` 한 줄(값이 다를 때만). 몸무게 칸을 고치면 0.5초 뒤 손대지 않은 줄만 다시 받는다. 자리는 공통 8절(… 총액 → 예약금 줄 → 정기권 줄 → `오늘 받을 돈` → 결제 수단 → 메모).
2. **예약 등록** — `예상 금액 약 55,000원`(여러 마리면 아이마다 받아 더한다, 값이 하나도 없으면 줄이 없다, `sales:write` 가 없으면 줄이 없다). 메뉴 칩에도 추가 항목 줄을 둔다(고르지 않아도 된다). ⑭ 의 반복 예약이면 회차 하나의 값이다.
3. **메뉴 설정**(`menu_settings_screen.dart`) — 메뉴 편집 시트에 정가 아래 `견종·몸무게별 값 넣기`(누르면 가격표 시트 — 줄 목록, [줄 더하기]), `추가 항목으로 쓰기`, `알림장에 보이기`. 화면 맨 위에 `몸무게 구간` 한 줄(정하지 않았으면 `몸무게에 따라 값이 다르면 구간을 정해 주세요`).
   - 가격표 시트 맨 위에 한 줄: `넣지 않아도 돼요. 지난 기록에서 값을 채워 드려요. 넣으면 이 값이 먼저예요.`

색 딱지·경고 삼각형을 쓰지 않는다. 계산식을 화면에 풀어 쓰지 않는다.

|---|---|
| 견종 사전·견종 묶기(`말티`=`말티즈`) | 1.2. 물을 것 2 의 답에 따라. |

# 2부. 매출 CSV 와 내 기록 가져가기

## 2.1 왜

⑧ 은 CSV 를 "파일 공유 채널이 없다"는 까닭으로 미뤘다 — 공유 시트가 글자만 넘긴다(`lib/core/proxy/share_sheet.dart` 의 `shareText`). 세무사에게 넘기거나 엑셀로 보려면 파일이 필요하다.

경쟁 쪽: 티피는 엑셀을 주지만 "결제를 끊으면 지난 기록을 볼 수 없다"는 리뷰가 있고, 반짝은 매출 조회가 최대 90일이다(둘 다 앱스토어 리뷰·릴리스 노트 한두 건 — 약한 근거). **내 기록을 파일로 가져갈 수 있다**는 것을 기능으로 둔다. 다만 "언제든"이라는 약속 문구는 쓰지 않는다 — 정지된 매장은 지금 가드가 막는다(2.2).

## 2.2 정한 것

| 항목 | 결정 |
|---|---|
| 두 가지 | **매출 내보내기**(기간을 골라 방문 한 줄씩) · **내 기록 가져가기**(고객·반려동물·방문 기록·정기권 전부). |
| 파일은 어디서 만드나 | **기기에서.** 서버는 쪽으로 나눈 JSON 을 주고 앱이 CSV 로 적는다. 서버에 파일을 두지 않는다(`media` 를 건드리지 않는다). |
| 형식 | CSV. UTF-8 **BOM**, 줄 끝 CRLF, RFC 4180 따옴표 — 엑셀에서 한글이 깨지지 않는다. `=`·`+`·`-`·`@` 로 시작하는 칸은 앞에 `'` 를 붙인다(수식 주입). 전화번호는 하이픈 든 모양 그대로. xlsx 는 만들지 않는다. |
| 넘기기 | 공유 시트에 **파일을 넘기는 메서드를 더한다**(`shareFiles`). 외부 패키지 없이 네이티브 — iOS `UIActivityViewController` 에 파일 주소, 안드로이드 `FileProvider` + `ACTION_SEND(_MULTIPLE)`. 압축하지 않는다. |
| 지난달 한 번에 | 매출 탭에 **`지난달 파일 받기`** 한 줄이 늘 있다 — 누르면 지난달로 채워진 확인 시트가 뜨고 [받기]. 기간을 직접 고르는 `기간을 골라 받기` 도 그 아래에 남긴다(시작·끝, 빠른 고르기 `이번 달·지난달·올해·작년`, 길이 제한 없음). ⑧ 의 "임의 기간을 받지 않는다"는 한 번에 집계하는 요약의 이야기다 — 내보내기는 쪽으로 나눠 읽는다. |
| 누가 | **사장이 기본이고, 매장 설정에서 직원에게 열 수 있다**(공통 9절). 새 권한 `data:export` 를 사장 역할에 심는다. 매장 설정의 `직원도 고객 파일을 받을 수 있게`(기본 꺼짐)를 켜면 직원도 통과한다 — 역할 시드는 전 매장 공통이라 권한만으로는 매장별 허용을 못 하므로, `tenancy` 가 요청마다 매장의 이 칸을 보고 직원의 권한 묶음에 `data:export` 를 더한다(가드는 `ctx.permissions` 만 본다 — 지금 그대로). 매출 내보내기는 `sales:read` 도 필요하다(직원에게는 없다 — 직원 허용을 켜도 매출 파일은 사장만이다). |
| 정지된 매장 | 가드가 막는다(`resolve_shop_access_interactor` 의 `shop_suspended`). **정지 중에도 가져가기를 열지는 과금 설계 때 정한다.** 그때까지 화면·소개 글에 "언제든 가져갈 수 있다"고 적지 않는다. 지금 적는 규칙은 하나다: 나중에 요금제로 기능을 제한할 때 `data:export` 경로는 제한 목록에 넣지 않는다. |
| 사진·영상 | **넣지 않는다.** 한 해치 원본은 수 GB 라 기기에서 묶을 수 없고, 서버에서 묶으면 저장·전송 비용이 생긴다(유료 전환 지점). 방문 기록 파일에 사진·영상 **수**만 싣는다. 사진은 지금처럼 방문 상세에서 원본을 받는다. |
| 내보낸 사실 | 누가·언제·무엇을(종류, 기간, 줄 수) 남긴다. 내용은 남기지 않는다. 화면 아래에 최근 것 몇 줄을 보인다. |
| 익명화한 고객 | 고객·반려동물 파일에서 뺀다. 매출 줄에는 금액이 남고 이름 칸이 빈다(⑧ 의 S3 과 같다). |

## 2.3 파일의 칸

**매출**(`차곡노트_매출_2026-10-01_2026-10-31.csv`) — 완료한 방문 한 줄. 방문한 날 기준(⑧ 3.1).

`날짜 · 시각 · 고객 번호 · 보호자 · 아이 · 메뉴(이름을 " / " 로) · 항목 합 · 총액 · 정기권으로 낸 금액 · 예약금 · 나머지 · 나머지의 결제 수단`

- 돈 네 칸은 공통 6절의 가르기 그대로다(`총액 = 정기권 + 예약금 + 나머지`). ⑭ 의 정기권이 아직 없으면 정기권 칸은 0 이다.
- 메뉴마다 열을 만들지 않는다(매장마다 메뉴가 달라 열이 흔들린다).
- 총액을 적지 않은 완료 방문은 총액 칸이 빈 채로 나온다(0 이 아니다).
- 3부를 만든 뒤에는 **돌려주지 않은 예약금**이 든 취소·노쇼 방문도 줄로 나온다(총액 빈 칸, 예약금 칸에 금액, `상태` 칸). 3부보다 먼저 만들면 예약금 칸이 0 이고 `상태` 칸이 없다.

## 2.4 구조

- **읽기는 글의 주인이 준다.**
  - `visit`: `GET /v1/shops/{id}/sales/export?from=&to=&cursor=`(`sales:read` + `data:export`) · `GET /v1/shops/{id}/visits/export?cursor=` · (⑭ 뒤) `GET /v1/shops/{id}/passes/export?cursor=`(`data:export`). 고객·아이의 이름은 지금처럼 `CustomerDirectoryPort.briefs` 로 받는다.
  - `customer`: `GET /v1/shops/{id}/customers/export?cursor=` · `GET /v1/shops/{id}/pets/export?cursor=`(`data:export`).
  - 한 쪽 500줄, ID 오름차순 커서(매출은 `(starts_at, id)`). 응답 스키마는 칸을 하나하나 적는다. 한 쪽의 질의 수는 줄 수와 무관하다(테스트가 고정).
- **내보낸 기록과 직원 허용은 `tenancy` 가 갖는다.**
  - 새 표 `shop_export_logs(id, shop_id, member_id, kind 'sales'|'records', date_from null, date_to null, row_count null, created_at)`. 매장의 칸 `staff_export_allowed boolean not null default false`(매장 표에 — 정확한 표는 계획에서 `tenancy` 의 지금 모양을 읽고 정한다).
  - 시작: `POST /v1/shops/{id}/exports` `{kind, from?, to?}` → `{export_id}`. 끝: `PATCH …/exports/{export_id}` `{row_count}`. 목록: `GET …/exports`(최근 20). 모두 `data:export`. 직원 허용을 바꾸는 것은 `shop:update`.
  - 자료 경로는 `export_id` 를 받지 않는다 — 스포크끼리 묶지 않는다. 그래서 **앱이 알리는 기록은 사장 자신을 위한 흔적이고, 빠질 수 있다.** 실제로 믿을 흔적은 서버 로그다 — 자료 경로마다 `shop_id·member_id·kind·쪽 번호·줄 수` 를 남긴다. 계획은 이 로그 줄을 테스트로 고정한다.
  - ⑯ 의 콜아이디도 같은 방식(매장의 칸 하나 → `tenancy` 가 직원의 권한 묶음에 더한다)을 쓴다. 칸은 기능마다 따로다.
- **앱**: `features/sales` 에 매출 내보내기(매출 탭 맨 아래 — 공통 8절: … 지난 아이 → 내보내기), `features/shop` 에 내 기록 가져가기(매장 설정 화면의 `내 기록 가져가기` 한 줄 → 확인 시트)와 `직원도 고객 파일을 받을 수 있게`. 새 화면을 만들지 않고 시트로 한다.
  - CSV 적기는 순수 함수(`core/` 에 하나). 쪽을 받을 때마다 임시 폴더(`path_provider`)의 파일에 이어 적는다 — 전부를 메모리에 올리지 않는다.
  - 진행을 `1,200줄 받았어요` 로 보이고 취소할 수 있다. 중간에 실패하면 반쪽 파일을 지우고 넘기지 않는다.
  - 공유 시트를 띄운 뒤, 그리고 앱을 다시 열 때 임시 파일을 지운다. 문서 폴더·사진첩에 두지 않는다.
  - 확인 시트: 무엇이 들었는지 한 줄씩(`고객 128명 · 반려동물 163마리 · 방문 기록 1,940건`)과 `보호자 전화번호와 메모가 든 파일이에요. 믿을 수 있는 곳에만 보내 주세요.`

# 3부. 예약금 안내 (계좌 방식)

## 3.1 왜

노쇼를 줄이는 업계의 수단이 예약금이다. 그루머노트는 결제 연동 없이 계좌·예약금·환불 규칙을 안내하고, 티피는 카카오톡 결제 요청과 기한 내 미결제 자동 취소까지 간다(둘 다 업체 소개 페이지). 차곡노트는 결제가 없으므로 그루머노트 쪽이다. 지금 사장은 카카오톡에 계좌를 손으로 적어 보내고, 입금을 받았는지는 머리로 기억한다.

③-B 가 노쇼 이력을 이미 예약 앞에 띄운다(`no_show`) — 그 자리에서 **안내 글이 준비돼 있게** 한다.

## 3.2 정한 것

| 항목 | 결정 |
|---|---|
| 결제 | 없다. 계좌로 받고 사람이 `받았어요` 를 누른다. 은행 조회·자동 확인 없음. |
| 설정 없이 시작 | 예약 설정을 먼저 열지 않아도 된다. **처음 안내를 보낼 때 그 자리에서 계좌를 묻고 기억한다**(사장). 계좌가 빈 글은 나가지 않는다. 직원이 처음 누르면 `사장님이 계좌를 한 번 적으면 쓸 수 있어요` 가 뜬다(설정은 `shop:update`). |
| 예약마다 고친다 | 보내기 전 시트에서 **금액·기한·안내 글 전체**를 고칠 수 있다. 시트 아래 `이 값을 기본으로 쓰기` 를 켜면 금액·기한(며칠 안에)·매장 문장이 매장의 기본값(템플릿)으로 저장된다. |
| 기본값(템플릿) | 계좌 한 줄(60자) · 기본 금액 · 며칠 안에 보내 달라고 할지(기본 1일) · 매장 문장(300자, 기본 `예약금은 미용 요금에서 빼 드려요.`). 예약 설정의 `예약금` 구역에서도 고친다. 기본 금액이 없으면 보낼 때 그 자리에서 묻는다. |
| 계좌 확인 | 계좌를 저장할 때와 **처음 보낼 때** 계좌를 크게 다시 보이고 `이 계좌로 안내가 나가요` 를 확인받는다. 잘못 적은 계좌로 보호자가 돈을 보내는 사고를 막는다. |
| 보내기 | 공통 4절의 **보낼 것 묶음**에 `deposit` 토막으로 들어간다 — 예약 접수 안내·서류 링크와 한 글로 공유 한 번에 나간다. 묶음의 자리(조립 함수와 미리 보기 시트)는 ⑪ 이 만든다. 예약금 토막의 글은 `visit` 이 만든다(3.5). 방문 상세의 예약금 줄에서 따로 보낼 수도 있다. 알림톡으로는 나중(템플릿 심사·실발송). |
| 준비해 둔다 | 그 예약의 확인할 것에 `no_show` 또는 `caution` 이 있으면 **예약금 토막이 묶음에 미리 들어 있다**(금액·기한이 기본값으로 채워진 채 — 빼려면 한 번 누른다). 이력이 없는 고객은 토막이 빠져 있고 `예약금 안내 더하기` 로 넣는다. **보내는 것은 사람이다.** 확인할 것의 새 코드를 만들지 않는다(`확인 N` 의 수가 바뀌지 않는다). |
| 기한 | 안내 글에 `{안내한 날 + 며칠}까지`(예약이 그보다 이르면 `예약 시간 전까지`). **지나도 자동으로 취소하지 않는다** — 받았는지는 사람이 알고, 취소는 사람이 한다(공통 2절). |
| 누가 | 보내기·받음·돌려줌 표시는 `reservation:write`(사장·직원). 계좌와 기본값은 `shop:update`(사장). |
| 가족 묶음 | 예약금은 **묶음에** 받는다(공통 6절). 가족이 같은 날 함께 잡은 방문들이 예약금 하나를 함께 가리킨다. 한 마리가 취소돼도 남은 방문의 총액에서 빠진다. 금액에 마릿수를 곱하지 않는다 — 시트에서 고친다. |
| 보호자에게 | 공유한 글 말고는 아무것도 가지 않는다. 공개 알림장·보호자 웹에 예약금 칸이 없다. |

## 3.3 상태와 돈

예약금 하나는 넷 가운데 하나다.

| 상태 | 뜻 | 바뀌는 때 |
|---|---|---|
| 없음 | 안내한 적 없다 | — |
| 기다리는 중 | 안내를 보냈다(금액이 정해졌다) | 예약금 토막이 든 글의 공유 시트를 띄웠을 때. 다시 보내면 금액·기한을 덮어쓴다. [안내 취소]로 없음. |
| 받음 | 입금을 확인했다 | [받았어요]. 안내 없이 바로 받음으로 적을 수도 있다(현장·말로 받은 것). [되돌리기]로 기다리는 중. |
| 돌려줌 / 돌려주지 않음 | 처리했다 | 아래 두 경우의 버튼. |

**돈은 공통 6절대로 가른다**(함수 하나 — 5절).

- 매출은 지금 그대로 **완료한 방문의 기록 총액**이다. 총액은 예약금을 포함한 전체 요금이다.
- 예약금 몫 = `min(받은 예약금, 총액 − 정기권 몫)`. 예약금을 함께 가리키는 방문이 여럿이면 **방문 ID 오름차순으로** 차례로 채운다(앞 방문에서 다 쓰이지 않은 만큼이 다음 방문으로).
- 기록 화면: 총액 아래 `예약금 20,000원을 받았어요`, 그 아래(정기권 줄 다음) `오늘 받을 돈 35,000원`(= 나머지, 계산해 보일 뿐 저장하지 않는다).
- 결제 수단별 집계: 예약금 몫은 **`계좌`**(코드 값 `transfer` — 처음 안이 "이체"라 부른 것, ⑭ 의 "계좌"와 같은 줄)에 더한다. 합은 늘 매출과 같다.
- **`돌려줄 예약금`**: 함께 가리키는 방문이 모두 끝났는데(완료·취소·노쇼) 받은 예약금이 쓰인 몫보다 크면, 남은 돈이 방문 상세에 `돌려줄 예약금 5,000원 — [돌려줬어요] [돌려주지 않아요]` 로 남는다.
- **전부 취소·노쇼**: `예약금 20,000원 — [돌려줬어요] [돌려주지 않아요]`. 고르지 않아도 취소는 된다(막지 않는다).
- **돌려주지 않은 예약금은 매출에 넣지 않는다.** 매출 탭 예약 구역의 `쓰지 않고 끝난 돈` 한 줄(공통 6절 — 끝낸 정기권의 남은 돈·환불의 위약 차이와 함께)에 든다. 위약금을 매출로 볼지는 세무 판단이라 숫자에 섞지 않는다.
- 고르지 않은 것은 같은 구역에 `처리하지 않은 예약금 N건 ›` 으로 뜬다(누르면 그 방문 목록).
- ⑬ 의 `결제 완료`(`paid`)는 공통 6절의 정의를 쓴다 — 예약금이 요금을 다 덮은 방문은 결제 수단이 없어도 결제 완료다.

## 3.4 자료와 API

- `visit_shop_settings`: `deposit_account varchar(60) null`, `deposit_default_amount integer null`(1~1억), `deposit_due_days smallint not null default 1`(0~30), `deposit_message varchar(300) null`(NULL 이면 기본 문장).
- 새 표 `visit_deposits(id, shop_id, customer_id, amount integer, due_on date null, requested_at timestamptz null, received_at timestamptz null, received_by_member_id bigint null, settled varchar(10) null 'refunded'|'kept', settled_amount integer null, settled_at timestamptz null, created_at, updated_at)` · `visits.deposit_id bigint null → visit_deposits.id`.
  - 처음 안은 방문의 칸 여섯이었다 — 예약금을 묶음에 받기로 하면서 표로 바꿨다. 방문을 옮겨도(`reschedule`) `deposit_id` 는 따라간다. 묶음에서 한 마리를 다른 날로 옮겨도 같은 예약금을 가리킨다(이미 받은 돈이다).
  - CHECK: 받음이면 금액이 있다 · `settled` 는 받음일 때만.
- `PUT /v1/shops/{id}/visits/{visit_id}/deposit` `{amount, due_on?, state: 'requested'|'received', save_as_default?}` — 그 방문과 **같은 가족 묶음의 살아 있는 방문 전부**(같은 보호자·같은 시작 시각, 지금 `Visit` 의 묶음 계산)에 건다. `DELETE` 같은 경로(없음으로) · `PUT …/deposit/settlement` `{result: 'refunded'|'kept'|null}`. 모두 `reservation:write`. `save_as_default` 는 `shop:update` 가 있을 때만 듣는다.
- `GET /v1/shops/{id}/visits/{visit_id}/deposit/notice?amount=&due_on=` → `{text, account_missing}` — 토막의 글. 계좌가 없으면 `account_missing: true` 이고 글이 없다(앱이 묻는다).
- 방문 상세·하루 목록의 방문 항목에 `deposit: {amount, state, due_on, requested_at, received_at, received_by, settled, left_to_refund}|null`. ⑬ 이 이것으로 `marks` 의 `deposit_received` 와 하루 머리의 `예약금 기다리는 중 N` 을 만든다(3.5).
- `GET/PUT …/visit-settings` 에 설정 칸 넷. 매출 요약(`GET …/sales/summary`)의 결제 수단별에 3.3 의 가르기, 예약 구역에 `쓰지 않고 끝난 돈`·처리하지 않은 예약금. `GET …/sales/visits` 의 `filter` 에 `deposit_open`.
- 매출 탭의 공유 글(`sales_rules.dart` 의 `shareText` — 기간·매출·방문 수·결제 수단별·메뉴별)은 결제 수단별 줄이 가르기를 따라갈 뿐 줄을 더하지 않는다. `쓰지 않고 끝난 돈` 은 0 이 아닐 때만 한 줄 더한다.
- **잠금**: 예약금 쓰기는 방문 쓰기다 — `CustomerDirectoryPort.lock_family` 로 고객 행을 먼저 잠그고 방문 행(ID 오름차순)을 잠근다. 예약금 행은 고객 행 잠금 아래에서만 쓴다(한 고객의 것이다 — 따로 잠금 순서를 더하지 않는다).
- **이벤트**: 내지 않는다. 검색되는 글이 아니고(`SearchSourceChanged` 없음) 알림톡도 가지 않는다(`VisitEvent` 없음).
- 완료한 방문만 가리키는 예약금에는 새로 안내를 달 수 없다(409). 상태를 예약으로 되돌리면 `settled` 를 비운다.
- 고객 익명화: 예약금 행은 금액·날짜만 든 돈의 기록이라 남긴다(매출의 줄이 남는 것과 같다).

## 3.5 화면

1. **예약 설정**(`schedule_settings_screen.dart`)의 `예약금` 구역 — 줄 이름이 곧 설명이다.
   - `예약금 받을 계좌` · `예약금은 보통 얼마` · `며칠 안에 보내 달라고 할까요` · `안내에 덧붙일 말`
   - 구역 아래에 **보호자가 받는 글 그대로**(아래 5번의 모양, 지금 값으로 채워서).
2. **방문 상세** — 자리는 공통 8절(확인할 것 → **예약금 줄** → 보호자 줄).
   - 없음: `예약금 안내 보내기`(노쇼·주의가 있으면 `노쇼 이력이 있어요 · 예약금 안내가 준비돼 있어요`).
   - 기다리는 중: `예약금 20,000원 · 11월 17일까지 · 기다리는 중` + [받았어요] · 더 보기에 [다시 보내기] [안내 취소].
   - 받음: `예약금 20,000원 · 11월 16일에 받음(받은 사람)` · 더 보기에 [되돌리기].
   - 끝난 뒤: 3.3 의 두 버튼.
3. **보내기 시트** — 금액, 기한(날짜), 글 전체(고칠 수 있다), `이 값을 기본으로 쓰기`. 계좌가 없으면 맨 위에 계좌 칸이 먼저 나온다.
4. **하루 목록** — 줄의 낱말은 `예약금 받음` 하나(⑬ 의 `marks`). `예약금 기다리는 중` 은 남은 일이라 **줄의 낱말로 두지 않고** 하루 머리의 숫자(`예약금 기다리는 중 2`)와 방문 상세의 줄로만 보인다(공통 7절). 달력 칸에는 표시가 없다.
5. **안내 글**(`visit` 이 만든다 — 자동 줄 + 매장 문장)

```
[Hiss Haus] 예약금 안내
11월 20일(금) 오후 2시 콩이 예약을 잡아 두었어요.
11월 17일까지 예약금 20,000원을 보내 주세요.
국민 123-456-78-901234 홍길동
예약금은 미용 요금에서 빼 드려요.
```

   - 마지막 줄이 매장 문장이다(고칠 수 있다). 처음 안의 `보내 주시면 예약이 확정돼요` 는 뺐다 — 예약 상태는 바뀌지 않으므로 앱이 하지 않는 약속을 글에 넣지 않는다. 그렇게 쓰고 싶은 매장은 매장 문장에 적는다.
   - 보호자만의 방문이면 아이 이름이 빠진다. 가족 묶음이면 `콩이·보리`. 보낼 것 묶음 안에서는 첫 두 줄(매장·예약)이 접수 안내와 겹치므로 빼고 나간다.

## 3.6 위험과 막는 법

| # | 위험 | 막는 법 |
|---|---|---|
| D1 | 예약금이 매출에 두 번 들어간다 | 매출은 총액뿐. 가르기의 합이 매출과 같음을 테스트가 고정(예약금 > 총액, 총액 없음, 결제 수단 없음, **정기권 + 예약금 + 나머지**, 묶음의 두 방문에 걸친 예약금 포함). |
| D2 | 계좌번호가 로그·오류에 남는다 | 설정 본문을 로그에 남기지 않는 지금 규칙. 검증 오류 메시지에 값을 싣지 않는다. |
| D3 | 잘못 적은 계좌로 안내가 나간다 | 저장할 때와 처음 보낼 때 다시 보여 확인받는다(3.2). 글 미리 보기에 계좌가 늘 보인다. |
| D4 | 직원이 받지 않은 예약금을 받음으로 적는다 | 받은 사람을 남기고 상세에 이름이 보인다. |
| D5 | 안내만 보내고 예약이 확정된 것처럼 보인다 | 예약 상태는 바뀌지 않는다. 하루 머리의 숫자가 남은 일을 보인다. 기본 글에 "확정"이라는 말이 없다. |
| D6 | 자동 취소가 없어 자리가 묶인다 | 받아들인다 — 사람이 취소한다. 자동 취소는 "입금했는데 취소됐다"는 사고가 더 무겁다. |
| D7 | 방문을 옮기거나 되돌릴 때 예약금이 사라진다 | `deposit_id` 가 방문 행에 있다. 옮기기·상태 되돌리기·묶음에서 한 마리만 취소 테스트. |
| D8 | 한 마리만 취소됐는데 예약금이 떠 버린다 | 묶음에 받으므로 남은 방문의 총액에서 빠진다(3.3). 테스트로 고정. |
| D9 | 다른 매장의 방문에 단다 | `ShopContext` 로 거른다(404). |
| D10 | 보호자 쪽 응답에 예약금이 샌다 | 공개·보호자 스키마에 칸이 없다(칸 고정 테스트). |

# 4. 테스트와 검증

- **백엔드 단위**: 어림 규칙(표본 수·아이 수의 문턱, 몸무게 범위, 견종 글자 맞추기, 중앙값과 반올림, 견종 빼고 한 번 더, 추가 항목은 어림 없음, 금액 0 빼기), 가격표 찾는 순서, 경계 검증과 줄이면 줄 지우기 / 예약금 상태 전이, 가르기(공통 6절의 모든 갈래, 묶음의 차례 채우기, `돌려줄 예약금`), 안내 글(기한 두 갈래, 보호자만, 묶음, 매장 문장).
- **백엔드 통합**: 테넌트 격리(세 부 모두 첫 줄 — 어림이 다른 매장의 기록을 읽지 않는다), 권한(직원: 가격표·설정 403, 값 받기·예약금 표시는 됨, 내보내기는 직원 허용에 따라), 값 받기와 내보내기의 질의 수 고정, 익명화한 고객, 옮기기·되돌리기·한 마리만 취소와 예약금, 알림장에서 `report_visible` 이 꺼진 메뉴가 빠짐, 공개·보호자 스키마의 칸 고정, 허용 목록, 내보내기 로그 줄.
- **import-linter**: `visit`·`customer`·`tenancy` 가 서로를 import 하지 않는다.
- **앱 단위**: 근거 글의 문구, 손댄 줄은 다시 채우지 않음, `지난번에는 …` 줄, 값이 없을 때의 묻기 / CSV 적기(BOM·CRLF·따옴표·줄바꿈 든 메모·수식 주입·전화번호) / 오늘 받을 돈.
- **앱 위젯·골든**: 기록 화면(근거 글·두 칩 줄), 가격표 시트, 예약 설정의 예약금 구역(글 미리 보기 포함), 방문 상세의 예약금 줄 네 상태, 보내기 시트(계좌 없음 포함), 매출 탭의 예약 구역과 내보내기.
- **시뮬레이터 흐름**(iOS·안드로이드) — 0.1 의 누르기 수를 센다: ① 왔던 아이 완료 → 금액이 채워져 있음 → 저장 ② 처음 온 아이 → 근거 글 → 저장 ③ 매출 탭 → 지난달 파일 받기 → 공유 시트(임시 파일의 머리 줄을 읽어 확인) ④ 노쇼 이력 고객의 예약 → 준비된 안내 → 계좌 묻기 → 보내기 → 받음 → 완료 → 매출 탭의 계좌 줄.
- **설정 줄 이름 맞히기**(공통 3절): 예약금 구역·가격표 시트·직원 허용 줄의 이름만 떼어 이 프로젝트를 모르는 검토자에게 "켜면 무슨 일이 생기나"를 맞히게 한다.
- **흐름 스크립트**(`backend/scripts/`): `check_sales_flow.sh` 에 예약금이 든 방문을 더해 결제 수단 합을 손계산과 견준다.
- **눈으로 볼 것**: 만든 CSV 를 맥의 엑셀·숫자에서 열어 한글과 전화번호, 안드로이드의 `FileProvider` 공유, 아이패드의 공유 말풍선 자리.

# 5. 계획을 어떻게 나눌지

| 계획 | 백엔드 | 앱 | 기대는 것 |
|---|---|---|---|
| ⑮-1 기록에서 가격 채우기 | `is_extra`·`report_visible`, 값 받기(③④⑤), 알림장 조립의 거르기 | 근거 글, 두 칩 줄, 예약 등록의 예상 금액, 값이 없을 때 묻기 | 없음 |
| ⑮-2 예약금 안내 | 설정 칸 넷, `visit_deposits`, 예약금 쓰기 셋·글, 상세·하루 목록·매출 요약, 가르기 | 설정 구역, 방문 상세 줄, 보내기 시트, 기록 화면 한 줄, 매출 탭 | ⑪ 의 보낼 것 묶음, ⑬ 의 `marks` |
| ⑮-3 내보내기 | 권한 `data:export` 시드, 직원 허용, 읽기 넷(다섯), `shop_export_logs` | 공유 시트 `shareFiles`(네이티브), CSV 적기, 매출 탭·매장 설정의 시트 | 없음 |
| ⑮-4 가격표(선택) | 경계, `service_menu_prices`, 가격표 API, 값 받기에 ② 더하기 | 가격표 시트, 몸무게 구간 줄 | ⑮-1. **히스하우스의 답(물을 것 1) 뒤** |

- 권하는 순서는 **⑮-1 → ⑮-2 → ⑮-3 → ⑮-4**. 처음 안(계산기 → 예약금 → 내보내기)에서 가격표를 맨 뒤로 뺐다 — 가격표 없이도 값이 채워지고, 가격표의 모양은 첫 매장의 답에 달려 있다.
- **돈을 가르는 함수**: 공통 6절은 ⑭ 가 만들고 ⑮ 가 넓힌다고 정했다. ⑭ 는 반복 예약부터 만들고 정기권은 답 뒤라, ⑮-2 를 만들 때 함수가 아직 없을 수 있다. 그때는 **⑮-2 가 함수를 만들고 정기권 몫을 0 으로 둔다** — ⑭ 의 정기권이 같은 함수에 몫을 더한다. 어느 쪽이 먼저든 함수는 하나다.
- ⑪ 의 보낼 것 묶음이 아직 없으면 ⑮-2 는 방문 상세의 줄에서 따로 보내는 길만 만들고, 묶음에 토막을 더하는 일은 ⑪ 뒤로 미룬다.
- 마이그레이션 번호는 계획을 쓸 때의 다음 번호, 결정 기록은 **018**(공통 11절).

# 6. 만드는 사람에게 맡기는 것

- 문구의 마지막 다듬기, 시트의 모양(기존 시트를 따른다), 근거 글의 표기.
- 값 받기 응답의 칸 이름, 내보내기 응답의 칸 이름·순서, 커서의 모양.
- 어림의 걸러 내기를 SQL 에서 할지 파이썬에서 할지(질의 수 고정과 문턱 테스트만 지키면 된다), 가르기를 어디서 계산할지(합이 매출과 같다는 테스트만 지키면 된다).
- `shop_export_logs`·직원 허용을 다루는 `tenancy` 슬라이스의 이름과 칸이 놓일 표, 공유 시트 네이티브 코드의 파일 이름.

# 7. 사용자에게 물을 것

1. **히스하우스의 가격은 무엇에 따라 갈리나요?**(몸무게인지, 견종인지, 둘 다인지) 지금 설계는 가격표 없이 지난 기록에서 채우므로 답이 없어도 ⑮-1 은 만들 수 있습니다. 답은 선택 가격표(⑮-4)의 모양과, 처음 온 아이의 값을 견종까지 맞출지 몸무게만 맞출지를 정합니다.
2. **견종을 목록에서만 고르게 할까요?** 지금은 견종을 손으로도 적을 수 있어 `말티`와 `말티즈`가 다른 견종으로 세어집니다. 목록에서만 고르게 하면 어림이 정확해지지만, 목록에 없는 견종(믹스 등)을 적는 길이 좁아집니다. 이것은 고객 등록 화면을 바꾸는 일입니다.
3. **예약금 안내의 기본 문장이 히스하우스의 방침과 맞나요?** 기본은 `예약금은 미용 요금에서 빼 드려요.` 한 줄이고 매장이 고칠 수 있습니다. 취소했을 때 돌려주는 규칙(며칠 전까지 전액 등)을 기본 문장에 넣을지는 실제 방침을 알아야 정할 수 있습니다.

# 차곡노트 — 서브 프로젝트 ② 고객·반려동물과 기본 검색 설계

- 작성일: 2026-09-22
- 상태: 사용자 검토 대기
- 범위: 백엔드 `customer` 스포크(고객·반려동물·질병·검색), Flutter 고객 탭(목록·등록·상세·수정)
- 앞선 문서: `docs/superpowers/specs/2026-09-20-foundation-design.md`(① 기반), `_docs/decisions/004-flutter-app-and-reauth.md`
- 다음 단계: 이 문서가 승인되면 구현 계획을 두 개(②-1 백엔드, ②-2 앱)로 작성한다.

## 1. 배경과 이미 정해진 것

①의 설계 9절과 결정 기록 004 에서 넘어온 결정이다. 다시 묻지 않는다.

- 고객(사람)이 기본이고 반려동물은 선택적인 하위 대상이다. 반려동물 없는 고객도 성립한다(사람 뷰티 업종 확장 대비).
- 고객 등록 때 마케팅 수신 동의 필드를 처음부터 둔다.
- 권한은 ①의 시드에 이미 있다: `customer:write`(사장·직원 — 고객·반려동물 등록·수정), `customer:delete`(사장만 — 고객 삭제).
- 스포크 이름은 `customer`. 앱 기능 폴더는 `lib/features/customer/{screens,state,api}`. 홈 셸의 "고객" 탭을 채운다.
- 주의 고객·노쇼는 ③, 사진 업로드는 ④에서 다룬다. 사진 자리는 회색으로 두고 ④에서 `AppPhotoTile` 로 채운다.
- ① 최종 검토의 규칙: 스크롤 목록은 불투명 `AppCard`, 글래스는 떠 있는 층(탭바·시트)에만. 매장 범위 컨트롤러는 `autoDispose` + `runShopScoped`. 오류 화면에는 다시 시도와 뒤로 가기.

## 2. 사용자와 정한 것 (2026-09-22)

| 주제 | 결정 |
|---|---|
| 검색 | 검색창 하나에서 전화번호(뒷자리 포함)·보호자 이름·반려동물 이름을 모두 찾는다. 한글 초성 검색(ㅋㅇ → 콩이)도 된다. |
| 전화번호 | 필수. 매장 안에서 **전체 번호 기준으로 하나만**. 뒷자리가 같은 고객은 따로 등록되고, 뒷자리 검색은 여러 명을 보여 준다(보호자 이름·반려동물 이름·가린 번호로 구분). |
| 반려동물 필수 항목 | 이름, 종류(강아지·고양이), 품종, 성별, 중성화 여부, 나이(생일 또는 태어난 해 또는 **모름**), 몸무게(현재 값), 질병(또는 "질병 없음" 확인). 특이사항 메모만 선택. |
| 질병 | 반려동물 상세의 **별도 탭**. 정해진 항목을 칩으로 고르고 없는 건 "기타"로 직접 입력, 항목마다 짧은 메모. 질병이 없으면 "질병 없음"을 **직접 눌러야** 저장된다("없다고 확인함"과 "안 물어봄"을 구분). 질병이 있으면 목록·상세에 "질병" 표시. |
| 보호자 항목 | 전화(필수), 이름(필수, "콩이 보호자" 같은 자유 입력 허용), 마케팅 수신 동의(필수로 예/아니오 선택 + 동의 시각), 보조 연락처(선택, 중복 판단에 쓰지 않음), 메모(선택). 주소·생일·이메일은 받지 않는다. |
| 삭제 | 고객 삭제(사장만)는 **개인정보만 지우는 익명화**. 반려동물이 세상을 떠나면 삭제 대신 **"무지개다리"** 상태(목록에서 기본 숨김, 기록 유지). 잘못 등록한 반려동물은 직원도 삭제할 수 있다. |
| 목록 | 반려동물 중심. **같은 보호자의 아이들은 보호자별 카드(가족 카드)로 묶는다.** 제목 오른쪽 아이콘 토글로 [목록 ☰ / 격자 ▦] 전환(기본 목록, 마지막 선택을 기기에 기억). |
| 정렬 | [최근순(기본) / 가나다순] 선택. ③·④가 붙으면 "최근 방문순"을 더한다. |
| 등록 흐름 | 전화번호 → 보호자 → 반려동물 3단계. 1단계에서 이미 있는 번호면 알려 주고 그 보호자에게 반려동물 추가로 건너뛴다. |
| 상세 | 반려동물 한 마리 화면: 큰 사진 자리, 이름·요약, 탭 [기본 / 질병 / 보호자], 같은 보호자의 다른 아이로 이동. |
| 검색 방식 | 서버(PostgreSQL `pg_trgm`)에서 검색. 추가 비용 없음(기본 확장, 기존 DB). 검색은 포트 뒤에 두어 규모가 커지면 전용 검색 엔진으로 바꿀 수 있게 한다. |
| 입력 지연 | 한글 **조합이 끝난 뒤 0.3초** 쉬면 검색을 보낸다. |
| 정규화 | **모든 표는 3NF 까지.** 역정규화는 이유를 적은 경우에만(6.4절). |

### 2.1 삭제 방식의 근거 (조사 2026-09-22)

- 해외 펫 미용·돌봄 플랫폼(MoeGo, Gingr, Time To Pet)은 모두 "기록은 남기고 비활성으로 숨긴다"가 기본이다. MoeGo 는 세상을 떠난 반려동물에 비활성을 권한다 — 우리의 "무지개다리"와 같다. 세 곳 모두 개인정보만 골라 지우는 익명화 기능은 문서에서 찾지 못했다.
- 개인정보보호법은 불필요해진 개인정보를 지체 없이 파기하라고 한다. 우리는 매장의 개인정보 처리를 대신하는 수탁자라, 식별 정보(이름·전화·보조 연락처·메모, 반려동물 이름·메모)를 지워 알아볼 수 없게 하고 누군지 알 수 없는 틀만 남긴다. 나중의 방문·매출 기록(③·④)이 깨지지 않는다.
- 전자상거래법의 5년 보존은 온라인 판매 기록 규정이라 오프라인 매장 고객 정보에 바로 적용되지 않는다.

## 3. 범위

### 3.1 만드는 것

- 백엔드 `customer` 스포크: 고객·반려동물·질병 등록·조회·수정, 고객 익명화 삭제, 반려동물 무지개다리·삭제, 검색, 번호 조회.
- 마이그레이션: 표 5개(6절), 질병 종류 시드, `pg_trgm` 확장.
- 앱: 고객 탭 목록(가족 카드, 목록·격자, 정렬, 검색), 등록 3단계, 반려동물 상세(탭 3개), 반려동물·보호자 수정, 고객 삭제, 무지개다리.
- 미뤄 둔 것 하나: `Pressable` 의 Semantics 경계(스크린리더 포커스가 행 전체 폭으로 잡힘, 결정 기록 004 "남는 것")를 ②-1 의 첫 작업으로 고친다.

### 3.2 만들지 않는 것

- 사진(④), 주의 고객·노쇼(③), 방문·매출(③·④), 몸무게 이력(④ 방문마다), 알림(⑥), 보호자 회원(⑦), 의미 검색(⑨).
- 고객 목록 내보내기·가져오기(엑셀 등) — 필요해지면 따로.
- 오프라인 캐시 — ①과 같은 방향(개인정보를 기기에 쌓지 않는다).

## 4. 백엔드 구조

- 새 스포크 `backend/apps/customer/`, API 프로세스(`main.py`)에 장착한다. 경로 앞부분은 `/v1/shops/{shop_id}`.
- 폴더와 수직 슬라이스 1:1 규칙은 `_docs/architecture.md` 그대로다. 유스케이스마다 router·schema·dto·input 포트·interactor·provider·test 하나씩.
- 모든 라우터는 `core/shop_guard.py` 의 `require_permission("…")` 또는 `get_shop_context` 로 `ShopContext` 를 받고, 매장 범위 리포지토리 메서드는 `ShopContext` 를 첫 인자로 받는다.
- **새 허브 포트는 만들지 않는다.** 다른 스포크와 협력할 일이 아직 없다. 매장이 닫히거나 정지되면 기존 매장 접근 확인이 막는다.
- 검색은 아웃바운드 포트 `CustomerSearchPort` 뒤에 둔다. 구현은 `adapter/outbound/pg/` 의 PostgreSQL 검색. 전용 검색 엔진으로 바꿀 때 어댑터만 교체한다.
- 도메인 서비스(표준 라이브러리만):
  - `phone_number`: 입력에서 숫자만 남기고 한국 휴대전화·일반 전화 형식을 검증, 가린 표시(`010-12··-5678`)를 만든다.
  - `hangul_initials`: 한글 음절을 초성으로 바꾼다(콩이 → ㅋㅇ). 한글이 아닌 글자는 그대로 둔다.
  - `pet_age`: 생일·태어난 해·모름 중 정확히 하나 규칙과 나이 표시 계산.
  - `search_terms`: 고객과 반려동물 정보로 검색 문자열을 만든다(이름, 초성, 전화 숫자).
- 구조 계약(import-linter 6종)은 그대로 유지한다. 새 스포크는 "스포크 상호 독립"과 "core 는 스포크를 import 하지 않는다" 계약에 자동으로 들어간다.

## 5. API

모두 API 프로세스. 경로 앞부분 `/v1/shops/{shop_id}`. 오류 본문은 ①과 같은 `{code, message}`.

| 메서드·경로 | 권한 | 하는 일 |
|---|---|---|
| `GET /customers?q=&sort=recent\|name&include_passed=false&cursor=` | 멤버 | 가족 카드 목록. 카드마다 보호자(이름, **가린 번호**)와 반려동물 요약(이름, 종류, 품종, 나이 표시, 질병 여부, 무지개다리 여부). 기본은 무지개다리 제외, 반려동물이 모두 무지개다리인 가족도 제외. `q` 는 부분 일치. 커서 방식 페이지. |
| `GET /customers/lookup?phone=` | 멤버 | 등록 1단계. 삭제되지 않은 고객 중 이 번호가 있으면 `{customer_id, name, pet_names}`, 없으면 404 `CUSTOMER_NOT_FOUND`. |
| `POST /customers` | `customer:write` | 보호자와 첫 반려동물을 한 트랜잭션으로 등록. 번호가 겹치면 409 `CUSTOMER_PHONE_TAKEN`. |
| `GET /customers/{customer_id}` | 멤버 | 보호자 전체(전체 번호 포함)와 반려동물 전체(질병 포함). |
| `PUT /customers/{customer_id}` | `customer:write` | 보호자 수정(번호 변경 포함, 겹치면 409). |
| `DELETE /customers/{customer_id}` | `customer:delete` | 익명화 삭제(7.2절). |
| `POST /customers/{customer_id}/pets` | `customer:write` | 기존 고객에 반려동물 추가. |
| `GET /pets/{pet_id}` | 멤버 | 반려동물 전체와 보호자 요약, 같은 보호자의 다른 아이 목록. |
| `PUT /pets/{pet_id}` | `customer:write` | 반려동물 수정. 질병 목록은 통째로 교체. |
| `POST /pets/{pet_id}/passed-away` | `customer:write` | 무지개다리 표시. |
| `DELETE /pets/{pet_id}/passed-away` | `customer:write` | 무지개다리 되돌리기(잘못 누른 경우). |
| `DELETE /pets/{pet_id}` | `customer:write` | 잘못 등록한 반려동물 삭제. 고객의 마지막 반려동물이면 409 `LAST_PET`(고객 삭제를 안내). |
| `GET /pet-condition-types` | 멤버 | 정해진 질병 종류 목록(코드·이름·순서). |
| `GET /customers/myself` | 멤버 | 이 묶음의 엔드포인트·데이터·제약 설명(아키텍처 규칙). |

규칙:
- 다른 매장의 고객·반려동물 ID로 부르면 **404** 다(존재 여부를 알리지 않는다). 반려동물 경로는 반려동물 → 고객 → 매장 순서로 소속을 확인한다.
- 삭제된 고객은 조회·수정·검색·번호 조회에서 없는 것으로 본다(404).
- 목록 응답의 번호는 가린다. 전체 번호는 상세(`GET /customers/{id}`)에서만 준다.
- 입력 검증 실패는 422 `VALIDATION_ERROR`. 질병 규칙 위반은 422 `PET_HEALTH_REQUIRED`(질병도 없고 "질병 없음"도 아님) 또는 422 `PET_HEALTH_CONFLICT`(질병과 "질병 없음"을 함께 보냄).
- 새 오류 코드(`CUSTOMER_NOT_FOUND`, `PET_NOT_FOUND`, `CUSTOMER_PHONE_TAKEN`, `LAST_PET`, `PET_HEALTH_REQUIRED`, `PET_HEALTH_CONFLICT`)는 앱의 오류 문구 표에 더한다.

## 6. 데이터 모델 (3NF)

`shop_id` 는 다른 스포크(tenancy)의 ID 라 외래 키 없이 인덱스만 둔다(①의 규칙). 스포크 안의 관계는 외래 키를 건다.

### 6.1 표

**`customers`** — 보호자 한 명

| 칸 | 형식 | 비고 |
|---|---|---|
| `id` | bigint PK | |
| `shop_id` | bigint, 인덱스 | tenancy 의 매장 ID |
| `name` | text, null 가능 | 삭제되면 null. 살아 있는 고객은 필수(검증) |
| `phone` | text, null 가능 | 숫자만. 삭제되면 null |
| `phone_alt` | text, null 가능 | 숫자만, 선택 |
| `marketing_consent` | boolean | 필수 선택 |
| `marketing_consent_changed_at` | timestamptz | 동의 여부를 마지막으로 정한 시각 |
| `memo` | text, null 가능 | |
| `created_at`, `updated_at` | timestamptz | |
| `deleted_at` | timestamptz, null 가능 | 익명화 시각 |

- 부분 유일 색인: `UNIQUE (shop_id, phone) WHERE deleted_at IS NULL`.
- CHECK: `deleted_at IS NOT NULL OR (name IS NOT NULL AND phone IS NOT NULL)`.

**`pets`** — 반려동물 한 마리

| 칸 | 형식 | 비고 |
|---|---|---|
| `id` | bigint PK | |
| `customer_id` | bigint FK → customers | 매장은 고객을 거쳐 안다(여기에 `shop_id` 를 두지 않는다 — 이행 종속) |
| `name` | text, null 가능 | 삭제된 고객의 반려동물이면 null |
| `species` | text | CHECK `dog`·`cat` |
| `breed` | text | 자유 입력(앱이 자주 쓰는 품종을 추천) |
| `sex` | text | CHECK `female`·`male` |
| `neutered` | boolean | |
| `birth_date` | date, null 가능 | |
| `birth_year` | smallint, null 가능 | 생일을 모를 때만 |
| `weight_kg` | numeric(4,1) | 현재 몸무게. CHECK 0 초과 |
| `no_known_conditions` | boolean | "질병 없음"을 직접 확인함 |
| `memo` | text, null 가능 | 특이사항 |
| `passed_away_at` | timestamptz, null 가능 | 무지개다리 |
| `created_at`, `updated_at` | timestamptz | |

- CHECK: `birth_date IS NULL OR birth_year IS NULL`(둘 다 null 이면 "모름"). 태어난 해는 생일에서 나오는 값이라 둘을 함께 저장하지 않는다.
- "질병 있음 XOR 질병 없음 확인" 규칙은 두 표에 걸쳐 CHECK 로 표현할 수 없어 도메인에서 검증한다(쓰기는 한 트랜잭션).

**`pet_condition_types`** — 정해진 질병 종류(시드)

| 칸 | 형식 | 비고 |
|---|---|---|
| `code` | text PK | `patella_luxation`, `heart_disease`, `skin_disease`, `arthritis`, `allergy`, `ear_disease`, `disc_disease`, `seizure`, `diabetes`, `other` |
| `label` | text | 슬개골 탈구, 심장 질환, 피부병, 관절염, 알레르기, 귀 질환, 디스크, 발작·뇌전증, 당뇨, 기타 |
| `sort_order` | smallint | 칩 순서 |

**`pet_conditions`** — 반려동물이 가진 질병

| 칸 | 형식 | 비고 |
|---|---|---|
| `id` | bigint PK | |
| `pet_id` | bigint FK → pets (삭제 시 함께 삭제) | |
| `type_code` | text FK → pet_condition_types | |
| `custom_label` | text, null 가능 | `type_code = 'other'` 일 때만 필수, 그 밖에는 null |
| `note` | text, null 가능 | 짧은 메모(예: 2기, 왼쪽 뒷다리) |

- CHECK: `(type_code = 'other') = (custom_label IS NOT NULL)`.
- 유일: `UNIQUE (pet_id, type_code) WHERE type_code <> 'other'` (같은 질병을 두 번 넣지 않는다. 기타는 여러 개 가능).
- 정해진 질병의 이름은 `pet_condition_types.label` 에만 있다(이름을 복사해 저장하지 않는다).

**`customer_search_entries`** — 검색용(역정규화, 6.4절)

| 칸 | 형식 | 비고 |
|---|---|---|
| `customer_id` | bigint PK, FK → customers | 가족 하나에 한 줄 |
| `shop_id` | bigint, 인덱스 | 검색을 매장으로 먼저 거르기 위한 복사본 |
| `terms` | text | 보호자 이름·초성, 반려동물 이름·초성, 전화 숫자(보조 연락처 제외) |
| `phone_last4` | text | 뒷자리 검색 |
| `sort_name` | text | 가나다순 정렬 키 |
| `last_activity_at` | timestamptz | 최근순 정렬 키(고객·반려동물의 마지막 변경 시각) |

- `terms` 에 `pg_trgm` GIN 색인, `(shop_id, last_activity_at)`·`(shop_id, sort_name)` 색인.
- 삭제된 고객의 줄은 지운다.

### 6.2 3NF 점검

- **1NF:** 모든 칸은 원자값이다. 질병은 반복 칸이나 배열이 아니라 `pet_conditions` 의 행이다.
- **2NF:** 모든 표의 기본 키가 단일 칸이라 부분 종속이 없다.
- **3NF:** 기본 키가 아닌 칸이 다른 비키 칸에 종속되는 경우를 없앴다.
  - `pets` 에 매장을 두지 않는다(`customer_id` → 매장).
  - 나이 "모름" 칸을 두지 않는다(생일·태어난 해가 모두 null 이면 모름). 태어난 해를 생일과 함께 저장하지 않는다.
  - 질병 이름은 종류 표에만 있다. `pet_conditions` 에는 기타의 직접 입력 이름만 있다.
  - 번호 뒷자리, 가린 번호, 초성, 나이 표시는 저장하지 않고 계산한다 — 검색용 표만 예외(6.4절).

### 6.3 이름과 형식 규칙

- 전화번호는 숫자만 저장한다(하이픈·공백 제거). 앱은 입력 중 하이픈을 보여 줄 수 있지만 서버에는 숫자만 보낸다. 서버도 정규화한다.
- 문자열은 앞뒤 공백을 없애고, 빈 문자열은 null 로 저장한다.
- 길이 제한: 이름 50자, 품종 50자, 질병 직접 입력 30자, 질병 메모 100자, 메모 500자.

### 6.4 역정규화 — `customer_search_entries`

- **무엇을 복사하나:** 보호자·반려동물 이름에서 만든 검색 문자열과 초성, 전화 숫자와 뒷자리, 매장 ID, 정렬 키.
- **왜:** 검색 한 번이 가족 단위(보호자 + 반려동물 여러 마리)로 일치해야 하고, 초성·뒷자리는 계산 값이라 원본 표에서 조인·계산하면 색인을 쓸 수 없다. 고객 수천 명 규모에서도 검색이 즉시 반응하려면 색인 가능한 한 줄이 필요하다.
- **정합성:** 고객·반려동물·질병을 바꾸는 모든 유스케이스가 **같은 트랜잭션 안에서** 그 가족의 검색 줄을 다시 만든다(리포지토리 한 메서드 `rebuild_search_entry(ctx, customer_id)`). 검색 줄은 원본에서 언제든 다시 만들 수 있다 — 틀어지면 재생성 스크립트로 복구한다.
- **원본은 언제나 `customers`·`pets`** 다. 응답의 보호자·반려동물 정보는 검색 줄이 아니라 원본에서 읽는다(검색 줄은 찾기와 정렬에만).

## 7. 동작 규칙

### 7.1 등록과 수정

- 등록은 보호자 + 첫 반려동물을 한 트랜잭션으로 넣는다. 번호 충돌은 부분 유일 색인이 막고, 409 로 답한다(두 기기가 동시에 같은 번호를 등록해도 하나만 성공).
- 질병: 하나 이상이면 `no_known_conditions = false`, 없고 "질병 없음"이면 `true`. 둘 다 아니거나 둘 다면 422.
- 마케팅 수신 동의 값이 바뀔 때만 `marketing_consent_changed_at` 을 새로 찍는다.
- 수정은 전체 교체(PUT). 질병 목록도 통째로 교체한다.

### 7.2 삭제

- **고객 삭제(익명화, 사장만):** 한 트랜잭션으로 `customers` 의 `name`·`phone`·`phone_alt`·`memo` 를 null, `deleted_at` 을 찍고, 그 고객 반려동물의 `name`·`memo` 를 null, 질병 행을 지우고, 검색 줄을 지운다. 반려동물 행 자체와 종류·품종·성별 등 식별되지 않는 칸은 남긴다(③·④의 기록이 가리킬 틀).
- 삭제된 번호로 다시 등록하면 새 고객이다(부분 유일 색인이 삭제 안 된 고객에만 걸린다).
- **무지개다리:** `passed_away_at` 만 찍는다. 목록 기본에서 숨기고, 상세에서는 "무지개다리" 표시와 되돌리기.
- **반려동물 삭제(잘못 등록):** 행을 지운다(질병도 함께). 고객의 마지막 반려동물이면 409 `LAST_PET`. — ③ 이후 방문 기록이 붙은 반려동물을 지울지는 ③에서 다시 정한다.

### 7.3 검색

- `q` 를 정규화한다: 앞뒤 공백 제거, 숫자만이면 전화 검색(4자리 이하면 뒷자리 우선, 그 이상이면 전체 번호 부분 일치), 한글 초성만이면 초성 검색, 그 밖에는 `terms` 부분 일치. 공백으로 나뉜 여러 낱말은 모두 일치해야 한다(`5678 콩` → 뒷자리 5678 이면서 콩).
- LIKE 특수 문자(`%`, `_`, `\`)는 이스케이프한다.
- 결과는 가족 카드 단위, 정렬 키와 ID 로 만든 커서로 페이지(한 페이지 30 가족).
- 한 글자 검색도 허용한다(초성 한 글자 등). 부분 일치 성능은 `pg_trgm` 이 맡는다.

### 8.2 상태와 규칙

- 기능 폴더 세 층, `design/widgets` 만 사용, 새 위젯이 필요하면 `design/widgets` 에 더한다(예: 아이콘 토글, 선택 칩 묶음).
- 매장 범위 컨트롤러는 `autoDispose.family` + 모든 서버 호출 `runShopScoped`(`NOT_A_MEMBER` → 내 정보 재조회).
- 검색 입력: 한글 **조합 중에는 기다리고**, 조합이 끝난 뒤 **0.3초** 쉬면 요청한다. 새 요청이 나가면 앞선 응답은 버린다(늦게 온 옛 결과가 새 결과를 덮지 않게).
- 저장 버튼은 요청 진행 중 비활성(연타 방지). 오류 화면에는 다시 시도와 뒤로 가기, 모든 하위 화면 머리에 `AppBackButton`.
- 직원에게 고객 삭제 버튼을 보이지 않는다(보안 경계는 서버 403).
- 번호는 목록에서 가린 값만 쓰고, 전체 번호는 상세·수정 화면에서만 보인다. 로그·print 금지(① 규칙).

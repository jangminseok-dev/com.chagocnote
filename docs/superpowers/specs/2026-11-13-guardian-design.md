# 차곡노트 — ⑦ 보호자 회원 설계

2026-11-13. 보호자가 로그인해서 우리 아이의 지난 미용 알림장을 모아 본다.

- 범위: 백엔드(새 스포크 `guardian`, `visit` 의 보호자용 읽기, 허브 포트), 웹(`web/` — 로그인·내 기록), 앱(고객 상세의 연결 표시와 끊기).
- 하지 않는 것: 보호자용 앱, 매장 검색·예약 신청, 보호자가 반려동물 정보를 고치는 것, 푸시, 보호자 쪽 알림 수신 설정·차단(⑥ 설계가 ⑦로 미뤘던 것 — 다음으로 다시 미룬다), 매출 통계(⑧).
- 바탕: 기반 설계(`2026-09-20-foundation-design.md` 5.1 — User 는 플랫폼 단일 신원, 보호자는 고객 카드와의 "관계"), 알림장 설계(`2026-09-28-report-design.md`), 결정 기록 008.

## 1. 왜

경쟁 조사에서 확인한 빈틈이 "보호자 쪽 기록 누적·다시 보기"다. 지금 보호자는 받은 링크 한 장만 보고, 링크 기간(7·30일)이 지나면 다시 볼 길이 없다. 매장에는 "지난 사진 다시 보내 주세요" 요청이 온다.

## 2. 사용자와 정한 것 (2026-11-13)

| 항목 | 결정 |
|---|---|
| 어디서 보나 | **웹 먼저**(chagocnote.com). 보호자 앱은 만들지 않는다. 해외 선두(MoeGo·Gingr)는 웹 포털과 앱을 둘 다 두고 국내 경쟁사는 앱 쪽이다 — 설치 없이 바로 보는 쪽을 골랐다. |
| 본인 확인 | **받은 알림장 링크로 한다.** 업계 표준은 매장에 등록된 전화번호로 맞추는 것이고 이 방식은 표준과 다르다 — 문자 인증은 건당 비용이 들고 카카오의 전화번호는 사업자 심사가 필요해 지금은 쓰지 않는다. 나중에 전화번호 확인을 덧붙일 수 있게 **무엇으로 확인했는지를 연결 기록에 남긴다.** |
| 약점과 보완 | 링크를 전달받은 사람이 이을 수 있다. 고객 카드 하나에 계정 하나만 잇고, 매장이 연결을 보고 끊을 수 있다. |
| 보이는 범위 | **매장이 알림장을 보낸 방문만.** 링크 기간이 지난 알림장도 로그인하면 본다. 매장이 링크를 끊은 것은 안 보인다. 항목(금액·몸무게 등)은 매장의 알림장 설정을 따른다. |
| 내부 메모 | 절대 보이지 않는다 — 공개 알림장과 같은 조립(`report_reader.describe_report`)과 같은 응답 스키마를 쓴다. |
| 로그인 | 카카오·애플(매장 앱과 같은 계정). **실제 카카오·애플 웹 로그인 연결은 나중이다** — 이번에는 로컬의 개발용 로그인으로 만들고 검증한다. |
| 비용 | 기능과 로컬 테스트까지만 한다. 외부 서비스 연결(실계정·배포)은 사용자가 따로 말할 때. |
| 순서 | ⑦-1 백엔드 → ⑦-2 웹 → ⑦-3 앱. |

## 3. 보호자가 겪는 순서

1. 알림장 링크를 연다(지금의 `/r/<토큰>`).
2. 알림장 맨 아래의 [로그인하고 지난 기록 보기]를 누른다. 닫힌 알림장 화면에도 같은 버튼이 있다.
3. 로그인한다.
4. 열려 있는 링크였으면 그 링크의 고객 카드와 계정이 이어지고 "내 기록"으로 간다. 닫힌 링크였으면 잇지 않고 "내 기록"으로만 간다(이미 이어진 계정이면 기록이 보이고, 아니면 빈 화면의 안내 — 매장에 알림장을 다시 보내 달라고 한다).
5. 다음부터는 `/me` 에 로그인만 하면 된다. 다른 매장의 알림장으로 같은 일을 하면 한 계정에 함께 쌓인다.

## 4. 구조

### 4.1 스포크와 허브 포트

`guardian` 스포크(새로 만든다, 도메인 언어)가 **연결**을 소유한다. 알림장을 읽는 것은 `visit` 이 그대로 소유한다. 스포크끼리 import 하지 않는다.

| 허브 포트 | 구현 | 사용 | 용도 |
|---|---|---|---|
| `ReportLinkPort.resolve(token) → ReportLinkTarget(shop_id, customer_id, live) \| None` | visit | guardian(잇기) | 토큰의 서명을 확인하고 그 알림장의 매장·고객과 열려 있는지를 준다. 우리가 만든 토큰이 아니면 None. 열림의 뜻은 공개 조회와 같다(끊음·기간 지남·매장 정지·폐업·익명화·기록 없음이면 닫힘). |
| `GuardianAccessPort.resolve(user_id, link_id) → GuardianContext(link_id, shop_id, customer_id)` | guardian | visit(보호자용 읽기) | 그 계정의 살아 있는 연결인지 매 요청마다 DB 에서 본다. 아니면 404(남의 연결과 없는 연결을 구분하지 않는다). `ShopAccessPort` 와 같은 자리다. |
| `GuardianLifecyclePort.end_for_user(user_id)` | guardian | auth(탈퇴, 인증 프로세스) | 탈퇴한 계정의 연결을 끝낸다 — 고객 카드가 다른 계정으로 다시 이어질 수 있게. `auth_main.py` 가 tenancy 의 `MembershipLifecyclePort` 를 꽂는 것과 같은 방식이다. |
| `GuardianLifecyclePort.end_for_customer(shop_id, customer_id)` | guardian | customer(익명화) | 익명화하는 트랜잭션 안에서 그 고객 카드의 연결을 끝낸다(`anonymized`). |

- 가드는 `core/guardian_guard.py` 의 `get_guardian_context`(FastAPI 의존성 — `core/shop_guard.py` 와 같은 모양).
- 보호자용 읽기는 매장 멤버가 아닌 읽기다. `ShopContext` 가 필요한 저장소 호출에는 **`visit/app/services/public_context.py` 를 그대로 쓴다**(권한 빔, 읽기 전용). 루트 CLAUDE.md 의 "가드 없이 ShopContext 를 만드는 곳은 둘뿐"은 그대로 두고, 첫째의 설명을 "매장 멤버가 아닌 요청 경로(공개 알림장·보호자 읽기)"로 넓힌다.
- **`guardian` 은 고객·반려동물을 읽지 않는다**(매장 범위 포트는 `ShopContext` 가 필요하고 guardian 은 그것을 만들 수 없다). 연결 목록은 매장 이름(`ShopProfilePort.public_profile` — 매장 ID 만 받는다)과 이은 날만 주고, 반려동물은 `visit` 의 보호자용 읽기가 준다. 익명화는 연결을 끝내므로(위 포트) 죽은 고객의 연결이 목록에 남지 않는다.
- 잇기는 맨 앞에서 `ActiveUserGuardPort.lock_active` 로 유저 행을 잠근다 — 탈퇴와 겹치면 기다렸다가, 탈퇴 뒤에는 거절된다(초대 수락과 같은 이유). 잠금 순서에 "유저 행 → 보호자 연결 행", "고객 행 → 보호자 연결 행"을 더한다. 동시에 둘이 같은 카드를 이으면 부분 유일 색인이 둘째를 409 로 막는다(세이브포인트).

### 4.2 데이터 모델 (마이그레이션 0014, `guardian` 소유)

`guardian_links`

| 칸 | 형 | 뜻 |
|---|---|---|
| id | bigint PK | 보호자에게 보이는 연결 ID |
| user_id | bigint | 보호자 계정 |
| shop_id, customer_id | bigint | 매장의 고객 카드 |
| verified_by | varchar(20), CHECK `('report_link')` | 무엇으로 확인했나. 전화번호 확인을 더할 때 값이 는다. |
| created_at | timestamptz | 이은 시각 |
| ended_at | timestamptz null | 끝난 시각 |
| ended_by | varchar(20) null, CHECK `('guardian','shop','withdrawn','anonymized')` | 누가 끝냈나. `ended_at` 과 함께 있거나 함께 없다. |

- 부분 유일 색인 `uq_guardian_links_live(shop_id, customer_id) WHERE ended_at IS NULL` — **고객 카드 하나에 살아 있는 연결 하나.**
- 색인 `(user_id) WHERE ended_at IS NULL`.
- 전화번호·이름을 저장하지 않는다. 끝난 연결의 줄은 남긴다(누가 언제 이었고 끊었는지).

### 4.3 API

**보호자(`/v1/me/guardian/…`, 로그인 필요, 매장 소속과 무관)**

| 경로 | 소유 | 하는 일 |
|---|---|---|
| `POST /v1/me/guardian/links` (헤더 `X-Report-Token`) | guardian | 잇는다. 201 `{link_id}`. 같은 계정이 이미 이은 카드면 200 으로 같은 `link_id`. |
| `GET /v1/me/guardian/links` | guardian | 내 연결 목록 — `link_id`, 매장 이름, 이은 날. 정지·폐업한 매장의 연결은 빼고 준다. |
| `GET /v1/me/guardian/links/{link_id}/pets` | visit | 그 연결에서 **알림장을 받은 적 있는 아이들**(`pet_id`, 이름) — 알림장을 받은 적 없는 아이의 이름은 드러나지 않는다. 무지개다리를 건넌 아이도 넣는다(지난 기록은 남는다). 보호자만의 방문의 알림장은 `pet_id` 없이 목록에만 있다. |
| `DELETE /v1/me/guardian/links/{link_id}` | guardian | 보호자가 끊는다. 204. |
| `GET /v1/me/guardian/links/{link_id}/reports?pet_id=&cursor=` | visit | 지난 알림장 목록(최신순, 20개씩) — `report_id`, 날짜, 반려동물 이름, 대표 사진(썸네일), 사진·영상 수. |
| `GET /v1/me/guardian/links/{link_id}/reports/{report_id}` | visit | 알림장 한 장 — **공개 알림장과 같은 스키마.** |

- 보이는 알림장: 그 고객의 방문 가운데 **끊지 않은 알림장이 있는 것**(`revoked_at IS NULL` — 기간 지남은 상관없다), 기록이 있는 것. 매장이 정지·폐업이면 아무것도 안 보인다.
- `report_id` 는 그 연결의 고객 것일 때만 듣는다. 아니면 404.
- 열람 신호(`first_viewed_at`)는 보호자용 읽기가 찍지 않는다 — "링크를 열었는가"의 뜻을 지킨다.
- 한 장 응답의 기간(`expires_at`)은 늘 null 이다 — 지난 날짜가 "…까지 열려요"로 그려지지 않게. 로그인한 보호자에게는 기간이 없다.
- **기간이 지난 알림장 한 장만 숨기는 길은 따로 만들지 않는다.** 지금 [링크 끊기]는 열려 있는 링크에만 있다. 매장이 지난 알림장 하나를 감추려면 그 방문에서 알림장을 다시 보낸 뒤 끊거나, 보호자 연결을 끊는다. 기능을 넣기 전에 기간이 지난 알림장들도 이으면 함께 보인다 — 그것이 "지난 기록 다시 보기"다.

**매장(`/v1/shops/{shop_id}/customers/{customer_id}/guardian-link`, guardian 소유)**

| 경로 | 권한 | 하는 일 |
|---|---|---|
| `GET` | 소속 | `{linked: bool, linked_at}`. **보호자가 누구인지는 주지 않는다**(기반 설계 5.1 — 매장은 고객이 다른 매장의 사장인지 알 수 없다). |
| `DELETE` | `customer:write` | 매장이 끊는다. 204. 없으면 404. |

**오류 코드**

| 코드 | 상태 | 때 |
|---|---|---|
| `REPORT_NOT_FOUND` | 404 | 잇기: 토큰이 없거나 우리가 만든 것이 아니다(기존 코드) |
| `REPORT_CLOSED` | 410 | 잇기: 닫힌 알림장(기존 코드) |
| `GUARDIAN_ALREADY_LINKED` | 409 | 그 고객 카드가 이미 다른 계정에 이어져 있다 |
| `GUARDIAN_LINK_NOT_FOUND` | 404 | 없거나 남의 연결, 끝난 연결 |
| `GUARDIAN_RATE_LIMITED` | 429 | 잇기 시도가 잦다(계정당 시간당 10회 — Redis, 공개 알림장 제한기와 같은 방식) |

토큰은 헤더로만 받고 로그·오류 본문에 남기지 않는다(루트 CLAUDE.md).

### 4.4 웹

지금 웹은 알림장 한 장뿐이고 상태가 없다. 여기에 로그인과 "내 기록"이 생긴다.

| 경로 | 하는 일 |
|---|---|
| `/r/[token]` (기존) | 알림장 꼬리와 닫힌 화면에 [로그인하고 지난 기록 보기] — `POST /r/[token]/claim` 으로 가는 폼 버튼. |
| `POST /r/[token]/claim` | 로그인돼 있으면 백엔드에 잇기를 부르고 `/me` 로. 아니면 토큰을 **잠깐 사는 쿠키**(httpOnly, 10분)에 넣고 `/login` 으로 — 토큰이 든 주소를 새로 만들지 않는다(⑤-2 의 규칙). 로그인 직후 그 쿠키를 써서 잇고 지운다. |
| `/login` | 로그인. 개발 환경이면 개발용 로그인(이름 한 칸). 카카오·애플 버튼은 설정이 있을 때만 그린다(이번에는 없다). |
| `POST /logout` | 세션 쿠키를 지운다. |
| `/me` | 내 아이들 — 매장별로 반려동물. 연결이 없으면 안내. 연결마다 [연결 끊기]. |
| `/me/[linkId]` (`?pet=`) | 지난 알림장 — 사진 중심, 날짜순, [더 보기]. |
| `/me/[linkId]/[reportId]` | 알림장 한 장 — 지금의 `ReportView` 를 그대로 쓴다(꼬리의 로그인 버튼과 열람 신호는 뺀다). |

- **세션**: **웹 세션은 30분이고 연장하지 않는다**(2026-11-13 사용자 결정). 웹 서버가 로그인 때 받은 30분짜리 액세스 토큰 하나를 암호화해 httpOnly·Secure·SameSite=Lax 쿠키(수명 30분)에 둔다. 리프레시 토큰은 받지도 두지도 않는다. 30분이 지나면 `/login` 으로 보내고 로그인 뒤 보던 곳으로 돌아온다. 브라우저는 여전히 백엔드를 직접 부르지 않는다.
- **설정**: 새 필수 설정 `WEB_SESSION_SECRET`(쿠키 암호화)과 `AUTH_BASE_URL`(로그인·로그아웃은 인증 프로세스에 있다 — compose 는 `http://auth:9000`). 개발용 로그인은 `DEV_LOGIN` 이 켜져 있을 때만 그리고 받는다(기본 꺼짐. 백엔드도 `APP_ENV=dev` 에서만 `dev` 제공자를 연다).
- **왜 연장하지 않나**: 리프레시 토큰 재사용에는 유예가 없고(기반 설계), 재사용이 감지되면 그 계정의 모든 세션이 끊긴다. 웹은 탭 둘·뒤로 가기만으로 갱신이 겹칠 수 있고 보호자 계정은 매장 앱과 같은 계정이라, 웹에서 겹치면 사장·직원의 앱까지 로그아웃된다. 그래서 웹에는 리프레시 토큰을 주지 않는다. 불편하다는 말이 나오면 인증을 고쳐 웹 세션을 분리한다(6절).
- **인증의 변경(⑦-1)**: 소셜 로그인 요청에 웹 세션 표시를 더한다 — 그 표시가 있으면 액세스 토큰의 수명이 30분이고 리프레시 토큰을 내주지 않는다. 표시가 없으면(매장 앱) 지금 그대로다(액세스 15분 + 리프레시 30일). 웹 로그아웃은 쿠키를 지운다.
- 상태를 바꾸는 경로(잇기·로그아웃·끊기)는 `Sec-Fetch-Site` 가 있고 `same-origin` 이 아니면 403 이다(열람 신호와 같은 규칙).
- 응답 헤더 셋(noindex·no-store·no-referrer)은 새 경로에도 그대로다. 루트(`/`)는 여전히 404 다.
- 문구는 한국어 해요체, 영문 장식은 알림장의 목업을 따른다. 화면은 지금 알림장의 글꼴·색·여백을 그대로 쓴다.

### 4.5 앱 (매장)

고객 상세에 한 줄 — "보호자 계정 연결됨 · 11월 13일"과 `···` 의 [연결 끊기](확인: "보호자가 지난 기록을 더는 볼 수 없어요. 알림장을 다시 보내면 다시 이을 수 있어요."). 이어지지 않았으면 줄이 없다. 끊기는 `customer:write`(직원도 한다). 자리는 반려동물 상세의 [보호자] 탭(`customer/screens/pet_detail_screen.dart` 의 `_OwnerTab`)이고 호출은 `customer/api` 에 더한다 — 다른 기능을 import 하지 않는다.

## 5. 보안·경계

| # | 시나리오 | 막는 것 |
|---|---|---|
| G1 | 전달받은 링크로 남이 잇는다 | 감수한다(2절). 카드당 연결 하나, 매장이 보고 끊는다, 열린 링크로만 잇는다. |
| G2 | 남의 `link_id`·`report_id` 로 조회 | `GuardianAccessPort` 가 계정으로 찾는다 — 404. `report_id` 는 연결의 고객 것만. |
| G3 | 닫힌·끊은 링크로 잇기 | 410. 닫힌 화면의 버튼은 로그인만 시킨다. |
| G4 | 토큰을 마구 넣어 본다 | 토큰 서명 + 계정당 시간당 10회. |
| G5 | 내부 메모·끈 항목이 보호자에게 샌다 | 공개와 같은 조립·같은 스키마. 새 스키마를 만들지 않는다. |
| G6 | 매장이 끊은 알림장이 보인다 | `revoked_at IS NULL` 만. |
| G7 | 이미 이어진 카드를 다른 계정이 잇는다 | 부분 유일 색인 — 409. 동시에 둘이면 둘째가 409. |
| G8 | 탈퇴한 계정의 연결이 남아 카드가 묶인다 | 탈퇴가 `end_for_user` 를 부른다(`withdrawn`). |
| G9 | 익명화한 고객·닫힌 매장의 기록이 보인다 | 익명화가 연결을 끝내고(알림장 링크도 끊는다), 매장 정지·폐업은 읽을 때마다 확인한다 — 빈 목록. |
| G10 | 다른 사이트가 잇기·끊기·로그아웃을 시킨다 | `Sec-Fetch-Site` 검사 + SameSite=Lax. |
| G11 | 세션 쿠키를 훔친다 | httpOnly·Secure·암호화. 스크립트가 읽을 수 없다. |
| G12 | 토큰이 로그·주소·쿠키에 남는다 | 헤더로만 넘기고, 쿠키는 httpOnly·10분·쓰면 지운다. `console.*` 금지. |
| G13 | 매장 직원이 [다시 공유]로 얻은 링크로 자기 계정에 잇는다 | 감수한다 — 매장 안에서는 이미 다 보이는 사람이다. 매장을 떠난 뒤에도 볼 수 있다는 것이 남는 위험이고, 매장이 "연결됨"을 보고 끊는다. |
| G14 | 매장이 보호자가 누구인지 안다 | 매장용 응답은 연결 여부와 날짜뿐. |

감수하는 것: G1·G13. 서명 주소(미디어)는 지금처럼 짧게 살고 페이지는 저장하지 않는다. 보호자가 끊거나 매장이 끊어도 이미 내려받은 사진은 회수할 수 없다.

## 7. 검증

- **백엔드**: 단위(스텁 포트) — 잇기의 갈래(열림·닫힘·없는 토큰·이미 내 것·남의 것·횟수 제한), 끊기 넷(보호자·매장·탈퇴·익명화), 다시 잇기. 통합 — 테넌트 격리(남의 연결 404, 다른 매장 고객 404), 동시에 둘이 잇기(하나만), 기간 지난 알림장이 보이고 끊은 알림장은 안 보인다, 익명화·매장 정지 뒤 빈 목록, 응답에 내부 메모·끈 항목이 없다(공개 스키마와 같은 칸), 탈퇴 뒤 다른 계정이 잇는다. 구조 — `.importlinter` 에 `guardian`, 라우트 표 전후 비교, 로그인 없는 경로 목록 불변, 허브 포트 자리 채움, 스키마 대조. 흐름 스크립트 `check_guardian_flow.sh`(게이트웨이 경유).
- **웹**: 컴포넌트 — 꼬리의 버튼, 내 아이들·목록·빈 화면. 서버 응답(`check:server`) — 로그인 없는 `/me` 의 이동, 쿠키 속성, 헤더 셋, 잇기 쿠키가 쓰이고 지워진다, 기록에 토큰·세션이 없다, 다른 출처의 POST 403. 실제 브라우저(e2e) — 알림장 → 버튼 → 개발용 로그인 → 내 기록 → 한 장 → 끊기, 닫힌 알림장에서의 로그인, 30분이 지난 뒤 다시 로그인하고 보던 곳으로 돌아오기.
- **앱**: 위젯·골든 — 연결된 고객과 아닌 고객, 끊기 확인·거절·실패, 직원.
- 새 규칙마다 변이 한 번.

# ⑯ 들어오는 예약 — 전화 올 때 고객 표시(콜아이디)·네이버 예약 글 받기 — 설계

2026-11-16. 경쟁 조사(`.superpowers/research/reports/펫미용 앱 경쟁 기능 비교.md`)의 10·11순위다. 두 기능은 서로 기대지 않는다 — **1부 네이버 예약 글 받기**(작다, 먼저), **2부 콜아이디**(크다, 조건이 찰 때)로 나눠 적는다.

사용자는 "순위에 있는 11개의 설계를 시작"하라고 했다. **아래의 범위·방식·기준값은 모두 내가 정한 것이고**, 사용자가 처음부터 확정해 둔 것은 넷이다 — 과금되는 일과 외부 서비스 연결은 하지 않는다 · 통화 녹음과 콜봇은 하지 않는다 · 앱은 네이티브다 · 주의 고객 정보는 매장 사이에 공유하지 않는다.

## 1. 왜

예약은 카카오톡으로만 오지 않는다. 네이버 예약으로 들어온 것은 사장님이 달력에 손으로 옮겨 적고, 전화로 온 것은 받는 순간 누구인지 모른 채 "성함이…"부터 묻는다.

- **네이버 예약.** 공비서·뷰티인프라는 네이버 예약이 들어오면 달력에 자동 등록된다(각사 홍보 페이지). 새 앱 띵동모아는 "네이버·인스타그램·전화 예약을 한 화면에"를 간판으로 삼았다(검색 요약으로만 확인 — 근거가 약하다). 정식 연동의 조건·비용·심사는 조사하지 못했다.
- **콜아이디.** 반짝은 안드로이드에서만 되고, iOS 요청이 2022-03·2022-04·2026-05 리뷰에 반복된다. 그루머노트는 릴리스 노트(3.14.0, 연도 추정)에 발신자 표시를 적었다. 티피는 기능 이름만 확인했다.
- **첫 매장에는 급하지 않다.** 첫 입점 매장은 예약을 전부 카카오톡으로 받는 1인 매장이다. 네이버 예약을 쓰는지는 모른다(끝의 물을 것 1). 전화 예약이 많다는 증언도 없다. 그래서 2부는 설계만 해 두고 **계획의 순서는 맨 뒤**다(2부 9절의 조건).

## 2. 지금 있는 것 (코드에서 확인)

- **글 → 예약 초안(③-A3).** `POST /v1/shops/{id}/visit-drafts`(`reservation:write`)가 1,000자까지의 글을 받아 날짜·시각·메뉴·보호자 후보를 돌려준다. 아무것도 저장하지 않는다. 해석은 `visit/domain/services/draft_parser.py`(순수 함수) — 날짜는 `오늘/내일/모레/글피`, `이번·다음 주 ○요일`, `○요일`, `M월 D일`, `M/D`, `D일`, 시각은 `오후 2시(반/N분)`, `2:30`, `2시`. 카카오톡 머리말(`[오후 2:31]`, `2026년 9월 24일 오후 2:31, `)은 지운다. **`2026.11.20`·`2026-11-20`·`11.20` 꼴은 읽지 못한다.**
- **"누구"** 는 글의 낱말(최대 20개, 4자리 숫자는 번호 뒷자리, 8자리 이상 숫자는 전체 번호)로 `CustomerDirectoryPort.find_draft_candidates` 가 찾는다(최대 5 가족). 응답의 번호는 가린 꼴(`phone_masked`)이다.
- **앱.** 예약 ① 위의 [카톡 붙여넣기](클립보드), 공유 받기(iOS 공유 확장 `ShareViewController.swift` + App Group `group.com.chagocnote.app` + `chagocnote://share`, 안드로이드 `ACTION_SEND` `text/plain`), 채널 `com.chagocnote.app/share`, 초안 화면 `/visits/draft`, 폼에 넘기는 `VisitPrefill`. 공유 확장은 글만 받는다(주소 `public.url` 은 받지 않는다).
- **같은 예약 막기.** 같은 아이(보호자만이면 같은 보호자)의 같은 시각에 살아 있는 예약이 있으면 등록이 409 `VISIT_DUPLICATE` 다.
- **없는 것.** 방문에 "어디로 들어온 예약인지"를 적는 칸이 없다. 전화번호는 `customers.phone`·`phone_alt`(숫자만, 11자까지)에 평문으로 있다(매장 안 유일은 `phone` 만). 고객 번호를 통째로 내려 주는 경로는 없다. 푸시가 없다.

# 1부 — 네이버 예약 글 받기

## 3. 목표와 하지 않는 것

**목표**

- 네이버 예약 알림 글(톡톡·문자·스마트플레이스 앱의 예약 내용)을 **붙여넣거나 공유하면** 지금의 초안 화면이 채워진다. 새 화면을 만들지 않는다.
- 처음 온 손님이면 글의 이름·번호로 **새 고객 등록 칸이 미리 채워진다**(네이버 예약은 새 손님이 들어오는 창구다).
- 같은 예약을 두 번 넣지 않게 **넣기 전에 알린다**.
- 예약에 "네이버로 들어옴"을 남겨, 앱에서 바꾸거나 취소할 때 **네이버에서도 바꿔야 한다**는 것을 잊지 않게 한다.

**하지 않는 것**

| 항목 | 까닭·때 |
|---|---|
| 네이버 예약 정식 연동(자동 등록·변경·취소 반영) | 제휴 조건·비용·심사를 모른다. 외부 서비스 연결이다. 5.4 의 "확인할 것"을 푼 뒤 따로 설계한다. |
| 안드로이드 알림을 읽어 자동으로 초안 만들기 | 알림 접근 권한은 스토어 정책 위험이 크다(2026-09-22 메시지 수집 아이디어에서 정리한 것). |
| 받은 글·주소를 서버가 열어 보기 | 외부 호출 없음. 주소(`public.url`)는 여전히 받지 않는다 — 로그인이 필요한 페이지라 열어도 쓸 것이 없다. |
| 초안을 자동으로 저장 | 지금 규칙 그대로다 — 사람이 확인한 뒤 저장한다. |
| 취소·변경 알림 글로 예약을 자동으로 고치기 | 그 날의 예약을 보여 주기만 한다(4.4). |
| 인스타그램 DM 등 다른 창구의 전용 규칙 | 견본이 없다. 일반 글은 지금 해석기로 읽힌다. |
| 창구별 매출 통계 | 칸만 남긴다(4.5). 통계는 필요하다는 말이 나오면 ⑧에 더한다. |

**이렇게 되면 실패다**: 네이버 글의 "보낸 날짜"를 예약 날짜로 읽는다 · 취소 알림을 붙여넣었더니 새 예약이 생긴다 · 견본 없이 지어낸 형식 규칙이 실제 글과 달라 틀린 날짜를 "짐작 아님"으로 보인다 · 글이나 번호가 로그에 남는다.

## 4. 무엇을 만드나

### 4.1 견본 없이 하는 것과 견본이 오면 더할 것

**실제 네이버 예약 알림 글의 모양을 나는 모른다. 지어내지 않는다.** 그래서 둘로 나눈다.

| | 견본 없이 (이번) | 견본이 오면 (더한다) |
|---|---|---|
| 출처 알아보기 | 글에 `네이버 예약`·`네이버예약`·`스마트플레이스` 가 있으면 네이버 글로 본다 | 실제 머리말·꼬리말로 굳힌다 |
| 날짜 | 지금 것에 더해 `YYYY.MM.DD`, `YYYY-MM-DD`, `YYYY년 M월 D일`, `MM.DD`(뒤에 요일 괄호가 붙어도) | 보낸 날짜·신청 일시 줄을 지우는 규칙 |
| 시각 | 지금 것 그대로(`오후 2:00`, `14:00`, `2시`) | `14:00~15:30` 같은 범위에서 소요를 읽기 |
| 이름표 줄 | `이름표 : 값` / `이름표: 값` 꼴의 줄을 읽는다. 이름표 사전은 작게 — 예약자·예약자명·이름·성함 / 연락처·전화번호·휴대폰 / 예약일시·이용일시·일시·날짜·시간 / 상품·예약상품·메뉴 / 요청사항 | 실제 이름표로 사전을 고친다 |
| 누구 | 전체 번호(8자리 이상 숫자, 하이픈 포함)와 이름으로 후보 찾기 — 지금 그대로 | 안심번호(050…)를 주는지 확인하고, 주면 번호를 "누구"에 쓰지 않는다 |
| 메뉴 | 매장 메뉴표의 이름이 글에 있으면 고른다 — 지금 그대로 | 네이버 상품 이름 → 매장 메뉴 대응 |
| 예약 번호 | 읽지 않는다 | 읽어서 중복 막기에 쓴다(4.3) |

- 이름표 줄에서 읽은 날짜·시각은 본문에서 읽은 것보다 **앞선다**. 이름표 사전에 없는 줄은 지금처럼 본문으로 읽는다.
- **견본 없이 읽은 네이버 글의 날짜·시각은 늘 "짐작"으로 표시한다**(이름표 줄에서 읽었어도). 견본으로 규칙을 굳힌 뒤에 짐작 표시를 뗀다.
- 이름표 사전은 일반 양식의 흔한 말이지 네이버의 실제 말이 아니다 — 맞는지는 견본으로만 안다.
- ③-A3 가 미룬 `N일 뒤` 오독("3일 뒤" → 3일)을 함께 고친다(같은 함수다).

### 4.2 처음 온 손님

- 초안 응답에 **글에서 읽은 연락처**(`contact: {name|null, phone|null}`)를 싣는다. 이름은 이름표 줄(`예약자`류)에서만, 번호는 전체 번호 하나만 읽는다. 카카오톡 글에서도 전체 번호가 있으면 번호는 실린다.
- 후보가 없으면 초안 화면의 [고객 찾기] → 새 고객 등록 ①(번호)·②(보호자 이름)에 미리 채운다. 사람이 고칠 수 있다. 반려동물 정보는 채우지 않는다(네이버 글에 있는지 모른다).
- 이 값은 요청으로 온 글에서 나온 것이라 새로 드러나는 정보가 아니다. 그래도 로그·오류 응답에 싣지 않는다.

### 4.3 같은 예약을 두 번 넣지 않기

- **넣기 전에 알린다.** 후보가 한 가족으로 좁혀지고 날짜를 읽었으면, 응답에 그 가족의 **그 날 살아 있는 예약**(`same_day_visits: [{visit_id, starts_at, pet_names}]`)을 싣는다. 초안 화면이 날짜 줄 아래에 `이 날 예약이 이미 있어요 · 14:00 콩이` 를 보이고, 누르면 그 방문 상세로 간다. [예약 이어서]는 그대로 눌린다(막지 않는다 — 하루에 두 번 올 수도 있다).
- **넣을 때 막는다.** 같은 아이·같은 시각이면 지금의 409 `VISIT_DUPLICATE` 가 막는다. 고치지 않는다.
- **예약 번호로 막기는 견본 뒤다.** 번호의 꼴을 알아야 읽는다. 그때 `visits` 에 바깥 예약 번호 칸을 더하고 매장 안에서 유일하게 한다.

### 4.4 취소·변경 알림

네이버 글로 보이고 `취소` 가 들어 있으면(견본 뒤에는 `변경`도) 응답에 `notice: "cancel"` 을 싣는다. 초안 화면 맨 위에 `취소 알림 같아요. 아래 예약을 확인해 주세요` 와 4.3 의 그 날 예약을 보인다. 앱은 아무것도 스스로 취소하지 않는다. 날짜를 못 읽었거나 후보가 없으면 안내 글만 보인다.

### 4.5 들어온 창구를 남긴다

- 방문에 **창구**(`channel`) 한 칸. 값은 `naver` 하나뿐이고 나머지는 비어 있다(카카오톡·전화·직접은 가르지 않는다 — 사람이 고르게 하면 입력이 는다).
- 초안이 네이버 글이었으면 예약 폼이 저장할 때 `channel: "naver"` 를 함께 보낸다. 초안 화면에 `네이버 예약` 한 줄이 보이고 [아니에요]로 뗄 수 있다(글에 "네이버 예약"이라는 말만 있었던 경우).
- 보이는 곳은 **방문 상세 한 곳**: `네이버 예약으로 들어왔어요`. 그 방문을 수정·옮기기·취소·노쇼로 바꾸면 끝난 뒤 `네이버 예약에서도 바꿔 주세요` 를 스낵바로 한 번 보인다(연동이 없으니 사람이 해야 한다 — 이 한 줄이 이 칸의 쓸모다).
- 달력 칸·하루 목록의 표식은 ⑬(달력 칸 상태 표시)이 정한다. 여기서는 넣지 않는다.
- 공개 알림장·보호자 웹·알림톡에 싣지 않는다.

### 4.6 화면에서 바뀌는 것

1. 예약 ① 위의 [카톡 붙여넣기] → **[글 붙여넣기]**(카카오톡만이 아니게 됐다. 최종 문구는 구현에서).
2. 초안 화면: `네이버 예약` 줄(4.5), 그 날 예약 줄(4.3), 취소 안내(4.4). 나머지는 그대로다.
3. 새 고객 등록: 미리 채운 번호·이름(4.2).
4. 방문 상세: 창구 한 줄(4.5).
5. 공유 받기는 바꾸지 않는다 — 네이버 톡톡·문자 앱의 [공유]가 글을 넘기면 지금 경로로 온다. 스마트플레이스 앱이 글을 넘기는지 주소를 넘기는지는 **실기기에서 본다**(주소만 넘기면 붙여넣기를 쓴다).

## 5. 어떻게 — 정해 둔 것

### 5.1 백엔드

- 해석은 지금 자리 `visit/domain/services/draft_parser.py` 에 더한다. `DraftParse` 에 `source`(`naver`|없음), `notice`(`cancel`|없음), `contact_name`, `contact_phone` 을 더한다. 순수 함수이고 표 기반 테스트로 검증한다. `VisitDraftParserPort` 의 모양이 따라 바뀐다.
- `ParseVisitDraftInteractor` 가 후보가 하나이고 날짜가 있으면 visit 저장소에서 그 가족의 그 날 살아 있는 방문을 읽는다(읽기 한 번, 잠금 없음).
- 응답 `VisitDraftSchema` 에 `source`, `notice`, `contact`, `same_day_visits` 를 더한다. 옛 앱은 모르는 칸을 버린다. `guessed` 는 그대로다(네이버 글이면 `date`·`time` 이 늘 true).
- `visits.channel varchar(16) null`(CHECK `channel = 'naver'`). 등록 요청에 `channel` 선택 칸, 상세 응답에 `channel`. 방문 수정으로는 바꾸지 않는다. 마이그레이션 번호는 계획에서(다른 묶음과 겹치지 않게).
- 글·낱말·읽은 이름·번호를 로그·DB·오류 응답에 남기지 않는다(V9 그대로). 새 로그를 더하지 않는다.
- 권한은 그대로 `reservation:write`. 검색되는 글에 닿지 않으므로 `SearchSourceChanged` 는 해당 없다(`channel` 은 검색 문서에 넣지 않는다).

### 5.2 앱

- `VisitDraft` 에 새 칸, `VisitPrefill` 에 `channel` 과 `contact`. 서버의 `source`·`notice` 문자열은 `fromJson` 에서 enum 으로 한 번만 바꾸고 모르는 값은 없는 것으로 본다.
- 새 고객 등록에 미리 채우기는 `visit → customer` 방향이라 허용된다.
- 공유 확장·안드로이드 인텐트·채널은 손대지 않는다.

### 5.3 테스트와 검증

- 도메인 단위(표 기반): 새 날짜 꼴, 이름표 줄이 본문을 앞서는 것, 네이버 글의 짐작 표시, `취소` 알림, 연락처 읽기, `N일 뒤`, **카카오톡 글의 기존 표가 그대로 통과**하는 것.
- 통합: 그 날 예약이 다른 매장 것을 싣지 않는다, 익명화한 고객의 예약은 싣지 않는다, `channel` 저장·읽기, 응답과 로그에 글이 없다.
- 앱: 초안 화면의 세 줄, 미리 채운 등록 폼, 상세의 창구 줄과 스낵바. 골든은 초안 화면 하나.
- 흐름 스크립트 `check_visit_flow.sh` 에 판정 몇 줄(네이버 꼴 글 → `source`·짐작 → 등록 → 상세의 `channel`).
- **실기기**: 네이버 톡톡·문자·스마트플레이스 앱에서 공유했을 때 무엇이 넘어오는지.

### 5.4 정식 연동을 하려면 먼저 확인할 것 (이번에 하지 않음)

네이버가 예약 정보를 바깥 프로그램에 주는 길(제휴 CRM 연결)이 있다는 것만 안다(2026-05 스마트플레이스가 일부 CRM 을 연결했다는 기사 — 검색 요약). 아래는 **모른다**: 신청 자격(사업자·법인·규모), 비용, 심사 기간, 받는 정보의 범위(번호가 안심번호인지), 반려동물 업종의 칸, 매장마다의 동의 절차. 공식 문서와 제휴 창구로 확인한 뒤 따로 설계한다.

# 2부 — 전화 올 때 고객 표시 (콜아이디)

## 6. 목표와 하지 않는 것

**목표**

- 매장 고객의 번호로 전화가 오면 받기 전에 **`보호자 이름 · 아이 이름`** 이 보인다. **iOS 에서도 된다**(경쟁사가 4년째 못 준 것).
- 앱은 **통화를 보지도 듣지도 않는다.** 번호와 이름표의 목록을 기기에 미리 넣어 둘 뿐이다.
- 고객 번호 목록이 기기에 내려가는 일이므로, **켠 사람·켠 기기가 서버에 남고, 끄면 지워진다.**

**하지 않는 것**

| 항목 | 까닭 |
|---|---|
| 통화 녹음, 통화 내용 요약, 전화를 받는 콜봇 | 확정된 제외. |
| 통화 기록 읽기, 부재중 전화 목록, 통화 뒤 "예약 잡을까요" 띄우기 | 통화 기록 권한은 스토어의 제한 권한이다. 통화를 보지 않는다는 약속과 어긋난다. |
| 이름표에 주의 고객·노쇼 횟수·메모·지병 넣기 | 7.2. |
| 기기 주소록에 고객을 써 넣기 | 7.4 — 다른 앱이 읽는다. |
| 다른 앱 위에 뜨는 창(오버레이) | 7.4. |
| 모르는 번호의 스팸 판정·차단 | 다른 일이다. |
| 거는 전화에 표시 | 받는 전화만. |
| 매장 전화(유선)와의 연동 | 휴대전화로 받는 매장만 해당한다. |

**이렇게 되면 실패다**: 직원이 그만둔 뒤에도 그 사람 전화기에 고객 이름이 계속 뜬다 · 잠금 화면에 주의 사유가 뜬다 · 다른 매장의 고객이 뜬다 · 익명화한 고객의 이름이 계속 뜬다 · 고객 번호가 로그에 남는다 · 카카오톡 같은 다른 앱이 고객 번호를 읽어 간다.

## 7. 무엇을 만드나

### 7.1 켜고 끄기

- **기기마다, 기본은 꺼짐.** 설정에 `전화 올 때 고객 표시`. 켜면 무엇이 기기에 내려가는지 한 번 알린다(`이 전화기에 매장 고객의 번호와 이름이 저장돼요`).
- **한 기기에 한 매장.** 켠 순간 고른 매장의 고객만 내려간다. 다른 매장으로 화면을 바꿔도 목록은 그대로이고, 설정에 어느 매장 것인지 보인다. 두 매장 것을 섞지 않는다.
- **사장만 켠다(기본).** 사장이 매장 설정에서 `직원 전화기에도 허용`을 켜면 직원도 켤 수 있다. 직원의 개인 전화기에 고객 번호 전체가 내려가는 일이라 사장이 정한다(끝의 물을 것 2).
- 매장 설정에 **켜 둔 기기 목록**(멤버 이름·기기 종류·마지막으로 맞춘 때)과 기기마다 [끄기]. 사장만 본다.

### 7.2 이름표

- 꼴: **`{보호자 이름} · {아이 이름}`**. 아이가 둘이면 `콩이·두부`, 셋 이상이면 `콩이·두부 외 1`. 아이가 없으면 보호자 이름만. 무지개다리를 건넌 아이는 뺀다. 40자에서 자른다.
- **주의 고객 표시·노쇼 횟수·메모를 넣지 않는다.** 전화가 오는 화면은 잠금 화면에도 뜨고 옆 사람도 본다. 주의 사유는 사람에 대한 평가이고 매장 안에서만 보이게 돼 있다. 표시만(`주의`) 넣는 것도 하지 않는다 — 손님 앞에서 전화기가 울릴 수 있다. 전화를 받은 뒤 앱에서 본다.
- `phone` 과 `phone_alt` 둘 다 싣는다. 한 번호가 두 고객에 걸리면(`phone_alt` 는 유일하지 않다) `phone` 이 그 번호인 고객이 앞서고, 그래도 겹치면 고객 ID 가 작은 쪽이다.
- 익명화한 고객은 빠진다.

### 7.3 iOS

- **Call Directory Extension**(CallKit 의 `CXCallDirectoryProvider`). 앱이 번호 → 이름표 목록을 시스템에 넘겨 두면, 전화가 올 때 시스템이 번호 아래에 이름표를 보인다. 확장은 통화를 받지 않고 통화 때 실행되지도 않는다.
- 사용자가 **설정 앱에서 한 번 켜야 한다**(전화 → 차단 및 발신자 확인 쪽). 앱은 상태를 읽어 `설정에서 켜 주세요` 와 설정으로 가는 버튼을 보인다.
- 번호는 나라 번호를 붙인 정수(`010…` → `8210…`)로, **오름차순·겹침 없이** 넘긴다. 나라 번호는 82 로 고정한다(국내 번호만).
- 넘기는 길: 본체가 목록을 App Group 의 파일로 적고 확장을 다시 읽게 한다 → 확장이 시스템에 넘긴다 → **본체가 파일을 지운다.** 기기에 남는 것은 시스템이 쥔 목록뿐이다. 끄기·로그아웃은 빈 목록으로 다시 읽게 하는 것이다.
- **기기 주소록에 있는 번호는 주소록 이름이 뜬다**(시스템의 순서). 이름표 앞에 시스템이 앱 이름을 붙여 보인다.
- App Group 은 ③-A3 의 것(`group.com.chagocnote.app`)을 쓴다. 새 확장 타깃 하나가 는다. 과금 없음(개발자 계정은 이미 필요하다).
- **구현 전에 공식 문서로 다시 확인**: 설정 메뉴의 정확한 자리와 이름, 확장의 메모리 한도와 항목 수(수천 건이면 문제없을 것으로 보지만 수치는 확인하지 않았다), 바뀐 것만 넘기는 방식을 쓸지, 이름표가 보이는 꼴, 시뮬레이터에서 확인할 수 있는지(전화를 받을 수 없어 실기기가 필요하다고 본다).

### 7.4 안드로이드 — 방식 고르기

| 방식 | 필요한 것 | 위험 | 판단 |
|---|---|---|---|
| **통화 선별 역할**(`CallScreeningService`, Android 10+) | 사용자가 "발신자 확인 앱"으로 고른다. 전화가 오면 시스템이 번호를 서비스에 준다 | 역할은 한 앱만 가진다(다른 스팸 차단 앱을 쓰면 하나를 골라야 한다). 스토어 심사에서 용도를 설명해야 할 수 있다 | **고른다** |
| 전화 상태·통화 기록 권한으로 듣기 | `READ_PHONE_STATE` + `READ_CALL_LOG` | 통화 기록은 스토어의 제한 권한 — 기본 전화 앱이 아니면 신청·심사 대상이고 거절될 수 있다 | 버린다 |
| 다른 앱 위에 창 띄우기 | `SYSTEM_ALERT_WINDOW` | 권한 설명이 무겁고, 잠금 화면·제조사마다 다르게 군다 | 버린다 |
| 기기 주소록에 고객을 써 넣기 | `WRITE_CONTACTS` | **주소록을 읽는 다른 앱이 고객 번호를 가져간다**(카카오톡 친구 자동 추가 등). 구글 계정으로 올라갈 수 있다. 지우기가 불완전하다 | 버린다 |

- 고른 방식에서 표시는 **전화가 울리는 동안의 알림 하나**다(머리 위 알림). 오버레이를 쓰지 않는다. 알림 권한(Android 13+)이 필요하다. 전화가 끝나면 알림을 지운다.
- 알림을 누르면 그 고객의 반려동물 상세(아이가 없으면 고객)로 간다. iOS 에는 이 길이 없다.
- 목록은 **앱 전용 저장소**에 둔다. 번호는 설치마다 다른 소금을 친 해시로 적는다(평문 목록을 두지 않으려는 것 — 번호의 가짓수가 적어 완전한 보호는 아니라는 것을 적어 둔다). 이름표는 평문이다.
- 서비스는 전화마다 목록의 **받은 때**를 본다. 14일 넘게 못 맞춘 목록이면 아무것도 보이지 않는다(그만둔 직원의 기기가 앱을 열지 않아도 2주 뒤에는 멎는다).
- 통화를 막거나 거절하거나 기록하지 않는다 — 늘 "그대로 통과"로 답한다.
- **구현 전에 공식 문서로 다시 확인**: 역할을 받는 조건과 스토어 정책의 지금 문구, 제조사(삼성) 전화 앱에서 서비스가 불리는지, 알림이 전화 화면 위에 실제로 보이는지, 번호가 `+82` 꼴로 오는지. 에뮬레이터는 걸려 오는 전화를 흉내 낼 수 있어 흐름의 일부는 자동으로 본다.

### 7.5 맞추기(동기화)

- **통째로 다시 받는다.** 바뀐 것만 받는 방식은 두지 않는다 — 매장 하나의 고객은 수백에서 수천이고, 판(version)이 같으면 본문 없이 끝난다.
- 때: 켠 순간 · 앱이 앞으로 올 때 마지막으로 맞춘 지 6시간이 넘었으면 · 이 기기에서 고객·반려동물을 등록·수정·삭제·익명화한 직후. 다른 기기에서 바꾼 것은 다음에 앱을 열 때 온다(푸시가 없다).
- iOS 의 백그라운드 새로 고침은 **되면 좋은 것**으로만 둔다(시스템이 돌려 줄 때만 돈다 — 기대지 않는다).
- 서버가 "이 기기는 꺼졌다"고 답하면 앱이 목록을 지우고 설정을 끈다.

### 7.6 지우기 — 그리고 못 하는 것

| 때 | 하는 일 |
|---|---|
| 설정에서 끔 | 기기의 목록을 지우고 서버에 알린다 |
| 로그아웃, 세션이 끝남(갱신 실패) | 지운다 |
| 매장에서 나감·내보내짐, 탈퇴, 사장이 그 기기를 [끄기] | 서버가 다음 맞추기를 거절한다 → 앱이 지운다 |
| 고객 익명화 | 다음 맞추기에서 빠진다 |
| 앱 삭제 | 시스템이 확장·저장소와 함께 지운다 |

**못 하는 것을 적어 둔다.** 서버는 기기의 목록을 멀리서 지울 수 없다. 내보낸 직원이 앱을 다시 열지 않으면 — 안드로이드는 14일 뒤 멎지만, **iOS 는 시스템이 쥔 목록이 앱을 열거나 지울 때까지 남는다.** 그래서 직원 허용은 기본 꺼짐이고, 켜 둔 기기 목록을 사장에게 보인다. 기기를 잃어버렸을 때는 기기 잠금이 막는 것이 전부다(주소록과 같다).

## 8. 어떻게 — 정해 둔 것

### 8.1 백엔드

- **customer 스포크**에 둔다(번호와 이름은 customer 의 사실이다). 다른 스포크를 부르지 않는다.
- `GET /v1/shops/{id}/caller-directory` — 헤더 `X-Device-Id`(설치 때 만든 무작위 값). 응답 `{version, entries: [{phone, label, open_pet_id|null}]}`, `Cache-Control: no-store`. 요청의 `If-None-Match` 가 지금 판과 같으면 304. 판은 목록 내용의 해시다.
- `PUT /v1/shops/{id}/caller-directory/devices/{device_id}`(켜기, 본문 `{platform}`) · `DELETE` 같은 경로(끄기 — 본인 것 또는 사장) · `GET /v1/shops/{id}/caller-directory/devices`(사장).
- 새 표 `caller_directory_devices(shop_id, device_id, member_id, platform, enabled_at, last_synced_at, revoked_at)` — 켠 기기와 마지막으로 내려받은 때. 이것이 "누가 번호 전체를 가져갔는가"의 기록이다. 매장 설정에 `caller_directory_staff_allowed bool` 한 칸(어느 표에 둘지는 계획에서).
- **권한**: 새 권한 `customer:caller_directory` 를 사장에게 준다. 직원은 매장 설정이 켜져 있을 때 통과한다(가드에서 볼지 유스케이스에서 볼지는 계획에서 — 지금 가드의 모양을 따른다). 목록 읽기는 **등록된, 꺼지지 않은 기기**만 된다(403 이면 앱이 지운다).
- 매장 범위 저장소 메서드는 `ShopContext` 가 첫 인자다. 목록은 그 매장의 살아 있는 고객뿐이다.
- 로그는 `shop_id`·`member_id`·건수·결과뿐이다. **번호·이름표·기기 ID 를 로그·오류 메시지에 남기지 않는다.** 응답 본문을 접근 로그에 찍지 않는다.
- 매장에서 나가거나 탈퇴하면 그 멤버의 기기 행을 그 트랜잭션에서 끈다(잠금 순서는 지금 그대로 — 멤버 행 다음. 정확한 자리는 계획에서 tenancy·auth 의 흐름을 읽고 정한다. 스포크끼리 import 하지 않으므로 허브 포트나 이벤트로 잇는다).
- 로그인 없는 경로·보호자 경로·공개 스키마는 건드리지 않는다. 허용 목록 테스트가 그대로 통과해야 한다.

### 8.2 앱

- 네이티브는 **직접 쓴다**(③-A3 와 같은 판단 — 패키지에 기대지 않는다). 채널 `com.chagocnote.app/caller_directory`: `status`(꺼짐·설정 필요·켜짐), `apply(entries)`, `clear`, `openSettings`.
- iOS: 새 타깃 `CallDirectoryExtension`, 본체 쪽 플러그인은 `AppDelegate.swift` 의 기존 플러그인 옆. 안드로이드: `CallScreeningService` 하나와 알림 채널 하나.
- Dart: 이름표 만들기·번호 바꾸기(`010…` → `8210…`)·정렬·겹침 없애기는 순수 함수. 번호 바꾸기와 이름표는 **서버가 만들어 내려도 된다** — 한쪽에만 둔다(계획에서 서버 쪽으로 정하는 것을 권한다. 두 플랫폼이 같은 것을 쓴다).
- 켜고 끄는 화면은 설정 안의 한 화면. 로그아웃·세션 종료의 지우기는 세션 컨트롤러의 로그아웃 경로에 건다.
- 내려받은 목록을 Dart 메모리나 로그에 남기지 않는다. `print` 금지는 지금 그대로다.

### 8.3 테스트와 검증

- 백엔드 통합: 첫 테스트는 **다른 매장의 고객이 목록에 없다**. 익명화한 고객이 없다, 무지개다리 아이가 이름표에 없다, 번호 겹침의 앞섬, 직원 허용 꺼짐이면 403, 꺼진 기기는 403, 304, 나감·탈퇴가 기기를 끈다, 로그에 번호가 없다.
- 앱 단위: 이름표·번호 바꾸기·정렬, 맞추기의 때(6시간·쓰기 직후), 403 에 지우기, 로그아웃에 지우기.
- **자동으로 못 보는 것**: 실제로 전화가 올 때 뜨는지. iOS 는 실기기 두 대(거는 쪽·받는 쪽)가 필요하다. 안드로이드는 에뮬레이터의 전화 흉내로 한 번, 실기기(삼성)로 한 번.
- 실기기 확인 표: 잠금 화면에서의 모습 · 주소록에 있는 번호 · 끈 뒤 사라지는지 · 로그아웃 뒤 사라지는지 · 고객 2,000명에서 넘기는 시간.

## 9. 언제 만드나 — 조건

2부는 **아래 가운데 하나가 참일 때** 계획을 쓴다. 그 전에는 설계만 둔다.

- 입점 매장(또는 입점을 의논하는 매장)이 전화로 예약을 받는다고 말한다.
- 첫 매장 사장님이 필요하다고 말한다.
- 스토어에 올린 뒤 같은 요청이 들어온다.

만들 때의 걸림돌을 미리 적는다 — 실기기가 있어야 검증된다(지금까지 미룬 실기기 확인이 먼저다), 스토어 심사에서 용도 설명이 필요할 수 있다, iOS 는 사용자가 설정에서 켜는 한 단계가 있다.

## 10. 나누기

- **⑯-1 네이버 예약 글 받기** — 백엔드(해석기·응답·`channel`)와 앱(초안 화면·등록 미리 채우기·상세)을 한 계획으로. 작다. 견본이 오면 4.1 의 오른쪽 칸을 같은 계획 안의 후속 작업으로 더한다.
- **⑯-2 콜아이디 백엔드** — 목록·기기·권한·끄기. 9절의 조건 뒤.
- **⑯-3 콜아이디 앱** — iOS 확장 → 안드로이드 서비스 → 설정 화면 → 실기기 확인. 9절의 조건 뒤.

## 11. 위험과 막는 법

| | 위험 | 막는 법 |
|---|---|---|
| N1 | 지어낸 네이버 형식 규칙이 틀린 날짜를 확신으로 보인다 | 견본 전에는 네이버 글의 날짜·시각을 늘 "짐작"으로 표시한다. 형식 규칙은 견본으로만 더한다. |
| N2 | 취소 알림이 새 예약이 된다 | `notice` 와 그 날 예약 보이기. 저장은 여전히 사람이 한다. |
| N3 | 기존 카카오톡 해석이 깨진다 | 기존 표 기반 테스트를 그대로 두고 통과시킨다. 이름표 줄은 사전에 있는 이름표만 읽는다. |
| N4 | 글·번호·이름이 로그에 남는다 | 새 로그 없음. 응답과 로그에 글이 없다는 통합 테스트(V9 를 넓힌다). |
| N5 | 앱에서 바꾼 예약이 네이버에는 그대로다 | `channel` 과 바꾼 뒤의 한 줄 안내. 연동이 없다는 것을 숨기지 않는다. |
| C1 | 그만둔 직원의 기기에 고객 이름이 남는다 | 직원 허용 기본 꺼짐, 기기 목록과 [끄기], 나감·탈퇴가 기기를 끔, 안드로이드 14일 기한. iOS 의 남는 구간은 7.6 에 적은 한계다. |
| C2 | 다른 앱이 고객 번호를 읽는다 | 주소록에 쓰지 않는다. iOS 는 시스템 목록, 안드로이드는 앱 전용 저장소. |
| C3 | 잠금 화면에 평가가 뜬다 | 이름표는 이름뿐이다. 주의·노쇼·메모를 넣지 않는다(응답 칸을 테스트가 고정). |
| C4 | 다른 매장의 고객이 뜬다 | 한 기기 한 매장, 매장 범위 저장소, 첫 통합 테스트. |
| C5 | 번호 전체를 내려받는 경로가 남용된다 | 사장 권한, 등록된 기기만, 기기 표에 기록, `no-store`. ⑮의 기록 내보내기와 같은 무게의 일이다 — 권한의 결을 맞춘다. |
| C6 | 스토어 심사에서 걸린다 | 제한 권한(통화 기록·오버레이·주소록 쓰기)을 쓰지 않는다. 구현 전에 정책을 다시 읽는다. |

## 12. 만드는 사람에게 맡기는 것

- 문구의 마지막 다듬기, 초안 화면 새 줄들의 자리와 여백, 설정 화면의 모양(기존 설정 화면을 따른다).
- 응답 칸의 정확한 이름, 이름표 사전의 낱말(견본이 오면 바꾼다), 판(version)의 계산법.
- 폴더 이름은 작명 규칙을 따른다(실제 그 패턴일 때만 패턴 이름).
- 결정 기록: 1부는 `_docs/decisions/006-visit-reservation.md` 에 절을 더하고, 2부는 만들 때 새 번호로 쓴다.

## 13. 사용자에게 물을 것

1. **첫 매장이 네이버 예약을 쓰나요? 쓴다면 실제로 받은 예약 알림 글 두세 개(이름·번호는 가리고)를 주실 수 있나요?** 견본이 있으면 4.1 의 오른쪽 칸까지 한 번에 만들고, 없으면 왼쪽 칸만 만듭니다. 네이버 예약을 쓰지 않는다면 ⑯-1 도 뒤로 미루는 편이 맞습니다.
2. **직원의 개인 전화기에도 고객 번호 목록을 내려도 되나요?** 설계는 "사장만, 사장이 켜면 직원도"입니다. 아예 사장만으로 못 박으면 설정 한 칸과 기기 목록이 단순해집니다.
3. **콜아이디는 9절의 조건이 찰 때까지 계획을 쓰지 않아도 되나요?** 지금 바로 만들기를 원하시면 실기기 두 대(아이폰·안드로이드)로 확인하는 일이 먼저 필요합니다.

# ⑬ 아이별 미용 주기·재방문 안내와 달력의 상태 표시 — 설계

2026-11-16. 경쟁 조사(`.superpowers/research/reports/펫미용 앱 경쟁 기능 비교.md`)의 3순위(반려동물 단위 미용 주기와 재방문 안내)와 6순위(달력의 상태 표시)를 한 묶음으로 만든다. 둘 다 "이미 있는 사실을 예약·달력 앞에 모아 보이는" 일이고, 새 입력을 거의 받지 않는다.

여섯 묶음(⑪~⑯)이 함께 따르는 기준은 `2026-11-16-next-designs-common.md`(아래 "공통")에 있다. 어긋나면 공통이 앞선다. **이 문서는 공통 5절(하루 마무리)·7절(줄·칸의 상태 표시)·8절(화면의 자리)의 정본이다.**

**아래의 규칙·기준값·문구·화면 자리는 모두 내가 정한 것이다.** 기준값은 기본값일 뿐이고 매장이 바꿀 수 있다(3.7). 사용자가 답해야 하는 것은 10절에 따로 적었다.

- 범위: 백엔드(`visit` 의 주기 계산·목록·달력과 하루 응답·매장 설정 칸, `customer` 의 칸 둘, 허브 포트·이벤트의 칸, `notification` 의 주 수 규칙), 앱(`features/visit` 의 목록 화면·달력·하루 줄·하루 마무리, `features/customer` 의 반려동물 상세 한 줄). 웹은 바꾸지 않는다.
- 바탕: ③ 예약 설계(다음 예약 제안), ⑧ 매출 설계 3.3(다시 올 때가 지난 아이), ⑥ 알림톡 설계(`next_visit` 종류), ③-B 설계(확인할 것·`care_facts`).
- 과금: 없다. 자동 발송은 알림톡 실발송이라 "나중"이고, 이번에 바꾸는 것은 가짜 게이트웨이 위에서 도는 줄 만들기 규칙뿐이다.
- 번호: 마이그레이션은 계획 때 head 다음 번호(⑪·⑫ 뒤라 0020 쯤), 결정 기록은 `016`(공통 11절).

## 1. 왜

**주기.** 지금 앱은 "언제 다시 오는 아이인가"를 세 군데에서 서로 다르게 센다.

| 곳 | 지금 규칙 | 코드 |
|---|---|---|
| 완료 뒤 '다음 예약' 초안 | 최근 두 완료 방문의 간격(주, 1~12), 한 번뿐이면 4주 | `visit/domain/services/visit_cycle.py` |
| 알림톡 '다음 예약 제안' | 매장 알림 설정의 고정 주 수(`next_visit_after_weeks`), 없으면 직전 완료와의 간격, 없으면 4주 | `notification/app/use_cases/handle_visit_event_interactor.py` |
| 다시 올 때가 지난 아이 | 모든 아이에게 8주(56일) 고정 | `visit/adapter/outbound/pg/sales_pg_repository.py` |

4주마다 오는 아이는 5주째에 이미 늦었는데 8주가 될 때까지 목록에 없고, 12주마다 오는 고양이는 9주째에 "지난 아이"로 잘못 나온다. 직전 간격 하나만 보는 규칙은 한 번 늦게 온 것으로 주기가 흔들린다. 경쟁사는 더 거칠다 — 그루머노트는 15·30·60·90일 넷 가운데 고르고, MoeGo 는 **고객 단위**로 4주를 기본값으로 둔다(여러 마리 집에서 맞지 않는다는 것은 조사의 추론이고 그런 불만 리뷰는 찾지 못했다).

또 지금 목록은 `sales:read`(사장만) 뒤에 있고 누르면 반려동물 상세로 갈 뿐이다. 연락도 예약도 거기서 못 한다(⑧ 이 미뤄 둔 것).

**달력.** 그루머노트 리뷰에 "결제완료된 예약건은 색이 바뀌었음 좋겟어요"(답 없음), 반짝 개편 뒤 리뷰에 "일정이 한눈에 안 보인다"가 있다(앱스토어 리뷰 몇 건이 근거의 전부다 — 얼마나 흔한 불만인지는 모른다). 지금 하루 줄에는 `확인 N`·`겹침`·`정리 필요`·`알림장 보냄` 이 있고 **돈을 적었는지는 없다.** 달력 칸에는 사진·마릿수와 정리 안 된 예약의 수(작은 검정 숫자, `calendar_tab.dart` 의 `unresolvedCount`)뿐이다. 그리고 하루의 남은 일을 끝내려면 방문을 하나씩 찾아 들어가야 한다.

## 2. 목표와 하지 않는 것

**목표**

- 주기를 **아이마다 하나**, 한 곳에서 계산하고 세 군데(다음 예약 초안·알림 줄·목록)가 같은 값을 쓴다.
- 사장이 고르지 않아도 된다. 지난 방문에서 계산해 보이고, 틀리면 고친다. 계산한 값인지 직접 정한 값인지 어림인지 늘 가려 보인다.
- 완료할 때 **다음 예약의 날짜·시간이 채워져 있다**(주기와 지난번 시간). 빈칸이 없다.
- 다시 올 때가 **다가온** 아이와 **지난** 아이를 한 목록에서 나눠 보이고, **안내 글이 써진 채** 올라와 그 자리에서 예약을 잡거나 카카오톡으로 보낸다(0원).
- 하루 줄과 달력에서 **남은 일**(돈을 안 적었다, 알림장을 안 보냈다, 정리가 안 됐다)과 **끝낸 일**(결제 완료, 알림장 보냄)을 상세에 들어가지 않고 안다.
- 그날의 남은 일을 **한 화면에서 차례로 넘기며** 끝낸다(하루 마무리).
- 사진 중심 달력을 흐리지 않는다.

**하지 않는 것**

| 항목 | 까닭 |
|---|---|
| 알림톡 실발송, 발송 미리 보기(MoeGo 의 "앞으로 30일") | 과금. 줄을 만드는 규칙만 맞춘다. |
| 견종별 기본 주기 | 믿을 견종별 수치가 없다. 매장의 기본 간격 하나와 아이별 값으로 한다(3.7). |
| 계산한 주기를 "권장 주기"로 보호자에게 보이기 | 지난 간격일 뿐 권고가 아니다. 보호자 웹·알림장에 싣지 않는다. |
| "이 아이는 안내하지 않기" 표시 | 1년이 지나면 목록에서 빠진다. 필요하다는 말이 나오면. |
| 안내를 보냈는지 확인 | 공유 시트는 보냈는지 알려 주지 않는다. 시트를 연 날만 적는다. |
| 달력 칸에 금액·색 딱지·아이콘 줄 | 직원은 매출을 못 본다 / 무채색 톤 / 사진이 주인이다. |
| 정기권 차감(⑭)·예약금 받음(⑮)을 **언제** 싣는가 | 각 묶음이 정한다. 코드와 낱말·순서는 여기서 굳힌다(4.4). |
| 반복 예약 | ⑭. 이 묶음의 주기 값을 읽어 쓴다(공통 11절). |

**이렇게 되면 실패다**: 계산한 숫자가 사실처럼 보인다(방문 두 번으로 "보통 6주마다") · 앞으로 예약이 잡힌 아이가 목록에 나온다 · 다음 예약 초안의 날짜가 비어 있다 · 달력 칸이 표시로 덮여 사진이 안 보인다 · 직원의 화면에 금액이 나온다 · 세 군데의 주기가 여전히 다르다 · 정기권으로 다 낸 방문이 "결제 안 적음"에 남는다.

## 3. 무엇을 만드나

### 3.1 미용 주기 — 계산

아이 한 마리의 주기는 아래 순서로 정한다. 보호자만의 방문에는 주기가 없다.

1. **직접 정한 값**이 있으면 그것(1~52주). 출처 `manual`.
2. 없으면 **계산한 값**: 그 아이의 완료 방문(시작 시각, 매장 시간대의 날짜) 가운데 **최근 6번**(매장이 3~12번으로 바꾼다 — 3.7)을 보고, 이웃한 방문 사이의 날 수(최대 5개) 가운데 **7일 미만인 것을 버린 뒤**(부분 손질·다시 손보기, 매장이 0~28일로 바꾼다 — 0 이면 버리지 않는다), **중앙값**을 주로 반올림해 1~52주로 자른다. 2년(730일)보다 오래된 방문은 보지 않는다. **간격이 둘 이상일 때만** 계산한 값이다. 출처 `computed`.
3. 간격이 하나뿐이거나 없으면 **주기를 모른다.** 날짜가 필요한 곳(다음 예약 초안·목록·알림 줄)은 **매장의 기본 간격**(3.7, 처음 값 4주)을 쓰고 **어림**이라고 표시한다. 출처 `single`(간격 하나) 또는 `none`.

**간격 하나의 지위**: 한 번의 간격은 주기가 아니다. `single` 의 지난 간격은 **글로만** 보이고(`지난번에는 6주 만에 왔어요`), 다음 올 때·'곧·지남' 묶음·알림 줄의 주 수에는 쓰지 않는다. 2주 간격으로 두 번 온 아이가 15일째에 '지남'이 되는 일을 막는다.

| 출처 | 반려동물 상세의 말 | 날짜에 쓰는 값 |
|---|---|---|
| `manual` | `6주마다 와요 · 직접 정함` | 직접 정한 값 |
| `computed` | `보통 6주마다 와요 · 지난 방문에서 계산` | 계산한 값 |
| `single` | `지난번에는 6주 만에 왔어요` + `다음은 매장 기본 간격(4주)으로 어림해요` | 매장의 기본 간격(어림) |
| `none` | `아직 한 번 왔어요` + `다음은 매장 기본 간격(4주)으로 어림해요` | 매장의 기본 간격(어림) |

- **다음 올 때**: 마지막 완료 방문의 날 + 날짜에 쓰는 값. 화면에는 `다음은 12월 3일쯤` — 늘 "쯤"을 붙이고, 어림이면 `12월 3일쯤(어림)`. 완료 방문이 없는 아이에게는 없다.
- 중앙값을 쓰는 까닭: 한 번 늦게 온 것(여행·병)에 흔들리지 않는다. 짝수 개면 가운데 둘의 평균.
- 계산은 **읽을 때** 한다. 저장하지 않는다(방문을 고치거나 되돌리면 저절로 맞는다).
- 지금의 `visit_cycle.interval_weeks`(직전 간격, 1~12주, 기본 4주)는 이 규칙으로 바꾼다. 범위를 1~52주로 넓히는 것은 알림 쪽(`NEXT_VISIT_WEEKS_MIN/MAX = 1, 52`)과 맞추기 위해서다. ⑭ 의 반복 간격은 이 값을 1~12 로 잘라 기본값으로 쓴다(공통 11절).

### 3.2 직접 정하기

- 반려동물 상세 정보 탭의 **주기 줄**(자리는 공통 8절: 동의 줄 아래)을 누르면 시트: 지금 값과 출처 한 줄, 주 수(1~52, 한 주씩 올리고 내리기), 아래에 `이렇게 정하면 다음은 12월 3일쯤이에요`(바꾸는 대로 따라 바뀐다), [저장], 직접 정한 값이 있으면 [계산한 값으로 돌아가기].
- 주기 줄은 완료 방문이 한 번이라도 있는 아이에게 늘 있다. 완료 방문이 없는 아이에게는 `미용 주기 정하기` 한 줄이 대신 있다.
- 같은 시트를 완료 시트의 다음 예약 줄(3.4)과 목록의 줄(3.3)에서도 연다 — 쓰는 자리에서 바꾼다.
- 사장·직원 모두(`customer:write`). 누가 정했는지는 남기지 않는다(판단이 아니라 숫자다).

### 3.3 다시 올 때가 된 아이 — 목록

⑧ 의 "다시 올 때가 지난 아이"를 넓힌다.

| 묶음 | 조건 |
|---|---|
| **곧** | 출처가 `manual`·`computed` 이고, 다음 올 때가 오늘부터 **7일 안**(오늘 포함, 날 수는 바꿀 수 있다 — 3.7)이다 |
| **지남** | 다음 올 때가 어제 이전이다. 출처가 `single`·`none` 인 아이는 매장의 기본 간격으로 어림한 날이 지났을 때 |

- 어림인 아이(`single`·`none`)는 '곧'에 넣지 않는다 — 모르는 주기로 "곧 올 아이"라고 말하지 않는다. '지남'에는 넣는다("처음 오고 안 온 손님"을 놓치지 않는다).
- 공통 조건은 ⑧ 그대로다: 마지막 완료 방문이 1년을 넘지 않았다 · 앞으로 잡힌 예약이 없다(오늘 0시 이후의 `reserved` 와 미용 중) · 무지개다리를 건너지 않았다 · 익명화되지 않았다. 지금 거르기는 `visit/app/services/due_pets.py` 에 있다 — `showable_pets`(이 매장에 있고 이름이 있는 아이, 곧 익명화되지 않은 아이)를 거친 뒤 `passed_away` 를 뺀다. 이 둘을 그대로 쓴다.
- **8주 고정을 주기로 바꾼다.** 고정값은 자주 오는 아이를 늦게, 드물게 오는 아이를 일찍 띄운다. **매출 탭의 "다시 올 때가 지난 아이 N마리"는 '지남'의 수가 되고 값이 달라진다**(같은 함수를 쓴다). 주기를 모르는 아이의 기준은 8주 고정에서 매장의 기본 간격(처음 값 4주)으로 바뀐다 — 다음 예약 초안이 "4주 뒤"로 잡는 아이를 8주까지 기다리지 않는다.
- 줄: 사진·이름·`6주마다 · 5일 지남`(곧이면 `3일 뒤쯤`, 어림이면 `5주 전에 왔어요 · 어림`)·안내한 적이 있으면 `11월 10일에 안내`. '지남'은 오래 지난 순, '곧'은 가까운 순.
- 줄을 누르면 반려동물 상세(지금 그대로). 줄 끝에 둘:
  - **[예약]** — 예약 등록 화면이 보호자·아이·메뉴·소요 시간·**날짜·시간**까지 채워져 열린다(마지막 완료 방문의 '다음 예약' 초안을 쓴다 — 3.4). 초안의 날이 지났으면 오늘 이후의 가장 가까운 같은 요일로 옮기고, 시간은 지난번 시작 시각 그대로다. 누르기 둘(줄의 [예약] → [예약 잡기])로 끝난다.
  - **[안내]** — 안내 글이 **이미 써진** 미리 보기 시트가 열린다. [보내기] 한 번으로 공유 시트에 넘긴다. 시트를 열면 그 아이에 **안내한 날**(오늘)을 적는다.
- **안내 글**: 매장의 템플릿(3.7)에 아이 이름·지난 주 수·매장 이름을 넣어 만든다. 처음 값(주기를 권고처럼 쓰지 않고 지난 사실만):

```
안녕하세요, {매장}예요.
{아이}가 미용한 지 {주}주가 됐어요.
편하신 날 알려 주시면 예약 잡아 드릴게요.
```

- 미리 보기 시트에서 글을 **이번만 고쳐** 보낼 수 있다. 시트 아래의 `안내 글 템플릿 바꾸기` 로 매장의 기본 글을 바꾼다(3.7). 매장 이름이 비어 있으면 보내기 전에 그 칸만 묻는다(빈칸을 내보내지 않는다 — 공통 1절).
- 안내한 날은 **마지막 완료 방문보다 뒤일 때만** 보인다(다녀가면 저절로 사라진다). 목록에서 빼지는 않는다.
- **사장·직원 모두 본다.** 돈이 없는 목록이고 손님에게 연락하는 사람이 직원일 수 있다. 경로를 `/sales/…` 밖으로 옮긴다(5.2).
- 들어가는 곳: 캘린더 탭의 "정리 안 된 예약" 알림 줄(지금 `calendar_tab.dart` 의 `unresolvedBanner`) 아래에 `다시 올 때가 된 아이 7 ›`(곧 + 지남, 0 이면 없다), 매출 탭의 기존 줄(사장 — 자리는 공통 8절).

### 3.4 다음 예약 초안과 알림 줄

- **초안**(`GET …/visits/{id}/next-draft`)은 3.1 의 "날짜에 쓰는 값"을 쓴다. **날짜와 시간이 늘 채워져 있다** — 날짜는 완료한 날 + 주기(같은 요일), 시간은 이번 방문의 시작 시각, 메뉴·소요 시간은 지금처럼. 응답에 `cycle_weeks`·`cycle_source` 를 싣고, 완료 시트의 다음 예약 줄은 출처를 말한다:
  - `computed`: `6주 뒤 12월 3일(수) 오후 2시 · 보통 오는 간격`
  - `manual`: `6주 뒤 12월 3일(수) 오후 2시 · 직접 정한 간격`
  - `single`·`none`: `4주 뒤 12월 3일(수) 오후 2시 · 매장 기본 간격(어림)`
- 줄을 누르면 날짜·시간을 고친다(지금 그대로). 줄 옆의 `간격 바꾸기` 는 3.2 의 시트(그 아이의 값) 또는 매장의 기본 간격(3.7)을 연다. [다음 예약 잡기]까지 누르기 하나다(완료 시트가 이미 떠 있다).
- **알림 줄**(`next_visit`, 기본 꺼짐): 보낼 주 수의 순서를 `아이에게 직접 정한 값 → 매장 알림 설정의 고정 주 수 → 계산한 값(간격 둘 이상) → 매장의 기본 간격` 으로 바꾼다. 지금은 `알림 설정 → 직전 간격 → 4주` 다. 아이의 값이 매장의 고정 주 수보다 앞선다(아이를 보고 정한 값이 더 구체적이다). `single` 의 간격은 쓰지 않는다.
  - 허브 이벤트 `VisitClosed` 에 칸 둘(`cycle_weeks: int | None = None`, `cycle_source: str = "none"`)을 더하고 `previous_completed_at` 은 남긴다. 새 칸은 기본값을 갖고 `family_pet_ids` **앞**에 둔다(공통 11절).
  - **가족 묶음**: 묶음의 제안은 한 통이다(`_create_for_group`). 주 수는 묶음의 아이들 가운데 **짧은 쪽**이다 — 둘째 방문의 완료가 묶음의 줄에 합쳐질 때 더 짧으면 줄의 보낼 때와 `interval_weeks` 변수를 당긴다.
  - **대기 줄에 굳는 값**: 주 수는 완료 때 줄에 굳는다. 그 뒤에 아이의 주기를 고쳐도 이미 대기 중인 줄은 그대로다(다음 완료부터 새 값). **받아들인 한계**로 적는다 — customer 가 notification 에 알리는 새 이벤트를 만들지 않는다.
  - 문안(`#{간격}주 정도마다 미용하면 좋아요`)은 심사받은 템플릿이라 건드리지 않는다. 실발송은 나중이다.
- **앞날 예약이 있으면 보내지 않는 것**은 지금 구조가 한다. 다만 막는 곳은 완료 때가 아니라 **보낼 때**다 — 디스패처가 `VisitLedgerPort.customer_has_upcoming` 을 보고 대기 줄을 취소한다(`notification/app/services/dispatcher.py`, 사유 `has_upcoming`). **아이 단위가 아니라 고객 단위**다: 형제에게 앞날 예약이 있으면 이 아이의 제안도 가지 않는다. 받아들인다(한 보호자에게 가는 글이다). `VisitReserved` 처리는 되살린 예약일 때만 대기 줄을 거둔다.

### 3.5 하루 줄·피드·방문 상세의 상태

원칙(공통 7절의 정본) — **남은 일은 숫자로 모아 위에, 끝낸 일은 낱말로 줄에.** 색·아이콘을 더하지 않는다(지금의 작은 글자 표시 그대로).

| 표시 | 뜨는 조건 | 어디 |
|---|---|---|
| `결제 완료` (새로) | 완료 방문이 `paid` 다(아래) | 하루 줄, 피드, 방문 상세의 이름 카드 |
| `알림장 보냄` | 지금 그대로 | 지금 그대로 |
| `정기권` · `예약금 받음` | ⑭·⑮ 가 채운다(4.4) | 하루 줄, 피드, 방문 상세의 이름 카드 |
| `확인 N`·`겹침`·`정리 필요` | 지금 그대로 | 지금 그대로 |

- **`paid` 의 정의**(공통 6절): 기록에 총액이 있고, **(받을 나머지가 0 이거나 결제 수단이 있다)**. 나머지 = `총액 − 정기권 몫 − 예약금 몫`. ⑭·⑮ 가 오기 전에는 나머지가 총액과 같으므로 "총액과 결제 수단이 둘 다 있다"와 같다. 이 판정은 visit 도메인의 순수 함수 하나에 두고, 돈을 가르는 함수(⑭ 가 만든다)가 생기면 그 나머지를 받는다 — 정기권으로 다 낸 방문·예약금이 요금을 덮은 방문이 "결제 안 적음"에 남지 않는다.
- 줄의 표시 순서: `확인 N · 겹침 · 정리 필요 · 결제 완료 · 알림장 보냄 · 정기권 · 예약금 받음`. 남은 일이 앞, 끝낸 일이 뒤.
- 가족 묶음은 `알림장 보냄` 과 같은 규칙 — 완료한 방문이 **모두** 해당할 때만 뜬다.
- **하루 화면 머리의 요약**에 남은 일의 수를 더한다(0 이면 없다): `결제 안 적음 2` · `알림장 안 보냄 1` · (지금의) `정리 필요 1`. 누르면 **하루 마무리**(3.6)가 그 종류부터 열린다. 이것이 "결제된 것만 색이 바뀌면 좋겠다"에 대한 답이다 — 끝낸 줄에 낱말이 붙고, 안 끝낸 수가 위에 모인다.
  - `결제 안 적음` = 완료했고 `paid` 가 아닌 방문.
  - `알림장 안 보냄` = 완료했고 기록이 있는데 알림장을 보내지 않았고 `보내지 않음` 으로 넘기지도 않은 방문. 매장이 "알림장을 남은 일로 세지 않기"를 고르면(3.7) 세지 않는다.
  - `예약금 기다리는 중`(⑮)은 남은 일이라 이 요약에 숫자로 든다(⑮ 가 더한다). 줄의 낱말로는 두지 않는다.
- 총액만 있고 결제 수단이 없으며 나머지가 0 이 아닌 방문은 `결제 완료` 가 아니다. 매출에는 지금처럼 "미선택"으로 든다(⑧).
- **직원**: 이 표시는 "적었는지"의 참·거짓이고 금액이 아니다. 직원도 금액을 적는 사람이므로(`sales:write`) 그대로 보인다. **줄·칸·요약 어디에도 금액 숫자를 싣지 않는다** — 금액은 지금처럼 방문 상세의 기록과 매출 탭(사장)에만 있다.
- 창구(`channel`, ⑯)는 줄·칸에 표시하지 않는다. 방문 상세의 한 줄뿐이다.

### 3.6 하루 마무리

그날의 남은 일을 한 화면에 모아 **차례로 넘기며** 끝낸다(공통 5절의 정본). 방문을 하나씩 찾아 들어가지 않는다.

- **들어가는 곳**: 하루 화면 머리의 남은 일 숫자(3.5). 누른 종류부터 시작한다. 달력에서 고른 날의 카드에 남은 일이 있으면 카드의 `남은 일 3 ›` 로도 들어간다.
- **차례**: 정리 안 된 예약 → 결제 안 적음 → 알림장 안 보냄. 종류 안에서는 시작 시각 순. 위에 `3개 중 1번째` 와 넘김 점.
- **한 장**은 방문 하나(가족 묶음은 한 장)이고, 위에 사진·이름·시간·메뉴가 있어 어떤 아이인지 안다.

| 종류 | 그 장에서 하는 일 | 채워져 있는 것 |
|---|---|---|
| 정리 안 된 예약 | [완료] · [노쇼] · [취소] — 지금 방문 상세의 동작 그대로(완료는 기록 화면으로 이어진다) | — |
| 결제 안 적음 | 총액과 결제 수단을 적고 [저장] | 총액은 기록에 있으면 그 값, 없으면 메뉴 값의 합(지금 기록 화면의 채움 규칙). 결제 수단은 그 고객이 지난번에 쓴 수단. 둘 다 고칠 수 있다 |
| 알림장 안 보냄 | [미리 보고 보내기](지금의 보내기 흐름) · [보내지 않음] | — |

- 모든 장에 **[건너뛰기]**(아무것도 적지 않고 다음 장). 건너뛴 것은 남은 일에 그대로 남는다.
- **[보내지 않음]** 은 그 방문을 "알림장을 안 보내기로 했다"고 적는다(`visits.report_skipped_at`). 남은 일에서 빠지고 방문 상세에서 되돌릴 수 있다. 장 아래에 `알림장은 앞으로 남은 일로 세지 않기` 한 줄 — 누르면 매장 설정을 바꾼다(3.7, 쓰는 자리에서 바꾼다).
- 한 장을 끝내면 저절로 다음 장으로 넘어간다. 한 장을 끝내는 데 누르기 둘 이하다(결제: 수단 고르기 → [저장], 알림장: [미리 보고 보내기] → [보내기]).
- **끝났을 때**: `오늘 일을 다 마쳤어요` 와 그날의 수(완료 5 · 알림장 4 — 금액 없음). 건너뛴 것이 있으면 `2개는 남겨 뒀어요` 와 [다시 보기]. [닫기]는 하루 화면으로 돌아간다.
- 직원도 쓴다(쓰는 권한은 지금의 각 동작 그대로 — `reservation:write`·`sales:write`·`record:write`). 권한이 없는 종류의 장은 나오지 않는다.
- 지난 날에도 열린다(달력에서 그날을 고르고 들어간다). 앞날에는 남은 일이 없다.

### 3.7 기준값과 설정 — 기본값이 있고, 바꿀 수 있다

기준값을 고정하지 않는다(공통 1절). 건드리지 않아도 돌고, 바꾸는 길은 **쓰는 자리**에 있다. 같은 값을 예약 설정 화면에서도 고친다.

| 값 | 처음 값 | 쓰는 자리에서 바꾸기 | 설정 화면의 줄 이름과 그 아래 보이는 것 |
|---|---|---|---|
| 매장의 기본 간격(1~52주) | 4주 | 완료 시트의 `간격 바꾸기`(어림일 때), 목록의 어림 줄 | `처음 온 아이의 다음 미용은 몇 주 뒤로 잡을까요` — 아래에 `한 번 온 아이: 4주 뒤로 잡고, 4주가 지나면 '지남'에 올라요` |
| '곧'으로 치는 날 수(1~30일) | 7일 | 목록의 [곧] 묶음 머리 `7일 안 · 바꾸기` | `다시 올 날 며칠 전부터 '곧'에 올릴까요` — 아래에 지금 값으로 '곧'에 오르는 아이의 수 |
| 안내 글 템플릿(300자) | 3.3 의 글 | 안내 미리 보기 시트의 `안내 글 템플릿 바꾸기` | `다시 올 때가 된 아이에게 보낼 글` — 아래에 실제 아이 이름을 넣은 **보호자가 받는 모습** |
| 알림장을 남은 일로 세기 | 켜짐 | 하루 마무리의 한 줄 | `알림장을 안 보낸 방문을 남은 일로 세기` — 아래에 `끄면 하루 머리와 달력에서 세지 않아요` |
| 계산할 때 볼 최근 방문 수(3~12번) | 6번 | — | `미용 주기를 계산할 때 최근 몇 번의 방문을 볼까요` — 아래에 `최근 6번의 방문 사이 간격의 가운데 값을 써요` (10절의 답) |
| 손질로 보고 뺄 날 수(0~28일) | 7일 | — | `며칠 안에 다시 온 방문은 손질로 보고 뺄까요` — 아래에 `7일 안에 다시 온 방문은 주기 계산에서 빼요`(0 이면 `모든 방문을 셈에 넣어요`) (10절의 답) |
| 아이의 주기 | 계산 | 주기 줄·완료 시트·목록 | (설정 화면에 없다 — 아이의 값이다) |

- 템플릿 편집: 글 칸 위에 넣을 수 있는 칩 셋(`아이 이름`·`지난 주 수`·`매장 이름`), 아래에 미리 보기. 칩이 하나도 없어도 저장된다. [처음 글로 돌아가기].
- 계산 규칙의 속 가운데 **최근 몇 번(6번)과 며칠 안의 방문 빼기(7일)는 예약 설정에서 바꾼다**(10절의 답 — 줄 이름은 `미용 주기를 계산할 때 최근 몇 번의 방문을 볼까요`·`며칠 안에 다시 온 방문은 손질로 보고 뺄까요`). 중앙값·2년 창은 내지 않는다.
- 알림 설정의 고정 주 수(`next_visit_after_weeks`, ⑥)는 "모든 아이에게 같은 주 수로 알림톡을 보낸다"는 다른 뜻이라 그대로 둔다. 알림톡 설정의 그 줄 아래에 `아이에게 직접 정한 주기가 있으면 그 값이 앞서요` 를 더한다.
- 설정 줄의 말은 널리 쓰는 말 그대로다(템플릿, 리마인드). "AI"라는 말이 없다.

### 3.8 달력 칸

- **새 표시를 더하지 않는다.** 칸에는 이미 정리 안 된 예약의 수를 보이는 작은 검정 숫자가 있다(오른쪽 위). 이 숫자의 뜻을 **그날의 남은 일의 수**로 넓힌다 — 정리 안 된 예약 + 결제 안 적음 + 알림장 안 보냄. (공통 7절은 "고리"라고 적었으나 같은 자리에 같은 일을 하는 표시가 이미 있어 그것을 쓴다. 표시가 둘이 되는 것을 막는다.)
- 뜨는 조건(공통 7절): **지난 날과 오늘의 남은 일**이 있을 때만. 앞날의 확인할 것은 칸에 표시하지 않는다 — 노령·지병 아이의 예약이 있는 날마다 표시가 뜨면 표시가 뜻을 잃는다.
- 무엇이 남았는지는 **고른 날의 미리보기 카드**에 글로: `결제 안 적음 2 · 알림장 안 보냄 1 ›`(누르면 하루 마무리). 앞날을 고르면 그날의 확인할 것이 `확인 1` 로 카드에 보인다 — 이 수는 달력 응답이 아니라 **고른 날의 하루 응답**에서 읽는다(4.3).
- "한눈에 안 보인다"를 피하는 법: 칸의 주인은 사진과 마릿수 그대로 두고, 칸에 새로 더해지는 것이 없으며, 글은 고른 날 하나에만 나온다. 시간 순서는 하루 화면(목록·시간표)이 맡는다 — 달력에 시간표를 겹치지 않는다. 사진 중심 달력이 시간 순서를 흐리는지는 조사도 답하지 못했다. 첫 매장에서 본다.

### 3.9 화면의 자리 (공통 8절의 정본)

위에서 아래 순서다. 해당하는 것이 없으면 줄이 없다. 뒤의 묶음은 자기 줄을 이 순서의 자리에 넣는다.

| 화면 | 순서 |
|---|---|

## 4. 어떻게 — 정해 둔 것

### 4.1 어디에 사는가

- **계산은 visit 이 한다.** `visit/domain/services/visit_cycle.py` 의 순수 함수(완료 날짜 목록·직접 정한 값·매장의 기본 간격을 받아 주기·출처·간격 수·날짜에 쓰는 값·다음 올 때를 낸다). DB 를 모른다.
- **직접 정한 값과 안내한 날은 customer 가 갖는다.** 아이의 사실이고 "지금의 것 하나"다 — 동의 받은 날과 같은 자리.
  - `pets.grooming_cycle_weeks smallint null` (CHECK 1~52)
  - `pets.revisit_nudged_on date null`
  - 익명화는 둘 다 비운다.
- **매장의 값은 visit 이 갖는다** — `visit_shop_settings` 에 칸 여섯: `default_cycle_weeks smallint not null default 4`(CHECK 1~52), `revisit_soon_days smallint not null default 7`(CHECK 1~30), `revisit_message text null`(300자, null 이면 처음 글), `count_unsent_reports boolean not null default true`, `cycle_sample_visits smallint not null default 6`(CHECK 3~12), `cycle_min_gap_days smallint not null default 7`(CHECK 0~28)(뒤의 둘은 10절의 답).
- **방문에 칸 하나** — `visits.report_skipped_at timestamptz null`(3.6 의 [보내지 않음]).
- **visit 은 직접 정한 주기를 허브 포트로 읽는다.** ③-B 의 `CustomerDirectoryPort.care_facts` 가 돌려주는 아이 사실에 **`grooming_cycle_weeks` 하나**를 더한다(여러 아이를 한 번에 읽는 길이 이미 있다. ⑪ 은 같은 DTO 에 `consent_form_sent_at` 을 더한다 — 공통 11절). **안내한 날은 판정용 DTO 에 싣지 않는다** — 돌봄 사실이 아니다. 목록이 쓰는 읽기 `CustomerDirectoryPort.revisit_nudges(ctx, pet_ids) -> dict[int, date]` 를 따로 둔다.
- **반려동물 상세(customer)는 주기를 허브 포트로 받는다.** `VisitLedgerPort` 에 읽기 하나 — 아이 ID 와 직접 정한 값을 받아 주기·출처·간격 수·지난 간격(주)·마지막 완료 방문의 날·다음 올 때·앞으로 예약이 있는지를 돌려준다. customer 는 계산 규칙을 모른다. (⑭ 는 같은 포트에 `customer_has_live_pass` 를 더한다.)
- 스포크끼리 import 하지 않는다. `notification` 은 주기를 이벤트로만 받는다.

### 4.2 목록의 질의

지금 `due_candidates` 는 "마지막 완료 방문이 57~365일 전"을 SQL 로 거른다. 주기는 아이마다 달라 SQL 한 줄로 못 거른다. **후보를 넓혀 읽고 파이썬에서 거른다**: 마지막 완료 방문이 1년 안이고 앞으로 예약이 없는 아이 전부 → 그 아이들의 최근 완료 방문 날짜를 한 번에(아이마다 6개, 창 함수) → `care_facts` 한 번 → 순수 함수로 주기·묶음 → 보이는 쪽의 `revisit_nudges` 한 번. 작은 매장의 한 해 손님은 수백 마리다(⑧ 과 같은 전제 — 미리 계산한 표·캐시를 두지 않는다). 질의 수는 아이 수와 상관없이 고정이고 테스트가 호출 수를 고정한다.

**이 계산을 달력 응답에 싣지 않는다.** 달력을 열 때마다 한 해 후보 전체와 `care_facts` 가 돌면 가장 자주 여는 화면이 무거워진다. 캘린더 탭의 `다시 올 때가 된 아이 N` 은 따로 읽는다(4.3).

### 4.3 API (모양은 계획에서 굳힌다)

- `GET /v1/shops/{id}/revisits?bucket=soon|due&cursor=` — 매장 멤버(`get_shop_context`). 20개씩. 항목: 아이 카드(사진·이름), `last_visit_date`, `last_visit_id`, `cycle_weeks`(날짜에 쓰는 값), `cycle_source: manual|computed|single|none`, `last_interval_weeks|null`, `due_date`, `estimated: bool`, `nudged_on|null`, `message`(템플릿에 값을 넣은 안내 글). **`GET /sales/due-pets` 는 없앤다**(아직 배포 전이라 옛 앱이 없다).
- `GET /v1/shops/{id}/revisits/counts` → `{soon, due}` — 매장 멤버. 캘린더 탭이 달력과 **따로** 읽는다(늦게 와도 달력은 먼저 뜬다). 매출 요약의 지난 아이 수는 같은 함수의 `due`.
- 캘린더 응답(`VisitCalendarSchema`)의 날마다 `unpaid_count`·`report_unsent_count`(SQL 집계 — 지난 날·오늘만 0 이 아니다). 재방문 수·확인할 것의 수는 싣지 않는다.
- 하루 응답의 `counts` 에 `unpaid`·`report_unsent`(지금의 `unresolved` 옆)와 `checks`(확인할 것이 있는 살아 있는 방문의 수 — 하루 응답은 이미 방문마다 확인할 것을 판정한다). 하루 목록·피드 항목에 `marks: [code]`(4.4).
- `GET /v1/shops/{id}/days/{date}/wrap-up` → 하루 마무리의 장 목록(종류·방문·채워 둘 값). 쓰기는 지금 있는 경로들을 쓴다(완료·노쇼·취소, 기록 저장, 알림장 보내기)와 `PUT …/visits/{id}/report-skip`·`DELETE` 같은 경로.
- `GET …/visits/{id}/next-draft` 응답에 `cycle_weeks`·`cycle_source`. 날짜·시간은 늘 있다.
- visit 설정(`visit-settings`)의 읽기·쓰기에 칸 넷(4.1).
- customer: `PUT /v1/shops/{id}/pets/{pet_id}/grooming-cycle` `{weeks}` · `DELETE` 같은 경로 · `PUT …/pets/{pet_id}/revisit-nudge`(본문 없음, 오늘로 적는다). 반려동물 상세 응답에 `revisit: {cycle_weeks, cycle_source, interval_count, last_interval_weeks, last_visit_date, due_date, estimated, has_upcoming, nudged_on}`.
- 로그인 없는 경로·보호자 경로·공개 스키마는 건드리지 않는다.

### 4.4 줄의 낱말 — `marks` (공통 7절의 정본)

하루 목록·피드의 방문 항목에 문자열 목록 `marks` 를 둔다. 서버가 그 방문에 해당하는 코드를 싣고, 앱은 **아는 코드만** 아래 순서로 낱말로 바꾼다(모르는 코드는 버린다 — 서버가 더해도 옛 앱이 죽지 않는다).

| 순서 | 코드 | 낱말 | 누가 채우나 |
|---|---|---|---|
| 1 | `paid` | `결제 완료` | 이 묶음(3.5 의 정의) |
| 2 | `report_sent` | `알림장 보냄` | 이 묶음(지금의 `report_sent` 칸은 남기고 같은 값을 싣는다) |
| 3 | `pass_used` | `정기권` | ⑭ — 정기권 몫이 있는 완료 방문 |
| 4 | `deposit_received` | `예약금 받음` | ⑮ — 예약금을 받은 방문 |

- 코드는 이 넷으로 굳는다. **낱말과 순서는 이 표가 정본**이고 ⑭·⑮ 는 "언제 싣는가"만 정한다.
- **`consent_*` 는 없다.** 동의서를 보냈는지·서명했는지는 확인할 것의 `consent` 항목에 실린다(⑪). "보냈지만 서명 전"은 남은 일이라 줄의 낱말이 될 수 없다.
- **창구(`channel`)는 없다**(⑯ — 방문 상세 한 줄뿐).
- 규칙: **줄에는 끝낸 일의 낱말만, 남은 일은 `확인 N` 과 머리 요약의 숫자로.** 새 묶음이 "남은 일"을 더하고 싶으면 확인할 것(③-B 의 판정 연쇄)에 항목을 더하거나 하루 머리의 숫자를 더한다(⑮ 의 `예약금 기다리는 중`).
- 한 줄에 낱말이 넷을 넘으면 뒤의 것을 `+2` 로 접는다. 달력 칸에는 `marks` 가 가지 않는다.

### 4.5 앱

- 목록 화면은 `features/sales` 에서 `features/visit` 로 옮긴다(`sales` 는 `auth` 만 import 한다 — 예약 등록·공유 문안과 이을 수 없다. `visit → customer` 는 허용된다). 경로 `/revisits`. 매출 탭은 라우터 경로로만 간다. 세그먼트 [지남][곧], `AsyncBody`, 20개씩.
- 하루 마무리는 `features/visit/screens/` 의 새 화면(경로 `/days/:date/wrap-up`). 장마다의 동작은 지금 있는 컨트롤러(상태 바꾸기·기록 저장·알림장 보내기)를 부른다 — 새 쓰기 규칙을 만들지 않는다.
- 주기의 문구(`보통 N주마다`·`N일 지남`·`쯤`·`어림`), 초안 날짜 옮기기는 `features/visit/state/` 의 순수 함수. 반려동물 상세의 주기 줄과 시트는 `features/customer`(`grooming_consent_row.dart` 옆, 쓰기는 `CustomerCommands`).
- `marks` 는 `fromJson` 에서 enum 으로 한 번만 바꾼다. 달력 칸의 숫자는 `Semantics` 이름표에 `남은 일 N` 을 싣는다.
- 공유는 `shareSheetProvider`. 안내 글에 보호자 이름·번호를 넣지 않는다.

### 4.6 나누기

- **⑬-1 백엔드** — 칸(아이 둘·매장 넷·방문 하나)과 마이그레이션, 주기 함수와 세 군데 바꾸기, `care_facts`·`revisit_nudges`·`VisitLedgerPort`·`VisitClosed` 의 칸, `/revisits`·`/revisits/counts`, `paid` 판정과 달력·하루·피드 응답, 하루 마무리의 읽기와 `report-skip`, 흐름 스크립트.
- **⑬-2 앱** — 목록 화면 옮기기와 [예약]·[안내]·템플릿 편집, 반려동물 상세의 주기 줄·시트, 완료 시트의 다음 예약 줄, 하루 줄·피드·상세의 `결제 완료`, 머리 요약, 하루 마무리, 달력 칸의 숫자와 미리보기 카드, 예약 설정의 네 줄, 시뮬레이터 흐름.

## 5. 잠금·권한·보안

### 5.1 잠금

- 주기·안내한 날의 쓰기는 customer 의 가족 잠금을 맨 앞에서 잡는다(동의 쓰기와 같다). 방문 행을 건드리지 않는다.
- `report-skip` 은 방문을 쓰는 유스케이스다 — `lock_family` 로 고객 행부터 잠그고 방문 행을 잠근다(지금 규칙 그대로).
- 잠금 순서에 새 줄을 더하지 않는다(공통 10절의 합친 모양에 ⑬ 의 줄은 없다).
- 검색되는 글이 아니므로 `SearchSourceChanged` 를 내지 않는다(안내 글 템플릿은 매장의 설정이지 기록이 아니다).

### 5.2 권한

새 권한을 만들지 않는다. `/revisits`·`/revisits/counts` 와 달력·하루의 새 칸, 하루 마무리의 읽기는 매장 멤버. 주기·안내한 날의 쓰기는 `customer:write`. 매장의 값 넷은 지금 visit 설정을 쓰는 권한 그대로. 매출 요약의 수는 지금처럼 `sales:read`.

### 5.3 위험과 막는 법

| | 위험 | 막는 법 |
|---|---|---|
| R1 | 다른 매장의 아이·방문이 섞인다 | 모든 질의가 `ShopContext` 의 `shop_id`. 통합 테스트의 첫 줄은 테넌트 격리. |
| R2 | 익명화한 고객·무지개다리 아이가 목록·수에 나온다 | `due_pets.py` 의 거르기(`showable_pets` + `passed_away`)를 그대로 쓴다. 익명화가 칸 둘을 비운다. |
| R3 | 직원 화면에 금액이 나온다 | 새 응답 칸(목록·요약·`marks`·하루 마무리의 끝 화면)에 금액이 없다(스키마 테스트가 칸을 고정). 하루 마무리의 결제 장은 금액을 **적는** 화면이고 `sales:write` 가 있어야 나온다. |
| R4 | 방문 두 번으로 "보통"이라고 말한다, 간격 하나로 '지남'에 올린다 | 출처와 간격 수를 응답에 싣고 문구 함수가 가른다. `single` 은 날짜에 매장의 기본 간격을 쓴다. 테스트에 간격 0·1·2개와 "2주 간격으로 두 번 온 아이의 15일째". |
| R5 | 날짜 경계 — 다음 올 때가 하루 어긋난다 | 전부 매장 시간대의 날짜. 테스트에 예상일 당일·하루 전·하루 뒤·'곧'의 경계 안팎, 자정 앞뒤 방문. |
| R6 | 목록이 아이 수만큼 질의한다, 달력이 무거워진다 | 4.2 — 호출 수 고정 테스트. 달력 응답은 재방문·확인할 것을 계산하지 않는다(달력 유스케이스가 `care_facts` 를 부르지 않는 것을 테스트로 고정). |
| R7 | 알림 줄의 주 수가 바뀌어 심사받은 문안과 어긋난다 | 문안의 변수(`#{간격}`)는 그대로 주 수다. 순서만 바뀐다. 가짜 게이트웨이 흐름으로 확인. |
| R8 | 안내 글·이름이 로그에 남는다 | 템플릿과 만든 글을 로그·오류 메시지에 싣지 않는다. 새 로그를 더하지 않는다. |
| R9 | 다음 예약 초안의 날짜가 비어 나온다 | 초안은 늘 날짜·시간을 낸다(주기를 모르면 매장의 기본 간격). 테스트에 완료 방문 한 번뿐인 아이. |
| R10 | 정기권·예약금으로 다 낸 방문이 "결제 안 적음"에 남는다 | `paid` 는 나머지를 본다(3.5). ⑭·⑮ 의 등식 테스트에 "나머지 0, 결제 수단 없음 → paid". |
| R11 | 템플릿을 비워 저장해 빈 글이 나간다 | 글이 비면 저장을 막고, 값이 빈 칩(매장 이름)은 보내기 전에 묻는다. |

**받아들인 한계**: 대기 중인 알림 줄의 주 수는 뒤에 고친 주기를 따라오지 않는다(3.4) · 앞날 예약을 보는 것은 고객 단위다(3.4) · 안내를 실제로 보냈는지는 모른다(시트를 연 날만).

## 7. 테스트와 검증

- **백엔드 단위**: 주기 함수(중앙값·짝수 개·7일 미만 버리기·2년 창·1~52 자르기·직접 정한 값 우선·`single` 은 날짜에 기본 간격), 묶음 판정(어림은 '곧'에 없다), `paid` 판정(나머지 0), `marks` 조립과 순서, 알림 주 수의 순서와 가족 묶음의 짧은 쪽, 템플릿 채우기.
- **백엔드 통합**: 격리, `/revisits` 의 두 묶음과 공통 조건(앞날 예약·무지개다리·익명화·1년), 주기 모르는 아이의 기본 간격, 요약의 수와 목록의 수가 같다, 직원도 200, 달력·하루의 수, 하루 마무리의 장 목록과 `report-skip`, 매장의 값을 바꾸면 묶음이 바뀐다, 익명화가 칸을 비운다, 변이로 판별력 확인(매장 거르기·'곧'의 경계·`single`).
- **흐름 스크립트** `backend/scripts/check_revisit_flow.sh`: 방문 몇 번 → 주기를 손계산과 견준다 → 목록의 두 묶음 → 직접 정하기 → 예약을 잡으면 빠진다 → 안내한 날 → 완료한 방문에 금액을 적으면 `paid` → 하루 마무리의 장이 줄어든다.
- **앱**: 문구 함수, 목록 화면(두 묶음·[예약]·[안내]·템플릿), 주기 시트, 완료 시트의 다음 예약 줄(세 출처), 하루 줄·머리 요약, 하루 마무리(세 종류·건너뛰기·끝 화면), 달력 칸의 숫자, 골든(하루 화면·달력은 의도한 변화라 다시 찍고 눈으로 본다), 시뮬레이터 흐름 iOS·안드로이드(6절의 횟수).
- `flutter analyze` 0, import-linter, 라우트 허용 목록 그대로.

## 8. 만드는 사람에게 맡기는 것

- 문구의 마지막 다듬기, 시트의 모양(기존 시트를 따른다), 하루 마무리의 넘김 효과.
- `revisit` 응답 칸의 이름, 후보 질의의 정확한 모양, 색인이 모자라면 같은 마이그레이션에.
- 초안의 날이 지났을 때 "가장 가까운 같은 요일"이 쉬는 날이면 — 지금 등록 화면의 휴무 경고에 맡긴다.
- 하루 마무리의 결제 장이 쓰는 "지난번에 쓴 결제 수단"을 어디서 읽을지(방문 기록의 최근 것).

## 9. 근거가 약한 곳

- "MoeGo 의 고객 단위 주기가 여러 마리 집에서 불편하다"는 조사의 추론이다. 불만 리뷰는 없다.
- 달력 불만의 근거는 앱스토어 리뷰 몇 건이다. 네이버 카페·블로그의 미용사 후기는 한 건도 읽지 못했다.
- 중앙값·최근 6번·7일·"곧 = 7일"·기본 간격 4주는 내가 정한 값이고 실제 매장의 방문 자료로 맞춰 본 것이 아니다. 첫 매장의 기록이 쌓이면 다시 본다.
- "하루 마무리"가 사장의 실제 하루 끝과 맞는지(그날 저녁에 몰아서 정리하는지, 손님마다 바로 하는지)는 모른다.

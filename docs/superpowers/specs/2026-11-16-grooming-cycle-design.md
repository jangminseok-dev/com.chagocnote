# ⑬ 아이별 미용 주기·재방문 안내와 달력의 상태 표시 — 설계

2026-11-16. 경쟁 조사(`.superpowers/research/reports/펫미용 앱 경쟁 기능 비교.md`)의 3순위(반려동물 단위 미용 주기와 재방문 안내)와 6순위(달력의 상태 표시)를 한 묶음으로 만든다. 둘 다 "이미 있는 사실을 예약·달력 앞에 모아 보이는" 일이고, 새 입력을 거의 받지 않는다.

사용자는 조사 보고서의 순위 열한 개를 보고 "설계를 시작해 달라"고 했다. **아래의 규칙·기준값·문구·화면 자리는 모두 내가 정한 것이다.** 사용자가 답해야 하는 것은 9절에 따로 적었다.

- 범위: 백엔드(`visit` 의 주기 계산·목록·달력 응답, `customer` 의 칸 둘, 허브 포트·이벤트의 칸), 앱(`features/visit` 의 목록 화면·달력·하루 줄, `features/customer` 의 반려동물 상세 한 줄). 웹은 바꾸지 않는다.
- 바탕: ③ 예약 설계(다음 예약 제안), ⑧ 매출 설계 3.3(다시 올 때가 지난 아이), ⑥ 알림톡 설계(`next_visit` 종류), ③-B 설계(확인할 것·`care_facts`).
- 과금: 없다. 자동 발송은 알림톡 실발송이라 "나중"이고, 이번에 바꾸는 것은 가짜 게이트웨이 위에서 도는 줄 만들기 규칙뿐이다.

## 1. 왜

**주기.** 지금 앱은 "언제 다시 오는 아이인가"를 세 군데에서 서로 다르게 센다.

| 곳 | 지금 규칙 | 코드 |
|---|---|---|
| 완료 뒤 '다음 예약' 초안 | 최근 두 완료 방문의 간격(주, 1~12), 한 번뿐이면 4주 | `visit/domain/services/visit_cycle.py` |
| 알림톡 '미용 주기 안내' | 매장 설정의 고정 주 수, 없으면 직전 완료와의 간격, 없으면 4주 | `notification/domain/services/schedule_rules.py` |
| 다시 올 때가 지난 아이 | 모든 아이에게 8주(56일) 고정 | `visit/adapter/outbound/pg/sales_pg_repository.py` |

4주마다 오는 아이는 5주째에 이미 늦었는데 8주가 될 때까지 목록에 없고, 12주마다 오는 고양이는 9주째에 "지난 아이"로 잘못 나온다. 직전 간격 하나만 보는 규칙은 한 번 늦게 온 것으로 주기가 흔들린다. 경쟁사는 더 거칠다 — 그루머노트는 15·30·60·90일 넷 가운데 고르고, MoeGo 는 **고객 단위**로 4주를 기본값으로 둔다(여러 마리 집에서 맞지 않는다는 것은 조사의 추론이고 그런 불만 리뷰는 찾지 못했다).

또 지금 목록은 `sales:read`(사장만) 뒤에 있고 누르면 반려동물 상세로 갈 뿐이다. 연락도 예약도 거기서 못 한다(⑧ 이 미뤄 둔 것).

**달력.** 그루머노트 리뷰에 "결제완료된 예약건은 색이 바뀌었음 좋겟어요"(답 없음), 반짝 개편 뒤 리뷰에 "일정이 한눈에 안 보인다"가 있다(앱스토어 리뷰 몇 건이 근거의 전부다 — 얼마나 흔한 불만인지는 모른다). 지금 하루 줄에는 `확인 N`·`겹침`·`정리 필요`·`알림장 보냄` 이 있고 **돈을 적었는지는 없다.** 달력 칸은 사진과 숫자뿐이다.

## 2. 목표와 하지 않는 것

**목표**

- 주기를 **아이마다 하나**, 한 곳에서 계산하고 세 군데(다음 예약 초안·알림 줄·목록)가 같은 값을 쓴다.
- 사장이 고르지 않아도 된다. 지난 방문에서 계산해 보이고, 틀리면 고친다.
- 다시 올 때가 **다가온** 아이와 **지난** 아이를 한 목록에서 나눠 보이고, 그 자리에서 예약을 잡거나 안내 글을 카카오톡으로 보낸다(0원).
- 하루 줄과 달력에서 **남은 일**(돈을 안 적었다, 확인할 것이 있다)과 **끝낸 일**(결제 완료, 알림장 보냄)을 상세에 들어가지 않고 안다.
- 사진 중심 달력을 흐리지 않는다.

**하지 않는 것**

| 항목 | 까닭 |
|---|---|
| 알림톡 실발송, 발송 미리 보기(MoeGo 의 "앞으로 30일") | 과금. 줄을 만드는 규칙만 맞춘다. |
| 주기를 매장이 한꺼번에 정하기, 견종별 기본 주기 | 설정 화면을 늘리지 않는다. 믿을 견종별 수치도 없다. |
| 계산한 주기를 "권장 주기"로 보호자에게 보이기 | 지난 간격일 뿐 권고가 아니다. 보호자 웹·알림장에 싣지 않는다. |
| "이 아이는 안내하지 않기" 표시 | 1년이 지나면 목록에서 빠진다. 필요하다는 말이 나오면. |
| 안내를 보냈는지 확인 | 공유 시트는 보냈는지 알려 주지 않는다. 시트를 연 날만 적는다. |
| 달력 칸에 금액·색 딱지·아이콘 줄 | 직원은 매출을 못 본다 / 무채색 톤 / 사진이 주인이다. |
| 동의서 상태(⑪), 정기권 차감(⑭), 예약금 받음(⑮) 표시의 내용 | 각 묶음이 정한다. 여기서는 **들어올 자리**만 만든다(4.4). |
| 반복 예약 | ⑭. 이 묶음의 주기 값을 읽어 쓴다. |

**이렇게 되면 실패다**: 계산한 숫자가 사실처럼 보인다(방문 두 번으로 "보통 6주마다") · 앞으로 예약이 잡힌 아이가 목록에 나온다 · 달력 칸이 표시로 덮여 사진이 안 보인다 · 직원의 화면에 금액이 나온다 · 세 군데의 주기가 여전히 다르다.

## 3. 무엇을 만드나

### 3.1 미용 주기 — 계산

아이 한 마리의 주기는 아래 순서로 정한다. 보호자만의 방문에는 주기가 없다.

1. **직접 정한 값**이 있으면 그것(1~52주).
2. 없으면 **계산한 값**: 그 아이의 완료 방문(시작 시각, 매장 시간대의 날짜) 가운데 **최근 6번**을 보고, 이웃한 방문 사이의 날 수(최대 5개) 가운데 **7일 미만인 것을 버린 뒤**(부분 손질·다시 손보기), **중앙값**을 주로 반올림해 1~52주로 자른다. 2년(730일)보다 오래된 방문은 보지 않는다.
3. 간격이 하나도 없으면(완료 방문이 한 번뿐이거나 없다) **주기 없음**.

| 간격 수 | 화면의 말 | 뜻 |
|---|---|---|
| 0 | (줄이 없다) | 주기를 모른다. 4주라고 지어내지 않는다. |
| 1 | `지난번에는 6주 만에 왔어요` | 한 번의 간격은 주기가 아니다. |
| 2 이상 | `보통 6주마다 와요` | 중앙값. |
| 직접 정함 | `6주마다 와요 · 직접 정함` | |

- **다음 올 때**: 마지막 완료 방문의 날 + 주기. 화면에는 `다음은 12월 3일쯤` — 늘 "쯤"을 붙인다. 주기가 없으면 없다.
- 중앙값을 쓰는 까닭: 한 번 늦게 온 것(여행·병)에 흔들리지 않는다. 짝수 개면 가운데 둘의 평균.
- 계산은 **읽을 때** 한다. 저장하지 않는다(방문을 고치거나 되돌리면 저절로 맞는다).
- 지금의 `visit_cycle.interval_weeks`(직전 간격, 1~12주, 기본 4주)는 이 규칙으로 바꾼다. 범위를 1~52주로 넓히는 것은 알림 쪽(`NEXT_VISIT_WEEKS_MIN/MAX = 1, 52`)과 맞추기 위해서다.

### 3.2 직접 정하기

- 반려동물 상세 정보 탭의 주기 줄을 누르면 시트: 주 수(1~52, 한 주씩 올리고 내리기), [저장], 직접 정한 값이 있으면 [계산한 값으로 돌아가기].
- 주기 줄이 없는 아이(간격 0)에게는 `미용 주기 정하기` 한 줄이 대신 있다.
- 사장·직원 모두(`customer:write`). 누가 정했는지는 남기지 않는다(판단이 아니라 숫자다).

### 3.3 다시 올 때가 된 아이 — 목록

⑧ 의 "다시 올 때가 지난 아이"를 넓힌다.

| 묶음 | 조건 |
|---|---|
| **곧** | 다음 올 때가 오늘부터 7일 안(오늘 포함)이다 |
| **지남** | 다음 올 때가 어제 이전이다. 주기가 없는 아이는 지금처럼 마지막 완료 방문이 56일 넘게 지났다 |

- 공통 조건은 ⑧ 그대로다: 마지막 완료 방문이 1년을 넘지 않았다 · 앞으로 잡힌 예약이 없다(오늘 0시 이후의 `reserved` 와 미용 중) · 무지개다리를 건너지 않았다 · 익명화되지 않았다.
- **8주 고정을 주기로 바꾸는 것이 맞다.** 고정값은 자주 오는 아이를 늦게, 드물게 오는 아이를 일찍 띄운다. 다만 주기를 모르는 아이(한 번 온 아이)를 목록에서 빼면 "처음 오고 안 온 손님"을 놓치므로 그 아이들에게만 8주를 남긴다. **매출 탭의 "다시 올 때가 지난 아이 N마리"는 '지남'의 수가 되고 값이 달라진다**(같은 함수를 쓴다).
- 줄: 사진·이름·`6주마다 · 5일 지남`(곧이면 `3일 뒤쯤`, 주기가 없으면 `9주 전에 왔어요`)·안내한 적이 있으면 `11월 10일에 안내`. '지남'은 오래 지난 순, '곧'은 가까운 순.
- 줄을 누르면 반려동물 상세(지금 그대로). 줄 끝에 둘:
  - **[예약]** — 예약 등록 화면이 보호자·아이·메뉴·소요 시간이 채워져 열린다(마지막 완료 방문의 '다음 예약' 초안을 쓴다). 초안의 날이 지났으면 오늘 이후의 가장 가까운 같은 요일로 옮긴다.
  - **[안내]** — 안내 글을 만들어 기존 공유 시트에 넘긴다. 시트를 열면 그 아이에 **안내한 날**(오늘)을 적는다.
- 안내 글(앱이 만든다, 주기를 권고처럼 쓰지 않고 지난 사실만):

```
안녕하세요, Hiss Haus예요.
콩이가 미용한 지 6주가 됐어요.
편하신 날 알려 주시면 예약 잡아 드릴게요.
```

- 안내한 날은 **마지막 완료 방문보다 뒤일 때만** 보인다(다녀가면 저절로 사라진다). 목록에서 빼지는 않는다.
- **사장·직원 모두 본다.** 돈이 없는 목록이고 손님에게 연락하는 사람이 직원일 수 있다. 경로를 `/sales/…` 밖으로 옮긴다(5.2).
- 들어가는 곳: 캘린더 탭의 "정리 안 된 예약" 알림 줄 자리에 `다시 올 때가 된 아이 7 ›`(곧 + 지남, 0 이면 없다), 매출 탭의 기존 줄(사장).

### 3.4 다음 예약 초안과 알림 줄

- **초안**(`GET …/next-draft`)은 3.1 의 주기를 쓴다. 주기가 없으면 지금처럼 4주로 잡되 응답에 `cycle_source: none` 을 실어, 완료 시트가 `4주 뒤로 잡아 둘게요(바꿀 수 있어요)` 처럼 계산한 값이 아님을 말하게 한다.
- **알림 줄**(`next_visit`, 기본 꺼짐): 보낼 주 수의 순서를 `아이에게 직접 정한 값 → 매장 설정의 고정 주 수 → 계산한 값 → 4주` 로 바꾼다. 지금은 `매장 설정 → 직전 간격 → 4주` 다. 허브 이벤트 `VisitClosed` 에 칸 둘(`cycle_weeks`, `cycle_source`)을 더하고 `previous_completed_at` 은 남긴다. 문안(`#{간격}주 정도마다 미용하면 좋아요`)은 심사받은 템플릿이라 건드리지 않는다. 실발송은 나중이다.
- 앞날 예약이 있으면 보내지 않고, 지난 아이에게는 자동으로 다시 보내지 않는 MoeGo 의 규칙은 지금 구조가 이미 한다(완료 때 한 줄, 예약이 잡히면 대기 줄 취소 — ⑥ 설계).

### 3.5 하루 줄·피드·방문 상세의 상태

원칙은 하나다 — **남은 일은 숫자로 모아 위에, 끝낸 일은 낱말로 줄에.** 색·아이콘을 더하지 않는다(지금의 작은 글자 표시 그대로).

| 표시 | 뜨는 조건 | 어디 |
|---|---|---|
| `결제 완료` (새로) | 완료 방문의 기록에 총액과 결제 수단이 **둘 다** 있다 | 하루 줄, 피드, 방문 상세의 이름 카드 |
| `알림장 보냄` | 지금 그대로 | 지금 그대로 |
| `확인 N`·`겹침`·`정리 필요` | 지금 그대로 | 지금 그대로 |

- 줄의 표시 순서: `확인 N · 겹침 · 정리 필요 · 결제 완료 · 알림장 보냄`. 남은 일이 앞, 끝낸 일이 뒤.
- 가족 묶음은 `알림장 보냄` 과 같은 규칙 — 완료한 방문이 **모두** 결제 완료일 때만 뜬다.
- **하루 화면 머리의 요약**에 `결제 안 적음 2` 를 더한다(완료했는데 총액이나 결제 수단이 빈 방문의 수, 0 이면 없다). 누르면 그 방문들로 내려간다. 이것이 "결제된 것만 색이 바뀌면 좋겠다"에 대한 답이다 — 끝낸 줄에 낱말이 붙고, 안 끝낸 수가 위에 모인다.
- 총액만 있고 결제 수단이 없는 방문은 `결제 완료` 가 아니다. 매출에는 지금처럼 "미선택"으로 든다(⑧).
- **직원**: 이 표시는 "적었는지"의 참·거짓이고 금액이 아니다. 직원도 금액을 적는 사람이므로(`sales:write`) 그대로 보인다. **줄·칸·요약 어디에도 금액 숫자를 싣지 않는다** — 금액은 지금처럼 방문 상세의 기록과 매출 탭(사장)에만 있다.

### 3.6 달력 칸

- 칸에는 **작은 고리 하나**만 더한다 — 그날에 남은 일이 있으면 날짜 숫자 옆에 속이 빈 작은 동그라미. 종류를 가르지 않고 수도 적지 않는다. 지금 정리 안 된 예약을 칸에서 보이는 표시가 있으면 그것과 합친다(구현에서 확인).
- 남은 일 = 정리 안 된 예약 · 결제 안 적은 완료 방문 · 확인할 것이 있는 살아 있는 방문(오늘 이후의 날만).
- 무엇이 남았는지는 **고른 날의 미리보기 카드**에 글로: `결제 안 적음 2 · 확인 1`. 카드는 이미 그날의 사진·이름을 보이는 자리다.
- "한눈에 안 보인다"를 피하는 법: 칸의 주인은 사진과 마릿수 그대로 두고, 칸마다 더해지는 것은 점 하나뿐이며, 글은 고른 날 하나에만 나온다. 시간 순서는 하루 화면(목록·시간표)이 맡는다 — 달력에 시간표를 겹치지 않는다. 사진 중심 달력이 시간 순서를 흐리는지는 조사도 답하지 못했다. 첫 매장에서 본다.

## 4. 어떻게 — 정해 둔 것

### 4.1 어디에 사는가

- **계산은 visit 이 한다.** `visit/domain/services/visit_cycle.py` 의 순수 함수(날짜 목록과 직접 정한 값을 받아 주기·출처·다음 올 때를 낸다). DB 를 모른다.
- **직접 정한 값과 안내한 날은 customer 가 갖는다.** 아이의 사실이고 "지금의 것 하나"다 — 동의 받은 날과 같은 자리.
  - `pets.grooming_cycle_weeks smallint null` (CHECK 1~52)
  - `pets.revisit_nudged_on date null`
  - Alembic `0018`(다른 묶음과 번호가 겹치면 계획에서 맞춘다). 익명화는 둘 다 비운다.
- **visit 은 그 값을 허브 포트로 읽는다.** ③-B 의 `CustomerDirectoryPort.care_facts` 가 돌려주는 아이 사실에 칸 둘을 더한다(새 메서드를 만들지 않는다 — 여러 아이를 한 번에 읽는 길이 이미 있다).
- **반려동물 상세(customer)는 주기를 허브 포트로 받는다.** `VisitLedgerPort` 에 읽기 하나 — 아이 ID 와 직접 정한 값을 받아 주기·출처·간격 수·마지막 완료 방문의 날·다음 올 때·앞으로 예약이 있는지를 돌려준다. customer 는 계산 규칙을 모른다.
- 스포크끼리 import 하지 않는다. `notification` 은 주기를 이벤트로만 받는다.

### 4.2 목록의 질의

지금 `due_candidates` 는 "마지막 완료 방문이 57~365일 전"을 SQL 로 거른다. 주기는 아이마다 달라 SQL 한 줄로 못 거른다. **후보를 넓혀 읽고 파이썬에서 거른다**: 마지막 완료 방문이 1년 안이고 앞으로 예약이 없는 아이 전부 → 그 아이들의 최근 완료 방문 날짜를 한 번에(아이마다 6개, 창 함수) → `care_facts` 한 번 → 순수 함수로 주기·묶음. 작은 매장의 한 해 손님은 수백 마리다(⑧ 과 같은 전제 — 미리 계산한 표·캐시를 두지 않는다). 질의 수는 아이 수와 상관없이 고정이고 테스트가 호출 수를 고정한다.

### 4.3 API (모양은 계획에서 굳힌다)

- `GET /v1/shops/{id}/revisits?bucket=soon|due&cursor=` — 매장 멤버(`get_shop_context`). 20개씩. 항목: 아이 카드(사진·이름), `last_visit_date`, `last_visit_id`, `cycle_weeks|null`, `cycle_source: manual|computed|single|none`, `due_date|null`, `nudged_on|null`. **`GET /sales/due-pets` 는 없앤다**(아직 배포 전이라 옛 앱이 없다).
- 캘린더 응답(`VisitCalendarSchema`)에 `revisit_soon_count`·`revisit_due_count`(달과 상관없이 오늘 기준 — `unresolved_total` 과 같은 성격), 날마다 `unpaid_count`·`check_count`. 매출 요약의 지난 아이 수는 같은 함수의 '지남'.
- 하루 목록·피드 항목에 `marks: [code]`(4.4). 하루 응답의 `counts` 에 `unpaid`.
- `GET …/visits/{id}/next-draft` 응답에 `cycle_source`.
- customer: `PUT /v1/shops/{id}/pets/{pet_id}/grooming-cycle` `{weeks}` · `DELETE` 같은 경로 · `PUT …/pets/{pet_id}/revisit-nudge`(본문 없음, 오늘로 적는다). 반려동물 상세 응답에 `revisit: {cycle_weeks, cycle_source, interval_count, last_visit_date, due_date, has_upcoming, nudged_on}`.
- 로그인 없는 경로·보호자 경로·공개 스키마는 건드리지 않는다.

### 4.4 표시가 들어올 자리 — `marks`

하루 목록·피드의 방문 항목에 문자열 목록 `marks` 를 둔다. 서버가 그 방문에 해당하는 코드를 싣고, 앱은 **아는 코드만** 정해진 순서로 낱말로 바꾼다(모르는 코드는 버린다 — 서버가 더해도 옛 앱이 죽지 않는다).

| 코드 | 낱말 | 누가 채우나 |
|---|---|---|
| `paid` | `결제 완료` | 이 묶음 |
| `report_sent` | `알림장 보냄` | 이 묶음(지금의 `report_sent` 칸은 남기고 같은 값을 싣는다) |
| `consent_sent`·`consent_signed` | (⑪ 이 정한다) | ⑪ 전자 동의서 |
| `pass_used` | (⑭ 가 정한다) | ⑭ 정기권 |
| `deposit_received` | (⑮ 가 정한다) | ⑮ 예약금 |

- 규칙: **줄에는 끝낸 일의 낱말만, 남은 일은 `확인 N` 과 머리 요약의 숫자로.** 새 묶음이 "남은 일"을 더하고 싶으면 확인할 것(③-B 의 판정 연쇄)에 항목을 더한다 — 그러면 하루 줄의 `확인 N` 과 달력의 고리에 저절로 든다.
- 한 줄에 낱말이 넷을 넘으면 뒤의 것을 `+2` 로 접는다. 달력 칸에는 `marks` 가 가지 않는다.

### 4.5 앱

- 목록 화면은 `features/sales` 에서 `features/visit` 로 옮긴다(`sales` 는 다른 기능을 import 하지 못해 예약 등록·공유 문안과 이을 수 없다. `visit → customer` 는 허용된다). 경로 `/revisits`. 매출 탭은 라우터 경로로만 간다. 세그먼트 [지남][곧], `AsyncBody`, 20개씩.
- 주기의 문구(`보통 N주마다`·`N일 지남`·`쯤`), 안내 글, 초안 날짜 옮기기는 `features/visit/state/` 의 순수 함수. 반려동물 상세의 주기 줄과 시트는 `features/customer`(`grooming_consent_row.dart` 옆, 쓰기는 `CustomerCommands`).
- `marks` 는 `fromJson` 에서 enum 으로 한 번만 바꾼다. 달력 칸의 고리는 `Semantics` 이름표에 `남은 일 있음` 을 싣는다.
- 공유는 `shareSheetProvider`. 안내 글에 보호자 이름·번호를 넣지 않는다.

### 4.6 나누기

- **⑬-1 백엔드** — 칸 둘·마이그레이션, 주기 함수와 세 군데 바꾸기, `care_facts`·`VisitLedgerPort`·`VisitClosed` 의 칸, `/revisits`, 달력·하루·피드 응답, 흐름 스크립트.
- **⑬-2 앱** — 목록 화면 옮기기와 [예약]·[안내], 반려동물 상세의 주기 줄·시트, 완료 시트의 문구, 하루 줄·피드·상세의 `결제 완료`, 머리 요약, 달력의 고리와 미리보기 카드, 시뮬레이터 흐름.

## 5. 잠금·권한·보안

### 5.1 잠금

- 주기·안내한 날의 쓰기는 customer 의 가족 잠금을 맨 앞에서 잡는다(동의 쓰기와 같다). 방문 행을 건드리지 않는다. 잠금 순서 규칙은 그대로다.
- 검색되는 글이 아니므로 `SearchSourceChanged` 를 내지 않는다.

### 5.2 권한

새 권한을 만들지 않는다. `/revisits` 와 달력·하루의 새 칸은 매장 멤버, 주기·안내한 날의 쓰기는 `customer:write`. 매출 요약의 수는 지금처럼 `sales:read`.

### 5.3 위험과 막는 법

| | 위험 | 막는 법 |
|---|---|---|
| R1 | 다른 매장의 아이·방문이 섞인다 | 모든 질의가 `ShopContext` 의 `shop_id`. 통합 테스트의 첫 줄은 테넌트 격리. |
| R2 | 익명화한 고객·무지개다리 아이가 목록·수에 나온다 | ⑧ 의 `showable_pets` 거르기를 그대로 쓴다. 익명화가 칸 둘을 비운다. |
| R3 | 직원 화면에 금액이 나온다 | 새 응답 칸에 금액이 없다(스키마 테스트가 칸을 고정). |
| R4 | 방문 두 번으로 "보통"이라고 말한다 | 간격 수를 응답에 싣고 문구 함수가 가른다. 테스트에 0·1·2개. |
| R5 | 날짜 경계 — 다음 올 때가 하루 어긋난다 | 전부 매장 시간대의 날짜. 테스트에 예상일 당일·하루 전·하루 뒤·7일 뒤·8일 뒤, 자정 앞뒤 방문. |
| R6 | 목록이 아이 수만큼 질의한다 | 4.2 — 호출 수 고정 테스트. |
| R7 | 알림 줄의 주 수가 바뀌어 심사받은 문안과 어긋난다 | 문안의 변수(`#{간격}`)는 그대로 주 수다. 순서만 바뀐다. 가짜 게이트웨이 흐름으로 확인. |
| R8 | 안내 글·이름이 로그에 남는다 | 글은 앱에서 만들고 서버로 보내지 않는다. 새 로그를 더하지 않는다. |
| R9 | 달력 한 달의 확인할 것 판정이 무겁다 | 오늘 이후의 살아 있는 방문만 판정하고 `care_facts` 한 번. 지난 날은 `unpaid_count` 만. |

## 6. 테스트와 검증

- **백엔드 단위**: 주기 함수(중앙값·짝수 개·7일 미만 버리기·2년 창·1~52 자르기·직접 정한 값 우선), 묶음 판정, `marks` 조립, 알림 주 수의 순서.
- **백엔드 통합**: 격리, `/revisits` 의 두 묶음과 공통 조건(앞날 예약·무지개다리·익명화·1년), 주기 없는 아이의 8주, 요약의 수와 목록의 수가 같다, 직원도 200, 달력·하루의 수, 익명화가 칸을 비운다, 변이로 판별력 확인(매장 거르기·"곧"의 경계).
- **흐름 스크립트** `backend/scripts/check_revisit_flow.sh`: 방문 몇 번 → 주기를 손계산과 견준다 → 목록의 두 묶음 → 직접 정하기 → 예약을 잡으면 빠진다 → 안내한 날 → 완료한 방문에 금액을 적으면 `paid`.
- **앱**: 문구 함수, 목록 화면(두 묶음·[예약]·[안내]), 주기 시트, 하루 줄·머리 요약, 달력 고리, 골든(하루 화면·달력은 의도한 변화라 다시 찍고 눈으로 본다), 시뮬레이터 흐름 iOS·안드로이드.
- `flutter analyze` 0, import-linter, 라우트 허용 목록 그대로.

## 7. 만드는 사람에게 맡기는 것

- 문구의 마지막 다듬기, 고리의 크기·자리, 시트의 모양(기존 시트를 따른다).
- `revisit` 응답 칸의 이름, 후보 질의의 정확한 모양, 색인이 모자라면 같은 마이그레이션에.
- 초안의 날이 지났을 때 "가장 가까운 같은 요일"이 쉬는 날이면 — 지금 등록 화면의 휴무 경고에 맡긴다.
- 결정 기록은 `_docs/decisions/014-…`(번호는 계획에서).

## 8. 근거가 약한 곳

- "MoeGo 의 고객 단위 주기가 여러 마리 집에서 불편하다"는 조사의 추론이다. 불만 리뷰는 없다.
- 달력 불만의 근거는 앱스토어 리뷰 몇 건이다. 네이버 카페·블로그의 미용사 후기는 한 건도 읽지 못했다.
- 중앙값·최근 6번·7일·"곧 = 7일"은 내가 정한 값이고 실제 매장의 방문 자료로 맞춰 본 것이 아니다. 첫 매장의 기록이 쌓이면 다시 본다.

# ⑨-1 기록 검색 — 설계

2026-11-14. 사용자는 방향("추천대로, 과금 없이")만 정했고 **항목·기준값·구조는 전부 내가 정했다**. 사용자가 본 것은 아래 1~2절의 요약이고 그대로 승인했다. 3절부터는 내 결정이다.

## 1. 왜

매장은 방문마다 글을 적는다 — 케어 노트, 내부 메모, 아이의 특이사항. 쌓이면 "귀 만지면 싫어하던 아이가 누구였지", "발톱 짧게 해 달라던 보호자" 같은 것을 찾을 길이 없다. 지금 검색은 이름·번호·초성뿐이다. 경쟁 서비스 조사에서 기록의 누적·검색은 빈틈이었다.

최종 목표는 대화형 검색(질문 → 근거 있는 답)이지만, 문장을 지어 주는 LLM 은 유료 API 라 지금은 하지 않는다(유료 전환 보류). **이번에는 찾아 주기만 한다.**

## 2. 무엇을 — 사용자가 승인한 것

- 매장이 적어 둔 글을 **뜻으로 찾는 검색 화면** 하나. 문장으로 찾으면 맞는 기록이 아이 사진·이름·날짜와 걸린 문장 한 줄로 나오고, 누르면 그 방문이나 아이 상세로 간다.
- **찾는 대상**: 방문 기록의 케어 노트와 내부 메모, 예약 메모, 반려동물 특이사항, 지병 메모, 보호자 메모.
- **빼는 것**: 주의 고객 사유(용도가 따로 있는 민감한 글).
- **들어가는 곳**: 홈의 기록 피드, 반려동물 상세의 [기록] 탭(그 아이 안에서만 찾기).
- **보는 사람**: 사장과 직원. 보호자 쪽에는 없다.
- 글자 일치와 뜻 일치를 함께 쓴다. 뜻 검색은 서버에서 도는 무료 공개 모델. 문장을 지어내는 AI 는 쓰지 않고 화면에 "AI" 표시도 없다.
- 모델은 별도 프로세스. 죽어도 글자 검색은 된다.
- 저장하면 잠시 뒤 검색에 반영된다. 삭제·고객 익명화 때는 검색 자료도 함께 지운다.
- 다른 매장의 글은 섞이지 않는다.
- 과금 0. 매장 데이터는 밖으로 나가지 않는다.
- 나누기: ⑨-1a 백엔드 → ⑨-1b 앱.

### 하지 않는 것

찾은 기록의 요약·답변(⑨-2), 사진 내용 검색, 음성 검색, 매장 사이의 검색, 보호자용 검색, 검색어 기록·추천어, 검색 결과의 쪽 나눔.

### 이러면 실패다

- 다른 매장의 글이 한 줄이라도 보인다.
- 지운 기록·익명화한 고객의 글이 검색에 남아 있다.
- 검색어나 걸린 문장이 로그에 남는다.
- 임베딩 프로세스가 죽었다고 검색 화면이 오류가 된다.
- 기록 저장이 색인 때문에 느려지거나 실패한다.

## 3. 어떻게 — 백엔드 (⑨-1a)

### 3.1 새 스포크 `search`

`backend/apps/search`. 다른 스포크를 import 하지 않는다. 글은 **허브 포트로 읽고**, 바뀌었다는 사실은 **허브의 이벤트로 듣는다.**

### 3.2 색인 대상 — 문서 여섯 종류

| kind | 글 | 누르면 | 날짜 |
|---|---|---|---|
| `care_note` | 방문 기록의 케어 노트 | 방문 상세 | 방문 날 |
| `internal_note` | 방문 기록의 내부 메모 | 방문 상세 | 방문 날 |
| `visit_memo` | 예약 메모 | 방문 상세 | 방문 날 |
| `pet_memo` | 반려동물 특이사항 | 반려동물 상세 | 없음 |
| `condition_note` | 지병 하나 — 이름과 메모(`심장 질환 — 약 복용 중`). **메모가 없어도 이름만으로 문서가 된다**(지병 이름으로 찾을 수 있게) | 반려동물 상세 | 없음 |
| `customer_memo` | 보호자 메모 | 그 보호자의 첫 아이 상세([보호자] 탭은 앱이 연다) | 없음 |

- 빈 글·공백만인 글은 문서가 없다(지병은 예외 — 위). 한 글이 한 문서다. 글은 길어야 1000자(케어 노트·내부 메모), 나머지는 500자다. **자르지 않는다** — 모델은 앞 512토큰까지만 읽으므로 아주 긴 글의 뒷부분은 글자 검색으로만 걸린다. 알고 받아들인다(나누면 유일 키와 같은 방문 접기가 복잡해진다).
- 방문의 상태는 가리지 않는다(취소한 예약의 메모도 찾아진다). 무지개다리 아이의 글도 찾아진다.
- 익명화한 고객의 것은 전부 지운다. 지운 반려동물·지운 기록의 것도 지운다.

### 3.3 표

- `search_documents` — `shop_id`, `kind`, `source_id`(그 kind 의 원본 행 ID; 방문 계열은 visit_id, `pet_memo` 는 pet_id, `condition_note` 는 지병 행 ID, `customer_memo` 는 customer_id), `customer_id`, `pet_id`(없을 수 있다), `visit_id`(없을 수 있다), `happened_on`(없을 수 있다), `body`(글 사본), `embedding vector(384)`(없을 수 있다 — 아직 임베딩 전이거나 모델이 죽어 있었다), `model`(임베딩을 만든 모델 이름), `updated_at`. 유일: `(shop_id, kind, source_id)`. 색인: `body` 의 trigram GIN, `embedding` 의 HNSW(cosine), `(shop_id, customer_id)`, `(shop_id, pet_id)`.
- `search_jobs` — 다시 색인할 대상의 줄(`shop_id`, `scope`, `ref_id`, `enqueued_at`, `generation`(같은 대상이 다시 바뀔 때마다 오른다), `attempts`, `next_attempt_at`). scope 는 `visit`·`pet`·`customer` 셋 — 그 대상의 문서를 **통째로 다시 맞춘다**(읽어서 있으면 upsert, 없어진 것은 지운다). 유일 `(shop_id, scope, ref_id)` 로 같은 대상이 겹쳐 쌓이지 않는다 — 이미 줄이 있으면 `generation` 을 올리고 `next_attempt_at` 을 지금으로 당긴다. 색인기는 일을 끝냈을 때 자기가 집은 `generation` 그대로일 때만 줄을 지운다(처리하는 사이의 변경이 사라지지 않게).
- pgvector 확장은 이 마이그레이션이 켠다(`CREATE EXTENSION IF NOT EXISTS vector`). 이미지(`pgvector/pgvector:pg17`)에 들어 있다.

글 사본을 두는 까닭: 글자 검색(trigram)과 걸린 문장 보이기를 스포크 경계를 넘지 않고 한 번의 질의로 끝낸다. 대가는 개인 글이 한 벌 더 있다는 것 — 그래서 지우는 길(3.5)이 이 설계의 가장 중요한 부분이다.

### 3.4 흐름 — 쓰기

1. visit·customer 의 유스케이스가 글에 닿는 쓰기를 하면 허브 이벤트를 낸다(같은 트랜잭션). 새 이벤트: `SearchSourceChanged(shop_id, scope, ref_id)` 하나. **지금의 이벤트 버스는 `VisitEvent` 전용이고 customer 는 낸 적이 없다** — 버스가 받는 형을 넓히고, 구독자가 자기 이벤트만 받게 하고(알림 구독자가 새 이벤트마다 질의를 하지 않게), customer 에 내는 자리를 더하는 것이 이 작업에 든다. 내는 곳 — 기록 저장·삭제, 방문 등록·수정·날짜 옮기기, 반려동물 등록·수정·삭제·무지개다리, 보호자 등록·수정, 고객 익명화.
2. `search` 의 구독자가 **그 트랜잭션 안에서** `search_jobs` 에 한 줄 넣는다(이미 있으면 그대로). 임베딩도 원본 읽기도 하지 않는다 — 저장이 느려지지 않는다.
3. **색인기**(API 프로세스 안의 백그라운드 루프, 알림 디스패처와 같은 모양)가 줄을 집어 커밋한 뒤:
   - 허브 포트 `SearchSourcePort.documents(ctx, scope, ref_id)` 로 지금의 문서 목록을 읽는다(visit·customer 가 구현한다. 익명화·삭제된 대상은 빈 목록).
   - 임베딩 프로세스에 글을 보내 벡터를 받는다. **잠금을 쥔 채 부르지 않는다.**
   - 그 대상의 문서를 한 트랜잭션에서 갈아 끼운다(없어진 것 삭제, 나머지 upsert). **이 트랜잭션은 먼저 고객 행을 잠그고(`CustomerDirectoryPort.lock_family`) 원본을 다시 읽어, 임베딩 전에 읽은 글과 같을 때만 쓴다** — 다르면 쓰지 않고 줄을 남긴다. 읽은 뒤에 익명화가 끼어들어도 옛 글을 되살리지 않는다. 잠금 순서는 고객 행 → 검색 표이고 루트 CLAUDE.md 의 잠금 순서 줄에 더한다.
   - 임베딩이 실패하면 `embedding` 을 비운 채 글만 넣고, 줄을 남겨 나중에 다시 한다(간격을 늘려 가며, 끝없이 되풀이하되 조용히).
4. 색인기는 `ShopContext` 를 가드 없이 만들어야 한다 — 요청 밖이므로 기존 `notification/app/services/system_context.py` 와 같은 종류다. **가드 없이 만드는 곳을 늘리지 않으려고 그 모듈을 허브 쪽 공용 자리로 옮기거나, search 가 포트로 받아 쓴다** — 어느 쪽이든 "권한이 비어 있고 포트 읽기에만 쓴다"는 규칙은 그대로고 루트 CLAUDE.md 의 그 줄을 고친다.

### 3.5 지우기 — 세 겹

1. 이벤트 → 줄 → 색인기가 빈 목록을 읽고 지운다(보통의 길).
2. **고객 익명화는 그 트랜잭션 안에서 바로 지운다** — 색인기를 기다리지 않는다. 익명화 유스케이스가 허브 포트(`SearchIndexPort.forget_customer(ctx, customer_id)`)를 부르고 search 가 구현한다. 고객 ID 로 모든 kind 를 지운다(익명화는 방문의 글을 이벤트 없이 비운다). 줄도 하나 넣어 뒤에서 한 번 더 맞춘다.
3. 맞춤 스크립트 `scripts/reindex_search.py [--shop <id>] [--purge-orphans]` — 전부 다시 줄에 넣고, 원본이 없는 문서를 지운다. 처음 배포할 때의 채우기도 이것이다.

### 3.6 임베딩 프로세스

- compose 서비스 `embed`. 파이썬, ONNX 런타임(CPU, 토치 없음). 모델 **`intfloat/multilingual-e5-small`**(384차원, MIT). **계획의 첫 작업은 이 모델이 실제로 올라가는지 확인하는 것이다** — `fastembed` 가 기본으로 지원하지 않으면 ONNX 파일을 직접 등록하고(평균 풀링·정규화를 맞춘다), 그것도 안 되면 `paraphrase-multilingual-MiniLM-L12-v2`(384차원)로 바꾼다(접두어 규칙이 없다). 질의에는 `query: `, 문서에는 `passage: ` 를 붙인다(모델의 규칙).
- 안쪽 HTTP 하나: `POST /embed {kind: "query"|"passage", texts: [...]}` → `{model, vectors}`. 게이트웨이에 싣지 않는다(밖에서 못 부른다). 인증 없이 compose 내부망만.
- 모델 파일은 이미지를 지을 때 받아 이미지에 넣는다(기동 때 인터넷이 필요 없다). 받는 곳은 공개 저장소이고 매장 데이터는 보내지 않는다.
- **글과 벡터를 로그에 남기지 않는다.** 로그는 건수·걸린 시간뿐.
- 백엔드 쪽 어댑터는 시간 제한(질의 1.5초, 색인 10초)을 두고, 실패하면 예외 대신 "없음"을 돌려준다.
- 모델을 바꾸면 `model` 이 다른 문서가 생긴다 — 뜻 검색은 지금 모델의 문서만 보고, `reindex_search.py` 가 다시 만든다.

### 3.7 검색

`GET /v1/shops/{shop_id}/search?q=&pet_id=` — 매장 멤버(`get_shop_context`).

- `q`: 다듬어서 2~100자. 아니면 422. `pet_id` 를 주면 그 아이의 문서(와 그 아이 보호자의 `customer_memo`)만.
- 글자 후보: `body` 에 검색어가 들어 있거나(ILIKE) trigram `word_similarity` 가 기준(0.3) 이상인 것, 위에서 50.
- 뜻 후보: 질의 벡터와 cosine 거리가 가까운 것 위에서 50, 유사도 기준(0.80 — e5 는 점수가 높게 몰린다. 3.9 의 품질 확인으로 맞춘다) 미만은 버린다. 임베딩을 못 받으면 이 후보는 없다.
- 둘을 순위 합치기(RRF, k=60)로 합쳐 위에서 30. 같은 방문의 `care_note`·`internal_note`·`visit_memo` 가 함께 걸리면 가장 높은 것 하나만 남긴다.
- 응답: `{items: [{kind, owner: {customer_id, name}, pet: {pet_id, name, photo}|null, visit_id|null, open_pet_id|null, date|null, snippet}], semantic: bool}`.
  - `owner.name` 은 늘 온다 — 아이가 없는 줄(보호자 메모, 보호자만의 방문)은 앱이 보호자 이름을 보인다.
  - `open_pet_id`: 방문이 없는 줄을 눌렀을 때 열 반려동물. `pet_memo`·`condition_note` 는 그 아이, `customer_memo` 는 그 보호자의 아이 가운데 무지개다리가 아닌 가장 먼저 등록한 아이(없으면 가장 먼저 등록한 아이). 앱에는 고객 상세 경로가 없어 서버가 정해 준다.
  - `snippet`: 글자가 걸렸으면 걸린 자리 앞뒤로, 아니면 글의 앞에서 — 80자까지, 잘렸으면 `…`. 강조 표시 자리는 주지 않는다.
  - `semantic`: 뜻 검색이 함께 됐는가. 앱은 이것으로 아무것도 그리지 않는다(진단용).
  - 이름·사진은 허브 포트로 읽어 붙인다 — 이름은 `CustomerDirectoryPort`, 프로필 사진은 `VisitLedgerPort.latest_covers` → `MediaLibraryPort.read_urls`(기존 것). 익명화·삭제된 것이 그 사이에 걸리면 그 줄을 뺀다.
- **검색어·snippet 을 로그·오류에 남기지 않는다.** 접근 로그는 이미 질의 문자열을 통째로 가린다(`core/access_log.py`) — 새 경로도 가려지는지 테스트 하나. 422 응답 본문이 입력값을 되돌려 주지 않는지 확인한다(`core/http_errors.py`).
- 공개 경로가 아니다(허용 목록을 건드리지 않는다). 구조 규칙대로 `GET <prefix>/myself` 를 둔다.

### 3.8 권한

새 권한 없음. 읽기는 매장 멤버. 내부 메모도 직원이 이미 본다.

### 3.9 품질 확인

- `backend/scripts/check_search_quality.py` — 가짜 매장에 기록 60개쯤(실제 같은 문장, 사람 이름·번호 없음)을 넣고 질문 30개의 정답 문서가 위 5개 안에 드는 비율을 잰다. **기준: 30개 가운데 24개(0.8) 이상.** 글자만으로 되는 질문과 뜻으로만 되는 질문(말을 바꾼 것)을 반씩.
- 기준에 못 미치면: 유사도 기준·후보 수를 먼저 고치고, 그래도 안 되면 같은 계열의 큰 모델(`multilingual-e5-base`, 768차원 — 표의 차원이 바뀐다)을 재 보고, 그래도 안 되면 **멈추고 사용자에게 유료 모델을 묻는다.**
- 이 확인은 임베딩 프로세스가 떠 있어야 해서 CI 에는 넣지 않는다(로컬 확인 — `_docs/harness.md` 에 적는다).

### 3.10 테스트

- 단위: 문서 만들기 규칙(빈 글, 지병 이름 붙이기), snippet, RRF, 같은 방문 접기, 질의 검증. 임베딩은 가짜(정해진 벡터).
- 통합(PG): 매장 격리(다른 매장의 문서가 후보에 없다), `pet_id` 거르기, 익명화 트랜잭션 안의 삭제, 색인기의 갈아 끼우기와 임베딩 실패 뒤 재시도, 줄의 중복 없음, 이벤트 → 줄.
- 흐름 스크립트 `check_search_flow.sh`(게이트웨이 경유): 기록을 적고 → 잠시 뒤 글자로 찾아진다 → 말을 바꿔도 찾아진다 → 기록을 지우면 사라진다 → 익명화하면 사라진다 → 다른 매장에서는 안 보인다 → `embed` 를 멈춰도 글자 검색은 200.
- import-linter: 스포크 독립 계약에 `search` 를 넣는다.

## 4. 어떻게 — 앱 (⑨-1b)

- 기능 폴더 `features/search`(`auth` 만 import, 상세로는 라우터 경로로 간다). 화면 `/search?pet_id=`.
- 들어가는 곳: 홈 기록 피드 머리의 돋보기, 반려동물 상세 [기록] 탭의 돋보기(그 아이로 좁혀 연다 — 화면 위에 `{이름}의 기록에서` 한 줄).
- 입력 칸 하나. 2자 이상에서 0.5초 쉰 뒤 묻는다. 새 검색을 보내면 늦게 온 옛 결과는 버린다.
- 줄: 사진 40 · 아이 이름(아이가 없는 줄은 사진 없이 보호자 이름) · 종류와 날짜(`케어 노트 · 11월 3일`) · snippet 두 줄까지. 누르면 방문 상세 또는 반려동물 상세.
- 빈 결과: `찾은 기록이 없어요`. 처음: `기록에 적어 둔 말로 찾아보세요` 와 예시 둘. 오류는 `AsyncBody`.
- 톤은 앱 그대로 — "AI"·반짝이 아이콘·색 딱지 없음.
- 위젯 테스트·골든·시뮬레이터 흐름(iOS·안드로이드).

## 5. 위험과 막는 법

| | 위험 | 막는 법 |
|---|---|---|
| S1 | 다른 매장의 글이 보인다 | 모든 질의가 `ShopContext` 의 shop_id 로 거른다(저장소 메서드의 첫 인자). 통합 테스트와 흐름. |
| S2 | 지운 글이 남는다 | 3.5 의 세 겹. 익명화는 같은 트랜잭션. |
| S3 | 소형 모델의 한국어 품질 | 3.9 의 기준과 올라가는 순서. 글자 검색이 늘 바닥을 받친다. |
| S4 | 임베딩이 느리거나 죽는다 | 시간 제한, 실패는 글자 검색으로. 색인은 줄에 남아 다시 한다. |
| S5 | 검색어·글이 로그에 샌다 | 3.6·3.7 의 규칙. 접근 로그 확인. |
| S6 | 저장이 느려진다 | 트랜잭션 안에서는 줄 한 줄뿐. |
| S7 | 메모리 | e5-small ONNX 는 수백 MB. 개발 맥에서는 문제없다. 배포 때 1GB 쯤 더(비용은 그때 밝힌다). |
| S8 | 색인기가 여러 프로세스에서 돈다 | 줄을 `FOR UPDATE SKIP LOCKED` 로 집는다(디스패처와 같다). |

## 6. 만드는 사람에게 맡기는 것

- 이벤트·포트·슬라이스의 정확한 이름, 폴더 이름(GoF 이름은 실제 그 패턴일 때만).
- snippet 의 정확한 자르기, RRF 상수의 미세 조정, 색인기의 재시도 간격.
- `system_context` 를 어디에 둘지(3.4 의 4).
- 품질 확인용 문장 60개·질문 30개의 내용.
- 결정 기록은 `_docs/decisions/013-record-search.md`.

# 005 — 고객·반려동물과 기본 검색에서 내린 결정

- 날짜: 2026-09-22
- 대상 브랜치: `feat/customer-2a-backend` (②-1 백엔드). ②-2 앱이 끝나면 같은 문서에 앱 몫을 더한다.
- 근거: 설계 `docs/superpowers/specs/2026-09-22-customer-pet-design.md`, 계획 `docs/superpowers/plans/2026-09-22-customer-2a-backend.md`

## 무엇을 만들었나 (②-1)

`backend/apps/customer` 스포크를 API 프로세스에 붙였다. 엔드포인트 14개(설계 5절 표 전부 — 목록·번호 조회·등록·고객 상세·수정·익명화 삭제·반려동물 추가·상세·수정·무지개다리·되돌리기·삭제·질병 종류·자기소개), 마이그레이션 `0005`(표 5개, 질병 종류 시드 10개, `pg_trgm`), 검색 포트 `CustomerSearchPort`와 PostgreSQL 구현, 검색 줄 재생성 스크립트, 흐름 확인 스크립트 `check_customer_flow.sh`. 앱 쪽은 `Pressable`의 의미 노드 경계 하나만 고쳤다 — `Semantics(container: true)`로 스크린리더 포커스와 이름표 탭 위치가 행 전체 폭이 아니라 버튼 크기(최소 44×44)로 잡힌다. 설계 3.1 은 이 항목을 "결정 기록 004 의 남는 것"이라 적었지만 004 에는 그 줄이 없었다.

## 가족을 바꾸는 쓰기는 고객 행을 먼저 잠근다

설계 9절 표에 없던 경합 두 개를 계획을 쓰며 찾았다.
- **익명화와 겹친 반려동물 추가(C14).** `pets` INSERT 는 `customers` 행에 `KEY SHARE`만 걸고, 익명화의 `UPDATE customers`(키가 아닌 칸)는 `NO KEY UPDATE`라 서로 막지 않는다. 잠금이 없으면 익명화가 커밋된 뒤 추가도 커밋되어 익명화한 고객에게 이름 있는 반려동물이 붙고, 검색 줄이 되살아난다.
- **마지막 두 마리 동시 삭제(C13).** 둘 다 "두 마리"로 세고 지워 반려동물 없는 가족이 남는다(목록은 반려동물 중심이라 그 가족이 보이지 않는다).

그래서 가족을 바꾸는 유스케이스는 맨 앞에서 고객 행을 `FOR UPDATE`로 잠그고 다시 읽는다(`lock_active`, 반려동물 경로는 `lock_owner`). 잠금을 기다리는 사이 익명화됐으면 PostgreSQL 이 풀려난 뒤 `deleted_at IS NULL` 조건을 다시 평가해 행이 빠지므로 404 가 된다. 검색 줄 재생성 스크립트(`scripts/rebuild_customer_search.py`)도 같은 순서를 따른다 — 고객마다 고객 행을 먼저 잠그고 짧게 커밋한다(살아 있는 고객만 보는 `lock_active`는 익명화한 고객에게 못 쓰므로 직접 잠근다).

두 세션 테스트는 잠금을 빼는 변이로 실패하는 것을 확인했다. 반려동물 수정은 익명화가 `pets` 행도 고치기 때문에 `lock_owner`의 잠금을 빼도 `pets` 행의 암묵적 잠금에서 기다렸다가 같은 결과(404)가 나온다 — 판별력이 없다. 그래서 그 경로는 인터랙터를 거치는 대신 저장소 수준으로 내려가 `PetPgRepository.lock_owner`가 고객 행을 실제로 잠그는지를 `test_lock_owner가_고객_행을_쥔_동안_다른_세션의_고객_잠금은_기다린다`로 직접 본다(`lock_owner`의 `FOR UPDATE`를 빼면 이 테스트가 바로 실패한다).

## 접근 로그의 쿼리 문자열을 가린다

번호 조회(`?phone=`)와 검색(`?q=` — 이름·번호 뒷자리)은 설계대로 GET 쿼리로 받는다. uvicorn 의 접근 로그가 쿼리를 그대로 남기므로(C7 "로그 금지"에 어긋남) API 프로세스가 import 될 때 `uvicorn.access` 로거에 쿼리를 `?[가림]`으로 바꾸는 필터를 단다(`core/access_log.py`). 경로는 남는다. 게이트웨이(Caddy)는 접근 로그를 켜지 않았다. 검토한 다른 안: 번호 조회를 POST 로 바꾸기(설계의 API 모양이 바뀌고 검색어 문제는 그대로 남는다), 접근 로그 끄기(경로까지 사라진다).

## 계획에서 새로 정한 것

설계의 빈틈을 가장 작게 메운 것이다. **계획서 머리말 "이 계획에서 새로 정한 것"(15개 항목) 가운데 ②-2 앱이 기댈 API 계약과 관련된 것을 옮겨 적는다 — 계획서 원문과 완전히 같지는 않다.**
- 뒷자리 검색은 "4자리 이하 숫자 → 번호 뒷자리가 그 숫자로 시작"이다(치는 중인 56 도 5678 을 찾는다). 5자리 이상은 전체 번호 부분 일치. **설계 7.3 의 "4자리 이하면 뒷자리 우선"(그 밖의 정렬과 섞어 보여 준다)을 "뒷자리로만"으로 좁혔다** — 가운데 자리 3~4자리로는 찾지 못한다. 순위를 섞으면 커서 페이지와 충돌하고, 뒷자리로만 찾으면 동작이 예측 가능하다.
- 가나다순의 키는 보호자 이름이다. 한글과 숫자·영문 사이의 순서는 DB 정렬 규칙(개발 DB `en_US.utf8` — 한글이 먼저)을 따른다.
- 최근순의 키는 고객과 그 반려동물의 `updated_at` 가운데 가장 늦은 값이다. 수정(PUT)·무지개다리는 값이 같아도 `updated_at`을 새로 찍는다. 반려동물 삭제는 활동으로 치지 않는다. **설계 7.2 는 무지개다리 표시에 `passed_away_at`만 찍는다고 했지만, 최근순 정렬(설계 7.3)을 위해 `updated_at`도 함께 찍는다** — 무지개다리를 표시하거나 되돌린 가족이 최근 활동으로 목록 위로 올라온다.
- 목록 응답에 `pet_count`(검색·무지개다리 조건에 맞는 반려동물 수 — 앱 제목 "고객 N마리")를 더했다.
- 번호 조회의 `pet_names`에는 무지개다리 아이를 넣지 않는다.
- 무지개다리를 다시 누르면 처음 시각을 지킨다.
- 전화번호 형식: 휴대전화(010·011·016~019), 서울(02), 지역 번호(031~065 범위의 세 자리, 없는 국번 포함), 인터넷 전화(070). `+82` 표기와 **전각 숫자는 받지 않는다. 보조 연락처도 같은 형식을 본다.**
- 질병 항목은 한 번에 20개까지. 모르는 질병 종류, 기타가 아닌데 이름을 넣은 것, 같은 정해진 질병 두 번은 422 `VALIDATION_ERROR`.
- 문자열 칸은 기존 관례대로 길이 제한이 있는 `varchar`다(설계 표의 `text` 대신). 전화번호 칸은 11자. **경로 변수(고객·반려동물 ID)가 bigint 상한(2^63-1)을 넘으면 DB 에 닿기 전에 422 다.**
- 검색 줄 재생성 스크립트 `backend/scripts/rebuild_customer_search.py`(설계 6.4 "재생성 스크립트로 복구한다")를 둔다.
- **`rebuild_search_entry(ctx, customer_id)`는 리포지토리가 아니라 `CustomerSearchPort`에 둔다.** 설계 6.4 는 "리포지토리 한 메서드"라고 했지만, 전용 검색 엔진으로 바꿀 때 색인 쓰기도 함께 바뀌어야 하므로 검색 포트가 맡는다. 이름과 동작(같은 트랜잭션, 원본에서 다시 만든다, 익명화면 지운다)은 설계 그대로다.
- **요청·응답 모양.** 등록 본문은 `{"customer": {…}, "pet": {…}}`. 등록·고객 수정·고객 상세는 `{customer, pets}`(고객 상세, 전체 번호 포함)를, 반려동물 추가·상세·수정·무지개다리·되돌리기는 `{pet, owner, siblings}`(반려동물 상세, 보호자 번호는 가림)를 돌려준다. 삭제 둘은 204. 몸무게는 JSON 숫자로 나간다.
- **커서는 정렬 키·고객 ID 를 담은 불투명 문자열이고, 틀리거나 다른 정렬의 커서면 422 다.** 이름순 커서는 base64 로 인코딩한 JSON 안에 마지막 보호자 이름(가나다순 키)을 담는다 — 앱은 커서를 해석하지 않고 그대로 돌려보내야 한다.
- **나이 표시:** 생일이 있으면 만 나이(1살 전에는 "N개월"), 태어난 해만 있으면 해의 차이("1살 미만"), 둘 다 없으면 "나이 모름". 기준 날짜는 한국 시각(UTC+9)의 오늘이다. 생일은 오늘보다 늦을 수 없고, 생일·태어난 해는 40년 전까지 받는다.
- **자기소개(`/customers/myself`)는 매장 경로 아래라 소속 확인을 거친다**(설계 5절 표의 "멤버"). 토큰 없는 `/v1/shops/myself`(tenancy)와 다르다.

## 계획서에도 없는데 앱이 알아야 할 것

계획을 코드로 옮기며 굳어진 동작이라 계획서 "이 계획에서 새로 정한 것"에는 없다.
- 목록의 `q`는 50자, `cursor`는 500자를 넘으면 422 다.
- 번호 조회에서 형식이 틀린 번호(전화번호 형식 규칙에 안 맞음)는 404 가 아니라 422 다 — 등록 1단계에서 입력 도중 조회하면(형식이 아직 안 맞으면) 422 가 난다는 뜻이다.
- 무지개다리가 아닌 아이를 되돌려도(이미 살아 있는 상태에서 "되돌리기"를 다시 눌러도) 200 이고, `updated_at`이 갱신되어 최근순 목록 위로 올라온다.
- `GET /pet-condition-types`는 감싸지 않은 배열 `[{code, label, sort_order}]`을 그대로 돌려준다.
- 요청 본문의 모르는 칸은 무시된다(Pydantic 기본값 — 거부하지 않는다).
- 반려동물을 지우면 그 가족의 최근순 위치가 뒤로 밀릴 수 있다(삭제는 활동으로 치지 않으므로 `last_activity_at`이 갱신되지 않는다).
- `pet_count`는 검색·무지개다리 조건에 걸린 가족의 반려동물 전부(무지개다리 제외)를 센다 — 검색어에 걸린 반려동물 한 마리만이 아니다.
- 이름·메모 등 문자열 입력에 NUL(`\x00`)이나 제어 문자가 있으면 422 `VALIDATION_ERROR`다(메모의 개행은 예외로 허용한다) — 최종 검토 B.
- 조작된 목록 커서(범위를 벗어난 고객 ID, 제어 문자가 든 키)는 422 `VALIDATION_ERROR`다 — 최종 검토 C.

## 검토에서 고친 것

사전 점검과 작업별 검토가 구현 중에 잡아 브리프를 살짝 넘어 고친 것이다.
- **테넌트 격리.** `CustomerPgRepository.anonymize`가 반려동물·질병 행을 지울 때, `PetPgRepository.update`가 반려동물을 고칠 때 컨텍스트의 매장(`ctx.shop_id`) 소속으로 한 번 더 거른다. 처음 코드는 `customer_id`만으로 걸러서, 다른 매장 컨텍스트에 실존하는 그 ID를 넣으면 그 매장의 반려동물·질병까지 지우거나 고칠 수 있었다.
- **판별력 없던 테스트 세 벌을 실제 DB 로 보강했다.** 무지개다리 아이도 반려동물 수에 들어가는지와 다시 누르면 처음 시각을 지키는지를 가짜 저장소가 아니라 실제 DB 로 확인(마이그레이션 시점의 통합 테스트), "다른 매장 데이터는 그대로"를 실제로 확인하지 않던 테넌트 격리 테스트(같은 값으로 쓰는 바람에 결함이 있어도 통과했다), 반려동물 수정×익명화의 판별력 없는 테스트를 저장소 수준 테스트로 교체(위 "가족을 바꾸는 쓰기" 절 참고).
- **브랜치 전체 최종 검토(②-1 16개 작업이 끝난 뒤)가 잡아 고친 것 세 가지.**
  - **A. DB 오류 로그에 SQL 파라미터가 새지 않게.** `core/database.py`와 `scripts/rebuild_customer_search.py`의 `create_async_engine`에 `hide_parameters=True`를 켰다 — SQLAlchemy `StatementError`(하위 `DBAPIError`) 문자열이 `[parameters: …]`를 붙이고, 처리되지 않은 예외는 uvicorn 이 `exc_info`로 남긴다.
  - **B. 문자열에 NUL·제어 문자가 오면 500 대신 422.** 고객·반려동물 입력 스키마의 문자열 타입, 목록 `q`, 번호 조회 `phone`에 공용 검증기(`customer/adapter/inbound/api/schemas/text_validators.py`의 `reject_control_chars`)를 달았다. NUL이 스키마를 통과해 DB에 닿으면 asyncpg 가 `CharacterNotInRepertoireError`를 내며 500이 됐다. 메모(`Optional500`)만 개행을 허용한다.
  - **C. 조작된 커서가 500 대신 422.** `customer_search_pg_adapter.py`의 커서 디코드가 `customer_id`의 bigint 범위(1~2^63-1)와 키의 NUL 문자를 확인해 벗어나면 `CustomerInputError`(422)를 던진다.

## 남는 것 — 알고 미룬다

- **낡은 `ShopContext`로 끝나는 쓰기.** 요청 가드가 소속을 확인한 뒤 고객 행 잠금을 기다리는 사이 내보내진 직원의 요청은 그대로 끝난다(tenancy 의 `update_shop`과 같은 모양, 003 의 "남는 것"). 고객 쓰기는 매장 행을 잠그지 않으므로 행위자 재확인을 넣으려면 잠금 순서를 새로 정해야 한다.
- **검색 줄의 반려동물 이름에는 무지개다리 아이도 들어간다.** 무지개다리 아이 이름으로 찾으면 그 가족 카드가 나오지만, 기본 목록에서는 그 아이가 카드에 보이지 않는다.
- **질병 메모·반려동물 메모에 개인정보를 적는 것은 막지 않는다.** 익명화 때 함께 지워진다.
- **재생성 스크립트는 고객마다 커밋한다.** 중간에 멈추면 일부만 갱신된 채로 남는다 — 다시 돌리면 같은 결과가 나오므로 그냥 다시 돌리면 된다.
- **asyncpg 의 DETAIL 은 `hide_parameters`로 가려지지 않는다.** 지금은 도달 경로가 없다 — 번호 외 무결성 위반은 스키마·도메인이 먼저 막아 DB 제약 위반까지 가지 않는다.
- **uvicorn 버전을 고정하지 않았다.** 접근 로그 쿼리 가림 필터(`core/access_log.py`)가 지금 버전의 로그 레코드 `args` 모양에 기댄다 — 버전이 바뀌면 필터가 조용히 안 먹을 수 있다.

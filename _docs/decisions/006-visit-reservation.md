# 006 — 예약·방문(③-A)에서 내린 결정

- 날짜: 2026-09-23(③-A1 백엔드)
- 대상 브랜치: `feat/visit-3a1-backend`(③-A1 백엔드), `feat/visit-3a2-app`(③-A2 앱)
- 근거: 설계 `docs/superpowers/specs/2026-09-23-visit-reservation-design.md`, 계획 `docs/superpowers/plans/2026-09-23-visit-3a1-backend.md`

## 무엇을 만들었나 (③-A1)

`backend/apps/visit` 스포크를 API 프로세스에 붙였다. 엔드포인트 20개(설계 8절 표에서 ③-A3 몫인 `POST /visit-drafts`를 뺀 전부 — 하루 목록·월 달력·시간 칸·지난번처럼·예약 등록·상세·수정·가족 옮기기·상태 전이·다음 예약 초안·자기소개, 일정 설정 조회·수정, 임시 휴무 조회·추가·삭제, 메뉴표 조회·추가·수정·보관), 마이그레이션 `0006`(표 6개와 검색 줄의 `last_visit_at` 칸), 허브 포트 둘(`CustomerDirectoryPort`는 customer 가, `VisitLedgerPort`는 visit 이 구현), `ShopContext.timezone`, customer 쪽 변경(409 셋, 익명화 때 방문 메모 비우기, 고객 상세의 노쇼 횟수·다가오는 예약, 최근 방문순), 복구 스크립트 `rebuild_last_visit.py`, 흐름 확인 스크립트 `check_visit_flow.sh`. 상태 전이는 `visit/domain/state/`(State 패턴)다.

## 방문을 쓰는 경로는 고객 행부터 잠근다

방문 표에는 고객·반려동물로 가는 외래 키가 없다(스포크를 넘는 ID). 그래서 외래 키의 암묵적 잠금도 없다 — 익명화와 예약 등록이 서로를 전혀 기다리지 않는다. 잠금이 없으면 익명화한 고객에게 앞으로의 예약이 생기거나(익명화가 먼저 커밋), 예약을 보지 못한 익명화가 지나간다(예약이 커밋 전).

그래서 방문을 쓰는 모든 유스케이스(등록·수정·옮기기·상태 전이)는 맨 앞에서 허브 포트 `CustomerDirectoryPort.lock_family`로 고객 행을 `FOR UPDATE` 잠그고, 그다음 방문 행을 ID 오름차순으로 잠근 뒤 다시 읽는다(`visit/app/services/visit_locking.py`). customer 쪽 익명화·무지개다리·반려동물 삭제는 원래 고객 행을 먼저 잠그고(②의 규칙) 그 안에서 `VisitLedgerPort`로 방문을 묻는다 — 같은 순서다. `CLAUDE.md`의 잠금 순서에 "고객 행 → 방문 행"을 더했다.

경합 테스트(`tests/integration/test_visit_locking.py`)의 판별력은 변이로 확인했다. 등록의 `lock_family` 호출을 빼거나 `lock_family`가 잠그지 않게(`get_active`) 바꾸면 익명화×예약 두 테스트가 실패한다. 유일 색인을 일반 색인으로 바꾸면 동시 중복 예약 테스트가 실패한다. 완료×노쇼 테스트는 잠금이 둘(고객 행, 방문 행)이라 하나만 빼면 다른 하나가 막아 통과하고, 둘 다 빼야 실패한다 — 방문 행 잠금은 고객 잠금이 있는 한 겹쳐 지키는 것이다.

## 계획에서 새로 정한 것

설계와 모순되는 것은 없다. 설계의 빈틈을 가장 작게 메운 것과 코드를 쓰며 찾은 것이다.

1. **`ShopContext.timezone`의 기본값은 `"Asia/Seoul"`이다**(`shops.timezone`의 기본값과 같다). 매장 접근 확인은 언제나 DB 값을 채우고, 기본값은 이미 있는 테스트의 컨텍스트 생성 20여 곳을 건드리지 않으려는 것이다.
2. **시각은 시간대를 붙여 받고 매장 시간대로 돌려준다.** 요청의 `starts_at`은 `AwareDatetime`(시간대 없는 시각은 422), 응답의 모든 시각은 매장 시간대(`+09:00`)다.
3. **경고 판단은 서버 한 곳(`visit_schedule.warnings_for`)에만 있다.** 등록·수정·옮기기 응답과 시간 칸 조회가 같은 함수를 쓴다. 같은 가족 묶음(같은 보호자 + 같은 시작 시각)끼리는 겹침이 아니고, 시간 칸 조회는 묶음 없이 묻는 것이라 누구의 방문과도 겹친다. 옮기기 화면을 위해 시간 칸 조회에 `exclude`(옮길 방문)를 더했다.
4. **수정에서 가족 확인에 넘기는 아이는 새로 고른 아이뿐이다.** 그대로인 아이를 넘기면 완료한 방문의 아이가 나중에 무지개다리를 건넌 경우 메모조차 못 고친다(`PET_PASSED_AWAY`). 지금 붙어 있는 메뉴는 보관됐어도 그대로 둘 수 있다.
5. **되돌리기는 아이도 확인한다.** 취소·노쇼·완료를 되돌리면 다시 시간을 차지하는 예약이 되므로, 무지개다리 아이의 방문이면 `PET_PASSED_AWAY`(422)로 막는다(V7). 다른 전이는 보호자만 잠근다.
6. **'최근 방문순'의 키는 마지막 완료 방문의 시작 시각이다**(완료 시각이 아니라 예약 날짜). 완료가 생기거나 풀리는 전이 뒤에 원본에서 다시 계산해 같은 트랜잭션에서 넘긴다. 방문한 적 없는 가족은 맨 뒤(NULLS LAST)이고, 커서의 빈 문자열 키가 "방문 없음"이다.
7. **가족 옮기기는 묶음에서 가장 긴 소요로** 자정 넘김과 경고를 본다.
8. **하루 목록은 취소·노쇼까지 모두 보인다.** 마릿수(`visit_count`)는 예약됨·미용 중·완료만 센다. 달력 위쪽의 "정리 안 된 예약 N건"(`unresolved_total`)은 달과 상관없이 매장 전체이고 가장 이른 날(`oldest_unresolved_date`)을 함께 준다.
9. **"앞으로의 예약"은 예약됨·미용 중인 방문이다** — 날짜가 지났어도 정리하지 않았으면 든다(익명화·무지개다리를 막는다). 고객 상세의 "다가오는 예약"은 그중 오늘(매장 시간대) 이후에 시작하는 것만, 최대 3건이다.
10. **반려동물 삭제는 `PET_HAS_VISITS`를 `LAST_PET`보다 먼저 본다.** 취소된 방문만 있어도 지우지 않는다.
11. **고객 상세(GET)만 방문 요약을 더한다**(`CustomerOverviewSchema` — `no_show_count`, `upcoming_visits`). 등록·수정 응답은 그대로다.
12. **일정 설정 수정은 설정 행 UPDATE 를 맨 먼저 한다.** 두 사장이 동시에 바꾸면 늦은 쪽이 그 행에서 기다렸다가 앞선 쪽이 커밋한 쉬는 요일을 지우고 넣는다 — 따로 잠그는 SELECT 가 필요 없다.
13. **설정·쉬는 요일·임시 휴무·메뉴는 설정 행을 외래 키로 가리킨다**(스포크 안의 관계). 그래서 휴무 추가와 메뉴 추가는 먼저 설정을 준비(`ensure`)한다. 메뉴 이름은 보관하지 않은 메뉴끼리만 겹치지 않는다 — 보관한 이름은 다시 쓸 수 있다.
14. **'지난번처럼'은 반려동물 ID 만으로 이 매장의 방문을 본다.** 다른 매장의 아이 ID 를 넣어도 빈 기본값이 될 뿐 아무것도 새지 않아 가족 확인(허브 포트)을 부르지 않는다.
15. **다음 예약 초안은 취소·노쇼가 아닌 방문에서**(취소·노쇼면 409), 같은 묶음에서 취소·노쇼가 아닌 아이들 전체로. 주기는 그 아이의 완료 방문 시작 시각 두 개로 계산하되, 아직 완료 전인 방문이면 그 방문을 "이번"으로 놓고 직전 완료 방문과의 간격을 본다. (처음에는 완료한 방문에서만 줬다 — ③-A2 의 완료 시트가 누르기 전에 "언제로 잡히는지"를 보여야 해서 넓혔다.)
16. **칸 형식.** ID 는 `bigint`, 상태·취소 사유는 `varchar(20)`, 메모 `varchar(500)`, 메뉴 이름 `varchar(30)`, 휴무 메모 `varchar(30)`. 임시 휴무 표의 칸 이름은 설계대로 `date`이고 ORM 속성은 `day`다(주석의 `date` 형과 부딪혀서). 요청 본문의 목록(반려동물·메뉴·방문 ID)은 10개까지, 같은 ID 두 번은 422 다.
17. **자기소개의 번호는 5번**(auth 1, tenancy 2, platform_admin 3, customer 4 다음).
18. **허브 포트 메서드 이름은 `briefs`다**(설계 4.1·5.4 의 `summaries`). 요약 묶음(`FamilyBriefs`)을 돌려준다는 뜻으로 바꿨다.

## 작업별 검토에서 고친 것

검토자가 계획서 코드를 검토되지 않은 것으로 보고 찾은 것이다. 모두 요청 하나로 500 이 나거나 설계 규칙이 경합에서 깨지던 것이다.

- **시간대가 붙은 영업시간은 422.** `"10:00+09:00"` 같은 값이 aware `time`이 되어 여는·닫는 시각 비교에서 `TypeError`(500)였다 — 설정 스키마의 `LocalTime`이 거절한다.
- **범위 끝의 예약 시각은 422.** `9999-12-31T23:50Z` 같은 `AwareDatetime`이 매장 시간대로 옮기는 순간 `OverflowError`(500)였다 — `check_start`가 시간대 변환 전에 범위를 본다.
- **범위 밖 날짜의 하루 목록·시간 칸은 422.** `date=9999-12-31`이 하루 경계 계산에서 `OverflowError`(500)였다(하루 목록은 그 전에 설정 준비 쓰기까지 했다) — 두 인터랙터가 맨 앞에서 2000~2100년만 받는다(달력과 같은 범위).
- **되돌리기는 잠근 뒤 반려동물을 다시 본다.** 잠그기 전에 읽은 반려동물로 가족 확인을 해서, 그 사이 반려동물이 바뀌고 무지개다리가 된 경합에서 무지개다리 아이의 예약이 되살아날 수 있었다(V7) — 수정 경로와 같은 409 재확인.
- **익명화 뒤 하루 목록도 확인한다.** 배선 테스트가 설명과 달리 상세만 봤다(V23).
- **`.importlinter`의 hub·core 격리 계약에 `visit`이 두 번씩 있던 계획서 결함** — 한 번씩만 등록했다.

## 최종 검토에서 고친 것

- **조작한 목록 커서로 500.** 고객 검색의 `recent`·`last_visit` 커서에 `9999-12-31T23:00:00-05:00` 같은 시간대 끝 값을 넣으면 UTC 로 바꾸는 순간 넘쳐 500 이었다 — 시간대 없는 값과 `OverflowError`도 잡아 422 로 바꾼다.
- **메뉴 순서값 32767 뒤 추가가 500 이고 이후 추가가 계속 막힘.** `sort_order`가 `smallint` 상한에 닿으면 새 메뉴 추가의 `max+1`이 넘쳐 500 이었고, 한 번 넘치면 계속 막혔다 — 수정 요청의 상한을 9999 로 낮추고, 추가 쪽은 상한을 넘지 않게 묶는다.
- **시간 칸 `at`에 시간대가 붙으면 422, `duration=0`은 매장 기본으로 바꾸지 않는다.** 영업시간 스키마와 같은 정책으로 맞췄다.
- **`update_details`의 방문 메뉴 지우기에 매장 조건을 더했다.** 동작은 바뀌지 않지만 다른 매장의 방문 ID 로는 지워지지 않는다는 것을 조건에도 드러낸다.

## 남는 것 — 알고 미룬다

- **익명화한 고객의 방문은 모든 쓰기(수정·옮기기·전이)가 404 `CUSTOMER_NOT_FOUND`다.** 가족 잠금이 살아 있는 고객만 잠근다. 지난 기록은 읽기만 된다.
- **낡은 `ShopContext`로 끝나는 쓰기**(005 의 "남는 것" 그대로). 방문 쓰기도 매장 행을 잠그지 않는다.
- **영업시간이 모든 요일에 하나다.** 요일별 시간은 필요해지면 `visit_weekly_closures`를 요일별 시간 표로 넓힌다(설계 13절).
- **복구 스크립트는 고객마다 커밋한다.** 중간에 멈추면 일부만 맞춰진 채로 남는다 — 다시 돌리면 같은 결과다.
- **처음 여는 GET 이 쓰기를 한다.** 설정·기본 메뉴는 매장을 처음 쓸 때 만든다(조회에서도). 읽기 전용 복제 DB 로 조회를 돌리게 되면 이 준비를 따로 떼어야 한다.
- **작업별 검토의 사소한 지적은 진행 장부에 남겨 최종 검토가 추렸다**(테스트 판별력 보강, 시간대 붙은 `at`의 오프셋 무시, 조작 커서의 범위 끝 시각 등).

## ③-A2(앱)로 넘기는 것

- 응답의 시각은 매장 시간대가 붙어 있다 — 기기 시간대로 바꾸지 말고 그대로 보인다.
- 저장 버튼 두 번 → `VISIT_DUPLICATE`(409)는 "이미 저장됐어요"로 처리하고 그날 목록을 다시 읽는다.
- 상태 전이 뒤에는 그날 목록과 그 달 요약을 다시 읽는다(낙관적 갱신을 하지 않는다 — 409 가 나면 화면이 서버와 어긋난다).
- 가족 카드의 버튼은 묶음 전체의 `visit_ids`로 한 번에 부른다. 묶음은 하루 목록의 `group_key`다.
- 옮기기 화면의 시간 칸은 `exclude`에 옮길 방문을 넣어 부른다.
- 새 오류 코드 12개(설계 8절) — 앱의 오류 문구 표에 더한다.
- '지금 시작'도 자정 넘김 검사를 받는다 — 밤 늦게 온 손님은 소요를 줄여 보내야 한다(아니면 422 `VISIT_CROSSES_MIDNIGHT`).
- 하루 목록의 `group_key`는 불투명한 키다 — 해석하지 말고 같은지만 본다.
- 소요를 비우면 메뉴 기본 소요의 합이 600 을 넘을 때 422 다 — 앱은 소요를 늘 채워 보낸다.

### 이 계획에서 새로 정한 것

설계와 모순되는 것은 없다. 설계의 빈틈을 가장 작게 메운 것과, 참조 구현을 만들며 정한 것이다.

1. **시각은 `ShopTime`(벽시계 + 서버 문자열)이다.** 응답의 `2026-10-02T14:00:00+09:00`에서 앞 열여섯 자리로 시간대 없는 `DateTime`을 만들어 보이고, 저장에는 받은 문자열을 그대로 쓴다. 새 예약의 시각도 앱이 만들지 않는다 — 고른 시각을 `GET /visits/slots?at=HH:MM`로 다시 물어 그 응답의 `starts_at` 문자열과 경고를 쓴다. 매장 시간대는 앱 어디에도 없다.
2. **예약 ②의 날짜 줄은 월요일 시작 한 주**이고 ‹ › 로 한 주씩 옮긴다. 휴무일은 월 요약(`closed_day`)으로 옅게 보이되 고를 수 있다(경고만).
3. **시간 칸은 서버가 준 정시 칸만** 보이고, 칸을 길게 누르면(`Pressable.onLongPress`) 그 시(時)의 10분 단위 여섯 개를 고른다. 겹치는 칸은 줄을 긋고, 휴무·영업시간 밖은 옅게 — 그래도 누를 수 있다.
4. **반려동물이 한 마리뿐인 보호자면 그 아이를 미리 고르고 "지난번처럼"을 채운다.** 여러 마리면 고르지 않고 저장 버튼에 "반려동물이나 '보호자만'을 골라 주세요"를 적어 막는다. 무지개다리 아이는 칩이 없다.
5. **소요는 ± 10분, 길게 누르면 30분, 10~600분**(일정 설정의 기본 소요와 메뉴의 기본 소요도 같다). 메뉴를 고르면 소요를 메뉴 기본 소요의 합으로 채우되, 한 번 손대면 더는 바꾸지 않는다. 앱은 소요를 늘 채워 보낸다.
6. **등록의 `VISIT_DUPLICATE`(저장 두 번)는 이미 저장된 것으로 보고 닫는다.** 저장한 날짜를 돌려주며 닫고, 부른 화면이 그 날을 고른다 — 다른 달이면 달력도 그달로 간다.
7. **[지금 시작]은 예약 ②에 늘 보인다**(`walk_in: true`, 시각 없이 — 서버가 지금으로 놓는다). 밤 늦게 온 손님은 소요를 줄여야 한다(아니면 422).
8. **새 고객 등록은 ①에서 `/customers/new?pick=1`로 열고, 등록이 끝나면 고객 ID 를 돌려받아 ②로 바로 간다**(`RegisterCustomerScreen.pickForReservation`).
9. **수정은 PUT 하나다.** 묶음 방문의 시간을 바꾸면 "보리도 같이 옮길까요?"를 묻고, [같이 옮기기]면 `reschedule`(자기 + 예약됨인 형제)을 먼저 보내고 그다음 PUT 을 보낸다. 예약됨이 아니면 날짜·시간·반려동물 칩이 눌리지 않는다.
10. **방문 상세의 버튼은 같은 묶음에서 이 방문과 상태가 같은 방문을 한 번에 바꾼다.** 노쇼는 확인 시트를 거친다. 완료는 [완료 / 완료하고 다음 예약 잡기] 시트이고, 시트를 띄우기 전에 `next-draft`를 읽어 다음 예약 미리보기를 보인다(초안을 못 읽어도 시트는 뜨고 완료할 수 있다). `···`에는 수정(취소·노쇼 제외), 바로 완료(예약됨), 되돌리기(예약됨 외), 다음 예약 잡기(완료)가 있다.
11. **묻기와 보내기를 나눈다**(`askVisitAction` / `sendVisitAction`). 시트가 떠 있는 동안 화면을 "보내는 중"으로 두지 않는다.
12. **하루 목록의 묶음은 `group_key`로** 묶는다. 빈 시간은 시간을 차지하는 묶음(취소·노쇼 제외) 사이가 60분 이상일 때 "— N시간 비어 있음 —"으로 잰다. 카드 버튼은 묶음의 상태가 모두 같을 때만 바로 눌리고, 섞이면 상태 칩이다. 취소·노쇼 카드는 반투명이고 시간표에는 그리지 않는다.
13. **시간표는 영업시간을 기본 범위로 하고 밖의 방문이 있으면 넓힌다.** 한 시간 64px. 겹치는 묶음은 왼쪽부터 빈 칸에 둔다.
14. **캘린더 탭은 자기 머리를 쓴다**(월 숫자·연도·영문 월·‹ ›·설정 톱니). 매장 이름은 매출 탭 머리에만 남는다. 달력은 일요일 시작. 지난날·오늘은 `AppPhotoTile`, 앞날은 `AppDashedTile`, 예약 없는 휴무는 옅은 "휴무", 정리 안 된 예약이 있는 날은 오른쪽 위에 그 수. 미리보기 글래스 카드는 최대 4줄이다.
15. **설정 허브의 "일정"·"메뉴" 행은 사장에게만 보인다**(V8). 일정 화면은 영업시간·기본 소요·쉬는 요일을 [저장]으로 한 번에 보내고, 임시 휴무는 줄마다 바로 더하고(`YYYY.MM.DD`, 오늘부터) 지운다. 하루 화면의 `···`(사장만)에서도 같은 API로 "이 날 휴무로 표시"/"휴무 해제"를 한다. 메뉴 화면은 행마다 ▲▼(순서값 맞바꾸기)·수정 시트·보관이다.
16. **고객 상세 모델에 `noShowCount`·`upcomingVisits`를 더한다**(조회 응답에만 있고 등록·수정 응답에는 없어 0·빈 목록). 보호자 탭에 "노쇼 N회"와 "다가오는 예약" 카드를 보인다. 목록 정렬에 "최근 방문순"을 더한다.
17. **`AppDashedTile`을 `design/widgets`에 더한다.** `AppBigDate`에 `static monthName(int)`을 더한다. `PrefsStore`에 `readDayViewMode`/`writeDayViewMode`를 더한다(기기 설정, `clear()`가 지우지 않는다).
18. **홈의 빈 캘린더 문구를 지우고**, 매출 탭 + 의 문구를 "매출은 다음 업데이트에서 만나요"로 바꾼다.
19. **#15 는 ③-A2 Task 1 이 이미 위와 같이 고쳤다.**
20. **하루 화면 머리는 큰 날짜 숫자 + 기울인 영문 요일 + "2026년 9월"**(목업 그대로). `AppBigDate.weekdayName(int)`을 더한다.
21. **수정 화면의 "시간이 바뀌었나"는 서버 문자열이 아니라 벽시계(`ShopTime.wall`)로 견준다.** 캘린더 탭의 보고 있는 달은 따로 들지 않고 고른 날에서 계산한다.

### 독립 검토(Fable, 2026-09-23)에서 사용자와 정한 다섯 가지

- 완료 시트의 다음 예약 미리보기(백엔드를 넓혀 반영 — 위 15, 006 #15).
- 소요 ± 10분, 길게 누르면 30분.
- [지금 시작]을 예약 ②에 상시 노출.
- 새 고객 등록을 마치면 예약 ②로 직행.
- 하루 화면 `···`에 휴무 표시를 더한다.

### 실행 중 검토가 잡아 고친 계획 결함

1. **`GET /visits/{id}`의 `group`은 자기를 뺀 형제다**(서버 계약이 정본). 앱은 상태 전이에 앵커(자기)를 먼저 넣고 같은 상태의 형제를 더하며, 수정 화면의 `exclude`는 자기 ID 를 따로 넣는다. 계획의 앱 코드·픽스처는 자기 포함으로 잘못 썼다 — 실서버에서는 혼자 온 방문의 상태 버튼이 422 였을 결함이다.
2. **[지금 시작]은 보던 날이 아니라 서버가 저장한 날짜**(`visits.first.starts_at`)를 돌려준다 — 홈이 오늘로 간다.
3. **완료 시트 전 `next-draft`를 읽는 동안 상세·하루 카드는 `_asking`으로 재진입만 막고 스피너는 켜지 않는다.**
4. **시간표의 30분 블록은 둘째 줄(메뉴·보호자·상태)을 생략한다**(44px 기준). 계획 코드는 14px 넘쳤다.
5. **메뉴 ▲▼ 둘째 PUT 이 실패해 순서값이 같아지면, 다음 누름에서 위로 갈 메뉴 v·아래로 갈 메뉴 v+1 로 푼다.** 계획의 "다시 누르면 바로잡힌다"는 틀렸었다.
6. **흐름 확인 스크립트의 '통과' 줄은 27이다**(판정 25 + 준비 2) — 위 "검증" 절의 "28개" 문구를 27로 정정했다.
7. **최종 검토 fix 로 반영한 것.** 묶음의 끝 시각은 시간을 차지하는 구성원(취소·노쇼 제외) 기준이다. 임시 휴무 입력 키보드는 `datetime`이다(iOS 숫자 패드에 점이 없어서). 시간표 마감의 분(19:30)은 올림으로 셈한다. 등록의 `VISIT_DUPLICATE`는 걸어 들어온 손님이면 오늘을 돌려준다.

### 이 계획으로도 남는 것

계획서 목록:

- 예약 폼의 `!widget.busy`는 `AppButton` 비활성과 겹쳐 테스트로 따로 판별되지 않는다.
- 등록의 `VISIT_DUPLICATE`는 문구 없이 닫는다(설계 6.2 는 "이미 저장됐어요" 문구를 말한다 — 앱에 스낵바 관례가 없어 두었다).
- 달력의 오늘 표시는 설계의 "검정 테두리" 대신 검정 원 숫자이고, 고른 날이 테두리다. 날짜 줄은 목업의 "고른 날부터 5일"이 아니라 월~일 한 주다. 캘린더·고객 탭 머리에 매장 이름이 없다(매출 탭에만).
- 메뉴 순서 ▲▼ 는 PUT 두 번이라 둘째가 실패하면 두 메뉴의 순서값이 같아진다(서버에 순서 바꾸기 API 가 없다) — 다음 누름에서 바로잡힌다(위 결함 5).
- 오늘·지난 날 판단은 기기 날짜(`todayProvider`)다 — 매장 시간대는 앱에 없다는 원칙의 대가. 해외 기기에서 자정 전후에 어긋날 수 있다.
- 예약 ②에서 메뉴나 소요를 바꿀 때마다 시간 칸 전체와 고른 시각을 둘 다 다시 묻는다 — 실기기에서 깜빡임을 본다.
- 완료 시트 골든(`complete_sheet.png`)은 시트 카드만 짚었는데도 경로 전체가 찍힌다 — 시트 모양을 보는 용도로만 쓴다.
- 시간표의 짧은 방문 블록은 글자가 빠듯하다(설계가 이미 아는 A안의 단점). 목업대로 목록이 기본이다.
- 익명화한 고객의 방문은 모든 쓰기가 404 `CUSTOMER_NOT_FOUND`다. 앱은 "고객을 찾을 수 없습니다" 문구로 보인다.
- 오프라인·목록 캐시가 없다.

최종 검토가 더한 것:

- 상태가 섞인 가족 카드의 칩은 첫 방문의 상태만 보인다(설계 "섞이면 상태 칩" 해석 — 사용자 확인).
- 캘린더 미리보기는 4줄까지만, 초과 표시("외 N건") 없음 — 제품 판단.
- "완료하고 다음 예약"에서 초안이 없어 다시 읽다 실패하면 완료는 됐어도 오류 문구가 뜬다.
- 두 마리를 고를 때 첫 아이의 "지난번처럼"이 두 마리 폼에 남는다.
- 예약 ①의 새 고객 등록에서 "이미 있는 번호 → 이 보호자에게 반려동물 추가"는 ②로 돌아오지 않고 반려동물 상세로 간다(③-A3/후속).
- 메뉴 동률 해소의 v+1 이 9999 캡을 넘을 수 있다(비현실적).
- 달력 칸은 `ExcludeSemantics`라 스크린리더가 예약 수·휴무를 못 읽는다. 다가오는 예약의 접근성 라벨은 날짜뿐이다.
- 휴무 추가·삭제 실패 문구가 첫 카드 [저장] 위에 뜨고 `_busy` 하나라 [저장] 스피너가 돈다.

Step 3(시뮬레이터·실서버 확인)에서 새로 나온 것:

- 다음 예약 ②에서 한 아이의 시각이 이미 예약돼 서버가 `VISIT_DUPLICATE`를 주면 앱은 저장된 것으로 보고 조용히 닫는다 — 다른 아이 몫도 저장되지 않은 채 안내가 없다(스낵바 관례 부재).
- 다가오는 예약에 오늘 미용 중인 방문도 든다(서버 정의).
- 달력 "휴무" 글자가 옅어 잘 안 보인다.
- 자정을 넘기는 방문은 시간표 끝 시각을 고려하지 않는다.
- 가족 카드의 시작 시각은 첫 구성원 기준이다.

### Step 3 확인 결과(2026-09-24, 시뮬레이터 iPhone 18 Pro + 실서버, 사용자 대신 통합 테스트로 확인)

설계 11절의 완료 기준 12개 모두 통과했다. 3번(완료 시트의 다음 예약 미리보기)은 처음에 어긋났는데, 원인은 앱이 아니라 `uvicorn --reload`가 Task 1 의 `next-draft` 변경을 반영하지 못한 채 돌던 백엔드 프로세스였다 — 재시작한 뒤에는 통과했다.

사용자 판단으로 남긴 것:

- 상태가 섞인 가족 카드는 칩 "미용 중"만 보이고 [완료하기]가 없다(완료된 아이가 카드에 드러나지 않는다).
- 미리보기 5묶음 이상이면 4줄까지만 보이고 초과 표시가 없다.
- 보호자 탭에 "노쇼" 라벨과 "노쇼 N회" 값이 겹쳐 중복으로 보인다.
- 시간표의 30분 블록은 이름만 보인다.
- 예약 ②의 옅은 칸(휴무·영업 밖)과 줄 그은 칸(겹침)이 같은 회색이다.

위협 점검표 V8 의 Task 9 테스트 이름 `직원에게는 일정이 보이지 않는다`는 실제로 Task 10 의 `직원에게는 일정·메뉴가 보이지 않는다(V8…)` 하나가 덮는다.

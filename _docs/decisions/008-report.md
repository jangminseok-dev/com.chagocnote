# 008 — 미용 알림장(⑤)에서 내린 결정

설계: `docs/superpowers/specs/2026-09-28-report-design.md`. 이 기록은 계획마다 절을 더한다(⑤-1 백엔드 → ⑤-2 웹 → ⑤-3 앱).

## 사용자와 정한 것 (2026-09-28)

설계 2절 그대로다.

| 주제 | 결정 |
|---|---|
| 링크 기간 | 매장이 설정에서 고른다 — 7일·30일·계속(무기한). 기본 30일 |
| 실리는 사진·영상 | 기본은 전부. 보내기 전 미리보기에서 빼고 싶은 것만 뺀다 |
| 함께 보여 줄 항목 | 메뉴 이름·금액·몸무게·매장 정보를 모두 만들고 매장이 켜고 끈다. 한 번 정하면 바꿀 때까지 유지 |
| 항목의 처음 값 | 메뉴 이름·매장 정보 켬, 금액·몸무게 끔 |
| 보낸 뒤 기록 수정 | 같은 링크에 바로 반영. 알림장은 기록을 비추는 창이다 |
| '보냄' 판정 | 링크를 만든 시점. 공유 시트에서 실제로 보냈는지는 앱이 알 수 없다 |
| 끊기·재발급 | 끊거나 기간이 지나면 옛 링크는 영영 안 열리고 방문은 '안 보냄'으로 돌아간다. 다시 보내면 주소가 다른 새 링크. 살아 있는 동안 다시 공유하면 같은 링크 |
| 미리보기 카드 | 미용 후 대표 사진 + "○○의 미용 알림장" + 날짜·매장 이름 |
| 열람 확인 | 처음 연 시각만. 횟수·접속 주소·기기 정보는 저장하지 않는다 |
| 웹 방식 | Next.js 서버 렌더링, 저장소의 `web/`, Vercel |
| 토큰 저장소 | 링크는 Postgres. Redis 는 횟수 제한에만 쓴다. 조회 결과 캐시는 두지 않는다 |
| 권한 | 보내기·끊기는 `record:write`(직원 가능), 알림장 설정 변경은 `shop:update`(사장만) |
| 앱 화면 | 전부 네이티브. 웹뷰 패키지를 넣지 않는다 |
| 미루는 것 | CloudFront 서명 URL, 서버 측 EXIF 검증, 실제 Vercel 배포 |

## ⑤-1 백엔드에서 정한 것

visit 스포크에 알림장 링크(발급·끊기·미리보기), 알림장 설정, 공개 조회와 열람 신호, 횟수 제한. 허브 포트 `ShopProfilePort`(tenancy 구현)와 `MediaUrls.download_url`(media). 새 라우트 7개(설정 둘, 매장용 알림장 셋, 공개 둘 — 라우트 표의 나머지는 그대로), 마이그레이션 0010(`visit_reports`, `visit_record_media.hidden_from_report`, `visit_shop_settings`의 `report_*` 다섯 칸), 새 비밀값 `REPORT_LINK_KEY_B64`, 스크립트 `check_report_flow.sh`. 단위 883 → 1294, 통합 300 → 405, 구조 계약 6종. 새 의존성은 없다.

### 이 계획에서 새로 정한 것

- **토큰은 `public_id + HMAC`으로 매번 계산하고 저장하지 않는다.** DB 에는 `public_id`(16바이트)만 있다. 살아 있는 링크를 다시 공유할 수 있고, DB 만 유출되어서는 링크를 열 수 없다. 키를 바꾸면 모든 링크가 닫힌다.
- **공개 API 는 토큰을 헤더로 받는다**(`X-Report-Token`). 경로에 두면 백엔드와 게이트웨이의 접속 기록에 남는다. 질의 문자열로 보내도 읽지 않는다.
- **뺀 사진 표시는 링크가 아니라 사진 줄에 붙는다.** 링크를 끊고 새로 보내도 빠져 있다.
- **`PUT …/report`의 `hidden_media_ids`는 "뺄 것 전부"다.** 목록에 없는 것은 앞서 뺐더라도 되살아난다. 같은 본문으로 여러 번 불러도 결과가 같다.
- **살아 있는 링크가 있는 방문은 되돌리기·기록 삭제를 할 수 없다**(409 `VISIT_REPORT_SENT`). 링크를 먼저 끊는다.
- **Redis 장애 때 횟수 제한은 통과시킨다.** 경고 로그를 남긴다. 토큰 크기(무작위 128비트 + 서명 128비트)가 1차 방어다.
- **`report_sent`는 하루 목록·피드의 항목에, `report`는 방문 상세에 있다.** 달력은 날짜 칸이 방문 단위가 아니라 바꾸지 않는다.
- 발급은 기간이 지난 줄을 먼저 닫는다(`close_expired` → `get_live` → `create`). 기간이 지나 닫힌 줄과 끊은 줄은 `revoked_at`만으로는 구분되지 않는다(`expires_at <= revoked_at`이면 기간이 지나 닫힌 것).
- 요청 하나에서 지금 시각은 한 번만 읽는다. 닫기·살아 있음 판단·`created_at`·`expires_at`이 같은 시각이다.
- 링크의 기간은 만들 때 정해진다. 보여 줄 항목은 조회할 때마다 읽는다.
- 끊기는 뺀 표시를 건드리지 않고 방문의 상태도 보지 않는다.
- 공개 조회용 `ShopContext`는 `public_context` 한 곳이 만든다(멤버 ID 0, 역할 `public`, 권한 없음, 매장의 시간대).
- 횟수 제한의 접속 주소는 해시해서 Redis 키에 넣는다. 410 은 실패로 세지 않는다.
- 내려받는 파일 이름은 `chagocnote-{미디어 ID}.jpg`·`.mp4`다.

### 설계·브리프와 다르게 간 것

- **429 의 코드는 `TOO_MANY_ATTEMPTS`다.** 기존 초대 코드 시도 제한(tenancy)이 쓰는 이름에 맞췄다.
- **"로그인 없이 열리는 경로" 목록은 `find_route_violations`가 아니라 `routes_without_login` + 프로세스별 테스트다.** `find_route_violations`에 넣으면 기존 테스트의 가짜 앱(로그인 의존성이 없는 경로)이 새 위반을 낸다. 프로세스마다 목록 전체를 `==`로 못 박는다(API 넷, 인증 다섯). `/v1/public/` 규칙 둘(허용 목록, 로그인·매장 확인 금지)은 `find_route_violations` 안에 있다.
- **공개 응답의 캐시·검색 금지 헤더는 200·204 에만 달린다.** 오류 응답은 앱 전체의 오류 처리기가 만들어 헤더가 없다. 보호자가 닿는 것은 웹 서버이고 웹(⑤-2)이 모든 응답에 단다.
- **보내기는 설정을 링크를 읽기 전에 한 번만 읽는다.** 설계의 순서("링크가 없으면 설정을 읽어")대로면 새 링크일 때 두 번 읽는다. 검사 → 쓰기의 순서는 그대로다.
- **`append_media`를 고쳤다.** 있던 미디어를 다시 만들어 뺀 표시를 잃던 것을 순서만 바꾸게 했다(`replace(m, sort_order=…)`). 전체 교체는 설계대로 `carry_hidden`이다.
- **되돌리기가 아닌 전이도 링크를 읽는다**(질의 하나). 행동을 가리면 인터랙터가 "어느 행동이 링크를 보는가"를 알게 된다 — 그것은 상태 클래스의 일이다.
- **`report_sent`는 `VisitView`가 아니라 항목에 있다**(`DayVisitItemView`·`FeedItemView`). `VisitView`에 두면 등록·수정·전이 응답에도 칸이 생기고 그때마다 링크를 읽어야 한다.
- **뷰 DTO 를 만들지 않은 곳.** 알림장 설정 유스케이스는 도메인의 `ReportSettings`를 그대로 돌려준다(칸이 똑같다). 보내기는 미리보기의 `VisitReportPreview`·`VisitReportSchema`를 함께 쓴다.
- **`ReportLinkView.in_zone(zone)`을 더했다.** `describe_link`는 시간대를 받지 않고 UTC 를 담는다. 응답으로 내보내는 쪽이 매장 시간대로 바꾼다.
- **공개 인터랙터는 DTO(`token`, `client`)를 받고 `PublicReportView(report, expires_at)`를 돌려준다.** 횟수 제한에 접속 주소가 필요하고 `ReportView`에는 `expires_at`이 없다.
- **공개 라우터는 `JSONResponse`를 직접 돌려준다.** `response_model_exclude`는 요청마다 바꿀 수 없다. 스키마는 OpenAPI 문서에만 쓰이고 본문은 `PublicReportSchema.body()`가 만든다.
- **제한기 포트는 메서드 셋이다**(`allow`, `note_miss`, `missed_too_much`). 요청 세기(`allow`)와 실패 세기(`note_miss`)와 실패 수 읽기(`missed_too_much`)가 각각 다른 Redis 호출이다. 한도 상수는 어댑터에 있다.
- 설계 7.1 은 "실패는 10분에 20회, 넘으면 429"라고만 했다. 계획서의 코드는 이를 그 주소의 모든 요청에 걸었는데, 작업 검토가 "한 통을 나눠 쓰는 보호자 전체를 익명 요청 20번으로 막을 수 있다"고 짚어 서명이 틀린 요청에만 걸도록 고쳤다. 실패 수 차단은 억지력이지 추측 속도 제한이 아니다 — 추측을 막는 것은 토큰의 크기다.
- **`read_token`에 "32바이트가 아니면 None" 검사가 없다.** 43글자는 언제나 32바이트로 풀려 닿을 수 없는 가지다. 길이와 문자 집합은 정규식 하나가 본다.
- **매장 범위 저장소는 조인이 아니라 하위 질의로 거른다**(`visit_id IN (SELECT id FROM visits WHERE shop_id = …)`). UPDATE 는 조인을 못 쓴다. 공개 조회의 `find`만 조인이다.
- **`visit_reports.created_at`에 `server_default now()`가 있다.** 기존 표들의 모양을 따랐고 저장소는 언제나 시각을 넘긴다.
- **tenancy 저장소에 `find_by_id`를 더했다.** 기존 `get_by_id`는 없는 매장에서 터진다.
- **`presign_get_url`이 더 받는 것은 `content_disposition` 하나다.** 일반 질의 매개변수로 넓히지 않았다. `attachment; filename="…"` 글자열은 어댑터가 만들고 포트는 파일 이름만 받는다.
- **보내기·끊기의 스키마 상한은 도메인의 `MAX_HIDDEN`을 가져다 쓴다**(33).
- **`.env.example`·`generate_dev_env.py`에 `REPORT_WEB_SECRET`도 넣었다.**
- **통합 테스트에 "권한 없는 역할의 403"이 없다.** 시드의 역할 둘(사장·직원)이 모두 `record:write`를 가진다. 라우터 단위 테스트가 권한을 줄인 스텁으로 본다.
- 자기소개(`visit/myself`)에 새 경로와 규칙을 더했다.
- 흐름 스크립트는 설계 11.1 의 다섯 단계에 설정·미리보기·되돌리기 거절·다시 보내기·위조 토큰·내려받기를 더해 열셋이다. 토큰과 서명 URL 은 화면에 찍지 않는다.

### 알려진 동작 — 막지 않기로 했다

- `link_days`에 `30.0`·`7.0`을 보내면 받아들인다(저장은 정수). `30.5`·`"30"`·`true`는 422 다.
- 알림장 설정을 처음 저장하는 매장에는 일정 설정 행과 기본 메뉴가 함께 생긴다.
- 뺀 사진을 기록에서 지웠다가 다시 붙이면 다시 보인다(새로 붙인 사진으로 본다).
- 살아 있는 링크가 있는 방문에 사진을 덧붙이면 바로 보호자에게 보인다.
- 살아 있는 링크가 있으면 사진을 전부 빼거나 메모를 비워도 막지 않는다. 페이지는 이름과 날짜만 보인다.
- 익명화한 고객의 방문에 다시 보내면 404 `CUSTOMER_NOT_FOUND`다(기존 가족 잠금이 거절한다). 코드가 `VISIT_…`가 아니다. 그 방문의 끊기·되돌리기·기록 삭제도 같은 404 `CUSTOMER_NOT_FOUND`다(배선 테스트로 고정했다).
- 조회와 열람 신호는 같은 통에 센다 — 페이지를 한 번 열면 요청이 둘이다.
- 429 는 맞는 토큰에는 나지 않는다 — **실패 수 차단은 서명이 틀린 요청에만 건다.** 같은 접속 주소의 서명이 틀린 요청이 10분에 20번을 넘으면 그 주소의 다음 틀린 요청부터 429(세지 않는다). 서명이 맞는 토큰은 실패가 몇 번 쌓였든 막히지 않는다 — 분당 60회의 전체 한도만 받는다.
- 웹 서버의 비밀값이 없으면 모든 보호자가 연결 주소 하나로 세어진다.
- `X-Report-Client-IP`의 형식은 검사하지 않는다. 비밀값이 새면 제한을 피할 수 있다.
- 서명 주소(객체 키)와 내려받는 파일 이름에 매장 ID·미디어 ID 숫자가 들어 있다. 응답에 ID 칸은 없다. 감추려면 객체 키 규칙을 바꿔야 한다 — 하지 않는다.
- 대표 사진의 가로·세로는 원본의 크기다(비율은 같다).
- 닫힌 이유(끊음·기간·정지·익명화)는 가르지 않고 모두 410 `REPORT_CLOSED`다.
- 미리보기(GET)는 잠그지 않는다. 기록 쓰기와 겹치면 앞뒤가 섞인 모습을 볼 수 있다.
- 기록 PUT·덧붙이기의 응답에는 `hidden`이 없다. 앱은 뺀 표시를 미리보기에서만 본다.

### 막지 못하고 감수하는 것

설계 7.6 그대로다.

1. 링크를 끊거나 사진을 빼도, 그 전에 미디어 서명 주소를 복사해 둔 사람은 최대 48시간 그 파일을 열 수 있다.
2. 카카오톡 대화방에 이미 뜬 미리보기 카드의 사진과 이름은 카카오 서버에 남는다.
3. 사장님이 링크를 직접 열어도 '확인함'으로 찍힌다.
4. 보호자가 링크를 남에게 넘기면 그 사람도 본다.
5. 앱을 거치지 않고 올린 사진의 EXIF 는 서버가 확인하지 않는다.

### 남는 것 — 알고 미룬다

- 기존 `.env`에 `IDENTITY_TOKEN_ENC_KEY`가 있다(인증 프로세스 전용이라 `.env.auth`에 있어야 한다). `.env.example`도 파일을 나누지 않았다. 이 계획 전부터 있던 상태다 — 운영 배포 전에 정리한다.
- `REPORT_LINK_KEY_B64`는 필수다. 없으면 API·인증 프로세스 둘 다 기동하지 않는다. `generate_dev_env.py`는 `.env`가 있으면 아무것도 하지 않으므로 기존 개발 환경은 한 줄을 직접 더한다(명령은 `README.md`). 키가 base64 가 아니면 `RuntimeError`가 아니라 `binascii.Error`로 멈춘다.
- 개발 DB 에 마이그레이션 0010 을 올려야 새 경로가 동작한다(compose 의 backend 가 기동할 때 올린다).
- 돌려 보지 않은 경합: 익명화와 보내기, 끊기를 동시에 두 번. 둘 다 같은 잠금에 기대므로 성립할 것이나 테스트는 없다. 되돌리는 동안 온 보내기(R9 의 반대 방향)와 열람 신호의 동시 요청은 두 세션 테스트로 고정했다.
- 기록 삭제가 링크를 잠금 뒤에 읽는지는 경합 통합 테스트 하나만 잡는다.
- `GET /v1/shops/myself`·`GET /v1/auth/myself`가 로그인 없이 열려 있다(기존 동작, 목록에 고정했다). 의도한 것인지 확인하지 않았다.
- 테스트 파일을 골라 돌릴 때 `tests/test_hub_port_binding.py`를 통합 파일 사이에 두면 `fixture 'wired' not found`다(전체 실행에는 없다, 원인 미조사).

**본문.**

- 설정(요청·응답 같다): `{link_days: 7 | 30 | null, show_menus, show_shop_info, show_weight, show_amount}`. 요청은 다섯 칸 모두 필수이고 불리언은 엄격하다(`"true"`·`1`은 422).
- 보내기 요청: `{hidden_media_ids: [int]}`. 필수 칸이고 33개까지다. 뺄 것이 없으면 빈 배열.
- 미리보기(GET·PUT 응답): `{report, link, settings}`.
  - `report`: `pet_name`, `visit_date`, `care_note`, `media[]`(`media_id`, `kind`, `phase`, `hidden`, `width`, `height`, `duration_seconds`, `display_url`, `thumb_url`, `download_url`), `cover`(`url`, `width`, `height`), `menus[]`(`name`, `amount`), `total_amount`, `weight_kg`, `shop`(`name`, `phone`, `address`). 뺀 미디어도 `hidden: true`로 함께 온다. 끈 항목은 `null`이다(공개 응답과 다르다). 대표는 빼지 않은 것 가운데서 고른다.
  - `link`(방문 상세의 `report`와 같다): `{status: "none" | "live", url, expires_at, first_viewed_at, created_at}`. `none`이면 나머지는 null. 시각은 매장 시간대. `url`은 `{REPORT_WEB_BASE_URL}/r/{토큰}`이다.
  - `settings`: 지금 매장 설정.
- 공개 알림장: `pet_name`, `visit_date`, `care_note`, `media[]`(`kind`, `phase`, `width`, `height`, `duration_seconds`, `display_url`, `thumb_url`, `download_url`), `cover`, `expires_at`은 늘 있다. `menus`·`menus[].amount`·`total_amount`·`weight_kg`·`shop`은 매장이 켰을 때만 **칸이 있다.** 켰지만 값이 없으면 `null`이다. `media`는 후 → 전, 그 안에서 순서대로이고 뺀 것은 없다. 사진의 `display_url`은 표시용, 영상은 원본이다. `menus`는 예약 메뉴가 아니라 기록의 항목이다. ID 칸은 없다.
- 오류 본문은 `{code, message}`뿐이다.

**오류 코드.**

| 코드 | 상태 | 언제 |
|---|---|---|
| `VISIT_NOT_FOUND` | 404 | 없는 방문, 다른 매장의 방문 |
| `CUSTOMER_NOT_FOUND` | 404 | 익명화한 고객의 방문에 보내기(가족 잠금) |
| `VISIT_NOT_COMPLETED` | 409 | 완료가 아닌 방문에 보내기 |
| `VISIT_NO_RECORD_YET` | 409 | 기록이 없는 방문의 미리보기·보내기 |
| `VALIDATION_ERROR` | 422 | `hidden_media_ids`에 이 기록의 것이 아닌 ID·중복·33개 초과·범위 밖 숫자, 설정의 허용 밖 기간·불리언이 아닌 값·빠진 칸 |
| `REPORT_EMPTY` | 422 | 새 링크를 만드는데 빼지 않은 미디어도 케어 메모도 없다 |
| `REPORT_NOT_FOUND` | 404 | 끊을 살아 있는 링크가 없다. 공개: 토큰이 없거나 우리가 만든 것이 아니다 |
| `REPORT_CLOSED` | 410 | 공개: 끊음, 기간 지남, 매장 정지·폐업, 익명화, 기록 없음 |
| `TOO_MANY_ATTEMPTS` | 429 | 공개: 접속 주소별 분당 60회 초과, 또는 서명이 틀린 요청의 실패가 10분에 20회 |
| `VISIT_REPORT_SENT` | 409 | 살아 있는 링크가 있는 방문의 되돌리기·기록 삭제 |
| `PERMISSION_DENIED` | 403 | 직원의 설정 변경, `record:write` 없는 보내기·끊기 |

보내기의 오류 순서는 `VISIT_NOT_FOUND` → 가족 잠금의 오류 → `VISIT_NOT_COMPLETED` → `VISIT_NO_RECORD_YET` → `VALIDATION_ERROR` → `REPORT_EMPTY`다.

**공개 조회의 판정 순서.** 분당 한도(429) → 서명 확인 → (틀리면) 실패가 찼으면 429, 아니면 세고 404 → (맞으면) 링크 찾기(없으면 세고 404) → 살아 있음(410) → 매장(410) → 기록(410). 열람 신호는 기록을 보지 않는 것만 다르다. 열람 신호는 한 번 남으면 바뀌지 않고 닫힌 링크에는 남기지 않는다.

**헤더.**

| 헤더 | 방향 | 뜻 |
|---|---|---|
| `X-Report-Token` | 요청 | 토큰 43글자. 없으면 404 |
| `X-Report-Web-Secret` | 요청 | 웹 서버와 나눈 비밀값. 맞을 때만 아래 주소를 믿는다 |
| `X-Report-Client-IP` | 요청 | 보호자의 접속 주소. 횟수를 이 주소로 센다 |
| `Cache-Control: private, no-store`, `X-Robots-Tag: noindex, nofollow` | 응답 | 200·204 에만 있다. 오류 응답에는 웹이 단다 |

**설정 상수.**

| 이름 | 필수 | 뜻 |
|---|---|---|
| `REPORT_LINK_KEY_B64` | 필수 | 토큰 서명 키. 32바이트 이상을 base64 로 |
| `REPORT_WEB_BASE_URL` | 기본 `http://127.0.0.1:3010` | 보호자 웹의 주소. 끝의 `/`는 뗀다 |
| `REPORT_WEB_SECRET` | 기본 빈 값 | 웹 서버와 나누는 비밀값. 비어 있으면 웹 서버가 알려 준 주소를 믿지 않는다 |

## ⑤-2 웹에서 정한 것

`web/` 신설 — Next.js 16.3.6(App Router, Turbopack)·React 19.3.0·TypeScript 7.0.2(`strict`)·pnpm 11.17.0. 경로는 알림장 페이지 `/r/[token]`과 열람 신호 경로 핸들러 `/r/[token]/viewed`(POST) 둘이고 나머지는 404 다. 글꼴은 npm `pretendard` 1.3.9(OFL-1.1)의 subset 셋을 직접 싣는다. 그 밖의 런타임 의존성(상태 관리·UI 라이브러리·CSS 프레임워크·분석 도구)은 없다. compose 에 `web` 서비스(`next dev`, 호스트 포트 3010)를 더했다. 테스트: Vitest 125(파일 10), 서버 응답 검사(`pnpm check:server`) 45줄, 실제 브라우저(Playwright) 11. 백엔드 코드와 API 계약은 바꾸지 않았다.

### 사용자와 정한 것 (2026-09-29)

- **페이지의 상태 코드는 200 과 404 뿐이다.** 설계 7.3 의 표를 고쳤다 — 404·형식이 틀린 토큰은 404(`notFound()`), 410 은 "닫힌 알림장이에요"(200), 429·연결 실패·5xx·그 밖은 "잠시 후 다시 열어 주세요"(200). 스파이크 결과: App Router 페이지는 410·429·503 을 낼 수 없고, `rewrite`로 돌려도 status 는 무시된다. 유명 서비스 25곳을 받아 본 결과 410 을 내는 곳은 한 곳뿐이었고 대부분 200·404 만 냈다.
- **알림장을 열 때 백엔드 조회는 한 번이다.** `generateMetadata`와 본문이 React `cache`로 감싼 `getReport`를 나눠 쓴다. fetch 는 `cache: 'no-store'`다.
- **App Router 만 쓴다.** 프록시(`proxy.ts`)·Pages Router·별도 오류 경로 핸들러를 만들지 않는다.

### 이 계획에서 새로 정한 것

- **토큰 형식은 웹이 먼저 본다.** `^[A-Za-z0-9_-]{43}$`가 아니면 백엔드를 부르지 않고 404 다. 헤더에 넣을 수 없는 글자로 fetch 가 터지는 것도 막는다. 이상한 토큰 일곱(`/r/`, 42·44글자, 5000글자, 한글, `%0d%0a`, `..%2f`)이 모두 404 이고 백엔드 호출이 0번인 것을 서버 응답 검사가 본다.
- **설정 둘(`API_BASE_URL`, `REPORT_WEB_SECRET`)은 필수다.** `process.env`는 `lib/config.ts`에서만 읽고 `NEXT_PUBLIC_`을 쓰지 않는다. 없으면 `instrumentation.ts`의 `register()`가 변수 이름을 담아 던진다(값은 넣지 않는다). `next start`는 멈추지 않고 떠 있되 **모든 요청에 500** 이다. `process.exit`는 넣지 않았다 — Vercel 의 함수 환경에서 어떻게 되는지 확인할 수 없어서다. `next dev`는 같은 오류를 찍고 종료 코드 1 로 끝난다. `next build`는 설정 없이도 된다.
- **접속 주소는 `x-forwarded-for`의 첫 값이다.** Vercel 은 이 헤더를 플랫폼이 덮어쓴다. 직접 노출한 `next start`·compose 개발 환경에서는 위조할 수 있다 — 운영은 Vercel 뒤에서만 둔다는 전제다. 값이 없으면 `X-Report-Client-IP`를 보내지 않는다.
- **응답 헤더 셋**(`X-Robots-Tag: noindex, nofollow`, `Cache-Control: private, no-store`, `Referrer-Policy: no-referrer`)은 `next.config.ts`의 `headers()`로 단다. `source`는 `'/((?!_next/static/|og-default\\.png$).*)'` — 정적 파일(글꼴 등)과 공통 미리보기 그림은 뺀다. 미리보기 로봇이 캐시 금지 그림을 버릴 수 있다는 판단이다(그림에서는 검색 금지·Referrer 헤더도 함께 빠진다). 없는 경로의 404 는 Next 가 `Cache-Control`을 자기 값(`private, no-cache, no-store, …`)으로 바꾸므로 검사는 `private`·`no-store`의 포함 여부로 한다. 알림장 페이지(200)의 값은 정확히 `private, no-store`다. `X-Powered-By`는 끈다.
- **헤더 검사는 `next start`로 한다.** `next dev`는 페이지의 `Cache-Control`을 덮지 못한다.
- **글꼴**: Pretendard 는 `next/font/local`로 굵기 400·600·700 의 subset 만 싣는다(각 약 265KB, 합 약 796KB, `display: swap`). 가변 글꼴 하나는 2MB 다. 세리프(Didot)·명조는 시스템 글꼴 스택이다. 외부 도메인 요청은 없다(브라우저가 부른 호스트는 웹과 저장소 둘뿐인 것을 e2e 가 본다).
- **웹 서버 코드는 토큰·서명 주소·비밀값을 로그에 찍지 않는다.** 서버 응답 검사의 마지막 줄이 모든 요청 뒤 `next start`의 표준 출력·오류에 검사에 쓴 토큰(인코딩한 값·푼 값)과 비밀값이 없는지 본다. `next dev`는 들어온 요청의 주소(`GET /r/<토큰> 200 …`)를 기록에 찍는다 — `logging: { incomingRequests: false }`로 껐다. 끈 뒤 흐름을 다 돌려 web 기록이 0줄인 것을 봤다. Next 문서에는 dev 에서만 찍는 기록이라 운영 빌드에는 영향이 없다고 적혀 있다.
- **오류 화면의 설명은 닫힌 화면에만 있다.** 설계 7.3 에 문구가 있는 것이 그것뿐이다. 영문 장식은 `Not found`·`Closed`·`One moment`(busy·unavailable 은 같은 화면)이고 `aria-hidden`이다.
- **수치는 목업의 7/6 배다.** 목업은 폭 320px·본문 12px 의 축소판이고 웹의 본문은 14px 다. 알림장 화면과 오류 화면이 같은 배율이다. 오류 화면은 7/6 배로 키우자 폭 390 에서 "One moment"가 두 줄로 꺾여 영문 표시를 한 줄로 묶고 좁은 화면에서 줄게 했다.
- **대표 미디어의 높이는 실제 비율을 따르되 세로가 가로의 4/3 배를 넘지 않는다.** 3:4 사진은 자르지 않고, 9:16 영상은 `1080 / 1440` 칸에 `object-fit: cover`다. `width`·`height` 속성으로 자리를 잡아 그림이 오기 전후로 자리가 밀리지 않는다(그림 요청을 막고 열어 대표 칸과 미디어 줄의 자리가 같은 것을 봤다).
- **미리보기 정보**: `og:title`·`<title>` = "○○의 미용 알림장"(이름이 없으면 "미용 알림장"), `og:description` = "○월 ○일 · 매장 이름"(매장 정보가 없으면 날짜만), `og:image` = `cover`(가로·세로 포함). `cover`가 없으면 `/og-default.png`(1200×630 회색조)의 절대 주소를 `x-forwarded-proto`(없으면 `https`)와 `host`로 만든다. `og:url`·canonical 은 넣지 않는다. 오류 화면은 레이아웃의 제목 "차곡노트 미용 알림장"뿐이고 og 태그가 없다.
- **열람 신호는 브라우저 스크립트만 보낸다**(R12). 화면이 붙으면 `POST /r/<토큰>/viewed`를 `keepalive`로 한 번 보낸다(StrictMode 에서도 한 번). 페이지를 서버에서 그릴 때는 보내지 않는다. 신호 경로는 `Sec-Fetch-Site`가 있고 `same-origin`이 아니면 403 이고 백엔드를 부르지 않는다(헤더가 없는 옛 브라우저는 통과). 백엔드의 상태 코드(204·404·410·429)를 본문 없이 돌려주고 그 밖·연결 실패는 503 이다. GET 은 405 다. 실제 chromium 이 보낸 `Sec-Fetch-Site`는 `same-origin`이었다.
- **하나 저장은 `download_url`로 가는 링크(`<a>`)다.** 모두 저장은 먼저 빈 파일 하나로 `navigator.canShare`를 묻고, 안 되면 미디어를 받지 않고 600ms 간격으로 차례로 내려받는다. 되면 전부 받아 `navigator.share({ files })`를 한 번 부른다. 받기가 200 대가 아니거나(서명 만료의 403 등) 공유가 `NotAllowedError`면 차례로 내려받기로 넘어가고, 사용자가 공유를 취소하면(`AbortError`) 거기서 멈춘다.
- **카카오톡 안내는 모두 저장 버튼 아래 한 곳이다.** 사용자 에이전트에 `KAKAOTALK`이 있을 때 브라우저가 붙은 뒤에 판단해 그린다(`useSyncExternalStore`의 서버 값 `false` — 서버 HTML 에는 없다).
- **크게 보기**는 목업에 없어 모습을 정했다 — 검은 바탕, 위에 순번과 닫기, 아래에 이전·저장·다음. 끝에서는 이전·다음이 눌리지 않고 돌아서 넘어가지 않는다. 밀기는 가로로 40px 넘게, 세로보다 가로로 더 움직였을 때만 넘긴다. 열리면 초점이 닫기 버튼으로 가고, Esc 로 닫히며, 열린 동안 `body`의 `overflow`가 `hidden`이다. 넘기면 앞 영상은 멈춘다. **뒤로 가기(안드로이드의 버튼·몸짓)는 크게 보기만 닫는다** — 열 때 `history.pushState(null, '')`로 방문 기록에 한 칸을 쌓고(URL 인자가 없어 주소는 그대로, 넘기기는 쌓지 않는다, 개발 모드의 이펙트 두 번에도 한 번) `popstate`가 오면 닫는다. 닫기 버튼·Esc 로 닫으면 쌓은 칸을 `history.back()`으로 치워 뒤로 가기 한 번에 알림장을 떠난다.
- **`next.config.ts`의 개발용 두 줄.** `agentRules: false` — 빼면 `next dev`가 `web/AGENTS.md`·`web/CLAUDE.md`를 만든다(두 파일이 없을 때, 대조로 확인). 이제 `web/CLAUDE.md`가 있으므로 빼면 그 파일에 Next 의 에이전트 규칙 묶음을 끼워 넣는다(`generate-agent-files.js`를 읽고 한 판단). `allowedDevOrigins: ['127.0.0.1']` — 백엔드가 만드는 링크는 `http://127.0.0.1:3010/r/…`인데, 빼면 `next dev`가 `/_next/hmr` 등 개발 자원을 막아("Blocked cross-origin request") 브라우저 쪽 코드가 붙지 않는다. e2e 여섯 가운데 열람 신호·크게 보기·404 화면 셋이 실패한다.
- **카카오톡 미리보기 로봇은 og 태그를 스트리밍으로 받지 않는다.** `next.config.ts`의 `htmlLimitedBots`에 Next 기본 목록(`node_modules/next/dist/shared/lib/router/utils/html-bots.js`의 `HTML_LIMITED_BOT_UA_RE`)과 `kakaotalk-scrap`을 함께 넣었다. 기본 목록에 카카오 로봇이 없어 메타데이터가 스트리밍 대상이었다 — 지금까지 og 태그가 `<head>`에 온 것은 본문이 같은 조회(`getReport`)를 기다리기 때문일 뿐이었다. `kakaotalk-scrap` UA 로 받으면 `<body>` 바로 뒤의 스트리밍용 이어붙임 표시(`<div hidden><!--$--><!--/$--></div>`)가 사라져 Next 가 막힌 렌더링(html-limited)으로 인식한 것을 서버 응답 검사로 확인했다.
- **compose 의 `web`**: `node:24-alpine`, `corepack enable` 뒤 pnpm 11.17.0, `pnpm install --frozen-lockfile --store-dir node_modules/.pnpm-store` → `next dev -p 3010 -H 0.0.0.0`. `node_modules`·`.next`는 볼륨(`web_node_modules`·`web_next`)이라 맥의 것(darwin)과 컨테이너의 것(linux-musl)이 서로 가린다. pnpm 저장소를 `--store-dir`로 볼륨 안에 두지 않으면 저장소 루트에 `.pnpm-store/`(약 530MB)가 생긴다. `API_BASE_URL`은 compose 가 `http://backend:8000`으로 넣고 `REPORT_WEB_SECRET`은 저장소 루트의 `.env`에서 백엔드와 같은 값을 읽는다. 포트는 `127.0.0.1:3010`. 파일 변경 감지는 폴링 없이 된다(Docker Desktop, 맥).
- **보호자가 먼저 부딪힐 다섯은 테스트로 고정했다.**
  - 백엔드가 매달리면 5초 남짓(6초 안) 뒤 "잠시 후 다시 열어 주세요"(200), 열람 신호는 503 — `check:server`(가짜 백엔드 앞머리 `slow`).
  - 크게 보기를 연 채 뒤로 가기 — Vitest `tests/MediaGallery.test.tsx`(칸 쌓기·`popstate`·`history.back`), e2e `뒤로 가기` 둘.
  - 띄어쓰기 없는 긴 글·긴 이름 — e2e 가 긴 글 알림장을 폭 320·390 에서 열어 가로 넘침이 없는지 본다. 넘침을 막는 것은 `.page`의 `overflow-wrap: anywhere`다.
  - 여러 번 새로 고쳐도 `first_viewed_at`이 그대로 — e2e.
  - 영상만 있는 알림장의 `og:image`는 포스터(`cover`)이고 첫 HTML 에 재생 표시가 있다 — `check:server`(앞머리 `vid`).
- **e2e 는 compose 의 web 과 개발 스택에 붙는다.** `pnpm e2e:prepare`가 게이트웨이로 확인용 매장·고객·방문·사진 둘(30×40 JPEG)·기록을 만들고 보내기 → 끊기 → 다시 보내기로 끊은 링크와 살아 있는 링크를 `web/test-results/e2e-links.json`(gitignore)에 쓴다. 같은 매장·반려동물의 다른 방문으로 긴 글 알림장(케어 메모 `a` 600자·긴 URL·이모지, 메뉴 이름 30자, 매장 주소 255자 — 모두 백엔드 스키마의 한도 안)도 하나 더 만든다. 로그인 토큰은 파일에 쓰지 않고 개발용 로그인 이름을 쓴다(만료 때문). Playwright 는 `workers: 1`(첫 테스트가 "아직 아무도 열지 않은 링크"를 전제한다), 기기 `Pixel 7`, `outputDir: test-results/playwright`(Playwright 가 outputDir 를 비우므로 링크 파일과 떼었다)다.

### 설계·브리프와 다르게 간 것

- **404 의 첫 HTML 에는 화면 글자가 없다.** `notFound()`를 셸 전에 던지면 Next 가 빈 본문과 스크립트(RSC 페이로드)만 보낸다. `generateMetadata`에서 먼저 `notFound()`, 경로별 `not-found.tsx`를 시도했지만 같았다. 상태는 404 이고 `<title>`은 있으며, 실제 브라우저에서는 "알림장을 찾을 수 없어요"가 보인다(e2e). 스크립트를 돌리지 않는 로봇에게는 제목만 보인다.
- **React `cache`가 있어야 조회가 한 번이다.** 빼면 조회가 2번이 된다(서버 응답 검사로 확인) — Next 는 같은 fetch 를 합치지 않는다. `export const dynamic = 'force-dynamic'`은 필요 없다(`headers()`를 써서 이미 동적이다).
- **대표의 높이.** 목업은 높이 300px 고정에 `object-fit: cover`다. 실제 비율 + 4/3 한도로 바꿨다(위). 3:4 사진이면 390×798 화면의 첫 화면에 썸네일 줄이 절반쯤 걸린다.
- 머리·날짜·제목은 파일 하나(`ReportHead.tsx`)이고 `data-section`은 셋으로 따로다. CSS 는 모듈 하나(`ReportView.module.css`)를 조각들이 함께 쓴다.
- 재생 표시는 글자 ▶ 가 아니라 CSS 세모다(▶ 가 기기에 따라 그림 문자로 바뀌기 때문 — 실기기에서 본 것은 아니다).
- 미디어 줄은 넷이 한 줄에 차고 나머지는 가로로 넘긴다(목업은 넷만 그렸다). 목업에 없는 줄바꿈 규칙(`word-break: keep-all`, 영문 머리·금액·몸무게 줄 안 바꿈)을 눈으로 보고 더했다.
- `viewport`에 `themeColor: '#f5f5f5'`를 넣었다.
- 기본 미리보기 그림에도 `og:image:width`·`height`(1200·630)를 넣었다.
- 공개 응답의 `kind`·`phase`는 백엔드 스키마에서 `str`이지만 웹의 형은 `'photo' | 'video'`·`'before' | 'after'`로 좁혔다. 백엔드가 그 넷만 내는지는 코드로 확인하지 않았다.
- 서버 응답 검사의 가짜 백엔드는 미디어 주소를 `localhost`로 준다. 백엔드 주소(`127.0.0.1`) 아래에 두면 "첫 HTML 에 백엔드 주소가 없다"를 검사할 수 없다. 실제 서명 주소도 저장소 주소라 백엔드 주소와 다르다.
- e2e 준비의 사진은 진짜 JPEG 이다(`naturalWidth > 0`을 보려고). `check_report_flow.sh`는 0 바이트를 올린다.

### 알려진 동작 — 막지 않기로 했다

- 없는 토큰·형식이 틀린 토큰의 404 는 첫 HTML 에 글자가 없다(위). 루트(`/`)·그 밖 경로의 404 는 첫 HTML 에 글자가 있다.
- 닫힌 링크·오류 화면은 200 이다. 상태 코드로 닫힘을 가를 수 없다.
- 열람 신호의 "한 번"은 화면 하나 안에서다. 새로 고치면 다시 보낸다 — 백엔드가 첫 열람만 적는다.
- `Sec-Fetch-Site`가 `same-site`여도 403 이다(웹과 신호 경로는 같은 출처다).
- 설정 오류가 요청 시점에 나면 "잠시 후 다시 열어 주세요"로 삼켜진다. `register()`가 먼저 막으므로 `next start`에서는 닿지 않는 길이다.
- 매장이 메뉴를 켰지만 빈 목록이고 다른 줄도 없으면 "오늘의 케어" 구역이 없다.
- 썸네일은 모두 `loading="lazy"`인 `<img>`이지만 서명 주소는 첫 HTML 에 모두 들어간다(미디어 33개면 33개).
- 영상이 대표이면 포스터(`thumb_url`)를 크게 늘려 쓴다. 포스터가 작으면 흐리다.
- 받기 응답의 파일 이름은 `Content-Disposition`의 `filename="…"`만 읽는다(백엔드의 이름은 ASCII 다). 브라우저 코드에 그 헤더가 보이지 않으면 순번 이름이다.
- **크게 보기를 연 채 새로 고치면** 쌓아 둔 방문 기록 칸이 남아, 알림장을 떠나려면 뒤로 가기를 두 번 눌러야 한다.

### 남는 것 — 알고 미룬다

- **실기기·배포 뒤 확인**(설계 11.5 의 5~11 에 더했다). 모두 개발 맥의 chromium 으로만 봤다.
  - 모두 저장의 공유 시트 경로 — chromium 에 `canShare`가 없어 스텁으로만 확인했다. 받는 동안 사용자 동작의 유효 시간이 지나 `share`가 거절될 수 있다(그러면 받은 것을 버리고 차례로 내려받는다). 저장소(MinIO·S3) 버킷에 CORS 가 없으면 받기가 실패해 늘 차례로 내려받는다(버킷 CORS 는 보지 않았다). 영상이 섞인 목록을 iOS 가 공유해 주는지 모른다.
  - iOS Safari·카카오톡 내장 브라우저에서 여러 개를 차례로 내려받기.
  - 크게 보기의 스크롤 잠금이 iOS Safari 의 손가락 끌기에서 막히는지, 영상 위의 옆 밀기가 재생 막대와 겹치는지.
  - iOS Safari·카카오톡 내장 브라우저가 `Sec-Fetch-Site`를 보내는지.
  - 카카오 미리보기 로봇이 실제로 읽는 것. `kakaotalk-scrap/1.0` UA 로 받으면 og 태그가 `<head>`에 있었다 — 본문이 같은 조회를 기다려 셸 전에 메타데이터가 끝나기 때문이고, 본문에 Suspense 가 생기면 바뀔 수 있다(추측). 오류 화면처럼 `og:title`이 없을 때 `<title>`을 쓰는지 모른다.
  - 대표의 서명이 만료된 뒤의 미리보기 그림 — `og:image`는 대표의 서명 주소다. 카카오톡이 처음 받은 그림을 캐시할 것이다(추측).
  - 백엔드 장애·429 중에 카카오톡이 링크를 읽으면 미리보기 카드는 일반 제목뿐이고, 카카오가 그 카드를 캐시하면 복구 뒤에도 남을 수 있다(추측).
  - Vercel 에서 `x-forwarded-proto`·`host`가 실제 도메인인지(기본 그림의 절대 주소), `x-forwarded-for`가 플랫폼 값인지, 응답 헤더 셋, `register()`가 던질 때의 동작. `next start`에서는 `http://127.0.0.1:<포트>`로 나왔다.
  - `/og-default.png`의 실제 `Cache-Control`과 "로봇이 캐시 금지 그림을 버린다"는 전제.
  - Android 에서 세리프(Didot)·명조가 무엇으로 바뀌는지, iOS Safari 의 `background … fixed`·`backdrop-filter`.
- **크게 보기는 초점을 가두지 않는다.** Tab 을 계속 누르면 뒤 화면으로 가고, 닫아도 초점이 눌렀던 썸네일로 돌아가지 않는다.
- **dev 에서는 `X-Report-Client-IP`를 보내지 않는다.** 브라우저가 compose 의 `next dev`에 바로 붙어 `x-forwarded-for`가 없다. 그때 백엔드가 무엇으로 세는지는 보지 않았다.
- **백엔드의 `REPORT_WEB_SECRET`은 여전히 선택이다.** 웹 쪽만 필수로 했다. 운영에서 백엔드에 값이 없으면 웹이 보낸 접속 주소를 믿지 않아 모든 보호자가 웹 서버 주소 하나로 세어진다.
- **접속 기록의 토큰.** 웹 코드는 찍지 않고 `next dev`의 요청 기록은 껐다. `logging.incomingRequests: false`를 빼면 dev 서버는 토큰이 든 경로를 찍는다. Vercel 자체 접속 기록에 주소가 남는 것은 설계 7.2 대로 감수한다.
- 글꼴은 첫 HTML 에서 preload 되지 않는다(404 화면에서 확인). 느린 망에서는 시스템 글꼴이 먼저 보인다.
- 백엔드 호출은 5초에 끊도록 `AbortSignal.timeout`을 건다. 끊기면 "잠시 후 다시 열어 주세요"(200)·열람 신호 503 인 것을 서버 응답 검사가 실제로 기다려 본다. `x-forwarded-for`에 헤더에 넣을 수 없는 글자가 있으면 fetch 가 던져 "잠시 후 다시 열어 주세요"가 될 것이다(추측, 테스트 없음). 금액의 쉼표는 `toLocaleString('en-US')`에 기댄다(ICU 가 없는 런타임에서는 빠질 수 있다).
- 열람 신호의 `keepalive`는 Vitest 에서 인자로만 봤다.
- 개발 DB·버킷에 e2e 준비의 확인용 매장·유저·고객·방문·사진·알림장 링크가 쌓인다. 지우는 스크립트는 없다.
- compose 의 `web`이 떠 있는 동안 맥에서 `web/.next`를 지울 수 없다(볼륨의 마운트 자리). `web`을 지운 뒤 남는 빈 `web/.next`를 지울 수 있는지, 맥에서 `pnpm install`을 하지 않은 사람이 `web`을 띄우면 맥에 빈 `web/node_modules`가 생기는지는 확인하지 않았다.
- `web`은 `depends_on: backend`다. 참조 작업 트리처럼 다른 폴더의 compose 파일로 `web`만 띄울 때는 `--no-deps`를 붙인다(없으면 backend 가 그 폴더 기준으로 다시 만들어질 수 있다 — 해 보지는 않았다).
- 카카오톡 UA 는 Playwright 로 UA 글자만 바꿔 봤다. 사파리·카카오톡 내장 브라우저·Android 에서는 아무것도 보지 않았다.
- **모두 저장의 메모리·데이터 양과 중복 받기** — 공유 경로는 미디어 전부(영상은 개당 최대 200MB)를 메모리로 받은 뒤 공유 시트를 연다. 운영 배포 전에 사진만 또는 합계 크기 한도 안으로 좁히거나, 실패하면 남은 받기를 끊을지 정한다(설계 8.3 이 정한 방식이라 실기기 확인과 함께 정한다).
- **뒤로 가기의 실기기 확인**(설계 11.5 의 새 항목 12) — Android 뒤로 몸짓·버튼, iOS Safari 가장자리 밀기, 카카오톡 내장 브라우저에서 크게 보기를 연 채 뒤로 가면 크게 보기만 닫히는지. e2e 는 `next dev` 위 chromium 에서만 돌았다.
- **e2e 는 `next dev` 에만 붙는다.** 배포 전에 `next start` 대상으로 한 번 돌린다.

## ⑤-3 앱에서 정한 것

앱(`app/`)에 알림장을 더했다 — 방문 상세의 "알림장" 줄과 [알림장 보내기], 보낸 뒤의 꼬리표 "완료 · 알림장 보냄"·확인 카드·[다시 공유]·`···`의 [보낼 사진 고르기]·[링크 끊기], 보내기 전 미리보기 `/visits/:visitId/report`(`?pick=1`이면 보낼 사진 고르기), 알림장 설정 `/settings/report`, 하루 목록·시간표·피드의 "알림장 보냄" 표시, 공유 시트 자체 채널 `chagocnote/share_sheet`(iOS `ShareSheet.swift`, Android `ShareSheet.kt`), 모양 위젯 둘(`AppPickTile`·`AppSwitch`), 시뮬레이터 흐름 `integration_test/report_flow_test.dart`와 준비 스크립트 `app/tool/prepare_report_flow.sh`. 테스트 777 → 854(새 골든 여섯 — 미리보기, 고르는 타일, 방문 상세 보내기 전·후, 알림장 설정, 스위치. 갱신한 골든 둘 — 하루 목록, 피드). 새 pub 의존성은 없다(iOS 의 `LinkPresentation`은 시스템 프레임워크다). 웹뷰는 없다. 백엔드·웹 코드와 API 계약은 바꾸지 않았다. 참조 구현은 브랜치 `ref/report-5-3-app`의 커밋 일곱이다 — 작업 1 `a7c1bda` · 2 `cc85f06` · 3 `2c0e320` · 4 `c816036` · 5 `6d4a75a` · 6 `08af396` · 7 은 이 절을 담은 커밋.

### 이 계획에서 새로 정한 것

- **미리보기 화면은 "이번에 누른 것"만 든다**(`Map<int, bool>` — 미디어 ID → 뺄지). `PUT …/report`의 `hidden_media_ids`는 "뺄 것 전부"라, 낡은 화면이 제가 본 목록을 그대로 보내면 그 사이 다른 기기에서 뺀 사진이 되살아난다. 보내기 직전에 미리보기를 **다시 읽어** 서버의 지금 상태 위에 누른 것만 덮어 목록을 만든다(`ReportCommands.send` → `hiddenIdsOf`). 다시 읽기가 실패하면 PUT 을 보내지 않는다. 서버에 이제 없는 사진을 눌렀던 것은 버린다.
- **눌렀다가 되돌린 타일은 누르지 않은 것으로 친다.** 서버의 값으로 되돌아오면 "누른 것"에서 지운다 — 남겨 두면 그 사이 다른 기기가 바꾼 것을 내 보내기가 덮는다.
- **[다시 공유]는 서버를 부르지 않는다.** 방문 상세가 읽은 `report.url`을 그대로 공유 시트에 넘긴다. PUT 을 다시 부르면 뺀 표시를 건드린다.
- **공유 시트에는 글자(주소)만 넘기고 결과는 받지 않는다.** 시트를 띄우면 채널은 곧바로 끝난다. iOS 는 글자(`NSString`)로 넘겨도 주소처럼 생겼으면 시트 머리를 그리려고 그 주소를 받아 온다(시뮬레이터 로그의 `LPMetadataProvider: start fetching for URL`로 확인) — 보호자보다 먼저 페이지가 열릴 수 있다. 그래서 네이티브가 `UIActivityItemSource`로 넘기며 머리 정보(`LPLinkMetadata` — 제목은 주소의 호스트)를 직접 준다. 그 뒤 iOS 27.0 아이폰·아이패드, 26.5 아이폰 시뮬레이터에서 그 로그는 0줄이었다. 받는 앱에 가는 것은 여전히 글자다. 머리에 전체 주소(토큰)가 보이지 않는다.
- **Android 는 선택기에서 자기 앱을 뺀다**(`EXTRA_EXCLUDE_COMPONENTS`). 이 앱도 글 공유를 받아(③-A3) 빼지 않으면 대상에 "차곡노트"가 두 군데 뜬다(에뮬레이터 API 37 에서 변이로 확인).
- **공유 시트가 실패해도 미리보기는 닫힌다.** 링크는 이미 만들어졌다('보냄'). 스낵바로 "[다시 공유]로 다시 보낼 수 있어요"를 알린다. [다시 공유]의 실패 문구는 따로다("다시 눌러 주세요"). 채널 오류는 `PlatformException`·`MissingPluginException` 둘 다 `on Exception`으로 잡는다.
- **보내는 중에는 미리보기가 닫히지 않는다**(`PopScope`). 닫히면 만든 링크를 공유 시트에 넘기지 못한다. 타일·[고치기]도 눌리지 않는다.
- **보일 것이 없으면 [보내기]가 눌리지 않고, 이유는 서버의 `REPORT_EMPTY` 문구 그대로다.** 앱이 먼저 막을 때와 서버가 거절할 때 같은 글이 나온다. 빈칸뿐인 케어 메모는 없는 것으로 본다(서버와 같은 규칙).
- **[보낼 사진 고르기]는 같은 미리보기를 `?pick=1`로 연다.** 버튼이 [저장]이고 공유 시트를 열지 않는다. 전부 빼도 저장할 수 있다(서버는 링크를 새로 만들 때만 막는다 — 설계 7.4).
- **기간 안내는 링크가 살아 있는지로 가른다.** 살아 있으면 그 링크의 기한, 아니면 오늘에서 설정의 일수 뒤.
- **알림장 설정은 [저장] 버튼 없이 누르는 즉시 다섯 칸 전체를 교체한다.** 낙관적으로 그리지 않고, 다시 읽은 서버 값으로 그린다. 보내는 중·다시 읽는 중·다시 읽기에 실패해 이전 내용을 보이는 동안에는 누름을 받지 않는다 — 낡은 값 위에 덮어 보내면 방금 바꾼 칸이 되돌아간다. 이미 고른 기간은 다시 보내지 않는다. 설정 바꾸기는 실패해도 설정·미리보기를 다시 읽게 한다.
- **직원에게 알림장 설정은 읽기 전용으로 열린다.** 설정 화면의 "알림장" 줄은 직원에게도 보이고, 화면 맨 위에 "사장만 바꿀 수 있어요."가 뜬다.
- **보내기·끊기는 성공하든 실패하든 방문 상세·하루 목록·피드·미리보기를 다시 읽게 한다.** 달력·고객 쪽은 건드리지 않는다. 반려동물 상세의 [기록] 탭은 피드와 같은 프로바이더·같은 카드라 함께 바뀐다.
- **기록이 없는 완료 방문에는 [알림장 보내기]가 없다**(서버가 409 `VISIT_NO_RECORD_YET`). "알림장" 줄에 "기록을 쓰면 보낼 수 있어요"가 뜬다. 사진만 붙은 기록도 기록이 있는 것으로 친다 — 보일 것이 없으면 미리보기가 막는다.
- **방문 상세의 자리.** 확인 카드는 정보 카드들 맨 위(날짜 위), "알림장" 줄은 맨 아래다. 체크 표시는 보호자가 열었을 때만 그린다. 처음 연 시각은 앱의 다른 시각처럼 24시간 `15:20`이고 오늘이 아니면 날짜를 붙인다.
- **링크 끊기와 기록 삭제는 확인 시트 하나를 함께 쓴다**(`_confirmThen` — 글자 둘과 보내는 일만 다르다). 끊기는 `record:write`라 직원에게도 보인다.
- **하루 목록 묶음의 "알림장 보냄"은 완료한 방문이 하나 이상이고 그 전부가 보냈을 때만 뜬다**(`DayGroup.reportSent`). 시간표 블록의 둘째 줄에도 적는다. 피드 카드는 사진 수 뒤에 적고, 사진 수가 없어도 적는다.
- **스위치 모양 위젯 `AppSwitch`** — 누르는 영역 44×44, 그리는 알약 40×24. 값은 부모가 든다. `onChanged`가 null 이면 눌리지 않고 흐리며 스크린리더에는 사용할 수 없음으로 읽힌다.
- **오류 문구.** `VISIT_REPORT_SENT`는 설계 9.3 의 글자 그대로, `VISIT_NOT_COMPLETED`("완료한 방문만 알림장을 보낼 수 있어요.")·`REPORT_EMPTY`("보여 줄 사진·영상이나 케어 메모가 있어야 보낼 수 있어요.")·`REPORT_NOT_FOUND`("이미 닫힌 알림장이에요.")는 새로 정했다.
- **링크 주소는 어디에도 적지 않는다.** 테스트 픽스처의 주소는 가짜이고 테스트는 그 글자를 옮겨 적지 않는다. 시뮬레이터 흐름은 공유 시트를 받은 글을 적어 두는 대역으로 바꿔 끼우고 같다·다르다와 길이만 본다. 마지막 확인에서만 실제 채널로도 넘긴다.
- **흐름의 준비 스크립트는 진짜 JPEG 둘을 올린다**(30×40, 후는 밝은 회색·전은 어두운 회색 — 앱과 보호자 웹이 실제로 그린다). 운영자 지정은 `docker compose exec`로 한다 — 떠 있는 backend 컨테이너에서 돌아 새 컨테이너를 만들지 않는다.

### 설계·브리프와 다르게 간 것

- **목업의 모양을 새로 만들지 않고 지금 앱의 화면과 디자인 위젯을 따랐다.** [보내기]는 아래 고정 버튼이 아니라 스크롤 본문의 맨 아래다. 기간은 세그먼트가 아니라 `AppChoiceChip` 셋이다(설계 9.1 을 고쳤다). 안내는 회색 상자가 아니라 작은 글이다. 뺀 타일은 흑백 필터 없이 투명도만 낮춘다. 방문 상세의 [기록 보기] 버튼과 "··· 에서 [보낼 사진 고르기] [링크 끊기]" 안내 상자는 만들지 않았다 — 기존 [기록 수정]이 그 자리이고, 되돌리기 안내는 눌렀을 때 409 문구로 나온다.
- **iOS 의 활동 항목은 글자 그대로가 아니라 `UIActivityItemSource`다**(설계 9.2 를 고쳤다 — 이유는 위). iOS 의 `excludedActivityTypes`로는 우리 공유 확장이 빠지지 않아 넣지 않았다(아래 "알려진 동작").
- **미리보기의 격자는 `GridView`가 아니라 `Wrap`, 함께 보이는 항목 칩은 화면 안의 작은 위젯이다.** 기존 `AppPhotoTile`이 한 변 크기를 받고, "채운 칩 / 줄 그은 칩, 누르지 않음"에 맞는 디자인 위젯이 없다(쓰는 곳이 하나라 올리지 않았다). 사진·영상이 없으면 머리의 "○개 중 ○개"를 감춘다.
- **확인 카드의 시각은 목업의 "오후 3:20"이 아니라 `15:20`이다.** 기간 문구는 미리보기의 것을 그대로 써서 마침표가 붙는다("11월 2일까지 열려요."). "아직 안 보냄"은 목업의 회색이 아니라 다른 정보 카드와 같은 잉크색이다.
- **알림장 설정은 다시 읽는 동안에도 누름을 막는다**(브리프는 보내는 동안만). 한 칸 바꾸기는 모델에 `copyWith`를 더하지 않고 `fromJson({...toJson(), 칸: 값})`으로 한다 — `link_days`의 null 이 "그대로"와 겹쳐서다.
- **[다시 공유] 버튼의 사각형은 `GlobalKey`가 아니라 `Builder`의 context 로 잰다.** 버튼이 아래 위젯 안에 있어 키를 두 단계 내려보내는 대신 `onShareReport(Rect)` 하나만 내려보낸다.
- **흐름은 링크를 연 응답의 상태 코드를 보지 않는다.** `flow_kit`의 `download`는 본문만 준다. 웹의 상태 코드는 200·404 뿐이고 닫힌 화면도 200 이라, 본문에서 "두부의 미용 알림장"·케어 메모가 있고 "미용 전"이 없는지(뺀 사진), 끊은 뒤에는 "닫힌 알림장이에요"가 있는지를 본다. "미용 알림장"만으로는 가를 수 없다 — 닫힌 화면의 제목도 "차곡노트 미용 알림장"이다.
- **흐름의 끊기·다시 보내기·실제 공유 시트는 직원으로 한다.** 설정의 읽기 전용을 보려고 직원으로 바꾼 김에, 끊기·보내기가 직원에게도 되는 것(`record:write`)을 실제 서버로 본다.
- 준비 스크립트의 방문은 오늘이 아니라 어제 11시다(`check_report_flow.sh`와 같다). 흐름은 하루 목록의 날짜를 방문 상세에서 읽는다.

### 알려진 동작 — 막지 않기로 했다

- **다시 읽기와 PUT 사이의 틈은 남는다.** 그 사이에 다른 기기가 사진을 빼면 내 보내기가 되살린다. 틈이 화면을 연 시간에서 요청 하나만큼으로 줄었을 뿐이다 — 서버에 버전이 없어 앱에서 더 줄일 수 없다.
- **iOS 공유 목록에 우리 공유 확장("차곡노트")이 남는다.** `excludedActivityTypes`에 확장의 번들 ID 를 넣어도 듣지 않았다(iOS 27.0 아이폰·아이패드, 26.5 아이폰 시뮬레이터 — 제외 목록은 `sharingd`까지 갔다). 누르면 알림장 링크가 카톡 초안 화면으로 들어올 것이다 — 눌러 보지 못했다. Android 는 뺐다.
- **iOS 시트 머리의 그림 자리가 비어 보인다.** 머리 정보를 직접 주면서 그림은 주지 않아 빈 격자 아이콘이 그려진다(흐름의 스크린샷에서도 그렇다 — 옆에 호스트 이름). 거슬리면 `LPLinkMetadata.iconProvider`에 앱 아이콘을 준다.
- **[다시 공유]를 빠르게 두 번 누르면 공유 시트를 두 번 부른다.** 채널이 시트를 띄우고 곧바로 끝나 막을 구간이 짧다. 띄우는 중에 다시 부르면 iOS 가 어떻게 하는지는 보지 못했다.
- **기간이 지난 링크는 한 번도 안 보낸 것과 구분되지 않는다.** 서버가 `none`으로 주면 화면은 "아직 안 보냄"이다(계약에 `none`·`live`뿐이다).
- **미리보기에서 기록이 없으면 뜻이 맞지 않는 기존 문구가 뜬다.** 409 `VISIT_NO_RECORD_YET`의 문구가 "미용을 시작한 방문에만 기록을 쓸 수 있어요."이고 [다시 시도]가 붙는다(다시 해도 같다). 기록 없는 방문에는 [알림장 보내기]가 없어 평소에는 닿지 않고, 미리보기를 연 사이 기록이 지워지면 보인다.
- **설정을 누른 뒤 응답이 올 때까지 표시가 없다.** 낙관적으로 그리지 않고 진행 표시도 없어 느린 망에서는 스위치가 한동안 그대로이고(PUT 과 GET 두 번의 왕복 뒤에 바뀐다), 그 사이의 누름과 "이전 내용" 띠가 떠 있는 동안의 누름은 조용히 무시된다. **직원 화면의 기간 칩은 흐려지지 않는다** — 스위치는 흐린데 칩은 사장 화면과 같다(`AppChoiceChip`에 비활성 모양이 없다). 읽기 전용 꺼짐 스위치는 흰 카드 위에서 아주 옅다(흐름의 스크린샷에서도 그렇다).
- **꼬리표가 길어 이름 카드의 품종 줄이 접힐 수 있다.** "완료 · 알림장 보냄"이 카드의 왼쪽을 좁혀 긴 품종·몸무게("골든 리트리버 · 32.5kg")는 두 줄이 된다(깨지지는 않는다). "말티즈 · 3.4kg"은 한 줄이다.
- **상태가 섞인 가족 묶음은 완료한 아이가 다 보냈으면 표시가 뜬다.** 두부 완료(보냄) + 보리 미용 중이면 카드에 "알림장 보냄"이 보이고, 보리가 완료되는 순간 사라졌다가 보리까지 보내면 다시 뜬다. 일부만 보낸 가족 카드는 누가 안 보냈는지 말하지 않는다.
- 실패 문구는 다음에 누른 일까지 남는다(미리보기의 422, 방문 상세의 409·404 — 기존 화면의 방식). 닫힌 링크를 끊으면 화면은 "아직 안 보냄"으로 돌아오는데 "이미 닫힌 알림장이에요."가 버튼 위에 남는다.
- `live`일 때 서버가 늘 주소를 주지만 형으로는 `String?`다. 오지 않으면 공유 자리에서 죽는다(`url!`).
- 사장이 설정 화면을 연 사이 직원으로 바뀌면 내 정보를 다시 읽을 때까지 조작이 눌리고 누를 때마다 403 문구가 뜬다.
- 피드 카드는 화면 낭독기에 이름과 날짜만 읽힌다 — "알림장 보냄"도(사진 수도) 읽지 않는다. 읽기 전용 스위치에도 접근성의 누름 동작 표시는 남는다(`Pressable`의 기존 동작).
- 시간표 블록의 둘째 줄은 한 줄 말줄임이라 칸이 좁으면 맨 끝의 "알림장 보냄"부터 잘린다. 하루 목록 카드의 설명 줄은 길면 두 줄로 넘어간다.
- 보내기에 성공하면 닫히기 직전에 미리보기 GET 이 한 번 더 나갈 것이다(무효화 때문 — 횟수는 세지 않았다). 요청 하나가 버려진다.
- 확인 카드의 날짜에는 요일이 붙고 해가 바뀌어도 연도는 붙지 않는다. 한 카드 안에서 제목 줄에는 마침표가 없고 기간 줄에는 있다.

### 남는 것 — 알고 미룬다

- **실기기 확인**(설계 11.5 의 14~21 에 더했다). 공유 시트는 시뮬레이터·에뮬레이터에서 띄우는 것까지만 봤다.
  - **공유 시트에서 대상을 실제로 눌러 보지 못했다.** 받는 앱에 주소 글자가 그대로 가는지(iOS `itemForActivityType`, Android `EXTRA_TEXT`), 복사 결과, 카카오톡이 대상에 뜨는지와 실제 전송.
  - iOS 공유 목록의 우리 확장을 눌렀을 때 일어나는 일, 실기기에서도 확장이 남는지.
  - 실기기 iOS 가 시트 머리를 그리려고 주소를 받아 오지 않는지. 시뮬레이터 흐름에서는 실제 링크로 시트를 띄운 뒤에도 방문의 `first_viewed_at`이 비어 있었다(이 확인이 받아 오는 경우를 실제로 잡는지는 변이로 보지 않았다).
  - 아이패드의 말풍선이 [보내기]·[다시 공유]에 붙는지 — 임시 화면의 버튼으로만 봤다. 화면 분할·회전.
  - 카카오톡으로 보내고 돌아왔을 때의 방문 상세, 미리보기가 닫힌 뒤 시트가 올라오는 순서.
  - 실제 사진 위의 체크·"뺌"·영상 표시, 스위치가 움직이는 모습과 VoiceOver·TalkBack 이 읽는 말.
- **"보호자가 확인했어요 · 시각"은 실제 서버 값으로 보지 못했다.** 흐름은 링크를 브라우저가 아니라 HTTP 로만 열어 열람 신호가 가지 않는다 — "아직 안 열었어요"와 기간("11월 2일까지 열려요." — 서버의 `expires_at`과 같은 날)만 실제 값으로 봤다. 확인한 모습은 위젯 테스트와 골든뿐이다.
- **Android 에뮬레이터에서는 흐름을 돌리지 않았다.** 공유 시트 채널만 작업 2 에서 에뮬레이터(API 37)로 봤다. 돌리려면 `adb reverse`에 `tcp:3010`을 더한다.
- **새 작업 트리의 첫 iOS 빌드가 `Xcode build is missing expected TARGET_BUILD_DIR build setting.`으로 한 번 실패할 수 있다.** Xcode 빌드는 끝났는데 Flutter 도구가 실패로 끝난다. 그대로 다시 돌리면 된다(원인은 파지 않았다).
- **흐름이 시간 제한으로 끝나면 `flutter drive`의 결과를 믿지 않는다.** 흐름을 돌리는 중에 맥이 잠들어(덮개를 닫음) 프레임이 멈추자 기다리던 줄이 10분 시간 제한까지 매달렸고, 앱 쪽 기록은 `Some tests failed`인데 드라이버는 `All tests passed.`·종료 코드 0 을 냈다. 통과는 `PASS` 줄 수(열)로 센다. 긴 실행은 `caffeinate`로 감싼다.
- 못 본 것: 긴 케어 메모·사진 30장의 미리보기 스크롤, 작은 화면의 머리 줄, 큰 글자 크기, 인터넷이 끊긴 채 설정을 누른 화면, 시간표 블록에 표시가 그려진 모습, 다른 화면(시트·다이얼로그) 위에서 공유 시트를 띄우는 경우.
- 변이 검사는 작업마다 그 작업의 테스트 파일만 대상으로 돌렸다(변이마다 전체 테스트를 돌리지는 않았다). `AppSwitch`의 안쪽 상자 크기를 줄이는 변이 하나는 동작이 같아 잡히지 않는다.
- `glass_boundary_test.dart`의 화면 목록에 새 화면 둘을 더하지 않았다(글래스를 쓰지 않는다).
- 개발 DB·버킷에 흐름 준비의 확인용 매장·유저·고객·방문·사진·알림장 링크가 쌓인다. 지우는 스크립트는 없다.
- 미룬 판단: 꼬리표가 길 때 이름 카드를 넓힐지, 섞인 가족 묶음의 표시를 "전부 완료이고 전부 보냄"으로 좁힐지, 설정에 진행 표시를 넣을지, 공유 시트 머리에 "○○의 미용 알림장" 같은 제목과 앱 아이콘을 줄지(채널에 인자가 하나 더 필요하다), 기록 없는 미리보기의 문구.

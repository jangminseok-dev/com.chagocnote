# 003 — 계정 연결·해제와 회원 탈퇴에서 내린 결정

- 날짜: 2026-09-21
- 근거: 계획 2-2 작성 중 사용자 결정, 계획 2-1 최종 검토의 교훈, 작업 1~11 검토

## 구글 연결 끊기는 앱이 한다 (사용자 결정)

탈퇴·해제 때 Apple은 서버가 REST API로 리프레시 토큰을 폐기하고(App Store 심사 가이드라인 5.1.1(v) 필수), 카카오는 서버가 어드민 키로 연결을 끊는다. 구글은 서버가 ID 토큰만 검증하고 구글 토큰을 저장하지 않아 폐기할 것이 없다. 구글 공식 문서가 모바일 앱에 안내하는 경로대로 앱이 `google_sign_in`의 `disconnect()`를 부른다(계획 3). 검토한 다른 안: 요청 본문으로 구글 액세스 토큰을 받아 서버가 폐기(토큰이 없으면 어차피 못 끊고 API가 제공자별로 달라진다), 구글 리프레시 토큰을 저장(로그인 흐름·구글 콘솔 설정·저장 민감 정보가 늘어난다).

## `MembershipLifecyclePort`에 미리 조회하는 메서드를 두지 않는다

설계는 `check_withdrawal`로 영향을 조회한 뒤 `apply_withdrawal`을 부르게 했다. 조회와 적용 사이에 다른 요청이 사장 수를 바꿀 수 있어서(계획 2-1 최종 검토에서 같은 모양의 경합이 실제로 재현됐다) 적용이 매장 행을 잠근 뒤 스스로 확인하고 409로 막는다. 앱은 확인 없이 먼저 부르고, `SHOP_CLOSE_CONFIRM_REQUIRED`를 받으면 메시지(매장 이름 포함)를 보여 주고 확인을 받아 다시 부른다.

## 제공자 쪽 연결 끊기는 커밋 뒤에 한다

탈퇴는 유저 행과 매장 행을 잠근다. 그 상태로 외부 HTTP(최대 5초 × 신원 수)를 부르면 같은 매장의 멤버십 변경이 그동안 멈춘다. FastAPI의 백그라운드 작업은 function 스코프의 DB 세션이 커밋된 뒤에 돈다(실험으로 확인). 끊지 못하면 로그만 남긴다. 프로세스가 커밋과 연결 끊기 사이에 죽으면 제공자 쪽 연결이 남는데, 설계가 이미 "연결 끊기가 실패해도 탈퇴는 완료한다"고 정한 범위 안이다.

## 로그인 수단을 해제하면 모든 세션을 끊는다

해제한 수단으로 만든 세션이 다른 기기에 최대 30일 남는 것을 막는다. 요청한 기기는 응답의 새 토큰으로 이어 간다.

## 한 유저는 제공자마다 신원 하나

`DELETE /v1/auth/identities/{provider}`가 성립하려면 필요하다. 유일 제약 `(user_id, provider)`로 강제한다.

## 리프레시 토큰의 세대

토큰을 `{user_id}.{난수}`로 만들고 값에 발급 시점의 세대를 찍는다. "모든 세션 폐기"는 세대 증가 한 번이다. 갱신은 꺼낼 때 받은 세대로 새 토큰을 저장하므로 그 사이 폐기가 끼어들면 새 토큰도 무효다. 폐기된 세대의 옛 토큰을 다시 보내는 것은 재사용 신호로 보지 않는다(그러지 않으면 옛 토큰 하나로 재로그인한 세션을 계속 끊을 수 있다). 유저별 토큰 집합은 없앴다.

## 검토에서 고친 것

작업별 검토가 계획서 코드의 결함을 잡았다. 실행 순서대로 적는다.

- 리프레시 토큰 파서: 4300자리 넘는 숫자 접두사 → 인증 없는 갱신 엔드포인트의 500. 길이 상한(19자리)으로 막았다.
- `dispose_http`가 캐시된 resolver를 비우지 않아 닫힌 클라이언트를 쥐고 있었다.
- JWKS 재조회 스로틀이 제공자 장애 중에는 걸리지 않았다 → 실패도 60초 기억(음성 캐시).
- `ProviderRevoker.revoke_all`이 특정 예외만 잡았다 → 백그라운드 경계에서 모든 예외를 잡고 종류만 로그에 남긴다.
- 수락 잠금 순서 테스트가 FK의 `FOR KEY SHARE` 때문에 옛 코드에서도 통과했다 → 제3 세션 NOWAIT 탐침으로 다시 썼다. (Task 12 에서 쓴 링크·탈퇴 두 세션 테스트도 같은 함정에 처음 걸렸다 — 아래 "남는 것" 참고.)
- **F4(계획에 없던 구멍)**: 탈퇴와 겹친 초대 수락이 탈퇴한 유저의 소속을 되살렸다 → 작업 8b(`ActiveUserGuardPort`, 수락이 유저 행을 먼저 잠근다).
- 자기 계정에 이미 붙은 신원을 다시 연결하면 "그 계정에서 탈퇴하라"고 안내했다 → 소유자 조회로 구분.
- **잠근 뒤 재확인은 탈퇴와 정지를 둘 다 본다**: 인증 가드는 잠금 전에(연결은 제공자 왕복 전에) 읽는다. 연결·해제·탈퇴 셋 다 적용. 해제는 이것이 없으면 방금 정지된 계정에 새 토큰을 발급했다.
- `add_identity`의 소유자 조회 `scalar_one()` → 동시 해제와 겹치면 500. `scalar_one_or_none()`으로 바꿨다.
- 테스트 스텁이 인자를 버려 "누구의 세션을 끊고 누구에게 토큰을 줬는지"를 보지 못했다(연결·해제·탈퇴) → 인자를 기록한다.
- `TokenPair`의 기본 repr이 우리 토큰 원문을 찍었다 → 가렸다.
- auth 앱의 tenancy 오류 표 병합이 무검증이었다 → 구조 테스트.
- **복호화 실패가 탈퇴를 영구히 막았다** → 그 신원의 제공자 연결 끊기만 포기하고 탈퇴·해제는 진행한다.
- `confirm_close_shops`가 `"yes"`·`1`을 참으로 받았다 → `StrictBool`.

## 남는 것 — 알고 미룬다

운영 전환 전에 챙길 것:

- Redis 축출 정책: `auth:refresh:gen:{user_id}` 키는 만료가 없다. `allkeys-*` 정책이면 세대 키가 사라져 폐기된 토큰이 되살아날 수 있다. **`noeviction` 또는 `volatile-*` 필수.**
- `core/redis.py`에 소켓 타임아웃이 없다. 해제·탈퇴는 유저 행 잠금을 쥔 채 Redis를 부르므로 Redis가 멈추면 그 유저의 요청이 밀린다.
- `UserRepository.lock`에 대기 상한이 없다(`lock_timeout` 검토).
- 마이그레이션 0004의 유일 제약 추가는 큰 테이블에서 `ACCESS EXCLUSIVE`로 잠근다(`CREATE UNIQUE INDEX CONCURRENTLY` 패턴).
- `IDENTITY_TOKEN_ENC_KEY` 회전 절차가 없다(복호화 실패는 이제 치명적이지 않지만 회전 자체는 미설계).
- **정지된 유저는 앱에서 탈퇴할 수 없다**(가드가 403). 개인정보 삭제 요청에 응할 운영자 쪽 경로가 출시 전에 필요하다.
- 제공자 검증(`verify`·Apple `_exchange`)의 httpx 예외가 도메인 오류로 감싸이지 않아 제공자 타임아웃이 500이다(소셜 로그인·연결 공통, 기존 문제). 503 `PROVIDER_UNAVAILABLE` 후보.
- 연결 경로는 제공자 왕복(최대 5초) 동안 요청 트랜잭션이 `idle in transaction`으로 열려 있다(행 잠금은 쥐지 않는다).
- 인증 가드 유무를 보는 구조 테스트가 없다. auth 프로세스의 빈 자리 검사는 `integration` 마커에서만 돈다.

구조상 남는 틈(받아들인다):

- 세션 폐기(Redis INCR)와 새 토큰 발급은 DB 커밋 **전에** 일어난다. 커밋이 실패하면 계정은 그대로인데 모든 기기가 로그아웃된다(닫히는 쪽 실패). 되돌릴 수 없는 단계 중 유일하게 트랜잭션 밖이다.
- 수단 해제·세션 폐기 뒤에도 다른 기기의 **액세스 토큰은 최대 15분** 유효하다(가드는 탈퇴·정지만 본다). 탈퇴는 가드가 즉시 막는다.
- 세션 폐기와 경합한 갱신에서 발급된 액세스 토큰도 같은 15분.
- 해제 직후 같은 제공자를 곧바로 다시 연결하면, 늦게 도는 백그라운드 연결 끊기가 새 인가를 끊을 수 있다(다시 연결하면 복구).
- 이중 탈퇴: 잠금에서 기다린 두 번째 요청은 204, 커밋 뒤의 요청은 401. 앱(계획 3)은 둘 다 "끝났다"로 본다.
- `list_revocations`는 해제 때도 모든 신원의 토큰을 복호화한다(필요한 것은 하나).
- 동시 첫 로그인에서 진 쪽의 Apple 리프레시 토큰은 저장되지 않는다(다음 로그인에서 채워진다).
- JWKS `_load()`에 잠금이 없어 캐시가 빈 순간 동시 요청이 몰릴 수 있다(지속 폭주는 스로틀이 막는다).
- 권한 확인과 행위 사이의 틈: 매장 잠금을 기다리는 사이 내보내진 멤버가 낡은 `ShopContext`로 역할 변경·내보내기를 끝낼 수 있다(마지막 사장 규칙은 잠금 안에서 다시 세므로 지켜진다).
- `apply_withdrawal`은 막는 매장이 여럿이어도 하나씩만 알려 준다. 정지된 매장도 혼자 사장이면 닫는다.
- `SessionIssuer.issue(generation=None)`이 두 뜻을 겸한다. `save`의 `user_id` 인자는 쓰이지 않는다.
- **두 세션 잠금 테스트를 HTTP 왕복(`asyncio.gather`)만으로 쓰면 판별력이 약할 수 있다.** Task 12에서 로그인 수단 해제 경합(G1)을 이 저장소의 통합 테스트(`docker` 안의 로컬 Postgres, 왕복이 1ms 미만)에서 확인하다가 겪었다 — 잠금 호출을 지워도 우연한 스케줄링으로 5번 연속 통과했다. `social_identities.user_id → users.id` 외래 키의 암묵적 `FOR KEY SHARE`가 명시적 잠금 없이도 일부 겹침을 가려 버리는 경우(연결·탈퇴 경합, G2)도 있었다. 두 문제 다 직접 세션 두 개로 잠금 시점을 제어하는 기법(`test_unlink_vs_unlink_locking.py`, `test_link_vs_withdraw_locking.py`)으로 고쳤다. 이후 두 세션 경합 테스트를 새로 쓸 때는 HTTP 두 요청을 `gather`하는 방식을 기본으로 삼지 않는다.

계획 3(Flutter 앱)으로 넘기는 것 — 브리프 초안의 목록에 더한다:

- 이중 탈퇴의 204/401을 둘 다 "탈퇴 완료"로 처리한다.
- 탈퇴·해제의 409 확인 흐름에서 `confirm_close_shops`는 반드시 JSON `true`(문자열 금지).
- 401 `UNAUTHENTICATED`가 초대 수락에서 나오면 토큰 갱신 후 재시도하지 말고 로그인 화면으로 보낸다.

## 계획 2-2에서 새로 미룬 것

- **민감한 작업 앞의 재인증.** 세션을 훔친 공격자가 자기 소셜 계정을 피해자 계정에 붙이는 것은 지금 막지 못한다. 연결·해제·탈퇴 앞에 "방금 로그인했는가"를 확인하는 장치가 필요하다. 앱 흐름과 함께 정한다.
- **연결 끊기 실패의 재시도.** 지금은 로그만 남긴다. 실패가 잦으면 재시도 큐를 둔다.
- **`auth:refresh:gen:{user_id}`에는 만료가 없다.** 세션 폐기를 한 번이라도 겪은 유저마다 작은 키 하나가 남는다.
- **닫힌 매장의 데이터 파기.** 설계대로 ④ 이후의 운영자 기능이다.

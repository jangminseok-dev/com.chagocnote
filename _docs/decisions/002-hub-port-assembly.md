## 허브 포트 구현은 진입점이 꽂는다

`get_me`는 tenancy가 구현한 `MembershipDirectoryPort`가, tenancy의 멤버 목록은 auth가 구현한 `UserDirectoryPort`가 필요하다. `auth/dependencies/`가 `tenancy.adapter…`를 import하면 "스포크 상호 독립" 계약을 어긴다.

검토한 안은 셋이다. ① 진입점에서 조립 ② 허브에 레지스트리 ③ `*.dependencies`를 계약의 예외로 둔다. **①로 정했다.**

- 소비하는 스포크는 `dependencies/hub_ports.py`에 "자리" 함수를 둔다. 자리는 호출되면 `RuntimeError`를 던진다.
- `backend/main.py`(필요해지면 `auth_main.py`)가 `app.dependency_overrides[자리] = 구현 프로바이더`로 채운다. 진입점은 이미 모든 스포크를 import하는 유일한 곳이다.
- 구현 프로바이더가 `DbSession`을 받으면 같은 요청의 세션을 공유한다. 스포크를 넘는 작업도 한 트랜잭션으로 묶인다.
- 매장 접근 확인(`ShopAccessPort`) 자리는 모든 매장 범위 스포크가 쓰므로 `core/shop_guard.py`에 둔다. core가 허브의 추상(ABC·DTO)을 import하는 것은 허용한다. core가 스포크를 import하는 것은 여전히 금지다.
- 자리를 채우지 않은 실수는 구조 테스트가 잡는다. `tests/route_inspection.py`가 두 앱의 라우트 의존성 트리를 훑어 빈 자리를 찾고, `tests/test_hub_port_binding.py`(API 프로세스)와 `tests/integration/test_route_wiring.py`(인증 프로세스)가 그것을 돌린다. 손으로 관리하는 자리 목록은 없다.

②를 버린 이유: 허브가 "포트와 DTO만 가진다"는 규칙에서 벗어나 상태를 갖게 되고, 요청 단위 DB 세션을 넘길 방법을 따로 만들어야 한다. ③을 버린 이유: 스포크 간 결합이 조립 코드에 숨고 계약이 그만큼 약해진다.

## `factory/` 폴더의 패턴 표기를 "Factory"로 완화한다

`auth/adapter/outbound/factory/`의 `SocialProviderFactory`는 제공자별 인스턴스를 담아 두고 이름으로 골라 주는 객체이고, `build_social_provider_factory`는 설정을 보고 그 객체를 만드는 단순 팩토리다. GoF의 Factory Method(하위 클래스가 생성을 결정)와는 다르다. 폴더 이름과 코드는 그대로 두고 대응표의 패턴 칸만 "Factory"로 고친다. 제공자마다 Creator 클래스를 두는 구조로 바꾸면 클래스만 늘고 얻는 기능이 없다.

## 최종 검토에서 고친 것

브랜치 전체 최종 검토(9c8fc1b..589ed36)에서 나온 Important 셋을 이렇게 정리했다.

- **F1 내보낸 멤버가 만들어 둔 초대.** 내보내기는 `removed_at`만 남겨서, 그 멤버가 미리 받아 둔 초대 코드는 그대로 살아 있었다. 재현된 경로는 "사장으로 올림 → 코드를 만들어 둠 → 내보냄 → 자기 코드로 다시 합류". `InviteRepository.revoke_created_by`를 더해 내보내기와 사장→직원 강등 때 그 멤버의 미사용 초대를 같은 트랜잭션에서 무효화한다. 수락 쪽은 이미 `revoked_at`을 보고 있어 고칠 것이 없었다.
- **F2 읽기와 잠금 사이의 경합.** `count_owners`의 `FOR UPDATE`는 대상을 읽은 **뒤**에 걸려서, 읽고 잠그는 사이에 다른 요청이 역할을 바꾸면 낡은 값으로 판단했다(사장 0명 매장이 실제로 만들어졌다). 멤버십을 바꾸는 유스케이스는 맨 앞에서 `MemberRepository.lock_membership_changes`로 매장 행을 잠가 매장 단위로 직렬화한 뒤에 대상을 읽는다. `count_owners`의 잠금은 그대로 뒀다 — 멤버십을 바꾸는 경로끼리는 잠금 순서가 매장 → 멤버 → 초대로 일정해서 서로 교착하지 않는다(초대 수락과의 관계는 아래 "새로 미룬 것" 참조).
- **F3 운영자 확인을 라우터 가드로 옮겼다.** 가장 권한이 큰 표면이 "인터랙터 첫 줄을 빠뜨리면 열리는" 구조였고, 매장 쪽만 `require_permission` 가드라 방식도 달랐다. `platform_admin/dependencies/operator_guard.py`의 `require_operator`를 두 라우터에 라우터 수준으로 걸고, 인터랙터에서는 확인을 뺐다. **계획 2-1과 platform_admin 문서의 "유스케이스 안에서 확인한다"는 규칙을 뒤집은 결정이다.**
- **F4 자리·가드 검사를 구조 테스트로 바꿨다.** 손으로 관리하던 `_API_SLOTS` 목록은 자리를 새로 만들고 더하는 것을 잊으면 통과하면서 첫 요청에서 500이 났고, `auth_main.app`은 검사 대상도 아니었다. `tests/route_inspection.py`가 두 앱의 라우트 의존성 트리를 훑어 ① 빈 허브 포트 자리 ② `get_shop_context` 없는 `{shop_id}` 경로 ③ `require_operator` 없는 `/v1/platform/` 경로를 찾는다.

함께 고친 작은 것: int32를 넘는 경로 변수를 422로 막고(전에는 asyncpg `DataError`로 500), `MemberPgRepository.add`는 제약 이름이 `uq_shop_members_active`일 때만 "이미 멤버"로 바꾸며, "core는 스포크를 import하지 않는다"를 import-linter 계약으로 강제한다(계약 6종. 설계 문서의 5종에 하네스가 하나 더한 것이다).

## 계획 2-1에서 새로 미룬 것

- **직원이 스스로 매장을 나가는 기능.** 지금은 사장이 내보내야 한다. 설계에 없어서 만들지 않았다. 멤버십을 바꾸는 새 유스케이스(계획 2-2의 탈퇴)는 맨 앞에서 `lock_membership_changes`를 부르고, 그 멤버가 만든 초대도 `revoke_created_by`로 무효화해야 한다.
- **내보내기·강등과 초대 수락 사이의 이론적 교착.** 내보내기·강등은 매장 행 → 멤버 행 → 초대 행 순으로 잠그는데, 초대 수락은 매장 행 잠금 없이 초대 행 → 멤버 INSERT 순이다. 내보내지는 멤버가 같은 순간에 자기가 만든 코드를 수락하면 사이클이 되어 Postgres가 한쪽을 중단시킨다(일시적 500, 데이터 손상 없음). 전제가 매우 좁아 재검토에서 차단 사유로 보지 않았다. 계획 2-2에서 수락 경로도 맨 앞에서 매장 행을 잠그게 하면 사라진다.
- **초대 코드 목록·사장이 직접 하는 무효화.** 무효화는 내보내기와 사장→직원 강등 때 자동으로 일어난다. 사장이 코드를 보거나 직접 무효화하는 슬라이스는 여전히 없다. 7일 만료와 1회 사용으로 충분한지 Hiss Haus 투입 뒤에 본다.
- **사장용 첫 초대의 재발급.** 코드를 잃거나 7일 안에 못 쓰면 다시 발급할 방법이 없다. 운영자가 매장을 새로 만들어야 하고 고아 매장이 남는다.
- **`ShopRepository.get_by_id`의 이름.** 컨텍스트 없이 아무 매장이나 읽는 메서드라 용도를 드러내는 이름이 낫다.
- **정지된 매장에도 초대 수락으로 합류된다.** 들어가자마자 `SHOP_SUSPENDED`라 실해는 없다.
- **스키마 불일치 테스트의 빈틈.** 서버 기본값과 부분 인덱스의 `WHERE` 절은 비교하지 않는다.
- **매장 범위 요청마다 조회가 3번이다.** 소속·권한·매장 상태를 매번 읽는다. 캐시는 넣지 않았다.
- **초대 코드 해시에 서버 비밀값(pepper)을 섞지 않았다.** DB를 읽을 수 있는 공격자는 이미 그 매장의 데이터를 읽을 수 있고, 코드는 7일·1회용이라 얻는 것이 작다.
- **닫힌 매장·정지된 매장을 만드는 기능.** `closed_at`은 회원 탈퇴(계획 2-2)가, `suspended_at`은 이후 운영자 기능이 쓴다. 지금은 읽기만 한다.
- **`/v1/me`의 매장 목록에 정지된 매장이 나온다.** 들어가면 `SHOP_SUSPENDED` 안내를 받는다. 앱(계획 3)에서 표시를 정한다.

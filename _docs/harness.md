- CI 는 우분투 러너만 쓴다(비공개 저장소라 무료 분이 월 2,000분이고 macOS 는 10배로 깎인다). 작업마다 시간 상한(백엔드 30분·웹과 앱 20분)이 있고 같은 브랜치에 새로 푸시하면 앞선 실행을 취소한다. 백엔드의 `.env`·`.env.auth`는 `generate_dev_env.py`로 실행마다 새로 만드는 일회용이다. 앱 골든은 맥에서 만들어 리눅스와 글꼴 렌더링이 달라서 CI 는 `--dart-define=SKIP_GOLDEN_COMPARE=true`로 비교만 끈다(`app/test/flutter_test_config.dart`) — 골든은 로컬에서 본다. 맥의 Flutter 를 올리면 `app.yml`의 `flutter-version`도, pnpm 은 `web/package.json`의 `packageManager`를 따른다.
- 통합 테스트는 별도 데이터베이스 `chagocnote_test`를 쓴다. 개발 데이터를 건드리지 않는다. pytest가 세션마다 한 번 `scripts/prepare_test_db.py`를 돌려 스키마를 비우고 `alembic upgrade head`로 다시 만든다. 테스트 사이에는 시드 표(`roles`, `permissions`, `role_permissions`, `pet_condition_types`)와 마이그레이션 버전 표(`alembic_version`)를 뺀 모든 표를 비운다.
- 마이그레이션은 손으로 쓴다. `tests/test_schema_drift.py`가 마이그레이션 결과와 ORM이 어긋나면 실패한다. 새 ORM 모듈은 `backend/orm_registry.py`에 등록한다.
- 구조 위반은 테스트가 아니라 import-linter가 잡는다. 구조를 건드린 변경은 테스트와 구조 계약을 둘 다 돌린다. 계약은 6종이다 — 설계 문서가 말하는 5종에 "core는 스포크를 import하지 않는다"를 하네스에서 더했다.
- 라우터를 추가하거나 옮긴 변경은 라우트 표를 변경 전후로 비교한다.
- 앱의 구조 위반은 `test/design/feature_imports_test.dart`(기능 폴더 사이 import 는 `auth` 공용·`home` 껍데기·`visit → customer`만)와 `test/core/router/app_router_test.dart`(열린 경로 목록 밖의 모든 경로는 매장 선택이 없으면 막힌다)가 잡는다. 기능 폴더나 경로를 더한 변경은 이 둘을 돌린다.
- 유스케이스는 스텁 포트로 검증한다. mock 프레임워크보다 스텁 구현을 쓴다. 공용 스텁(`apps/*/tests/helpers/fakes.py`)은 포트 ABC를 상속한다 — 포트에 메서드를 더하고 스텁을 빠뜨리면 인스턴스를 만드는 순간 잡힌다(`apps/*/tests/test_fakes_are_ports.py`). 테스트 파일 안의 부분 스텁(`_Stub*`)은 그 테스트가 부르는 메서드만 가지므로 상속하지 않는다.
- `tests/integration/`은 두 프로세스의 실제 앱 객체에 붙어 프로바이더·DB 커밋·Redis까지 통과한다. 인증 프로세스의 개인키는 테스트마다 새로 만든 키로 바꿔 넣는다.
- 스포크를 새로 만들면 첫 통합 테스트로 "A매장 멤버가 B매장의 경로를 부르면 403"(테넌트 격리)을 둔다. notification 도 그렇게 시작했다(`tests/integration/test_notification_onboarding_wiring.py`·`test_notification_messages_wiring.py`의 첫 테스트).
- 요청 밖(디스패처·운영자 스크립트)에서 `ShopContext`를 만드는 곳은 `notification/app/services/system_context.py` 하나다(권한 빔). 테스트가 요청 밖 코드를 돌릴 때도 이것을 쓴다 — 가드를 흉내 내는 다른 생성자를 만들지 않는다.
- 디스패처는 테스트에서 루프를 띄우지 않고 `build_dispatcher(session, gateway=FakeGateway(), now=lambda: fixed).run_once()`로 한 번씩 돌린다(`tests/integration/test_notification_dispatcher_wiring.py`). 상한은 `monkeypatch.setattr(dispatcher_provider, "NOTIFICATION_DAILY_CAP", 1)`, 요청 쪽 게이트웨이는 `main.app.dependency_overrides[get_message_gateway] = lambda: fake`(끝나면 pop). `dispatcher_wakeup._event`는 처음 `wait()`한 이벤트 루프에 묶이므로 `wait`를 부르는 테스트 파일은 autouse 픽스처로 새 `asyncio.Event`를 넣는다.
- 통합 테스트 두 세션을 **동시에** 돌리면(전체 + 파일 하나) 같은 테스트 DB 를 TRUNCATE 해 서로 깨진다 — 차례로 돌린다. 대역 서버(테스트 DB 로 흐름 스크립트를 돌리는 임시 서버)도 통합 테스트와 같이 띄우지 않는다.
- 실제 발송 업체(`api.solapi.com`)는 테스트에서 부르지 않는다 — 어댑터 테스트는 `httpx.MockTransport`, 나머지는 `FakeGateway`/`SpyGateway`(`notification/tests/helpers/fakes.py`)다. `.env`의 `SOLAPI_*`가 비어 있으면 dev 는 가짜 게이트웨이다.
- 허브 포트 자리를 새로 만들어도 더할 목록은 없다. `tests/route_inspection.py`가 두 앱의 라우트 의존성 트리를 훑어 ① 채우지 않은 허브 포트 자리 ② `{shop_id}` 경로인데 `get_shop_context`를 거치지 않는 라우트 ③ `/v1/platform/` 경로인데 `require_operator`를 거치지 않는 라우트를 잡는다. API 프로세스는 `tests/test_hub_port_binding.py`가, 인증 프로세스는 `tests/integration/test_route_wiring.py`가 돌린다.
- 권한이나 불변식이 걸린 슬라이스를 계획할 때는 악의적이거나 운 나쁜 시나리오(내보내진 사람이 쥔 것, 같은 요청이 동시에 두 번, 읽기와 쓰기 사이)를 먼저 표로 적고, 각각을 막는 코드와 테스트를 작업에 넣는다. 작업별 검토는 계획서와의 일치가 아니라 그 표를 기준으로 한다.
- 통합 테스트에서 두 번째 로그인 수단이 필요하면 `fake_kakao` 픽스처를 쓴다.
- 통합 테스트는 compose 의 MinIO 도 쓴다(`backend` 서비스가 `minio`에 기댄다). 미디어가 필요한 테스트는 `media_storage` 픽스처를 쓴다 — 테스트 버킷 `chagocnote-test`를 시작 때 비우고(테스트마다 DB ID 가 1부터라 키가 겹친다), 컨테이너 안에서 서명 URL 로 PUT 하도록 공개 주소를 내부 주소로 둔다. 사진 하나를 확인까지 마치는 도우미는 `tests/integration/support.py`의 `ready_photo`다.
- 마이그레이션에 시드 표를 새로 만들면 루트 `conftest.py`의 `_KEEP_TABLES`에 더한다. 빠뜨리면 첫 테스트가 시드를 비워 그다음 테스트부터 실패한다.
- 두 세션 경합 테스트는 막힌 호출을 `asyncio.create_task`로 들고 있다가 앞선 세션이 커밋한 뒤의 결과를 본다. "기다렸다"만으로 판별하지 않는다 — 외래 키의 암묵적 잠금이나 같은 행의 다른 잠금 때문에 잠금 코드가 없어도 기다릴 수 있다. 잠금 코드를 빼는 변이로 테스트가 실패하는지 확인한다.
- 공개 경로(`/v1/public/`)는 `tests/route_inspection.py`의 허용 목록(`_PUBLIC_ROUTES`)에 더한다. 목록에 없는 공개 경로와 로그인·매장 확인을 거치는 공개 경로는 `find_route_violations`가 잡는다.
- 로그인 없이 열리는 경로는 프로세스마다 목록 전체를 못 박는다(`routes_without_login`) — API 프로세스는 `tests/test_hub_port_binding.py`(넷), 인증 프로세스는 `tests/integration/test_route_wiring.py`(다섯). 경로를 열거나 로그인 의존성을 빼면 목록과 달라져 실패한다. 일부러 연 경로는 두 곳(허용 목록, 프로세스별 목록)에 함께 적는다.
- 로그인 없는 경로의 응답은 표식 문자열로 본문 전체를 검사한다. 내부 메모·결제 수단·예약 메모·보호자 이름·전화번호·고객 메모에 표식을 넣고, 모든 항목을 켠 응답의 글자열 어디에도 없는지 본다(`tests/integration/test_public_report_wiring.py`). 칸 이름만 보는 검사로는 값이 다른 칸에 섞이는 것을 놓친다.
- 토큰·서명 URL 이 든 응답을 다루는 통합 테스트가 실패하면 pytest 가 지역 변수를 찍는다. 출력을 옮겨 적을 일이 있으면 `--tb=line`·`--tb=no`로 돌린다.
- 테스트 파일을 골라 돌릴 때 `tests/test_hub_port_binding.py`는 맨 뒤에 두거나 따로 돌린다. 통합 파일 사이에 두면 뒤쪽 통합 파일이 `fixture 'wired' not found`로 멈춘다(전체 실행에는 없다. 원인은 조사하지 않았다).
- 웹의 `check:server`는 `.next`의 빌드를 띄운다. 코드를 고친 뒤 `pnpm build` 없이 돌리면 옛 빌드를 검사한다. 빌드가 없으면 "먼저 `pnpm build` 를 돌린다"로 멈춘다. 응답 헤더 셋은 `next start`로만 본다 — `next dev`는 페이지의 `Cache-Control`을 덮지 못한다.
- dev 와 build 를 오가다 `web/.next`가 꼬이면 지운다. 다만 compose 의 `web`이 떠 있는 동안에는 맥에서 `web/.next`를 지울 수 없다(`Permission denied` — 볼륨의 마운트 자리다). `web`을 지운 뒤에 지운다. 맥의 `pnpm build`는 `web`이 떠 있어도 된다.
- compose 의 `web`은 `node_modules`·`.next`를 볼륨(`web_node_modules`·`web_next`)에 둔다. 맥의 `web/node_modules`(darwin 바이너리)와 컨테이너의 것(linux-musl)이 서로 가린다. pnpm 저장소는 `--store-dir node_modules/.pnpm-store`로 볼륨 안에 둔다 — 빼면 저장소 루트에 수백 MB 의 `.pnpm-store/`가 생긴다. 파일 변경 감지는 폴링 없이 된다(Docker Desktop, 맥).
- e2e 는 돌릴 때마다 먼저 `pnpm e2e:prepare`를 돌린다. 첫 테스트가 "아직 아무도 열지 않은 링크"를 전제하므로 준비 없이 다시 돌리면 그 테스트가 실패한다. `workers: 1`로 적힌 순서대로 돌며, 테스트 하나만 골라 돌리면(`-g`) 이 전제가 깨질 수 있다.
- e2e 준비는 개발 DB 와 버킷에 확인용 매장·유저·고객·방문·사진·알림장 링크를 남긴다. 지우는 스크립트는 없다.
- e2e 는 `next dev`에 붙는다. `next.config.ts`의 `allowedDevOrigins: ['127.0.0.1']`을 빼면 `http://127.0.0.1:3010` 에서 브라우저 쪽 코드가 막혀 크게 보기·열람 신호·404 화면 글자 테스트가 실패한다.
- 웹을 띄운 기록(`next dev`·`next start`)에 토큰이 없어야 한다. `check:server`의 마지막 줄이 `next start`의 기록을 보고, `next dev`는 `logging.incomingRequests: false`로 요청 주소를 찍지 않는다.
